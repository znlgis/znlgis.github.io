# 第八章：数据验证与条件格式

前两章管的是数据长什么样、公式怎么算，这一章管两件相邻的事：输入能不能进来，显示能不能随数据变化。数据验证在用户提交编辑时拦一道，把不合规的输入挡在单元格之外；条件格式在值变化后自动加样式，让异常数字自己跳出来。

两者都不修改单元格里的值。验证失败时用户看到提示，值不会写进去；条件格式只改外观，Data 读出来仍是原始数值。理解这一点，就不会在验证规则里期待「自动纠正」行为，也不会靠条件格式判断数据是否合法。

ReoGrid 的验证规则与条件格式规则都挂在区域上，一次设置作用于整块范围，后续插入行列时规则会跟着区域移动。这是把规则设在区域而不是逐个单元格上的主要原因。

## 8.1 数据验证基础

ReoGrid支持对单元格数据进行验证，确保输入的数据符合特定规则。

规则由两部分组成：类型与参数。类型决定校验方式（数字范围、列表、日期区间等），参数对象给出具体的上下限或候选项。示例的三个方法分别对应数字范围、下拉列表和日期范围，覆盖了报表里最常见的三种约束。

设置入口是 SetRangeDataValidation，第一个参数是区域，第二个是类型枚举，第三个是参数对象。区域可以用 A1 地址或 RangePosition，参数对象的类型必须与枚举匹配，类型写错时按版本不同会报错或被忽略。

```csharp
using unvell.ReoGrid.DataValidation;

public class DataValidationBasics
{
    private Worksheet sheet;
    
    public void SetNumberValidation(string range)
    {
        // 数字范围验证
        sheet.SetRangeDataValidation(range, DataValidationType.Number,
            new NumberValidationRule
            {
                Minimum = 0,
                Maximum = 100
            });
    }
    
    public void SetListValidation(string range)
    {
        // 下拉列表验证
        sheet.SetRangeDataValidation(range, DataValidationType.List,
            new ListValidationRule
            {
                Items = new string[] { "选项1", "选项2", "选项3" }
            });
    }
    
    public void SetDateValidation(string range)
    {
        // 日期范围验证
        sheet.SetRangeDataValidation(range, DataValidationType.DateTime,
            new DateTimeValidationRule
            {
                MinimumDate = DateTime.Now,
                MaximumDate = DateTime.Now.AddDays(30)
            });
    }
}
```

数字验证的参数是两个边界值 Minimum 与 Maximum，两端通常都包含。示例限定 0 到 100，用户输入 -1 或 101 时被拦下；输入 0 和 100 可以通过。边界值是否包含，建议在业务文档里写清楚，避免两方理解不一致。

列表验证的 Items 是一组字符串，用户在单元格里只能从这几项里选。下拉列表适合状态、类型、部门这类取值有限的字段，注意候选项区分全半角与首尾空格，看起来一样的两个值会被当成不同项。

日期验证用 MinimumDate 与 MaximumDate 两个 DateTime 参数。示例取「今天」到「三十天后」，适合预约、有效期这类相对当前时间的约束。DateTime.Now 带时间部分，如果只想按日期比较，把两端都取到当天零点，能避免同一天里因为时刻不同被判为超出范围。

## 8.2 条件格式化

条件格式化可以根据单元格的值自动应用不同的样式。

规则挂在区域上，由控件在值变化或重绘时求值。示例用 DataBarFormatRule 在 A1:A10 上画数据条：MinValue 与 MaxValue 设定刻度范围，BarColor 决定条的颜色。值越大条越长，单元格里的数字本身不变。

设置入口是 AddConditionalFormatRule，第一个参数是区域，第二个是规则对象。同一区域可以叠加多条规则，执行顺序与优先级由控件管理，规则冲突时后加的不一定覆盖先加的，调试阶段建议一次只开一条规则，确认效果后再叠加。

规则类型不止数据条，还有基于值比较的单元格样式规则、图标集等。不同版本提供的规则类不同，用到哪一类先看当前程序集里可用的类型，不要照抄其他版本的类名。

```csharp
using unvell.ReoGrid.ConditionalFormat;

public class ConditionalFormatting
{
    public void SetConditionalFormat(Worksheet sheet)
    {
        // 大于条件
        var rule = new DataBarFormatRule
        {
            MinValue = 0,
            MaxValue = 100,
            BarColor = Color.Blue
        };
        
        sheet.AddConditionalFormatRule("A1:A10", rule);
    }
}
```

数据条的刻度范围要按业务设定。MinValue 取 0、MaxValue 取 100，是因为这一列的数据落在 0 到 100 之间；如果数据实际范围是 0 到 10000，却仍按 0 到 100 设刻度，所有条都会顶满，失去比较意义。刻度跟着数据走，规则才有效。

条件格式与手动设置的样式会叠加。单元格本身设了浅黄底，条件格式又要加红底，最终显示哪个取决于规则与样式的应用顺序，通常条件格式优先。需要保留手工样式的场景，把条件格式限定在少数列上，避免整表冲突。

插入或删除行列后，规则区域会跟着移动。批量改结构之前先记下规则挂在哪块区域，改完再回来看一眼，确认规则没有偏到别的列上。

条件格式只影响显示，判断逻辑仍然要写在数据层。需要根据数值做业务动作（发提醒、拦保存）时，读取的是 Data，不是颜色；依赖颜色判断状态，会在条件格式被关掉或规则调整后失效。

规则多了以后要有清理机制。业务页面切换、数据源重载时，旧的规则仍挂在区域上，继续参与求值，重建数据集前先清掉本页添加的规则，或者干脆重建工作表，避免规则越堆越多。

## 8.3 本章小结

本章介绍了数据验证和条件格式化功能，帮助控制数据输入和动态显示。

两件事的定位不同，放在一起是因为都挂在区域上：

- 数据验证是守门员，输入时判断合法性，不合格就拒绝写入；
- 条件格式是显示器，值合法与否都照常显示，只是用颜色或图形把异常标出来。

验证规则不要设得太死。限制越严，用户遇到「填不进去又不知道原因」的概率越高，尤其是从剪贴板粘贴、批量填充这类不经过编辑器的入口，规则可能不触发也可能全部拦下。上线前用真实数据走一遍这几种输入方式，比只看文档更可靠。

条件格式的规则数量要克制。每条规则在重绘时都要参与判断，几十条规则叠在几万行上会明显拖慢滚动。优先把规则作用在必要区域，或者把判断结果算到辅助列里，再用一条简单规则上色。
