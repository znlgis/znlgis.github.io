# 第十七章：性能优化与最佳实践

表格控件卡顿的原因通常不是「控件慢」，而是调用方式不对：逐格触发重绘、每次赋值都重算公式、大表上反复自动调整行列。这一章把前面各章零散提到的性能要点集中起来，讲清楚什么时候该批量、什么时候该关掉自动行为、什么操作真正吃内存。

优化的顺序是：先量，再改，改完再量。凭感觉猜瓶颈经常猜错，数据量到十万行时，瓶颈可能在公式重算、可能在绘制、也可能在数据加载本身。用 Stopwatch 分段计时，比盲目套用「最佳实践」更有效。

## 17.1 性能优化原则

### 17.1.1 批量操作优化

示例对比了两种写法。逐格写入时，每次赋值都可能触发单元格失效、重绘和依赖重算，一千次就是一千份开销；批量写法把循环包进 BeginUpdate 与 EndUpdate 之间，中间只记录变化，最后统一刷新一次。

BeginUpdate 的配对必须严格。用 try/finally 保证 EndUpdate 一定被调用，否则一次异常就会让控件停留在挂起状态，界面不再刷新，看起来像死机。

样式也应当批量设置。示例把逐格的 SetCellStyle 换成一次 SetRangeStyles，区域相同，但只触发一次样式计算，代价从一千次降到一次。

```csharp
public class BatchOperations
{
    // ❌ 不推荐：逐个单元格操作
    public void SlowWay(Worksheet sheet)
    {
        for (int i = 0; i < 1000; i++)
        {
            sheet[i, 0] = i;
            sheet.SetCellStyle(i, 0, new WorksheetRangeStyle { Bold = true });
        }
    }
    
    // ✅ 推荐：批量操作
    public void FastWay(Worksheet sheet)
    {
        // 使用BeginUpdate和EndUpdate包裹批量操作
        sheet.BeginUpdate();
        try
        {
            for (int i = 0; i < 1000; i++)
            {
                sheet[i, 0] = i;
            }
            
            // 一次性设置样式
            sheet.SetRangeStyles("A1:A1000", new WorksheetRangeStyle { Bold = true });
        }
        finally
        {
            sheet.EndUpdate();
        }
    }
}
```

批量操作还有几种常见形态：整行写入、整区域复制、从数组一次性导入。它们的共同点是「先攒后写」，把 N 次小操作合并成一次大操作。数据量不大时差别不明显，超过几千行就会看出差距。

挂起重绘期间，界面上看不到中间结果，这是预期行为而不是故障。需要展示进度时，按批次调用 EndUpdate 再 BeginUpdate，或者用进度条单独提示。

### 17.1.2 禁用自动计算

公式表是自动计算的重灾区。一万行数据带公式，每次赋值都可能触发链式重算，总耗时随公式数量和依赖深度增长。关掉自动计算，写完数据再整表重算一次，耗时从「每格一次」降到「整表一次」。

开关是工作簿级的设置，用 SetSettings 修改。示例在循环前关、循环后开，中间手动调用 RecalculateAll，结构清晰。

关闭期间读公式单元格拿到的是旧结果。如果业务逻辑依赖计算结果，必须在重算之后再读，否则会拿到上一步的缓存值。

```csharp
public class CalculationOptimization
{
    public void OptimizeCalculation(ReoGridControl grid, Worksheet sheet)
    {
        // 大量数据操作时禁用自动计算
        grid.SetSettings(WorkbookSettings.Formula_AutoCalculate, false);
        
        // 执行数据操作
        for (int i = 0; i < 10000; i++)
        {
            sheet[i, 0] = i;
            sheet[i, 1] = $"=A{i+1}*2";
        }
        
        // 手动触发一次计算
        sheet.RecalculateAll();
        
        // 重新启用自动计算
        grid.SetSettings(WorkbookSettings.Formula_AutoCalculate, true);
    }
}
```

恢复设置的语句要放在 finally 里，和 BeginUpdate 同理。导入中途抛异常而忘记恢复，后续所有操作都不会再自动计算，用户改数据看不到结果，问题表现为「公式失灵」，排查方向容易跑偏。

重算也有优化空间。整表重算适合一次性导入；只改了几格时，可以只重算相关区域。区域级重算的接口是否提供取决于版本，没有的话退而求其次，按行分块调用。

## 17.2 内存管理

### 17.2.1 大数据集处理

大数据集的问题不在数据本身，而在「为每一行分配单元格对象」。ReoGrid 的行列对象是按需创建的，写多少格就建多少对象，几十万格意味着几十万个对象，内存占用会明显上升。

示例在写入前通过 ControlAdapter 拿到控件，关掉了网格线。网格线看着不起眼，但每一行每一列都要绘制，大表上关掉能省下可观的绘制时间；代价是界面变成纯白底，需要靠边框或交替色区分行列。

ControlAdapter 是工作簿与控件之间的桥。纯 Workbook 场景（不显示界面，只做计算与导出）没有控件，转换结果为 null，取到之后要先判空。

```csharp
public class LargeDataHandling
{
    public void LoadLargeData(Worksheet sheet, DataTable dataTable)
    {
        sheet.BeginUpdate();
        try
        {
            // 关闭不必要的功能
            var grid = sheet.Workbook.ControlAdapter as ReoGridControl;
            grid.SetSettings(WorkbookSettings.View_ShowGridLine, false);
            
            // 批量加载数据
            int row = 0;
            foreach (DataRow dataRow in dataTable.Rows)
            {
                for (int col = 0; col < dataTable.Columns.Count; col++)
                {
                    sheet[row, col] = dataRow[col];
                }
                row++;
            }
        }
        finally
        {
            sheet.EndUpdate();
        }
    }
}
```

数据加载用 BeginUpdate 包住，作用与前面相同：减少中间重绘。加载过程中不要逐行自动调整行高，那是 O(n²) 级别的开销。

真正的大数据场景要考虑分页。一次只加载当前页到工作表，翻页时清空重填，内存占用保持在可控范围。用户感知到的是「翻页稍慢」，而不是「程序崩溃」。

加载完成后把不必要的行删掉也很重要。导入模板往往预留了几百行空白，留着会占内存、也会出现在打印和导出结果里。

### 17.2.2 资源释放

控件实现了 IDisposable，用完要释放。示例用 try/finally 包住，即使中间抛异常也能走释放逻辑。在窗体里，控件通常加入 Controls 集合，由父容器负责释放，不需要手工调用；动态创建又没加入容器时才要自己管。

释放之后不能再访问控件或其工作表。继续调用会抛对象已释放的异常，定位时看到的是「控件莫名失效」，实际是释放顺序问题。

除了控件，图片、字体、画刷这类 GDI 资源也要释放。自定义绘制里创建的 Pen、Brush 用完立即 Dispose，不要指望垃圾回收及时处理句柄。

```csharp
public class ResourceManagement
{
    public void ProperDisposal()
    {
        ReoGridControl grid = null;
        try
        {
            grid = new ReoGridControl();
            // 使用grid
        }
        finally
        {
            grid?.Dispose();
        }
    }
}
```

资源释放与事件订阅是一对。控件释放前取消所有事件订阅，尤其是长生命周期的服务对象订阅了短生命周期的控件，容易造成对象无法回收。

反复创建销毁控件是另一种浪费。表格控件初始化有成本，页面切换时复用同一个实例、清空数据后重新填充，比每次 new 一个更划算。

## 17.3 最佳实践

### 17.3.1 代码组织

示例用扩展方法封装了批量写入。好处是调用处简单，sheet.FastSetData(...) 一行完成，内部保证挂起与恢复成对；坏处是隐藏了细节，排查性能问题时需要知道扩展方法里做了什么。

这类辅助方法应当集中放在一个静态类里，全项目共用同一份实现。各处自己写循环、各自决定要不要挂起重绘，是性能问题反复出现的根源。

扩展方法命名要能看出副作用。FastSetData 这类名字说明它会写数据；如果叫 WithData 之类的中性名称，调用方可能不知道它会批量刷新。

```csharp
// ✅ 推荐：使用辅助类封装常用操作
public static class ReoGridExtensions
{
    public static void FastSetData<T>(this Worksheet sheet, int startRow, int startCol, T[,] data)
    {
        sheet.BeginUpdate();
        try
        {
            int rows = data.GetLength(0);
            int cols = data.GetLength(1);
            
            for (int r = 0; r < rows; r++)
            {
                for (int c = 0; c < cols; c++)
                {
                    sheet[startRow + r, startCol + c] = data[r, c];
                }
            }
        }
        finally
        {
            sheet.EndUpdate();
        }
    }
}
```

代码组织的另一条经验是把「操作」和「数据」分开。操作知道怎么挂起重绘、怎么恢复设置；数据层只负责提供值。两者分开后，同一套操作逻辑可以复用到不同的数据来源上。

工具类不宜过大。一个类里堆几十个扩展方法会变成新的泥潭，按用途拆成读写、样式、行列操作几个文件，查找和修改都轻松。

### 17.3.2 错误处理

表格操作的异常多来自边界：行号越界、区域非法、单元格为 null、格式不匹配。示例用 try/catch 包住单格写入，失败时记录日志并返回 false，调用方可以决定继续还是中断。

捕获异常不要写空的 catch 块。至少记录地址和异常信息，否则排查时只有「某些格没写进去」这一个线索。

批量操作里的异常处理要分层：单格失败可以跳过继续，结构性失败（工作表已释放、区域非法）应当中断整批并向上抛。

```csharp
public class ErrorHandlingBestPractices
{
    public bool SafeSetCellValue(Worksheet sheet, string address, object value)
    {
        try
        {
            sheet[address] = value;
            return true;
        }
        catch (Exception ex)
        {
            Console.WriteLine($"设置单元格 {address} 失败: {ex.Message}");
            return false;
        }
    }
}
```

错误处理不能替代参数校验。行号来自用户输入时先判断范围，区域来自配置时先判断是否为空，这些检查比异常处理便宜得多，也更容易给出准确的提示。

抛异常本身有开销。在循环里用异常做流程控制（例如靠越界异常判断结束）会显著拖慢批量操作，正常路径上不要依赖异常。

### 17.3.3 性能监控

示例用 Stopwatch 包住一段操作并打印耗时。它是排查性能问题最基础的工具：先测出哪一段慢，再针对那一段优化。

计时点要放在有意义的边界上：数据加载、公式重算、样式应用、界面刷新，分开计时才能看出各自占比。只测总时长，得到的结论往往是「都很慢」。

测量结果受机器状态影响，跑一次不够。同一操作重复几次取稳定值，或者在同一台机器上对比优化前后的数据，结论才可信。

```csharp
using System.Diagnostics;

public class PerformanceMonitoring
{
    public void MeasurePerformance(Action operation, string operationName)
    {
        var sw = Stopwatch.StartNew();
        
        operation();
        
        sw.Stop();
        Console.WriteLine($"{operationName} 耗时: {sw.ElapsedMilliseconds}ms");
    }
}
```

监控数据要落到日志里，而不是只打印到控制台。生产环境出问题时，用户提供一份带耗时的日志，比让他描述「卡不卡」有效得多。

不要为了监控给每格操作都计时。Stopwatch 本身也有开销，逐格计时会让测量结果失真，只在批次边界计时。

## 17.4 常见性能问题

### 17.4.1 避免频繁重绘

最常见的性能问题是循环里直接改界面。示例对比了两种写法：每次赋值都触发重绘，一百次就是一百次；挂起重绘后，只在一百次结束时刷新一次。

重绘的代价与可见区域大小相关。窗口最大化时一次重绘要画的内容更多，逐格触发的代价也更高，这就是为什么同一段代码在小窗口里看不出卡、全屏时明显卡。

除了 BeginUpdate，减少不必要的属性设置同样有效。给同一个区域连续设十次样式，只有最后一次有意义；先算好再设一次，能省下九次。

```csharp
public class AvoidFrequentRedraw
{
    // ❌ 不推荐
    public void BadPractice(Worksheet sheet)
    {
        for (int i = 0; i < 100; i++)
        {
            sheet[i, 0] = i;
            // 每次都会触发重绘
        }
    }
    
    // ✅ 推荐
    public void GoodPractice(Worksheet sheet)
    {
        sheet.BeginUpdate();  // 暂停重绘
        for (int i = 0; i < 100; i++)
        {
            sheet[i, 0] = i;
        }
        sheet.EndUpdate();  // 一次性重绘
    }
}
```

频繁重绘还有一类隐蔽来源：在事件处理器里改样式。CellDataChanged 里给单元格上色，每次数据变化都会触发一次样式变更与重绘，数据量一大就卡。把这类逻辑改成批量处理，或者只在用户结束编辑后统一执行。

滚动时重绘是正常开销，不必强行消除。需要检查的是「静止状态下是否也在不停重绘」，那通常意味着某个定时器或事件在不必要地触发。

## 17.5 本章小结

本章介绍了ReoGrid的性能优化技巧和最佳实践。

把全章内容压成一张清单，按收益从高到低排列：

1. 批量操作包进 BeginUpdate / EndUpdate，异常路径用 try/finally 兜住；
2. 大批量写公式前关掉自动计算，写完统一重算，再恢复设置；
3. 大表关闭网格线等非必要绘制；
4. 自动调整行列宽高放在数据与样式设置完成之后，只执行一次；
5. 复用控件实例，避免反复创建销毁；
6. 及时释放图片、字体、画刷等 GDI 资源；
7. 用 Stopwatch 分段计时，按数据而不是按感觉优化。

性能优化最容易走偏的地方是「提前优化」。几百行的表格不需要挂起重绘，几百个单元格也不需要关闭自动计算，加上这些代码只会让逻辑更绕。等到数据量或用户反馈暴露问题，再按清单逐项排查。

另一条经验是保持基准数据。把「一万行导入耗时」「整表重算耗时」记在项目文档里，每次改动后跑一遍，性能回退能及时发现。没有基准，优化就变成了一次性的玄学。
