# 第十九章：高级应用与扩展

前十八章讲的是控件本身怎么用，这一章处理「把控件接进一个更大的系统」时要面对的问题：功能怎么拆成可插拔的模块，绘制能不能自定义，数据从数据库或接口来怎么加载，后台线程怎么安全地碰表格。

这些话题没有唯一答案，示例给出的是可以落地的骨架，实际项目按自己的架构调整。看这一章时关注「为什么要这样分层」，比记住具体代码更有用。

## 19.1 插件系统

ReoGrid 没有官方插件协议，示例定义了一个自己的接口，包含名称、描述、初始化与反初始化四个成员。这是插件化最常见的做法：约定接口，宿主按接口加载并调用生命周期方法。

插件的价值在于把可选功能从主程序里拆出去。导出 PDF、审计留痕、自定义函数库，这些功能只有部分客户需要，做成插件后主程序不必引用相关依赖。

接口设计要克制。成员越少，插件实现越容易；生命周期方法只有初始化和反初始化两个，插件内部自己管理事件订阅与资源分配。

```csharp
public interface IReoGridPlugin
{
    string Name { get; }
    string Description { get; }
    void Initialize(ReoGridControl grid);
    void Uninitialize();
}

public class ExamplePlugin : IReoGridPlugin
{
    public string Name => "示例插件";
    public string Description => "这是一个示例插件";
    
    private ReoGridControl grid;
    
    public void Initialize(ReoGridControl grid)
    {
        this.grid = grid;
        // 初始化插件
        RegisterMenuItems();
    }
    
    private void RegisterMenuItems()
    {
        // 添加自定义菜单项
    }
    
    public void Uninitialize()
    {
        // 清理资源
    }
}
```

示例插件在 Initialize 里拿到了控件引用并注册菜单项，Uninitialize 里清理资源。这两个方法必须成对，初始化里订阅的事件要在反初始化里取消，否则插件卸载后处理器还挂在控件上。

宿主需要一份插件清单，记录要加载的程序集和类型。清单可以写在配置里，也可以扫描目录下的 DLL 按接口匹配。扫描方式灵活，但要注意加载顺序与版本冲突。

.NET 的程序集一旦加载进默认上下文就无法卸载。插件更新通常需要重启应用，或者用可卸载的加载上下文（复杂度明显上升）。设计插件机制时先接受「重启生效」这个限制，能省下大量工作。

## 19.2 自定义渲染器

示例定义了一个自定义单元格渲染器，接管单元格的绘制。绘制方法里能拿到单元格对象和绘图上下文，先画背景，再画文本。

这个接口在不同版本里的名称与位置可能不同，示例用的是 Rendering 命名空间下的写法。如果当前程序集里没有这个类型，不必强行找替代，用第十五章的 CellBody 更稳妥：它同样是文档化的扩展点，重写 OnPaint 就能实现自定义绘制。

自定义渲染要遵守两条约束：只在单元格矩形内绘制，不要影响相邻格；颜色与字体从单元格样式读取，不要写死，否则选中、禁用等状态会看起来不对。

```csharp
using unvell.ReoGrid.Rendering;

public class CustomCellRenderer : ICellRenderer
{
    public void DrawCell(CellDrawingContext dc, Cell cell)
    {
        // 自定义单元格渲染逻辑
        var bounds = cell.Bounds;
        
        // 绘制自定义背景
        dc.Graphics.FillRectangle(
            new SolidBrush(Color.LightYellow),
            bounds
        );
        
        // 绘制文本
        if (cell.Data != null)
        {
            dc.Graphics.DrawString(
                cell.Data.ToString(),
                cell.Style.Font,
                Brushes.Black,
                bounds
            );
        }
    }
}
```

自定义渲染适合做特殊视觉：状态色块、迷你图、图标列。它的代价是每次重绘都要执行你的代码，逻辑越重滚动越卡。能用样式和条件格式解决的，不要写自定义渲染。

渲染器要处理边界情况：单元格为空、数据为 DBNull、文本超出宽度。这些情况在真实数据里天天出现，示例只画了非空值，生产代码要把兜底补齐。

## 19.3 数据源集成

数据库加载的骨架很固定：打开连接、执行查询、读列名做表头、逐行读数据写入单元格。示例用 using 包住连接与读取器，保证异常时也能释放。

表头来自 reader.GetName，这是最省事的做法，列名就是字段名。需要中文表头或调整顺序时，用列别名（SELECT 字段 AS 显示名），比在代码里做映射更简单。

写入循环包在 BeginUpdate 里，避免每格触发重绘。数据量大时还要考虑分页，一次性读几十万行进内存，再逐格写进表格，内存峰值会很高。

```csharp
public class DatabaseIntegration
{
    public void LoadFromDatabase(Worksheet sheet, string connectionString, string query)
    {
        using (var connection = new SqlConnection(connectionString))
        {
            connection.Open();
            using (var command = new SqlCommand(query, connection))
            using (var reader = command.ExecuteReader())
            {
                sheet.BeginUpdate();
                try
                {
                    // 加载列头
                    for (int i = 0; i < reader.FieldCount; i++)
                    {
                        sheet[0, i] = reader.GetName(i);
                    }
                    
                    // 加载数据
                    int row = 1;
                    while (reader.Read())
                    {
                        for (int col = 0; col < reader.FieldCount; col++)
                        {
                            sheet[row, col] = reader[col];
                        }
                        row++;
                    }
                }
                finally
                {
                    sheet.EndUpdate();
                }
            }
        }
    }
}
```

数据库里最常见的坑是 DBNull。reader[col] 取到空值时返回 DBNull.Value，直接赋给单元格，单元格里存的是一个 DBNull 对象，显示和后续转换都可能出问题。写入前判断 DBNull 并转成 null。

字段类型与单元格类型要匹配。数据库里的 decimal、DateTime 写进单元格后，显示格式由单元格的格式设置决定，不会自动带上货币符号或本地化日期写法，需要另外设置数据格式。

连接字符串不要硬编码在业务代码里。示例把它作为参数传入，实际项目应从配置或密钥管理读取，避免随源码泄露。

## 19.4 Web API集成

接口数据加载多两步：发请求、解析 JSON。示例用 HttpClient 取回字符串，反序列化成字典列表，再按行列写进工作表。

字典的键顺序不保证与 JSON 里的顺序一致，靠字典枚举决定列顺序，多行数据可能错列。稳妥做法是按第一行的键生成列顺序，所有行按同一顺序取值；或者反序列化成带属性的强类型对象。

NewtonSoft 反序列化到 object 时，数字与日期会变成 JToken 包装类型，直接写入单元格显示的是 JSON 片段而不是数值。取 Value 或按 JToken 类型转换后再写入。

```csharp
using System.Net.Http;
using Newtonsoft.Json;

public class WebApiIntegration
{
    public async Task LoadFromWebApi(Worksheet sheet, string apiUrl)
    {
        using (var client = new HttpClient())
        {
            var json = await client.GetStringAsync(apiUrl);
            var data = JsonConvert.DeserializeObject<List<Dictionary<string, object>>>(json);
            
            sheet.BeginUpdate();
            try
            {
                // 加载数据到工作表
                int row = 0;
                foreach (var item in data)
                {
                    int col = 0;
                    foreach (var kvp in item)
                    {
                        if (row == 0)
                        {
                            sheet[row, col] = kvp.Key;  // 列头
                        }
                        sheet[row + 1, col] = kvp.Value;  // 数据
                        col++;
                    }
                    row++;
                }
            }
            finally
            {
                sheet.EndUpdate();
            }
        }
    }
}
```

网络请求是异步的，UI 线程不能在等结果时阻塞。示例用 await 取数据，取回后再写表格，这个顺序是正确的。

接口返回的数据量不可控，要设上限。一次返回十万行会让加载和渲染都变慢，分页请求或限制条数，是接口集成的常规约束。

示例的写入逻辑按行号递增，没有处理「表头只写一次」的细节，多行数据时列头与数据会错位。实际实现时先写一行表头，数据从第二行开始。

## 19.5 多线程支持

表格控件是 UI 对象，绝大多数成员只能在创建它的 UI 线程上调用。示例在后台线程里调用 BeginUpdate 和写单元格，随后在 Dispatcher 里 EndUpdate，这种写法依赖控件内部是否做了线程封送，风险较高。

更稳的分工是：后台线程只做耗时计算与数据准备，整理成二维数组或对象列表；回到 UI 线程后一次性写入表格。计算与渲染分开，既避免跨线程问题，也让写入可以批量优化。

WPF 用 Dispatcher.Invoke 回主线程，WinForms 用 Control.Invoke 或 BeginInvoke。两者都要注意不要在 UI 线程上同步等待后台任务，否则界面会假死。

```csharp
public class MultiThreading
{
    public async Task LoadDataAsync(Worksheet sheet, DataTable dataTable)
    {
        await Task.Run(() =>
        {
            sheet.BeginUpdate();
            try
            {
                // 在后台线程加载数据
                for (int r = 0; r < dataTable.Rows.Count; r++)
                {
                    for (int c = 0; c < dataTable.Columns.Count; c++)
                    {
                        sheet[r, c] = dataTable.Rows[r][c];
                    }
                }
            }
            finally
            {
                // 回到UI线程更新
                Application.Current.Dispatcher.Invoke(() =>
                {
                    sheet.EndUpdate();
                });
            }
        });
    }
}
```

后台加载期间的进度反馈要做。用户看不到进度条，只会觉得程序没反应，反复点击按钮可能触发重复加载，问题被放大。

取消机制也要考虑。用户关闭页面或切换数据源时，后台任务应当能被取消，取消后不要再回调 UI。用 CancellationToken 贯穿整个加载流程，比事后判断标志位干净。

## 19.6 本章小结

本章介绍了ReoGrid的高级应用和扩展方法。

四个方向的要点：

- 插件：自定义接口加生命周期方法，宿主按清单加载，程序集无法卸载是常见限制；
- 渲染：自定义单元格绘制适合特殊视觉，能落在 CellBody.OnPaint 上就不必另找渲染接口；
- 数据源：数据库与接口加载都能复用「读表头、批量写、包 BeginUpdate」的骨架；
- 多线程：后台只做计算，UI 线程负责写控件，跨线程访问要回到宿主线程。

这一章的内容更像是架构建议而不是 API 手册。真正决定项目质量的，是这些边界有没有被守住：插件卸载是否清理了订阅，后台线程有没有碰控件，接口数据有没有设上限。

下一章用四个完整案例把这些能力串起来，看看一个真实的表格应用大概长什么样。
