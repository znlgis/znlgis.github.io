# 第十七章：企业级应用最佳实践

## 17.1 架构设计

单文件、单方法的 NPOI 代码在脚本里很好用，放进服务端项目就会暴露问题：每个业务类各自 new 工作簿、各自处理异常、各自拼表头，改一次样式要翻十几个文件。企业级应用的第一件事，是把文档读写从业务逻辑里剥离出来。

剥离的手段是分层加接口。业务层只描述"要导出什么数据"，基础设施层负责"怎么写成 xlsx"。中间靠接口和选项对象传递意图。这样做的收益不只是整洁——它让文档格式的调整、性能优化、异常统一处理都变成单点改动。

### 17.1.1 服务层封装

这段代码定义了三个类型：服务接口 `IExcelService`、导出/导入选项、以及实现类 `ExcelService`。

**接口设计**只有三个方法，覆盖导出、泛型导入、导入到 DataTable。方法少是有意的：接口越宽，实现和测试的成本越高，也越容易在业务层用到不该暴露的细节（比如工作表对象）。

**选项对象**把可变参数从方法签名里移出来。`ExportOptions` 带工作表名、是否含表头、列映射、列格式。用选项对象的好处是新增参数不破坏签名，调用方只填关心的字段，其余走默认值。`ImportOptions` 同理，额外有起始行和必填列。

实现部分逐段看。

**导出**用泛型加反射读属性：`typeof(T).GetProperties()` 拿到全部公共属性，按顺序建表头和数据列。反射读值 `properties[i].GetValue(item)` 有性能成本，但导出场景通常是几十到几万行，这个成本可以接受；行数上百万时应当换成表达式树编译的访问器，或者让调用方直接传二维数组。

表头名通过 `GetColumnName` 获取，优先用选项里的 `ColumnMappings`，其次读 `DisplayNameAttribute`，都没有才用属性名。这个优先级顺序合理：调用方显式指定 > 模型自描述 > 类型名兜底。

单元格赋值走 `SetCellValue`，按值的运行时类型分发。这里的分支覆盖了字符串、日期、双精度、小数、整数、布尔，其余类型统一 `ToString()`。日期分支会设置日期格式样式，这是必须的——NPOI 里日期写成数值后如果不设格式，Excel 显示的是 45000 这样的序列号。

样式缓存 `styleCache` 是个重要细节。NPOI 对工作簿里的样式数量有上限（xls 是 4000 左右，xlsx 更高但也不宜滥用），每个单元格新建样式很快就会触顶。缓存按格式描述复用样式对象，是标准的做法。

**自动列宽** `sheet.AutoSizeColumn(i)` 会按内容计算列宽。它在数据量大时很慢（每个单元格都要测量字体渲染宽度），导出几万行时这一句可能占总耗时的一半以上。企业应用里常见的做法是给固定列宽，只对短文本列自动调整。

**导入**先从表头建立列映射：遍历表头行的每个单元格，按列名找到对应属性，存进 `columnMap`。这一步把"第几列对应哪个属性"确定下来，后面逐行读取时就不用再做名称查找。

数据从 `startRow` 开始循环到 `sheet.LastRowNum`。`LastRowNum` 是最后一个有内容的行号，空行会被跳过（`row == null` 判断）。`hasData` 标记用于过滤全空行，避免把空行也加入结果。

`ConvertCellValue` 处理类型转换，覆盖了字符串、日期、数值三类。日期判断用 `DateUtil.IsCellDateFormatted(cell)` 区分"格式化为日期的数值"和"普通数值"——Excel 里日期本质是数值，只能靠格式判断。所有转换都包在 try/catch 里，转换失败返回 null，不中断整个导入。这个策略适合"尽力导入"的场景，代价是错误被静默吞掉，需要在调用方统计 null 数量来发现数据质量问题。

**导入到 DataTable** 走的是另一条路径：不做类型转换，所有单元格 `ToString()`，适合"先看数据再决定怎么处理"的场景。列名取表头文本，没有表头时用 `Column0`、`Column1` 这样的占位名。重复列名会让 `dt.Columns.Add` 抛异常，真实数据里重名列并不罕见，应当加去重逻辑。

```csharp
/// <summary>
/// Excel服务接口
/// </summary>
public interface IExcelService
{
    byte[] Export<T>(IEnumerable<T> data, ExportOptions options = null) where T : class;
    List<T> Import<T>(Stream fileStream, ImportOptions options = null) where T : class, new();
    DataTable ImportToDataTable(Stream fileStream, int sheetIndex = 0, bool hasHeader = true);
}

/// <summary>
/// 导出选项
/// </summary>
public class ExportOptions
{
    public string SheetName { get; set; } = "Sheet1";
    public bool IncludeHeader { get; set; } = true;
    public Dictionary<string, string> ColumnMappings { get; set; }
    public Dictionary<string, string> ColumnFormats { get; set; }
}

/// <summary>
/// 导入选项
/// </summary>
public class ImportOptions
{
    public int SheetIndex { get; set; } = 0;
    public bool HasHeader { get; set; } = true;
    public int StartRow { get; set; } = 0;
    public Dictionary<string, string> ColumnMappings { get; set; }
    public List<string> RequiredColumns { get; set; }
}

/// <summary>
/// Excel服务实现
/// </summary>
public class ExcelService : IExcelService
{
    public byte[] Export<T>(IEnumerable<T> data, ExportOptions options = null) where T : class
    {
        options ??= new ExportOptions();
        
        IWorkbook workbook = new XSSFWorkbook();
        ISheet sheet = workbook.CreateSheet(options.SheetName);
        
        var properties = typeof(T).GetProperties();
        
        // 创建表头
        if (options.IncludeHeader)
        {
            IRow headerRow = sheet.CreateRow(0);
            ICellStyle headerStyle = CreateHeaderStyle(workbook);
            
            for (int i = 0; i < properties.Length; i++)
            {
                string columnName = GetColumnName(properties[i], options.ColumnMappings);
                ICell cell = headerRow.CreateCell(i);
                cell.SetCellValue(columnName);
                cell.CellStyle = headerStyle;
            }
        }
        
        // 创建数据行
        int rowIndex = options.IncludeHeader ? 1 : 0;
        var styleCache = new Dictionary<string, ICellStyle>();
        
        foreach (var item in data)
        {
            IRow row = sheet.CreateRow(rowIndex++);
            for (int i = 0; i < properties.Length; i++)
            {
                ICell cell = row.CreateCell(i);
                object value = properties[i].GetValue(item);
                SetCellValue(cell, value, workbook, options, properties[i].Name, styleCache);
            }
        }
        
        // 自动列宽
        for (int i = 0; i < properties.Length; i++)
        {
            sheet.AutoSizeColumn(i);
        }
        
        using MemoryStream ms = new MemoryStream();
        workbook.Write(ms);
        return ms.ToArray();
    }
    
    public List<T> Import<T>(Stream fileStream, ImportOptions options = null) where T : class, new()
    {
        options ??= new ImportOptions();
        
        IWorkbook workbook = WorkbookFactory.Create(fileStream);
        ISheet sheet = workbook.GetSheetAt(options.SheetIndex);
        
        var result = new List<T>();
        var properties = typeof(T).GetProperties();
        
        // 建立列映射
        var columnMap = new Dictionary<int, PropertyInfo>();
        IRow headerRow = sheet.GetRow(options.StartRow);
        
        if (options.HasHeader && headerRow != null)
        {
            for (int i = 0; i < headerRow.LastCellNum; i++)
            {
                string columnName = headerRow.GetCell(i)?.ToString();
                if (string.IsNullOrEmpty(columnName)) continue;
                
                var prop = FindProperty(properties, columnName, options.ColumnMappings);
                if (prop != null)
                {
                    columnMap[i] = prop;
                }
            }
        }
        
        // 读取数据
        int startRow = options.HasHeader ? options.StartRow + 1 : options.StartRow;
        for (int i = startRow; i <= sheet.LastRowNum; i++)
        {
            IRow row = sheet.GetRow(i);
            if (row == null) continue;
            
            T item = new T();
            bool hasData = false;
            
            foreach (var kvp in columnMap)
            {
                ICell cell = row.GetCell(kvp.Key);
                if (cell == null) continue;
                
                object value = ConvertCellValue(cell, kvp.Value.PropertyType);
                if (value != null)
                {
                    kvp.Value.SetValue(item, value);
                    hasData = true;
                }
            }
            
            if (hasData) result.Add(item);
        }
        
        return result;
    }
    
    public DataTable ImportToDataTable(Stream fileStream, int sheetIndex = 0, bool hasHeader = true)
    {
        IWorkbook workbook = WorkbookFactory.Create(fileStream);
        ISheet sheet = workbook.GetSheetAt(sheetIndex);
        
        DataTable dt = new DataTable(sheet.SheetName);
        IRow firstRow = sheet.GetRow(0);
        
        if (firstRow == null) return dt;
        
        int columnCount = firstRow.LastCellNum;
        
        // 创建列
        for (int i = 0; i < columnCount; i++)
        {
            string columnName = hasHeader 
                ? firstRow.GetCell(i)?.ToString() ?? $"Column{i}"
                : $"Column{i}";
            dt.Columns.Add(columnName);
        }
        
        // 读取数据
        int startRow = hasHeader ? 1 : 0;
        for (int i = startRow; i <= sheet.LastRowNum; i++)
        {
            IRow row = sheet.GetRow(i);
            if (row == null) continue;
            
            DataRow dr = dt.NewRow();
            for (int j = 0; j < columnCount; j++)
            {
                dr[j] = row.GetCell(j)?.ToString() ?? "";
            }
            dt.Rows.Add(dr);
        }
        
        return dt;
    }
    
    // 辅助方法...
    private ICellStyle CreateHeaderStyle(IWorkbook workbook)
    {
        ICellStyle style = workbook.CreateCellStyle();
        IFont font = workbook.CreateFont();
        font.IsBold = true;
        style.SetFont(font);
        style.FillForegroundColor = IndexedColors.Grey25Percent.Index;
        style.FillPattern = FillPattern.SolidForeground;
        style.Alignment = HorizontalAlignment.Center;
        return style;
    }
    
    private string GetColumnName(PropertyInfo prop, Dictionary<string, string> mappings)
    {
        if (mappings != null && mappings.TryGetValue(prop.Name, out string name))
            return name;
            
        var displayAttr = prop.GetCustomAttribute<DisplayNameAttribute>();
        return displayAttr?.DisplayName ?? prop.Name;
    }
    
    private void SetCellValue(ICell cell, object value, IWorkbook workbook,
        ExportOptions options, string propName, Dictionary<string, ICellStyle> styleCache)
    {
        if (value == null) return;
        
        switch (value)
        {
            case string s:
                cell.SetCellValue(s);
                break;
            case DateTime dt:
                cell.SetCellValue(dt);
                cell.CellStyle = GetOrCreateDateStyle(workbook, styleCache);
                break;
            case double d:
                cell.SetCellValue(d);
                break;
            case decimal dec:
                cell.SetCellValue((double)dec);
                break;
            case int i:
                cell.SetCellValue(i);
                break;
            case bool b:
                cell.SetCellValue(b);
                break;
            default:
                cell.SetCellValue(value.ToString());
                break;
        }
    }
    
    private ICellStyle GetOrCreateDateStyle(IWorkbook workbook, Dictionary<string, ICellStyle> cache)
    {
        if (!cache.TryGetValue("date", out ICellStyle style))
        {
            style = workbook.CreateCellStyle();
            IDataFormat format = workbook.CreateDataFormat();
            style.DataFormat = format.GetFormat("yyyy-MM-dd");
            cache["date"] = style;
        }
        return style;
    }
    
    private PropertyInfo FindProperty(PropertyInfo[] properties, string columnName,
        Dictionary<string, string> mappings)
    {
        // 先检查映射
        if (mappings != null)
        {
            foreach (var kvp in mappings)
            {
                if (kvp.Value.Equals(columnName, StringComparison.OrdinalIgnoreCase))
                {
                    return properties.FirstOrDefault(p => p.Name == kvp.Key);
                }
            }
        }
        
        // 按名称匹配
        return properties.FirstOrDefault(p => 
            p.Name.Equals(columnName, StringComparison.OrdinalIgnoreCase));
    }
    
    private object ConvertCellValue(ICell cell, Type targetType)
    {
        if (cell == null) return null;
        
        Type underlyingType = Nullable.GetUnderlyingType(targetType) ?? targetType;
        
        try
        {
            if (underlyingType == typeof(string))
                return cell.ToString();
            
            if (underlyingType == typeof(DateTime))
            {
                if (cell.CellType == CellType.Numeric && DateUtil.IsCellDateFormatted(cell))
                    return cell.DateCellValue;
                if (DateTime.TryParse(cell.ToString(), out DateTime dt))
                    return dt;
                return null;
            }
            
            if (cell.CellType == CellType.Numeric)
                return Convert.ChangeType(cell.NumericCellValue, underlyingType);
            
            if (double.TryParse(cell.ToString(), out double d))
                return Convert.ChangeType(d, underlyingType);
            
            return null;
        }
        catch
        {
            return null;
        }
    }
}
```

### 17.1.2 依赖注入配置

服务封装好之后要解决"谁能拿到它"。示例给了两条：一个扩展方法把服务注册进容器，一个控制器演示注入。

`services.AddScoped<IExcelService, ExcelService>()` 的生命周期选择值得说明。Scoped 表示"每个请求一个实例"。NPOI 的工作簿对象不是线程安全的，把服务注册成 Singleton 会让并发的导出请求共享同一个服务实例——如果服务内部持有工作簿字段，就会出现数据串号。用 Scoped 或 Transient 更安全。

反过来，如果服务内部没有任何可变状态（示例的 `ExcelService` 就是无状态的，所有对象都在方法内创建），Singleton 也能工作，但没必要——Scoped 已经足够，且更不容易随代码演进出问题。

控制器里 `return File(fileBytes, "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet", "export.xlsx")` 直接返回字节数组。这里有两个工程问题示例没有覆盖：

- **大文件的内存占用**。`byte[]` 要求整个文件先生成在内存里。导出十万行时，这个数组可能是几十 MB，并发几个请求就把内存吃满。正确做法是流式返回，边生成边写响应流（SXSSF + `Response.Body`），见第十六章。
- **Content-Type 必须是 xlsx 对应的类型**。示例里的长字符串是正确的 xlsx 类型，写错会导致浏览器不识别为 Excel 文件。

实际项目里还会遇到"导出参数校验"和"导出权限控制"。这两件事应当在控制器层或过滤器里做，不要塞进服务实现——服务只负责生成文件。

```csharp
// ASP.NET Core 依赖注入配置
public static class ServiceCollectionExtensions
{
    public static IServiceCollection AddExcelServices(this IServiceCollection services)
    {
        services.AddScoped<IExcelService, ExcelService>();
        services.AddScoped<IWordService, WordService>();
        return services;
    }
}

// 使用示例
public class MyController : ControllerBase
{
    private readonly IExcelService _excelService;
    
    public MyController(IExcelService excelService)
    {
        _excelService = excelService;
    }
    
    [HttpGet("export")]
    public IActionResult Export()
    {
        var data = GetData();
        byte[] fileBytes = _excelService.Export(data);
        return File(fileBytes, "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet", "export.xlsx");
    }
}
```

## 17.2 异常处理

NPOI 抛出的异常类型很杂：文件格式错误抛 `InvalidFormatException` 或 `IOException`，公式问题抛 `FormulaParseException`，大数据量下抛 `OutOfMemoryException`，流被提前释放抛 `ObjectDisposedException`。

业务代码如果逐个 catch 这些类型，会散落得到处都是。更实用的做法是定义一个业务异常体系，在边界处把底层异常翻译成业务语义，向上层暴露稳定的异常类型。

### 17.2.1 自定义异常

三个异常类的分工很清楚。

**ExcelException** 是基类，两个构造函数分别接收消息和内部异常。所有 Excel 相关异常都从它派生，调用方 catch 一个类型就能覆盖全部。

**InvalidExcelFormatException** 带 `FileName` 属性，消息里也拼上了文件名。这个属性的价值在于"程序化处理"——上层可以按文件名做重试、跳过、或者生成用户可读的错误清单。只靠消息字符串解析文件名是很脆弱的做法。

**ExcelDataValidationException** 有两个构造函数：一个针对单字段错误（行号、列名、错误描述），一个接受错误列表。它把"第几行、哪一列、什么错"结构化保存，这正是校验场景需要的——用户看到一个笼统的"数据验证失败"毫无帮助，看到"第 15 行，金额列数据验证失败：必须大于 0"才知道怎么改。

设计异常类有两条原则值得记。第一，异常应当携带足够的上下文，让人不用调试就能定位问题。第二，异常消息面向最终用户可读，异常属性面向程序处理，两者都要有。

还有一个细节：继承 `Exception` 时如果要做跨进程序列化，需要实现序列化构造函数。现代 .NET 里这条规则放宽了，但涉及远程调用或跨 AppDomain 的老项目要注意。

自定义异常不要滥用。只有"调用方需要区别对待"的错误才值得建新类型。所有错误都建一个异常类，结果就是每个 catch 块都要写一长串判断。

```csharp
/// <summary>
/// Excel操作异常基类
/// </summary>
public class ExcelException : Exception
{
    public ExcelException(string message) : base(message) { }
    public ExcelException(string message, Exception innerException) : base(message, innerException) { }
}

/// <summary>
/// 文件格式异常
/// </summary>
public class InvalidExcelFormatException : ExcelException
{
    public string FileName { get; }
    
    public InvalidExcelFormatException(string fileName, string message) 
        : base($"文件 '{fileName}' 格式无效: {message}")
    {
        FileName = fileName;
    }
}

/// <summary>
/// 数据验证异常
/// </summary>
public class ExcelDataValidationException : ExcelException
{
    public int RowIndex { get; }
    public string ColumnName { get; }
    public List<string> Errors { get; }
    
    public ExcelDataValidationException(int rowIndex, string columnName, string error)
        : base($"第 {rowIndex} 行, {columnName} 列数据验证失败: {error}")
    {
        RowIndex = rowIndex;
        ColumnName = columnName;
        Errors = new List<string> { error };
    }
    
    public ExcelDataValidationException(List<string> errors)
        : base($"数据验证失败: {string.Join("; ", errors)}")
    {
        Errors = errors;
    }
}
```

### 17.2.2 异常处理中间件

这个类提供了两个重载：泛型版本返回结果，无返回值版本包装 Action。核心是"把底层异常统一翻译成 ExcelException"。

四个 catch 分支的顺序有意义。`IOException` 在前，`InvalidOperationException` 其次，`OutOfMemoryException` 再其次，最后是兜底的 `Exception`。C# 的 catch 按顺序匹配，派生类必须写在基类前面，否则编译不过。这四个类型之间没有继承关系，顺序不影响正确性，但按"具体到宽泛"排列是好习惯。

每类异常翻译后的消息都加上了操作名（`operationName` 参数）。这是这类包装方法最重要的设计——异常发生时，用户和日志里能看到"文件名操作失败"而不是"对象引用未设置为对象的实例"。

**OutOfMemoryException 的单独处理值得展开。** 它通常意味着文件太大，靠重试解决不了，需要调整处理策略（改用流式 API、分批处理）。把它翻译成明确的"文件可能过大"提示，比让用户看到 "Exception of type 'System.OutOfMemoryException' was thrown" 有用得多。

但也要知道这种 try/catch 有代价：`OutOfMemoryException` 被捕获之后，进程内存状态可能已经不可靠，继续处理有风险。稳妥的策略是捕获后立即返回错误，不做后续的复杂操作，并记录详细日志。

无参重载 `SafeExecute(Action, string)` 的实现方式是用 lambda 包一层 `return true`，复用了泛型版本。这是消除重复代码的常用技巧，比复制一份逻辑更可靠。

使用这类包装器时要注意不要过度使用。如果每一层都包一次，异常会被包装成多层嵌套，日志里出现三层 `ExcelException: ... InnerException: ExcelException: ...`。约定在边界层（控制器、消息处理入口）包一次就够了。

```csharp
/// <summary>
/// Excel异常处理
/// </summary>
public static class ExcelExceptionHandler
{
    public static T SafeExecute<T>(Func<T> action, string operationName)
    {
        try
        {
            return action();
        }
        catch (IOException ex)
        {
            throw new ExcelException($"文件操作失败: {operationName}", ex);
        }
        catch (InvalidOperationException ex)
        {
            throw new ExcelException($"操作无效: {operationName}", ex);
        }
        catch (OutOfMemoryException ex)
        {
            throw new ExcelException($"内存不足，文件可能过大: {operationName}", ex);
        }
        catch (Exception ex)
        {
            throw new ExcelException($"{operationName} 失败", ex);
        }
    }
    
    public static void SafeExecute(Action action, string operationName)
    {
        SafeExecute(() => { action(); return true; }, operationName);
    }
}
```

## 17.3 日志记录

Excel 相关的操作有两个特点，决定了日志必须记：耗时长（几秒到几分钟），失败原因多样（文件、数据、内存、权限）。出问题时如果只有"导出失败"四个字，排查等于从零开始。

日志的设计要考虑三件事：记什么、记多少、给谁看。示例的 `ExcelOperationLogger` 给了一个恰当的粒度。

### 17.3.1 操作日志

这个类包装了 `ILogger<ExcelOperationLogger>`，提供三个方法：记导出、记导入、记错误。

**LogExport** 记录文件名、行数、耗时。三个字段的组合能回答"这份文件导出了多少数据、花了多久"。行数与耗时的比值是性能基线：正常情况下一万行大约零点几秒，某天突然变成几十秒，说明数据或环境有了变化。

**LogImport** 在错误数大于 0 时降级为 Warning，并额外记录错误数。这个分级合理：导入部分失败不是致命错误，但必须让人知道。日志级别用对了，告警系统才能按级别过滤——把"部分数据没导进来"记成 Information，等于没人会看到。

**LogError** 用 `LogError(ex, ...)` 的重载，把异常对象作为第一个参数传给日志框架。这一步很关键：很多日志框架会自动展开异常类型、消息、堆栈、内部异常，只传字符串会丢掉这些信息。

消息模板用的是 `{FileName}` 这类占位符，而不是字符串拼接。结构化日志框架会把这些占位符转成可查询的字段，方便按文件名、按耗时过滤。字符串拼接出来的日志只能全文搜索。

这个类缺少的几样东西：没有记录用户或租户标识（多租户系统里这是必须的）、没有记录文件大小（行数不等于数据量）、没有采样控制（高频导出会把日志写满）。真实项目里按需要补。

日志内容本身也可能泄露敏感信息。文件名如果包含客户名、行数如果反映业务规模，在受监管行业里都属于需要脱敏的数据。日志脱敏应当在写日志的入口做，不要指望下游过滤。

```csharp
/// <summary>
/// Excel操作日志服务
/// </summary>
public class ExcelOperationLogger
{
    private readonly ILogger<ExcelOperationLogger> _logger;
    
    public ExcelOperationLogger(ILogger<ExcelOperationLogger> logger)
    {
        _logger = logger;
    }
    
    public void LogExport(string fileName, int rowCount, TimeSpan duration)
    {
        _logger.LogInformation(
            "Excel导出完成 - 文件: {FileName}, 行数: {RowCount}, 耗时: {Duration}ms",
            fileName, rowCount, duration.TotalMilliseconds);
    }
    
    public void LogImport(string fileName, int rowCount, int errorCount, TimeSpan duration)
    {
        if (errorCount > 0)
        {
            _logger.LogWarning(
                "Excel导入完成(有错误) - 文件: {FileName}, 总行数: {RowCount}, 错误数: {ErrorCount}, 耗时: {Duration}ms",
                fileName, rowCount, errorCount, duration.TotalMilliseconds);
        }
        else
        {
            _logger.LogInformation(
                "Excel导入完成 - 文件: {FileName}, 行数: {RowCount}, 耗时: {Duration}ms",
                fileName, rowCount, duration.TotalMilliseconds);
        }
    }
    
    public void LogError(string operation, Exception ex)
    {
        _logger.LogError(ex, "Excel操作失败 - 操作: {Operation}", operation);
    }
}
```

## 17.4 数据验证

导入是数据质量的第一道关口。用户的 Excel 里可能有空值、超范围数值、格式错误的日期、重复行。如果不在导入时校验，错误数据会流进数据库，等到报表出问题才被发现。

验证的时机选择：导入时校验（快速失败，用户能立刻修改）、写库前校验（统一规则，但反馈慢）、两者都做（成本高）。企业应用通常选第一种，并把错误集中返回给用户。

### 17.4.1 导入数据验证

这个验证器用"规则链"的方式组织：`AddRule` 加自定义规则，`Required` 和 `Range` 是内置的常用规则，`Validate` 遍历所有数据执行全部规则。

**规则的定义形式**是 `Func<T, int, ValidationResult>`，第二个参数是行号。把行号传进规则，是为了让错误信息能定位到具体行——这是验证结果是否有用的关键。

**Required** 用表达式树取属性：`Expression<Func<T, object>>` 让调用方写 `x => x.Name`，方法内部用 `GetPropertyInfo` 解析出 `PropertyInfo`。这个设计比传字符串属性名好：编译器能检查拼写，重命名属性时不会漏改。

`GetPropertyInfo` 里处理了两种情况：直接是成员表达式，和经过装箱转换的成员表达式。后者的原因是 `object` 类型的表达式参数会让值类型属性外面包一层 `Convert` 节点，解析时必须剥掉这层才能拿到 `PropertyInfo`。这是表达式树处理的常见坑。

**Range** 的签名用 `Expression<Func<T, double?>>`，要求属性是 `double?` 类型。这个约束有点强——整数属性、decimal 属性都用不了。更通用的写法是接收 `Func<T, IComparable>` 或者重载多个版本，示例做了简化。

Range 里对空值的处理是"空值跳过校验"，即 `if (value.HasValue && ...)`。这个语义需要明确：空值由 Required 规则负责，Range 只管有值时的范围。两条规则分开，用户能收到"不能为空"和"必须在范围内"两种不同的错误提示。

**Validate** 遍历数据，对每条数据执行全部规则，收集所有失败结果。`rowIndex` 从 1 开始递增，对应 Excel 里的行号习惯（第 1 行是表头，数据从第 2 行开始——所以这里的行号与 Excel 行号差 1，实际使用时要对齐这个语义，否则给用户的提示会指错行）。

**ValidationResult** 是简单的 DTO，带 `IsValid`、`RowIndex`、`ColumnName`、`Message` 四个字段，加两个静态工厂方法。用工厂方法而不是构造函数，调用处更清晰。

这套验证器缺少"跨字段规则"（比如"结束日期必须晚于开始日期"）。`AddRule` 接受整个对象，所以实现跨字段规则是可行的，只是内置方法没有提供。还缺少"规则分组"（新增时校验一部分、更新时校验另一部分），这需要额外的设计。

验证失败后的处理策略要事先定好：全量拒绝（任何错误都不导入）、部分导入（跳过错误行）、还是先返回错误清单让用户修正。示例没有涉及，这是企业应用里必须明确的业务规则。

```csharp
/// <summary>
/// 导入数据验证器
/// </summary>
public class ImportDataValidator<T> where T : class
{
    private readonly List<Func<T, int, ValidationResult>> _rules = new();
    
    public ImportDataValidator<T> AddRule(Func<T, int, ValidationResult> rule)
    {
        _rules.Add(rule);
        return this;
    }
    
    public ImportDataValidator<T> Required(Expression<Func<T, object>> property, string displayName = null)
    {
        var prop = GetPropertyInfo(property);
        displayName ??= prop.Name;
        
        _rules.Add((item, row) => {
            var value = prop.GetValue(item);
            if (value == null || (value is string s && string.IsNullOrWhiteSpace(s)))
            {
                return ValidationResult.Error(row, displayName, "不能为空");
            }
            return ValidationResult.Success();
        });
        
        return this;
    }
    
    public ImportDataValidator<T> Range(Expression<Func<T, double?>> property, 
        double min, double max, string displayName = null)
    {
        var prop = GetPropertyInfo(property);
        displayName ??= prop.Name;
        
        _rules.Add((item, row) => {
            var value = (double?)prop.GetValue(item);
            if (value.HasValue && (value < min || value > max))
            {
                return ValidationResult.Error(row, displayName, $"必须在 {min} 到 {max} 之间");
            }
            return ValidationResult.Success();
        });
        
        return this;
    }
    
    public List<ValidationResult> Validate(IEnumerable<T> items)
    {
        var errors = new List<ValidationResult>();
        int rowIndex = 1;
        
        foreach (var item in items)
        {
            foreach (var rule in _rules)
            {
                var result = rule(item, rowIndex);
                if (!result.IsValid)
                {
                    errors.Add(result);
                }
            }
            rowIndex++;
        }
        
        return errors;
    }
    
    private PropertyInfo GetPropertyInfo<TProperty>(Expression<Func<T, TProperty>> expression)
    {
        if (expression.Body is MemberExpression member)
        {
            return (PropertyInfo)member.Member;
        }
        if (expression.Body is UnaryExpression unary && unary.Operand is MemberExpression m)
        {
            return (PropertyInfo)m.Member;
        }
        throw new ArgumentException("Invalid expression");
    }
}

public class ValidationResult
{
    public bool IsValid { get; set; }
    public int RowIndex { get; set; }
    public string ColumnName { get; set; }
    public string Message { get; set; }
    
    public static ValidationResult Success() => new() { IsValid = true };
    public static ValidationResult Error(int row, string column, string message) 
        => new() { IsValid = false, RowIndex = row, ColumnName = column, Message = message };
}
```

## 17.5 模板引擎

报表生成到最后都会遇到同一个需求：格式固定、数据变化。每周的销售报表、每月的对账单，版式几乎一样，只是数字不同。

实现方式有三种层次：代码里写死格式（改格式要改代码）、用模板文件加占位符（改格式只改模板）、用报表引擎（学习成本高、灵活性最好）。NPOI 适合第二种：准备一个 xlsx 模板，里面用占位符标记数据位置，运行时替换。

### 17.5.1 基于模板的文档生成

`ExcelTemplateEngine` 的主方法是 `GenerateFromTemplate`：打开模板文件、遍历所有工作表、替换占位符、输出。

`ProcessSheet` 逐行逐单元格扫描，只处理 `CellType.String` 类型且包含占位符标记的单元格。只处理字符串单元格是合理的简化：数值、公式、日期的单元格不需要文本替换。代价是"占位符在公式里"这种场景处理不了。

`ReplacePlaceholders` 用正则 `\{\{(\w+)\}\}` 匹配双花括号包裹的标识符，从字典取值替换。几个设计细节：

- 正则只允许 `\w+`（字母、数字、下划线），不支持点号路径。要支持 `user.name` 这种嵌套取值，正则和取值逻辑都要改；
- 字典里没有对应 key 时返回原占位符，不报错。这个策略在开发期友好（能看出哪里漏了数据），在正式环境可能把内部标记泄露给用户；
- 值转换只做 `ToString()`，没有类型处理。数字会被写成字符串，Excel 里不能参与计算。

模板引擎真正的难点不在替换，而在**怎么处理"数据行数不固定"的表格**。报表里常见的"明细行"需要根据数据量插入或删除行，这涉及复制行格式、调整合并单元格、更新公式区域等一系列操作，示例完全没有覆盖。

实践中的折中做法是：模板里预留固定行数（比如 100 行明细），数据不足时删除多余行，超出时报警或分页生成。这种做法不完美，但实现简单、结果可预测。

另一个必须处理的问题是模板文件的版本管理。模板改版后，旧的占位符可能消失、新的出现。代码里用常量集中定义占位符名称，并在启动时做一次模板校验（检查必需占位符是否都存在），能在发布前发现问题，而不是等用户导出时看到一堆没替换的标记。

示例代码注意到的细节：`workbook` 没有 `using`，`FileStream` 用了 `using`。模板文件较大时，工作簿对象持有大量内存，用完应当释放。另外这段示例在网页里被包在 raw 标签里，是为了避免模板花括号被 Jekyll 当成模板语法处理。

{% raw %}
```csharp
/// <summary>
/// Excel模板引擎
/// </summary>
public class ExcelTemplateEngine
{
    /// <summary>
    /// 基于模板生成Excel
    /// </summary>
    public byte[] GenerateFromTemplate(string templatePath, Dictionary<string, object> data)
    {
        using FileStream fs = new FileStream(templatePath, FileMode.Open, FileAccess.Read);
        IWorkbook workbook = new XSSFWorkbook(fs);
        
        foreach (ISheet sheet in workbook)
        {
            ProcessSheet(sheet, data);
        }
        
        using MemoryStream ms = new MemoryStream();
        workbook.Write(ms);
        return ms.ToArray();
    }
    
    private void ProcessSheet(ISheet sheet, Dictionary<string, object> data)
    {
        for (int i = sheet.FirstRowNum; i <= sheet.LastRowNum; i++)
        {
            IRow row = sheet.GetRow(i);
            if (row == null) continue;
            
            for (int j = row.FirstCellNum; j < row.LastCellNum; j++)
            {
                ICell cell = row.GetCell(j);
                if (cell == null || cell.CellType != CellType.String) continue;
                
                string cellValue = cell.StringCellValue;
                if (cellValue.Contains("{{") && cellValue.Contains("}}"))
                {
                    string newValue = ReplacePlaceholders(cellValue, data);
                    cell.SetCellValue(newValue);
                }
            }
        }
    }
    
    private string ReplacePlaceholders(string template, Dictionary<string, object> data)
    {
        var regex = new Regex(@"\{\{(\w+)\}\}");
        return regex.Replace(template, match => {
            string key = match.Groups[1].Value;
            if (data.TryGetValue(key, out object value))
            {
                return value?.ToString() ?? "";
            }
            return match.Value;
        });
    }
}
```

## 17.6 单元测试

文档生成代码的测试比业务代码难写，因为"生成一个文件"很难断言对错。常见误区是把断言写成"文件存在且大小大于 0"——这种测试几乎没有价值。

有效的测试策略是"生成后用 NPOI 读回来断言内容"：把输出当成输入再解析一遍，检查行列数、单元格值、样式属性。这一节的示例就是这个思路。

### 17.6.1 服务测试

两条测试都遵循 Arrange-Act-Assert 结构，这是单元测试的标准写法。

**Export_WithValidData_ReturnsExcelFile** 先断言返回值非空、长度大于零，然后**关键的一步**：把字节数组塞回 `MemoryStream`，用 `XSSFWorkbook` 重新打开，检查工作表行数。

这一步让测试有了实际价值。行数断言 `Assert.AreEqual(3, sheet.LastRowNum + 1)` 验证了"1 行表头 + 2 行数据"的结构。如果表头逻辑改成不输出，或者数据行少写一行，测试会失败。

`LastRowNum` 是零基索引（最后一行的索引），所以行数要 `+1`。这个细节写错会让断言差一，是测试代码里常见的笔误。

**Import_WithValidFile_ReturnsData** 做的是往返测试：先导出，再导入，断言数据一致。往返测试能同时验证导出和导入两个方向，发现问题时也容易定位是哪个方向出错。

它的断言 `Assert.AreEqual(1, result.Count)` 和 `Assert.AreEqual("Test", result[0].Name)` 只验证了一行一条字段，覆盖偏薄。更完整的往返测试应当比对全部字段、包含日期与数值类型、包含空值。

**测试数据的构造**用内联的 `TestModel` 私有类，三个属性覆盖了 int、string、double。这是好习惯：测试数据就在测试文件里，不依赖外部数据库或固定文件。

实际项目中还需要补几类测试：

- **边界数据**：空集合、单行、超长字符串、Unicode 字符、负数；
- **异常路径**：传入无效流、超大文件、错误格式；
- **样式断言**：不止检查值，还要检查表头是否加粗、日期列是否有格式。样式断言需要读回单元格样式，比读值麻烦，但样式恰恰是最容易在重构中丢失的部分。

测试文件的清理容易被忽略。测试生成的临时文件应当在 `finally` 或 `Dispose` 里删除，否则 CI 的临时目录会越积越多，偶尔还会因为文件被占用导致后续测试失败。

```csharp
[TestClass]
public class ExcelServiceTests
{
    private IExcelService _excelService;
    
    [TestInitialize]
    public void Setup()
    {
        _excelService = new ExcelService();
    }
    
    [TestMethod]
    public void Export_WithValidData_ReturnsExcelFile()
    {
        // Arrange
        var data = new List<TestModel>
        {
            new() { Id = 1, Name = "Test1", Value = 100 },
            new() { Id = 2, Name = "Test2", Value = 200 }
        };
        
        // Act
        byte[] result = _excelService.Export(data);
        
        // Assert
        Assert.IsNotNull(result);
        Assert.IsTrue(result.Length > 0);
        
        // 验证内容
        using var ms = new MemoryStream(result);
        var workbook = new XSSFWorkbook(ms);
        var sheet = workbook.GetSheetAt(0);
        
        Assert.AreEqual(3, sheet.LastRowNum + 1);  // 1 header + 2 data rows
    }
    
    [TestMethod]
    public void Import_WithValidFile_ReturnsData()
    {
        // Arrange
        var exportData = new List<TestModel>
        {
            new() { Id = 1, Name = "Test", Value = 100 }
        };
        byte[] fileBytes = _excelService.Export(exportData);
        
        // Act
        using var ms = new MemoryStream(fileBytes);
        var result = _excelService.Import<TestModel>(ms);
        
        // Assert
        Assert.AreEqual(1, result.Count);
        Assert.AreEqual("Test", result[0].Name);
    }
    
    private class TestModel
    {
        public int Id { get; set; }
        public string Name { get; set; }
        public double Value { get; set; }
    }
}
```

## 17.7 本章小结

本章把 NPOI 的使用从"能生成文件"提升到"能在生产环境里稳定运行"。六个主题可以归成三组。

**结构组**（架构、依赖注入）：把文档读写收敛到服务层，用接口隔离、用容器管理生命周期。目标是"改一处、影响可控"。

**健壮组**（异常、日志、验证）：异常翻译成业务语义并携带上下文，日志按级别记录关键字段，导入数据在入库前校验并返回可定位的错误。目标是"出问题时能查到、能修"。

**质量组**（模板引擎、单元测试）：模板把格式与代码分离，测试用"生成后读回断言"的方式验证内容与结构。目标是"改动能被验证"。

这六项没有一项是 NPOI 特有的，它们都是把任意一个库用进生产系统时需要做的事。区别只是 NPOI 的错误模式（文件格式、内存、流句柄）比较特殊，所以异常与测试这两块要格外认真。

本章介绍了NPOI在企业级应用中的最佳实践。通过本章学习，你应该掌握：

- 服务层架构设计和依赖注入
- 自定义异常和异常处理
- 日志记录和操作追踪
- 数据验证机制
- 模板引擎的实现
- 单元测试方法

这些最佳实践可以帮助你构建健壮、可维护的企业级应用。

最后给一个落地顺序的建议：先做服务层封装（这是其余五项的前提），再加异常翻译与日志（成本低、收益立现），然后补导入校验，最后做模板与测试。一次全做容易拖成半成品，按这个顺序推进，每一步都能独立上线。
