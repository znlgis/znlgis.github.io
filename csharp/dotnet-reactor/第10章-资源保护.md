# 第10章：资源保护

## 10.1 资源保护概述

资源保护的对象是编译进程序集清单里的那一部分数据。C# 项目把图片、配置文件、脚本等以 EmbeddedResource 形式打包，运行时通过 `Assembly.GetManifestResourceStream` 读取。这些字节和 IL 代码一起躺在 DLL 或 EXE 里，用 `ildasm`、ILSpy 或者十六进制编辑器就能直接看到明文，改一个字节再用十六进制编辑器存回去，程序照样跑。对商业化交付的软件，这等于把配置结构和服务端地址表交给对方。

.NET Reactor 在这条链路上插入一层：编译完成后改写资源表，把原始字节换成压缩或加密后的数据，并在程序集里注入对应的解包代码。调用方仍然按原来的资源名读取，中间的变换由注入代码完成。理解这个前提后，选择保护级别就有依据了——资源保护改变的是资源的存储形态，不改变资源的访问接口。

需要说明一点：资源保护只针对**嵌入资源**。以文件形式随安装包分发的内容（比如安装目录下的 `appsettings.json`）不在这个范围内，它们要靠安装器加密或者运行时自行加密。

应用程序的嵌入资源（图片、配置文件、数据文件等）也可能包含敏感信息，需要适当保护。

### 10.1.1 需要保护的资源类型

判断一个资源是否需要保护，看两条：它泄露后是否直接造成损失；它是否必须保持端上可读。两条都成立才值得启用加密，只有第一条成立的，用混淆或按需下发更合适。

下面这份清单把常见资源分了五类，每一类的风险点不同。配置文件泄露的是内部地址、密钥前缀和业务参数；数据文件（`*.dat`、`*.bin`、规则库）泄露的是业务资产本身；许可证文件与密钥一旦可读，许可证体系形同虚设；图片类资源主要是品牌与水印被替换；帮助文档泄露通常是可接受的，但它会暴露产品功能边界。

```
1. 配置文件
   - *.config
   - *.xml
   - *.json

2. 数据文件
   - *.dat
   - *.bin
   - 数据库文件

3. 许可证文件
   - *.license
   - *.key

4. 图片资源
   - 水印图片
   - Logo
   - 品牌资源

5. 文档资源
   - 帮助文档
   - 说明文件
```

## 10.2 配置资源保护

配置项分三部分：开关、保护方法、压缩级别。开关打开后，Reactor 会按资源清单逐个处理，没有单独指定的资源使用全局方法。

保护方法的三选项各有代价：

| 选项 | 实际行为 | 适用 |
|------|----------|------|
| Compress Only | 只做无损压缩，运行时不需密钥 | 体积大、不敏感的文本类资源 |
| Encrypt Only | 只加密，输出体积与原体积接近 | 体积小但对保密要求高的配置 |
| Encrypt and Compress | 先压缩再加密 | 默认，兼顾体积与保密 |

压缩级别对应压缩算法的搜索深度。Fast 生成最快、压缩率最低；Optimal 是默认平衡点；Maximum 会明显拉长保护阶段的耗时，对已经压缩过的格式（jpg、png、zip）收益接近于零。对 PNJ 这类本身已压缩的数据，选 Optimal 即可，把压缩级别拉满几乎不会减小输出。

**基本配置：**
```
Settings → Protection → Resource Protection

☑ Enable Resource Protection

Protection Method:
○ Compress Only
○ Encrypt Only
● Encrypt and Compress

Compression Level:
○ Fast
● Optimal
○ Maximum
```

## 10.3 选择性保护

全量保护经常引发问题：`*.ico` 被加密后，Windows 资源管理器读不出图标；`app.manifest` 被改写后，UAC 清单失效；某些第三方库按文件名扫描资源目录，加密后的名字对不上就报错。选择性保护就是解决这类冲突的入口。

规则按 Include 与 Exclude 两段组织，先匹配 Include 决定处理范围，再由 Exclude 剔除例外。写法上有三种粒度：

- `<Pattern>` 按资源名通配符匹配，适合批量处理同类文件；
- `<Resource name="...">` 精确匹配单个资源；
- `<Folder path="...">` 匹配某个逻辑文件夹下的全部资源。

判断顺序建议记住一条原则：**被外部程序直接读取的资源、被清单或系统解析的资源，一律排除**。程序内部自己 `GetManifestResourceStream` 读取的资源才适合加密。

**使用模式匹配：**
```xml
<ResourceProtection enabled="true">
  <Include>
    <!-- 保护所有配置文件 -->
    <Pattern>*.config</Pattern>
    <Pattern>*.xml</Pattern>
    
    <!-- 保护特定资源 -->
    <Resource name="license.dat" />
    <Resource name="watermark.png" />
    
    <!-- 保护整个资源文件夹 -->
    <Folder path="Configs/" />
  </Include>
  
  <Exclude>
    <!-- 排除需要外部访问的资源 -->
    <Pattern>*.ico</Pattern>
    <Resource name="app.manifest" />
  </Exclude>
</ResourceProtection>
```

## 10.4 访问受保护资源

这一节的关键结论是：资源保护对业务代码透明。Reactor 在编译产物里替换的是资源流的来源，`GetManifestResourceStream` 这个 API 本身没变，所以原来的写法一行都不用动。

示例代码里 `GetManifestResourceStream("MyApp.config.xml")` 的参数是资源全名，格式是 `默认命名空间.文件夹.文件名`。命名空间取项目属性里的 Default Namespace，文件夹层级用英文句点连接，文件名保留扩展名。资源名拼错时该方法返回 `null`，而后续 `new StreamReader(null)` 会抛 `ArgumentNullException`，堆栈指向的是读取代码而不是配置错误，排查时容易误判。写一个反射遍历 `GetManifestResourceNames()` 的小工具，把实际名字打印出来，比猜更可靠。

**代码完全透明：**
```csharp
// 原始代码
var assembly = Assembly.GetExecutingAssembly();
using (Stream stream = assembly.GetManifestResourceStream("MyApp.config.xml"))
using (StreamReader reader = new StreamReader(stream))
{
    string content = reader.ReadToEnd();
    // 处理配置
}

// 保护后代码无需修改
// .NET Reactor 自动处理解密
```

## 10.5 嵌入和合并

嵌入依赖是另一个层面的资源保护：把 `Newtonsoft.Json.dll`、自研类库等附属程序集整体塞进主程序集，运行时从内存直接加载。带来的好处有两个，一是减少随包分发的文件数，降低被单独反编译和替换的概率；二是部署面变小，安装目录里少几个可疑的 DLL。

代价也要算清楚。程序集不再是独立单元，主程序集体积会明显增大；程序集加载失败时错误信息更难定位；某些依赖需要按文件名探测自身路径（例如读取同目录的配置文件），嵌入后会找不到文件。

下面两小节分别讲配置入口和运行时解析机制。需要强调，嵌入依赖只处理托管程序集，原生 DLL（比如 SQLite 的 `e_sqlite3.dll`）必须排除在嵌入清单之外，否则会得到 `BadImageFormatException`。

### 10.5.1 嵌入依赖DLL

配置面板里列出候选依赖，勾选即加入嵌入清单。三个选项的作用：

- **Compress Embedded DLLs**：存储时压缩，加载时在内存解压。体积收益通常有 30% 到 60%，代价是首次加载多一次解压。
- **Encrypt Embedded DLLs**：加密存储，防止别人用十六进制编辑器从主程序集里把 DLL 抠出来直接反编译。
- **Load on Demand**：延迟到首次使用该程序集时才解密加载，缩短启动阶段的工作量。

勾选依赖时容易忽略的一点是版本。同一目录里可能存在 `Newtonsoft.Json.dll` 的多个版本，Reactor 不会替你解决绑定重定向；如果主程序集引用 13.0.0 而分辨率加载的是 12.0.0，运行时会抛 `FileLoadException`，提示版本不匹配。嵌入前先确认 `app.config` 里的 `bindingRedirect` 只指向一个版本。

```
Settings → Resource Protection → Embed Dependencies

☑ Embed Dependent Assemblies

Dependencies to Embed:
☑ Newtonsoft.Json.dll
☑ System.Data.SQLite.dll
☑ Custom.Library.dll

Options:
☑ Compress Embedded DLLs
☑ Encrypt Embedded DLLs
☑ Load on Demand (按需加载)
```

### 10.5.2 自动解析依赖

嵌入之后，.NET 默认的探测顺序（同目录、GAC、私有探测路径）找不到那个 DLL，所以必须挂 `AssemblyResolve`，在需要时把字节还给运行时。

示例里是一个静态构造函数挂事件。实际项目更稳妥的写法要点有三条：事件在 `AppDomain` 上只挂一次，重复挂会多次触发；回调里要判断 `args.Name` 与嵌入资源名的对应关系，避免对每一个缺失程序集都尝试解密；拿到 `Assembly.Load(byte[])` 的返回值后返回，返回 `null` 表示放弃解析。

`args.Name` 是程序集强名称（包含版本、公钥标记），不是一个简单文件名。所以回调里通常先 `new AssemblyName(args.Name)` 取 `Name` 属性，再拼资源名。拼接时的常见错误是把 `.dll` 后缀重复加了两次，或者把强名称直接当资源 key 用，两种情况都会返回 null 并继续抛 `FileNotFoundException`。

```csharp
// .NET Reactor 自动注入
static Constructor()
{
    AppDomain.CurrentDomain.AssemblyResolve += 
        (sender, args) =>
    {
        // 自动从资源加载嵌入的 DLL
        return LoadEmbeddedAssembly(args.Name);
    };
}
```

## 10.6 卫星程序集

卫星程序集是 .NET 的本地化资源载体：每种语言一个子目录（`zh-CN`、`ja-JP`），里面放同名的 `<程序集>.resources.dll`，只有资源没有代码。它们同样是可以被反编译的对象，而且本地化字符串往往暴露界面文案与业务流程，对企业软件来说属于需要处理的信息。

Reactor 的卫星程序集处理有两条路：整体嵌入主程序集，或者保持独立文件但加密。嵌入的好处是分发干净、没有语言角标目录，缺点是主程序集体积扩大、所有语言一次性随包；保留独立文件的好处是按语言分发，缺点是文件仍在，需要额外做完整性保护。

### 10.6.1 保护本地化资源

配置项的 `Cultures` 列表决定处理哪些语言目录。没在列表里的语言目录会原样保留在输出中——这也是一个常见疏漏：新增了一种语言但忘记在清单里勾选，结果该语言的资源以明文留在发布目录里。

`Embed into Main Assembly` 与 `Keep Separate` 二选一时，可以按语言的文件尺寸判断：多语言文案文件通常只有几十 KB，嵌入对主程序集体积影响有限；但如果涉及多套图片资源，独立加密更合适，避免主程序集膨胀到影响加载时间。

```
Satellite Assemblies:
☑ Protect Satellite Assemblies

Cultures:
☑ zh-CN
☑ ja-JP
☑ de-DE
☑ fr-FR

Options:
☑ Embed into Main Assembly
○ Keep Separate (加密)
```

### 10.6.2 动态加载

`ResourceManager` 是按 `culture` 参数找卫星程序集的标准入口。构造时传入的 baseName 是资源基名（`MyApp.Resources.Strings`），程序集参数传主程序集；调用 `GetString(name, culture)` 时，运行时会先找对应的卫星程序集，找不到则回退到中性资源（neutral culture）。

回退顺序是中性资源优先还是父区域性优先，取决于 `ResourceManager` 的构造方式。使用默认的 `UltimateResourceFallbackLocation.MainAssembly` 时，`zh-CN` 缺失会回退到 `zh-Hans`、再无则回退到主程序集的中性资源。嵌入式卫星程序集在加载后仍然遵循这一回退链，因为嵌入改变的是物理位置，不改变资源查找逻辑。

调试时如果界面显示的是英文而系统语言是中文，先查 `CultureInfo.CurrentUICulture` 的实际值，再查卫星程序集名字是否匹配，不要急着怀疑保护工具。

```csharp
// 访问本地化资源
ResourceManager rm = new ResourceManager(
    "MyApp.Resources.Strings", 
    Assembly.GetExecutingAssembly());

string welcome = rm.GetString("Welcome", 
    CultureInfo.CurrentUICulture);
```

## 10.7 自定义资源加载器

Reactor 的透明加载能覆盖绝大多数 `GetManifestResourceStream` 场景。但有一类需求它处理不了：读取之后还要做业务层的二次变换，比如加载时解密业务密钥、按环境替换占位符、给资源做校验后返回。这时把读取逻辑收缩到一个自有加载器里，比散落在各处更可控。

这一节的两个示例分别解决"如何集中读取"和"如何避免重复读取"。前者是接口层的封装，后者是缓存层的实现，两者可以叠加使用。

### 10.7.1 实现自定义加载

`LoadResource` 的职责很清楚：按名字取流，交给 `ProcessStream` 做后续处理。返回 `Stream` 而不是 `byte[]` 的设计，是让调用方可以选择读取方式；`LoadBinaryResource` 则封装了常见的"一次读全"场景，内部用 `MemoryStream` 做中转。

要注意 `Stream` 的生命周期：`GetManifestResourceStream` 返回的流需要调用方负责释放，`using` 写在调用方还是写在加载器里，决定了这个 API 的所有权语义。示例中 `LoadBinaryResource` 用 `using` 包住了流，对字节数组版本是安全的；而 `LoadResource` 把流直接交出去，调用方必须自己释放，否则在高频调用时会累积句柄。

`ProcessStream` 在示例里没有给出实现，实际项目中可以在这里接入解密、校验、字符集转换等逻辑。

```csharp
public class CustomResourceLoader
{
    public static Stream LoadResource(string name)
    {
        // 从受保护的资源加载
        var assembly = Assembly.GetExecutingAssembly();
        Stream stream = assembly.GetManifestResourceStream(name);
        
        // 额外的处理（如果需要）
        return ProcessStream(stream);
    }
    
    public static byte[] LoadBinaryResource(string name)
    {
        using (Stream stream = LoadResource(name))
        using (MemoryStream ms = new MemoryStream())
        {
            stream.CopyTo(ms);
            return ms.ToArray();
        }
    }
}
```

### 10.7.2 缓存机制

示例的 `ResourceCache` 用静态 `Dictionary<string, byte[]>` 保存结果，第一次读取后缓存字节数组，后续直接命中。这个写法在单线程或一次性初始化场景下够用，但放进服务端或 UI 线程就会有并发问题。

`Dictionary` 不是线程安全的，两个线程同时 `ContainsKey` 为 false 时会各自加载，然后同时写入，最坏情况是数据损坏或抛 `InvalidOperationException`。生产代码应当换成 `ConcurrentDictionary<string, Lazy<byte[]>>`，用 `GetOrAdd` 保证同一 key 只加载一次，用 `Lazy` 避免重复解密。

缓存还有容量问题。资源如果按需加载且数量可观（比如按业务模块拆分的规则文件），无上限缓存会持续推高内存。给缓存加一个大小阈值或 LRU 淘汰，内存曲线才可控。

```csharp
public class ResourceCache
{
    private static Dictionary<string, byte[]> _cache = 
        new Dictionary<string, byte[]>();
    
    public static byte[] GetResource(string name)
    {
        if (!_cache.ContainsKey(name))
        {
            _cache[name] = CustomResourceLoader.LoadBinaryResource(name);
        }
        return _cache[name];
    }
}
```

## 10.8 性能优化

资源保护会在两个环节引入开销：保护阶段（构建机上多花的时间）和运行阶段（首次读取资源时的解压解密）。运行阶段的开销更值得关注，因为它落在用户感知的启动过程中。

优化的思路是"把工作挪到不用等的地方"：延迟加载把解密从启动时挪到首次使用；缓存把重复解密变成一次；压缩级别则在构建阶段就决定了运行阶段解压的工作量。

### 10.8.1 延迟加载

三种策略的差别在首屏体验：

- **Lazy Loading**：启动阶段不解密，用到哪个取哪个。启动最快，但首次进入某功能可能有一次可感知的卡顿。
- **Preload All**：启动阶段把所有资源解压到内存。启动最慢，但后续操作没有抖动。
- **Preload Critical**：只预加载首屏必需的资源，其余按需。大多数桌面软件的最优解。

`Cache Size` 配的是缓存池上限，`LRU` 表示超出时淘汰最久未使用的条目。上限设得太小会导致同一资源反复解密，反而比不缓存更慢；设得太大则挤占其他内存。以桌面软件为例，几十 MB 量级通常是安全区间。

```
Resource Loading Strategy:
● Lazy Loading (按需加载)
○ Preload All (预加载全部)
○ Preload Critical (预加载关键资源)

Cache Size:
Limit: [50] MB
Policy: LRU
```

### 10.8.2 压缩级别选择

表格里的星号是相对比较，不是绝对指标。三档的实际差别如下表：

| 级别 | 典型压缩率 | 保护阶段耗时 | 运行时解压耗时 | 内存峰值 |
|------|-----------|-------------|---------------|---------|
| Fast | 约 60% | 最低 | 最低 | 最低 |
| Optimal | 约 75% | 中等 | 中等 | 中等 |
| Maximum | 约 85% | 最高 | 最高 | 最高 |

选择依据是资源的使用频率。启动时就要加载的资源选 Fast，压缩率差一点但解压快；只在特定功能里用到的文档类资源可以选 Maximum，慢一点不影响主流程。表格里的压缩率数字针对文本类资源，对已压缩的图片格式（PNG、JPG）三档差别都很小。

```
┌──────────────┬──────────┬──────────┬──────────┐
│  压缩级别    │ 压缩率   │  速度    │  内存    │
├──────────────┼──────────┼──────────┼──────────┤
│ Fast         │   60%    │  ★★★   │  ★★★   │
│ Optimal      │   75%    │  ★★☆   │  ★★☆   │
│ Maximum      │   85%    │  ★☆☆   │  ★☆☆   │
└──────────────┴──────────┴──────────┴──────────┘
```

## 10.9 实战案例

前八节分别说明了机制，这一节把配置拼成可用的方案。案例一处理配置文件，案例二处理许可证密钥。两者都强调一点：加密只是门槛，密钥最终还是要和程序一起分发，所以不要把真正的商业机密放在端上加密，端上加密的目标是提高静态分析的成本。

### 10.9.1 保护配置文件

这份配置只处理两个文件：`appsettings.json` 与 `database.config`，每个都显式声明 `encrypt="true" compress="true"`。逐行看：

- `enabled="true"` 是总开关，缺省时整段配置不生效；
- 每个 `Resource` 上的 `encrypt` 与 `compress` 属性覆盖全局方法，允许对单个文件做例外处理；
- 没有写 `Include` 之外的内容，未列出的资源保持原样。

使用这类配置时要注意，如果 `appsettings.json` 是通过 `ConfigurationBuilder` 从文件路径读取的（`AddJsonFile`），那它根本不是嵌入资源，这段配置对它不起作用。判断标准只有一个：它是否出现在程序集清单的资源表里。

```xml
<!-- 项目配置 -->
<ResourceProtection enabled="true">
  <Include>
    <Resource name="appsettings.json" encrypt="true" compress="true" />
    <Resource name="database.config" encrypt="true" compress="true" />
  </Include>
</ResourceProtection>
```

### 10.9.2 保护许可证密钥

这段代码演示的是"资源里的密钥拿到后还要解一层"的模式：资源本身由 Reactor 保护，业务代码再做一次解密。双层结构的意义在于，即使有人绕过了 Reactor 的保护，拿到的也是业务层密文。

`LoadEncryptedKey` 返回 `byte[]` 而不是字符串，是因为密钥在内存中作为字符串驻留时不能主动擦除，作为字节数组至少可以在使用后清零。`GetLicenseKey` 里 `Decrypt` 的实现没有给出，实际项目中通常是对称解密（AES），密钥由签名校验或硬件标识派生。

这段代码的短板也直接：`Decrypt` 的逻辑必然在程序集里，反编译者顺着调用点就能找到解密入口。所以这种方案只能提高门槛，不能阻止有心人。真正的许可证校验应当把关键判断放到服务端，端上只保留验证结果的短时凭据。

```csharp
public class LicenseKeyManager
{
    private static byte[] LoadEncryptedKey()
    {
        // 从受保护的资源加载
        return CustomResourceLoader.LoadBinaryResource("license.key");
    }
    
    public static string GetLicenseKey()
    {
        byte[] encrypted = LoadEncryptedKey();
        byte[] decrypted = Decrypt(encrypted);
        return Encoding.UTF8.GetString(decrypted);
    }
}
```

## 10.10 本章小结

本章介绍了资源保护技术，包括：
- 各种资源类型的保护
- 选择性保护策略
- 嵌入和合并依赖
- 性能优化方法

通过合理保护资源，可以进一步增强应用程序的整体安全性。

理解资源保护的边界同样重要。它能阻止"打开 DLL 就看见配置"这类低成本窃取，挡不住有耐心的逆向分析。把资源保护作为整个保护体系的一层，和代码混淆、许可证校验、完整性检查配合使用，才能形成有层次的防护。

最后提醒三个排查习惯：资源加载失败时先打印 `GetManifestResourceNames()` 的完整列表；保护前后各跑一次功能测试，把差异定位到具体资源；变更保护配置后检查发布目录，确认没有意料之外的语言目录或附属 DLL 被编译进主程序集。
