# 第13章：高级配置选项

## 13.1 全局配置

全局配置的作用是给所有新建项目提供默认值。它影响的不是某一次保护的效果，而是团队内每次新建配置的起点：默认保护级别、默认输出目录、自动保存间隔。

有一个容易混淆的边界：全局配置只在**新建**项目时被复制进项目。已经存在的 `.nrproj` 不会因为改了全局设置而变化。这意味着"我在工具里把默认级别调成 Maximum 了，为什么旧项目还是 Standard"这类问题，答案永远在项目文件里，不在全局设置里。

### 13.1.1 默认设置

三个默认值的含义与影响：

- **Default Protection Level**：Standard、Enhanced、Maximum 三档。它决定新建项目时勾选哪些保护项的组合，是一个打包好的预设，不是单一开关。选定之后仍然可以逐项调整。
- **Default Output Path**：默认输出目录的相对路径。相对路径按项目文件所在目录解析，这是实际使用时要确认的一点，别按当前工作目录去推断。
- **Auto Save Interval**：界面自动保存配置的间隔，单位分钟。它影响的是配置持久化，与保护本身的耗时无关。设得太短在频繁调整参数时会有多次磁盘写操作，设得太长则意外退出会丢配置。

选哪一档没有统一答案。Standard 适合内部工具和更新频繁的产品；Enhanced 在混淆之外增加了更多保护项；Maximum 把能开的都打开，代价是保护耗时与运行开销都上升，且更容易触发兼容性问题的组合。新项目建议从 Standard 起步，逐项加，每加一项做一轮功能测试。

```
Tools → Options → Defaults

Default Protection Level:
● Standard
○ Enhanced
○ Maximum

Default Output Path:
[bin\Protected\]

Auto Save Interval:
[5] minutes
```

### 13.2 性能调优

性能调优要区分两个阶段：保护阶段的耗时（构建机上，工程师感受）和运行阶段的耗时（用户机器上，用户感受）。这两者的优化手段不冲突，但关注点不同，配置时不要混为一谈。

保护阶段的瓶颈通常在磁盘 IO 和加密运算；运行阶段的瓶颈在方法首次调用时的解密和 JIT。多线程和内存设置主要影响前者，混淆级别与加密策略主要影响后者。

### 13.2.1 多线程处理

这段 XML 有两个数字：`MaxThreads` 与 `ThreadPoolSize`。前者限制工具并行处理程序集或模块的线程数，后者是线程池的容量上限。

配置时参考运行构建机的核数。`MaxThreads` 超过物理核数不会有收益，反而因为上下文切换让总耗时上升。`ThreadPoolSize` 一般留出余量，避免工具线程与其他构建任务（编译器、打包、上传）争抢。

多线程环境下有一个实际问题：多个线程同时写同一个临时目录会冲突。工具通常会按任务分配临时子目录，但如果自定义了临时文件位置且多个实例共用同一路径，冲突概率立刻上升。构建机上同时跑多个保护任务时，给每个实例独立临时目录是最省事的做法。

另一个观察点：开启多线程后，保护阶段的日志顺序会交错，单文件日志的时序不再是执行顺序。排查问题时应按文件分日志，而不是按时间顺序读一份大日志。

```xml
<Performance>
  <MultiThreading enabled="true">
    <MaxThreads>4</MaxThreads>
    <ThreadPoolSize>8</ThreadPoolSize>
  </MultiThreading>
</Performance>
```

### 13.2.2 内存管理

三项设置各自的边界：

- **Max Memory Usage**：给工具设的上限。程序集越大、压缩级别越高，峰值内存越高。设得太低会导致工具内部频繁回收甚至失败，设得太高会影响同机的其他进程。
- **Temp File Location**：中间文件目录。必须指向空间充足、可写、路径不含特殊字符的位置。
- **Clear Temp Files**：退出时清理。打开它可以避免临时文件堆积，代价是无法在失败后检查残留的中间产物。调试保护失败时可以先关掉它，事后手动清理。

内存问题最典型的表现是处理大程序集时中途失败，日志里出现与内存相关的异常，退出码是一般错误。这时先看程序集大小，再试着关闭嵌入依赖减少同时驻留的数据量，最后才考虑调高上限。单纯调高上限而不减负载，往往只是把进程崩溃从工具变成了整机内存耗尽。

```
Memory Settings:
Max Memory Usage: [4096] MB
Temp File Location: [C:\Temp\Reactor\]
Clear Temp Files: ☑ On Exit
```

## 13.3 高级混淆选项

基础混淆改的是名字，高级选项改的是结构与符号层面。改得越多，逆向阅读成本越高，同时兼容性风险也越大。这一节的两项配置都属于默认值通常够用、只有明确需要时才调整的类别。

### 13.3.1 自定义命名方案

命名方案决定混淆后的符号长什么样。四个字段：

- **Pattern**：命名模板。示例的写法是下划线加 0x 前缀、后接 8 位十六进制的递增计数，其中 X8 表示 8 位大写十六进制。
- **Charset**：可用字符集。只写小写字母时，生成的符号全部由小写字母与数字组成。
- **MinLength / MaxLength**：符号长度范围。太短的符号在反编译工具里看起来更密，但也更容易和框架里的约定名冲突。

自定义命名与序列化天然冲突。JSON 序列化默认用属性名，改了名序列化结果就变；XML 序列化、数据契约、反射按名称查找的地方都有同样问题。所以命名方案调整后必须重跑序列化相关的测试。

命名规则里的花括号会被 Jekyll 之类的模板引擎误解析，写进文档时要用反引号包成行内代码。这是文档层面的坑，与工具行为无关。

```xml
<Obfuscation>
  <NamingScheme>
    <Pattern>_0x{counter:X8}</Pattern>
    <Charset>abcdefghijklmnopqrstuvwxyz</Charset>
    <MinLength>1</MinLength>
    <MaxLength>64</MaxLength>
  </NamingScheme>
</Obfuscation>
```

### 13.3.2 控制流复杂度

控制流混淆把原本清晰的 if/else、循环拆成跳转和状态机，让反编译出的代码结构难以还原。四个参数：

- **Complexity Level（1-10）**：整体强度。等级越高，插入的分支和跳转越多。超过 7 之后收益递减，而排错难度陡增。
- **Max Basic Blocks**：单个方法拆分出的基本块上限。设得太大会让个别方法急剧膨胀。
- **Loop Unrolling**：循环展开。把循环体复制多份以减少迭代次数，对执行速度可能有微小影响，对体积是净增加。
- **Branch Injection**：分支注入。插入永远走不到或恒真的分支，干扰阅读。

控制流混淆对性能的影响很实在：每个方法多出的跳转都会影响 JIT 的优化空间，热路径上的方法尤其明显。经验做法是把复杂度和这个方法在不在热路径上挂钩，热点方法降到低等级或干脆排除。

另一类风险是异常处理与调试。混淆后堆栈行号可能与源码对不上（除非保留行号），异常信息里的方法名也变成乱码。排查崩溃时先用符号映射还原，再去读代码。

```
Control Flow Obfuscation:
Complexity Level: [7] (1-10)
Max Basic Blocks: [50]
Loop Unrolling: ☑
Branch Injection: ☑
```

## 13.4 加密算法定制

加密配置决定字符串和方法体以什么方式加密。通常不需要改默认值，因为默认值已经取了安全性与性能的平衡。只有两类场景值得调整：合规要求指定算法，或者有明确的性能瓶颈需要换更轻的算法。

选择算法时有一件事不能妥协：**同一把密钥不能按固定逻辑从客户端推导出来**。无论选 AES 还是别的算法，密钥最终要从程序集里的某处派生，静态分析者顺着密钥派生路径就能找到它。算法选择影响的是破解所需的工作量，不是能不能被破解。

### 13.4.1 字符串加密

四个字段对应一个标准的密钥派生流程：

- **Algorithm**：加密算法。示例是 AES256，即 256 位密钥的 AES。
- **KeyDerivation**：密钥派生函数。示例用 PBKDF2，从一个基础秘密派生出实际密钥。
- **Iterations**：PBKDF2 的迭代次数。示例 10000 是十几年前的标准值，现代建议在设备性能允许的前提下提高。迭代次数直接影响每次派生密钥的耗时，而密钥派生发生在运行时，所以这个值同时是安全的旋钮和启动性能的旋钮。
- **SaltSize**：盐长度，单位字节。示例 32 字节。盐的作用是让相同的基础秘密派生出不同的密钥。

字符串加密覆盖的范围是字面量字符串。它的运行时开销集中在首次访问该字符串时，解密一次之后通常有缓存。如果一个方法在内层循环里反复访问大量加密字符串，且每次访问都走解密，性能会有可测的下降，这时应当把字符串在方法入口解一次，存到局部变量。

排查字符串相关的故障时，常见现象是界面出现乱码或截断。先确认原文是不是 Unicode 转义或拼接字符串，再确认是否开启了字符串加密；拼接字符串在编译期不会合并成一个字面量，加密器只处理能识别的字面量。

```xml
<StringEncryption>
  <Algorithm>AES256</Algorithm>
  <KeyDerivation>PBKDF2</KeyDerivation>
  <Iterations>10000</Iterations>
  <SaltSize>32</SaltSize>
</StringEncryption>
```

### 13.4.2 方法加密

方法加密与 NecroBit 属于同一类手段：把方法体从 IL 里拿出去，运行时再还原，区别在实现方式与强度。

密钥轮换是这段配置里最需要解释的一项：间隔为 100 表示每处理 100 个方法轮换一次密钥。轮换的意义是减少单个密钥暴露的收益——破解一个密钥只能解出一批方法，而不是全部。

代价也要看清。密钥轮换意味着运行时需要保存多把密钥以及方法与密钥的对应关系，程序集体积和初始化开销都会上升；轮换间隔太小会导致保护阶段生成的密钥表急剧变大，体积上的收益被抵消。

方法加密必须配合排除规则使用。反射调用、序列化回调、P/Invoke 入口、需要被框架按名字找到的方法，都不适合加密。判断标准很简单：这个方法的名字是否会被外部代码以字符串形式查找。会，就排除。

```xml
<MethodEncryption>
  <Algorithm>Custom</Algorithm>
  <KeyRotation enabled="true">
    <Interval>100</Interval>
  </KeyRotation>
</MethodEncryption>
```

## 13.5 代码注入

代码注入让保护阶段向程序集里写入自定义代码，常用于把初始化逻辑（许可证校验、环境检查、安全检测）放进模块构造函数或入口点。它的价值在于这些逻辑由工具注入而不是写在源码里，注入后与程序结构交织，删除或绕过都要付代价。

风险同样明显。注入的代码如果抛异常，程序会在极早期崩溃，症状是什么都没发生就退出了，很难定位。所以注入逻辑必须自己捕获所有异常，并且要有明确的失败策略：静默降级、提示后退出，还是记录日志后继续。

### 13.5.1 自定义代码注入

示例用反射命名空间里的 Obfuscation 特性标注一个方法，声明它作为注入目标。这个特性本身是 .NET 生态里表达"对某成员做特殊处理"的通用方式，不同工具识别不同的 Feature 字符串。示例中的标记是给工具的指令，具体语法以工具文档为准；能确定的是：被标注的方法由工具在保护阶段识别，并按配置安排在指定时机调用。

提示：示例代码块里的 [Obfuscation(Feature = "inject:OnStart")] 只是一种示意写法，实际是否被识别取决于工具版本与配置，不要把它当成通用 API。

这个方法内部调用三个检查，每一个都可能失败。实际写法应当把每个检查的异常隔离，用 try 与 catch 分别包住，否则第一个检查抛异常，后面的许可证验证不会执行，故障表现会指向错误的方向。

注入方法应当保持无参、静态、幂等。它可能在进程启动、模块加载或其他早期时机被调用，此时依赖注入容器还没建好，任何依赖构造函数注入的对象都不可用。

```csharp
// 在保护时注入自定义代码
[Obfuscation(Feature = "inject:OnStart")]
public static void CustomInitialization()
{
    // 自定义初始化代码
    SecurityCheck();
    LicenseValidation();
    EnvironmentCheck();
}
```

### 13.5.2 钩子点

五个可选钩子点的作用范围不同：

| 钩子点 | 执行时机 | 适用 |
|--------|----------|------|
| Module Constructor | 模块加载时，早于入口点 | 环境检查、调试器检测 |
| Entry Point | 主入口执行前 | 许可证校验 |
| Before Method Execution | 指定方法调用前 | 敏感方法的前置校验 |
| After Method Execution | 指定方法返回后 | 结果审计、水印写入 |
| Exception Handler | 异常抛出时 | 失败策略、日志上报 |

示例里 Exception Handler 没有勾选，这是合理的默认：全局异常处理插桩会改变异常传播行为，介入之后原始堆栈可能丢失，定位崩溃反而更难。

选择钩子点的原则是越早越好、越少越好。早期钩子能防止关键逻辑在未校验的情况下执行；数量少则减少对正常流程的干扰，也减少被单独定位的机会。每加一个钩子，都要在测试环境里验证一次启动流程与异常路径。

```
Injection Points:
☑ Module Constructor
☑ Entry Point
☑ Before Method Execution
☑ After Method Execution
☐ Exception Handler
```

## 13.6 符号映射

符号映射（symbol map）是混淆的配套文件：混淆前后的名字对照表。它有两个用途，一是还原用户提交的崩溃堆栈，二是调试自己发布的保护版本。

映射文件必须当机密处理。它相当于给了持有者一把反向改名的钥匙，泄露了映射再配合反编译，保护强度会明显下降。映射文件不要随程序分发，也不应提交到公开仓库。

### 13.6.1 映射文件格式

示例是映射文件的概念结构：Mappings 节点下按类型、方法列出 original 与 obfuscated 的对应关系。

读这类文件要注意三点。第一，映射是双向的：还原堆栈用混淆名查原名，验证保护配置则用原名查是否如预期改名。第二，不是所有成员都会出现在映射里，未被改名的成员通常不记录，所以查不到不等于没处理。第三，映射文件与程序集版本强绑定，每次构建都会变，按版本号归档是还原历史堆栈的前提。

归档命名建议包含程序集版本、构建号和时间戳。用同一个文件名覆盖历史映射，是事后无法还原堆栈的最常见原因。

```xml
<SymbolMap version="1.0">
  <Mappings>
    <Type original="MyApp.CustomerManager" obfuscated="A" />
    <Method original="ProcessPayment" obfuscated="a" />
  </Mappings>
</SymbolMap>
```

### 13.6.2 映射工具

映射工具是配套的还原程序，三个参数分别指定映射文件、包含堆栈的输入文件、还原后的输出文件。

实际流程是：用户提交崩溃日志，从中提取堆栈文本存成文件，用对应版本的映射还原，得到带原始类名、方法名的堆栈，再对着源码定位。

还原过程有三个常见坑：

- 映射版本对不上。用新版本映射还原旧版本堆栈，结果是错的，而且错得很隐蔽——名字能匹配上，但方法不是同一个；
- 堆栈被截断或格式化过。行号、文件路径被日志系统省略后，还原只能到方法级；
- 内联与优化。Release 构建下编译器可能内联方法，堆栈里的方法名是内联后的调用者，映射能还原名字但还原不了原始调用链。

所以还原结果只能作为定位线索，最终判断还是要靠对照源码和复现步骤。

```bash
# 使用映射还原堆栈跟踪
dotNET_Reactor.SymbolMapper.exe \
    -map symbol_map.xml \
    -stacktrace error.log \
    -output resolved.log
```

## 13.7 平台特定配置

同一份源码可能要在多个平台与架构上发布。不同平台的运行时能力不同：NecroBit 这类依赖原生加载器的技术，在部分平台上不可用或不稳定；x86 与 x64 的原生依赖不同；Linux 上的某些系统调用行为与 Windows 有差异。

平台配置的意义就是把哪些选项在哪个平台可用写进配置，而不是靠发布脚本手工挑参数。手动挑参数的流程，在一个平台发布失败时几乎无法回溯。

### 13.7.1 多平台支持

示例按平台声明不同强度：Windows-x64 用 Maximum 加 NecroBit，Linux-x64 用 Standard 且关闭 NecroBit。这个取舍反映的是一般经验：NecroBit 的实现依赖平台相关的加载机制，在非 Windows 平台上能不能用、稳不稳，要以目标版本和目标运行时实测为准；不确定时关闭它，其他保护项照常。

多平台配置要跟构建矩阵对齐。CI 的矩阵里有几个平台，配置里就应当有几个对应条目。缺一个平台的条目时，工具会用默认配置处理该平台产物，这是某平台保护没生效的典型原因。

架构差异不只是选项差异。AnyCPU 程序集在 32 位进程里会以 x86 方式加载，涉及原生依赖时可能失败。发布前确认目标平台的运行时标识（RID）与配置条目一致，比事后排查加载失败省事得多。

```xml
<Platforms>
  <Platform name="Windows-x64">
    <Obfuscation level="Maximum" />
    <NecroBit enabled="true" />
  </Platform>
  
  <Platform name="Linux-x64">
    <Obfuscation level="Standard" />
    <NecroBit enabled="false" />
  </Platform>
</Platforms>
```

### 13.7.2 条件编译

这是编译期的条件编译，与工具的平台配置是两回事，但两者常配合使用。

示例用条件编译指令包住特性标注。符号需要在项目文件里定义，常见做法是按操作系统判断后往 DefineConstants 追加一个自定义符号，这样同一份源码在不同平台构建时自动得到不同结果，不需要维护多个分支。

条件编译的用途通常是隔离平台相关代码：只在 Windows 上标注的特性、只在特定平台调用的 API。

要注意的是，条件编译屏蔽的是源码里的标注，与工具是否真的执行了该特性无关。符号没定义，特性不存在，工具自然看不到指令；符号定义了但工具版本不支持该特性，会走默认行为。两种情况表现相似、原因不同，排查时先确认编译产物里有没有那个特性。

```csharp
#if PROTECT_WINDOWS
    [Obfuscation(Feature = "necrobit")]
#endif
    public void PlatformSpecificMethod()
    {
        // ...
    }
```

## 13.8 调试配置

保护后的程序集出问题，定位手段只剩两样：日志和符号。调试配置决定这两样留多少。留得越多越好查，但产物体积增加、信息暴露也越多；留得越少越安全，代价是故障只能靠复现。

一个实用的做法是区分两种发布产物：内部测试版保留符号与行号，对外发布版去掉。两套配置分开维护，别用同一份配置改来改去。

### 13.8.1 调试符号

四项设置的效果各不相同：

- **Generate Symbol Map**：生成映射文件。这是还原堆栈的前提，建议始终开启并归档；
- **Preserve Line Numbers**：保留行号信息。堆栈能定位到源码行，代价是体积增加、暴露源文件结构；
- **Preserve Local Variables**：保留局部变量名。调试体验最好，但会暴露大量实现细节，通常只在内部版本开启；
- **Include Source File Names**：把源文件路径写进产物。路径里往往带开发者账号名或项目目录结构，属于信息泄露，公开版本应当关闭。

这四项的组合可以理解为调试友好度刻度。发布前逐项确认一次，比事后从用户机器上抓日志便宜得多。

```
Debug Settings:
☑ Generate Symbol Map
☑ Preserve Line Numbers
☐ Preserve Local Variables
☑ Include Source File Names
```

### 13.8.2 诊断模式

诊断模式会输出工具自身的运行细节：处理了哪些阶段、耗时多少、内存占用、加载了哪些配置。它面向的是保护过程本身出问题的场景，比如保护中途失败、产物行为异常、配置未生效。

三个开关的用途：

- **Enable Diagnostic Logging** 搭配 **Log Level**：Verbose 会记录每个处理步骤，日志量很大，建议只在单次排障时开启；
- **Performance Profiling**：记录各阶段耗时，用于优化保护阶段的整体时间，尤其是多线程配置调优时；
- **Memory Tracking**：记录峰值内存，用于判断内存上限设得是否合理。

诊断日志会包含文件路径、程序集名、配置项的值，属于内部信息。归档保存时注意访问权限，不要把诊断日志和公开发布物放在同一个目录里。

```
Diagnostics:
☑ Enable Diagnostic Logging
Log Level: [Verbose ▼]
Log Path: [logs\reactor-diagnostic.log]

☑ Performance Profiling
☑ Memory Tracking
```

## 13.9 许可证高级选项

许可证系统的核心决策是验证放在哪一层。端上验证的好处是离线可用、响应快，缺点是验证逻辑本身在客户端，总会被分析；服务端验证的好处是逻辑不可见、可随时调整策略，缺点是依赖网络、响应受服务可用性影响。

这一节的配置是折中方案：以服务端校验为主，配合本地缓存与离线回退，让正常用户在断网时也能继续使用一段时间。

### 13.9.1 许可证服务器

六个字段构成一条完整的远程校验策略：

- **Url** 与 **ApiKey**：校验端点与调用凭据。ApiKey 不应硬编码在客户端可见的明文里，它也是被窃取后伪造请求的入口；
- **Timeout**：单次请求超时，单位通常是秒。设得太短，网络抖动会导致误判为校验失败；
- **RetryCount**：失败重试次数。与超时组合决定最坏情况下用户要等多久；
- **FallbackMode**：服务不可用时的行为，示例的 offline 表示允许离线继续使用；
- **CacheDuration**：离线状态允许的持续时间。示例 7 天。

这组参数的本质是在用户体验和授权控制之间取平衡。缓存期设得太长，取消授权后用户仍可用很久；设得太短，出差或断网时正常用户会被锁在外面。业务上通常取 7 到 30 天。

排查许可证问题时的判断顺序：先看超时与重试是否导致等待过长，再看回退模式是否符合预期，最后看缓存是否按配置过期。这三步能把用户说用不了拆成可验证的具体原因。

```xml
<LicenseServer>
  <Url>https://license.example.com/api</Url>
  <ApiKey>your-api-key</ApiKey>
  <Timeout>30</Timeout>
  <RetryCount>3</RetryCount>
  
  <FallbackMode>offline</FallbackMode>
  <CacheDuration>7</CacheDuration>
</LicenseServer>
```

### 13.9.2 自定义验证

示例用一个类承载自定义校验，校验方法接收许可证信息对象返回布尔值。这类扩展点的价值是把业务规则（试用次数、功能模块授权、组织白名单）从工具配置里拿出来，用正常代码实现和测试。

写自定义验证有几个必须遵守的约束：

- **纯逻辑、无副作用**。验证可能在启动时被调用多次，不要在里面写文件、发请求、弹窗；
- **失败要可区分**。只返回布尔值无法区分许可证过期和许可证不属于本机，用户看到的提示会非常含糊。实际实现应当返回带原因的结果对象；
- **不抛异常**。验证过程抛异常在注入场景里会直接导致进程启动失败，所有分支都应当返回结果而不是抛出。

还有一点：自定义验证的代码同样会被保护工具处理。如果它调用了反射或依赖方法名，必须加入排除规则，否则验证逻辑本身可能在混淆后失效。

```csharp
[Obfuscation(Feature = "license:validator")]
public class CustomLicenseValidator
{
    public bool Validate(LicenseInfo license)
    {
        // 自定义验证逻辑
        return CheckCustomRules(license);
    }
}
```

## 13.10 输出优化

输出优化处理的是保护的副作用：混淆与注入会让产物变大，初始化与解密会让启动变慢。两个目标往往冲突——体积优化倾向去掉元数据，而启动优化依赖预加载与缓存，后者本身占体积。

选择依据是分发场景。下载安装的桌面软件对体积敏感，可以多开体积优化；局域网内部部署的软件对启动时间更敏感，体积大一点无妨。

### 13.10.1 大小优化

五项各自的机制与风险：

- **Remove Unused Code**：移除未被引用的代码。风险在于未引用是静态分析得出的，反射调用的方法看起来就是未引用，被删掉后运行时才暴露；
- **Merge Duplicate Strings**：合并重复字符串。对体积有帮助，对字符串加密的覆盖率可能有影响；
- **Compress Resources**：压缩资源。这是资源保护的常规手段，收益取决于资源类型；
- **Strip Debug Info**：去掉调试信息。体积下降明显，堆栈可读性下降，与 13.8 的调试配置直接相关；
- **Optimize Metadata**：优化元数据表。收益较小，一般无风险。

示例给出的 15% 到 25% 是笼统估计，实际取决于项目里字符串、资源、调试信息的占比。以自己项目的实测数据为准，不要拿估计值当验收标准。

移除未使用代码这一项建议在发布分支单独开启并做全量功能回归。它是最容易引入编译通过、运行时才炸这类问题的选项。

```
Size Optimization:
☑ Remove Unused Code
☑ Merge Duplicate Strings
☑ Compress Resources
☑ Strip Debug Info
☑ Optimize Metadata

Estimated Reduction: 15-25%
```

### 13.10.2 启动优化

四项措施围绕同一个思路：把解密、加载、初始化的工作从启动路径上挪走，或者提前并行做掉。

- **Preload Critical Methods**：预加载关键方法，把首次调用的解密成本提前；
- **Optimize Module Loading**：优化模块加载顺序，减少启动时的解析等待；
- **Cache Frequently Used Data**：缓存常用数据，减少重复解密；
- **Lazy Initialize Non-Critical**：非关键部分延迟初始化，把启动阶段的工作量压到最低。

示例的 10% 到 20% 是量级参考。真实验证方式是量启动到主窗口可交互的时间，在开启前后各测若干次取中位数。单次测量受磁盘缓存影响很大，容易得出错误结论。

启动优化与延迟加载有交互：延迟初始化把成本从启动挪到首次使用，如果用户在启动后立刻进入某个功能，感受上反而更慢。按实际使用路径决定哪些延迟、哪些预加载，比全开有效。

```
Startup Optimization:
☑ Preload Critical Methods
☑ Optimize Module Loading
☑ Cache Frequently Used Data
☑ Lazy Initialize Non-Critical

Startup Time Improvement: 10-20%
```

## 13.11 本章小结

本章覆盖的配置项可以归到三类：

**性能类**：多线程、内存、输出体积、启动时间。调整这些参数前先建立测量基线，改完再测一次，否则无法判断改动是否有效。

**强度类**：命名方案、控制流复杂度、加密算法、代码注入。强度提升必然带来兼容性与性能代价，每提升一档都要重跑功能测试与序列化测试。

**可维护类**：符号映射、调试符号、诊断日志。它们不影响保护强度，但决定了出问题时能不能查。发布流程里应当把它们当固定环节，而不是出事了再说。

最后一条实践原则：高级选项一次只改一项，改完验证再改下一项。同时改五个参数，出问题后无法归因，只能全部回退重来。

本章介绍了 .NET Reactor 的高级配置选项，包括：
- 全局设置和性能调优
- 高级混淆和加密配置
- 代码注入和符号映射
- 平台特定配置
- 调试和诊断选项

掌握这些高级选项可以实现更精细的保护控制。

把这些选项用好的前提，是清楚每一项在保护流水线的哪个环节起作用、影响的是构建时间还是运行时间。配置表看起来很长，真正需要按项目调整的通常只有少数几项：混淆强度、嵌入依赖、许可证校验方式。其余保持默认值，能少踩很多坑。
