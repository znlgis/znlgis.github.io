# 第12章：集成与自动化

## 12.1 Visual Studio 集成

把保护步骤放进 Visual Studio，解决的是"手工切工具"的摩擦：每改一次代码，要回到资源管理器里找到产物、切到 Reactor、选配置、点保护、再回 VS 调试。集成之后，保护成为构建流程的一环，谁按了 Build，行为都一致。

集成方式从轻到重有三层：装 VS 扩展，扩展在菜单里加一项；用 MSBuild 的 Target 挂在构建之后执行；用构建后事件写一条命令行。三者的底层都是调用命令行工具，差别在于执行时机、失败处理和是否随团队分发。

需要提前明确一点：**保护不是编译**。编译器产出的 IL 是保护工具的输入，保护后的产物是另一份文件。把保护后的文件再送回编译器或打包步骤时，要清楚当前操作的是哪一份。

### 12.1.1 安装扩展

扩展的安装路径和普通 VS 扩展一样：`扩展 → 管理扩展`，搜索关键字，下载后关闭 VS 完成安装、再重新打开。扩展的作用是提供菜单入口和图形面板，参数最终写入项目文件。

扩展装好不等于能用。VS 扩展与 VS 版本强绑定，2019 与 2022 的扩展包不能混用；工具装的版本与 VS 位数不一致时，扩展调用命令行可能找不到路径。装完之后先在菜单里手动跑一次，确认能定位到 `dotNET_Reactor.Console.exe`，再去改项目文件，这样出了问题能区分是扩展没生效还是项目配置写错。

团队场景里不推荐依赖扩展：成员不一定都装。扩展适合个人熟悉流程，团队共享的做法是把配置写进 MSBuild Target，见 12.2 节。

```
扩展 → 管理扩展 → 搜索 ".NET Reactor"
下载并安装
重启 Visual Studio
```

### 12.1.2 项目配置

这段 XML 挂在项目文件里，分两块：`PropertyGroup` 定义两个自定义属性，`Target` 声明一个构建后的动作。

`<ReactorEnabled>true</ReactorEnabled>` 与 `<ReactorProject>protection.nrproj</ReactorProject>` 本身不会被 MSBuild 识别，它们只是自定义属性，供后面的 Target 引用。属性名建议加团队或产品前缀，避免和 SDK 内置属性冲突。

`<Target Name="ProtectAssembly" AfterTargets="Build" Condition="'$(Configuration)' == 'Release'">` 这一行有三个关键点：

- `AfterTargets="Build"` 表示在 Build 目标完成后执行。项目可能被批量构建、可能只做 `Clean`，挂在 Build 之后能保证只在真正生成之后触发；
- `Condition` 用 `'$(Configuration)' == 'Release'` 做判断，等号两边要加引号，属性为空时会展开成 `'' == 'Release'`，不会解析报错；
- `Exec` 元素里的引号被写成 `&quot;`，因为 XML 属性值里不能直接放双引号。这是 XML 转义，与命令行本身的引号规则是两回事。

示例里 `$(ReactorPath)` 没有定义，直接照抄会得到一个空路径并触发 `Exec` 失败。补一个 PropertyGroup 定义它，或者在 `Exec` 里写绝对路径，是必须做的一步。

```xml
<!-- 在 .csproj 中添加 -->
<PropertyGroup>
  <ReactorEnabled>true</ReactorEnabled>
  <ReactorProject>protection.nrproj</ReactorProject>
</PropertyGroup>

<Target Name="ProtectAssembly" AfterTargets="Build" Condition="'$(Configuration)' == 'Release'">
  <Exec Command="&quot;$(ReactorPath)&quot; -file &quot;$(TargetPath)&quot; -project &quot;$(ReactorProject)&quot;" />
</Target>
```

### 12.1.3 构建后事件

构建后事件是 VS 里最轻量的挂钩点：项目属性 → 生成事件 → 后期生成事件命令行。它其实是一段批处理命令，执行时机是构建成功后、程序集已在输出目录时。

`^ ` 是 cmd 的续行符，把一条命令拆成多行便于阅读。三个宏的含义：`$(TargetPath)` 是输出程序集的完整路径，`$(TargetDir)` 是它所在目录，`$(TargetFileName)` 是文件名。示例把输出写到 `$(TargetDir)Protected\` 子目录，避免覆盖正在被 VS 引用的原始产物。

构建后事件有几个界定清楚的行为：

- 事件返回非零退出码时构建失败并显示 MSB3073 错误，错误信息里只有命令行，具体原因要看工具日志；
- 事件在每次构建后执行，增量构建也会执行，不能假定"只做一次"；
- 事件的工作目录默认是项目目录而不是输出目录，相对路径要按项目目录来算。

直接改写 `$(TargetPath)` 本身是常见的错误做法：下一次增量构建会认为产物已过期，调试时加载的也可能是被保护过的版本，堆栈和源码对不上。输出到独立目录更稳。

```
Post-build event:
"C:\Program Files (x86)\Eziriz\.NET Reactor\dotNET_Reactor.Console.exe" ^
  -file "$(TargetPath)" ^
  -targetfile "$(TargetDir)Protected\$(TargetFileName)" ^
  -project "$(ProjectDir)protection.nrproj"
```

## 12.2 MSBuild 集成

MSBuild 集成的目标是让保护成为构建图里的一个节点，而不是外挂脚本。它比构建后事件更强的地方在于：可以声明自定义任务、可以被其他项目引用、可以参与依赖顺序，也能在 `dotnet build` 与 `msbuild` 两种入口下一致工作。

一条原则：**能不加自定义任务就不加**。自定义任务需要额外的程序集，部署到构建机时多一份依赖，出错时的错误信息也更难读。用 `Exec` 调命令行已经能覆盖绝大多数需求。

### 12.2.1 自定义任务

这段 `ReactorTask.targets` 展示了自定义任务的声明方式：`UsingTask` 指定任务名与实现程序集，`Target` 里以元素形式声明参数。

- `xmlns` 是 MSBuild 2003 的命名空间。用 `<Project Sdk="...">` 的新式写法时，`UsingTask` 仍然可以出现在项目文件里，但更常见的组织方式是把这份 targets 文件单独保存，再用 `<Import Project="..." />` 引入；
- `AssemblyFile="Reactor.MSBuild.dll"` 要求该文件能被 MSBuild 找到。相对路径按 MSBuild 的当前目录解析，构建机上路径不一致就会失败。示例假定安装目录提供了这个任务程序集，如果实际安装里没有，直接改用 `Exec` 调命令行更可靠；
- 任务参数（InputFile、OutputFile、ProjectFile、Obfuscation、NecroBit）必须与任务类定义的属性名严格对应，大小写敏感。拼错不会报"参数不存在"，而是走默认值，行为难以察觉；
- `AfterTargets="Build"` 同样决定执行时机，想更精确时可以用 `DependsOnTargets` 显式声明依赖。

把这份 targets 放进仓库、由项目 `Import`，团队成员不需要各自配置，是这一层集成的实际价值。

```xml
<!-- ReactorTask.targets -->
<Project xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <UsingTask TaskName="ReactorTask" AssemblyFile="Reactor.MSBuild.dll" />
  
  <Target Name="ProtectWithReactor" AfterTargets="Build">
    <ReactorTask
      InputFile="$(TargetPath)"
      OutputFile="$(TargetDir)Protected\$(TargetFileName)"
      ProjectFile="$(ProjectDir)protection.nrproj"
      Obfuscation="true"
      NecroBit="true"
    />
  </Target>
</Project>
```

### 12.2.2 条件执行

条件的本质是 MSBuild 属性求值。构建开始前，命令行、环境变量、项目文件、导入的 targets 依次参与属性赋值，后赋值的覆盖先赋值的。所以 `EnableReactor` 可以在项目文件里给默认值，在流水线上用 `-p:EnableReactor=true` 覆盖：

```bash
dotnet build -c Release -p:EnableReactor=true
```

`Condition` 支持 `AND`、`OR`、`!=` 等运算符，字符串比较要加引号。示例只检查两个条件，实践中还常加一条"只在 CI 上执行"，比如用环境变量是否存在来判断：

```xml
<Condition>'$(Configuration)' == 'Release' AND '$(EnableReactor)' == 'true' AND '$(CI)' != ''</Condition>
```

条件建议写在 Target 上，而不是写在 Target 内部的每个任务上。条件写在 Target 上，不满足时整个目标被跳过，日志里有一行明确的跳过记录；写在内部则要为每个任务都写一次，漏一个就会出现部分执行。

```xml
<Target Name="ProtectAssembly" 
        AfterTargets="Build" 
        Condition="'$(Configuration)' == 'Release' AND '$(EnableReactor)' == 'true'">
  <!-- 保护逻辑 -->
</Target>
```

## 12.3 NuGet 包保护

用 Reactor 保护要发布到 NuGet 的包，是一个需要先说清限制的场景。NuGet 消费方拿到包后要能引用、能编译、能读 XML 文档，这意味着程序集的公共类型名、方法签名、命名空间都不能被改名，否则编译期就断。所以对 NuGet 包，可用的手段集中在方法体加密、字符串加密、控制流混淆这些不改公共表面的选项上，改名类混淆必须对公共 API 关闭。

另一个限制更实际：**包本身是公开分发的**。解开 nupkg 就是 DLL。保护能提高阅读成本，不能阻止分发。

### 12.3.1 打包前保护

`<Target Name="ProtectBeforePack" BeforeTargets="Pack">` 把保护挂在 `Pack` 之前。执行顺序是：编译 → 保护 → 打包。挂在之后不行，那时压缩包已经生成。

`$(TargetPath)` 指向 `bin\Release\netX.Y\MyLib.dll`，`dotnet pack` 默认从同一目录取文件。因此这个 Target 有一个副作用需要处理：如果直接原地覆盖 `$(TargetPath)`，打包拿到的是保护后的文件，但随后重新构建会因文件被改动而失败。稳妥做法是把保护输出写到临时目录，再替换要打包的项；退一步的简单方案是保留原始产物，用专门的"打包专用"构建配置。

另一个常见的翻车点是重复保护：包被保护一次，下游项目引用后又对整个输出做了一次保护，第二次处理会破坏第一次的结构。给保护后的文件加命名标记，或在项目文件里用属性标记状态，可以避免重复执行。

```xml
<Target Name="ProtectBeforePack" BeforeTargets="Pack">
  <Exec Command="dotNET_Reactor.Console.exe -file $(TargetPath) ..." />
</Target>
```

### 12.3.2 自动化流程

四步流程看着简单，每一步都有需要卡住的检查点。

**构建**：确认产物是 Release、是目标框架、带不带符号文件。构建产物最好带版本号，后面所有步骤都围绕这个版本号做记录。

**保护**：以 `.nrproj` 为唯一配置来源，命令行只传产物路径。保护后检查退出码和体积变化，体积异常增大往往说明嵌入了不该嵌入的依赖。

**打包**：确认包里是保护后的文件，且 `lib\<tfm>\` 结构没变。用解压工具列一下包内文件，比相信流程更可靠。

**发布**：先发预发布版本到内部源，做一次真实消费方安装测试，再发正式版本。NuGet 的版本号一旦发出就不能回收，所以这一步的验证不能省。

整个流程的判定标准应当落到脚本的退出码上，而不是靠人看日志。任何一步失败就中断，不要"继续往后跑完再说"。

```
1. 构建项目
   ↓
2. 保护程序集
   ↓
3. 创建 NuGet 包
   ↓
4. 发布到 NuGet
```

## 12.4 Docker 集成

容器化构建 .NET 项目很常见，把 Reactor 放进去有两个现实障碍：工具是 Windows 可执行文件，官方只提供 Windows 版本；许可证激活通常需要交互或本机状态。所以示例用 `mono` 在 Linux 镜像里运行 `.exe`，并假定授权已经就位。

这个方案能不能用，取决于两点：工具在 mono 下的兼容性，以及许可证在容器内的存放方式。两点都要在目标镜像上实测。如果实测不可行，更稳的路径是在 Windows 构建机上做保护，把产物作为制品传给 Docker 构建阶段，容器只负责部署。

### 12.4.1 Dockerfile

多阶段构建的意图很清楚：第一阶段装 SDK、还原、编译、保护，第二阶段只保留运行时和产物，体积小、攻击面少。

逐段看几个关键行：

- `FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build` 命名了构建阶段，后面可以用 `--from=build` 引用它的文件系统；
- 先 `COPY` 项目文件再 `RUN dotnet restore`，是为了让依赖还原这一层能命中 Docker 层缓存，源码变动不会导致重新还原；
- `COPY . .` 把全部源码复制进去后 `dotnet build -c Release -o /app/build` 产出程序集；
- `COPY ["dotnet-reactor/", "/opt/dotnet-reactor/"]` 把工具目录一起放进来。示例假定仓库里有一份工具副本，实际更常见的做法是在这一步下载安装包并静默安装，工具本身不进代码仓库；
- `RUN mono ...` 执行保护，三个路径都是容器内绝对路径，`protection.nrproj` 相对路径按 `WORKDIR` 解析；
- 最终阶段 `COPY --from=build /app/protected .` 只拿保护产物，不带工具、不带源码、不带 SDK。

还有两个工程细节：保护阶段需要的授权文件要能进入镜像，但**不要通过 `COPY` 写死在镜像层**，否则会留在构建历史和最终镜像里，改用构建参数或密钥挂载。容器内区域设置与工具行为有关，测试镜像与生产镜像保持一致能减少"本地能跑容器不能跑"的问题。

```dockerfile
# Dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

# 复制项目文件
COPY ["MyApp/MyApp.csproj", "MyApp/"]
RUN dotnet restore "MyApp/MyApp.csproj"

# 复制源代码
COPY . .
WORKDIR "/src/MyApp"
RUN dotnet build -c Release -o /app/build

# 安装 .NET Reactor
COPY ["dotnet-reactor/", "/opt/dotnet-reactor/"]

# 保护程序集
RUN mono /opt/dotnet-reactor/dotNET_Reactor.Console.exe \
    -file /app/build/MyApp.dll \
    -targetfile /app/protected/MyApp.dll \
    -project protection.nrproj

# 最终镜像
FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY --from=build /app/protected .
ENTRYPOINT ["dotnet", "MyApp.dll"]
```

## 12.5 自动化测试

保护后的程序集必须重新验证：加载是否成功、关键功能是否正常、性能损耗是否可接受。这三项覆盖了绝大多数保护引入的故障。测试要对着**保护后的产物**跑，而不是对原始构建产物跑，这是本节最核心的要求。

单元测试直接引用保护后的 DLL 有个前提：测试代码用到的类型名和方法名必须没变。如果混淆改掉了内部类型名，测试编译不过；这时测试要改为通过反射按接口调用，或者只测试公共 API 表面。

### 12.5.1 单元测试

示例写了两条测试：一条验证程序集能加载，一条验证功能正确。逐条看要点。

第一条测试 `Assembly.LoadFile("protected/MyApp.dll")`。相对路径按测试进程的工作目录解析，在 VS 里跑和在 CI 里跑工作目录不同，路径经常因此失效。测试项目里应当用 `AppContext.BaseDirectory` 拼路径，或者把保护产物作为测试项目的内容文件复制到输出目录。

第二条测试里，`assembly` 变量在第一个方法内声明，第二个方法里无法访问——这是 C# 作用域规则，不是保护工具的限制。示例想表达的是"加载之后反射调用"，实际写的时候要把加载动作放进每个需要它的方法，或者写成测试类字段在 `[TestInitialize]` 里初始化。

反射调用还要注意：`GetType("MyApp.Calculator")` 用的是全名，如果类型被混淆改名，这里直接返回 null，后续 `Activator.CreateInstance(null)` 抛 `ArgumentNullException`。这正说明测试只应覆盖公共表面，内部类型改名属于预期行为，不要因此判断保护失败。

```csharp
[TestClass]
public class ProtectedAssemblyTests
{
    [TestMethod]
    public void TestProtectedAssembly_LoadsSuccessfully()
    {
        // 加载保护后的程序集
        var assembly = Assembly.LoadFile("protected/MyApp.dll");
        Assert.IsNotNull(assembly);
    }
    
    [TestMethod]
    public void TestProtectedAssembly_FunctionalityWorks()
    {
        // 测试保护后的功能
        var type = assembly.GetType("MyApp.Calculator");
        var instance = Activator.CreateInstance(type);
        var method = type.GetMethod("Add");
        
        var result = method.Invoke(instance, new object[] { 2, 3 });
        Assert.AreEqual(5, result);
    }
}
```

### 12.5.2 集成测试

集成测试把整条保护流水线当作被测对象：构建、保护、验证、功能测试四步串行执行，任何一步失败就整体失败。

这种测试写法上要注意三件事：

- **外部进程要判退出码**。构建和保护都是子进程，必须读 `Process.ExitCode`，只看有没有输出会漏掉失败；
- **测试环境要干净**。上一次运行残留的 protected 目录会让"文件存在即通过"的断言失效，测试开始前先删目录；
- **耗时要有上限**。构建加保护通常在几分钟量级，CI 里给测试设一个超时，卡住时能及时失败而不是占着执行器。

示例中的 `BuildProject()`、`ProtectAssembly()`、`VerifyProtection()`、`TestFunctionality()` 都是占位方法。实际项目中前两个通常是 `Process.Start` 调 `dotnet build` 与 Reactor 命令行，第三个检查产物存在性与体积变化，第四个加载程序集跑几条关键路径。

```csharp
[TestClass]
public class ProtectionIntegrationTests
{
    [TestMethod]
    public void TestCompleteProtectionPipeline()
    {
        // 1. 构建项目
        BuildProject();
        
        // 2. 保护程序集
        ProtectAssembly();
        
        // 3. 验证保护
        VerifyProtection();
        
        // 4. 功能测试
        TestFunctionality();
    }
}
```

## 12.6 持续集成最佳实践

CI 环境里跑保护，除了构建本身，还要处理工具安装、许可证、缓存、并行和产物存放。这些不是 Reactor 独有的问题，但保护步骤往往处在"构建成功之后、发布之前"的咽喉位置，它一失败整条流水线就停，所以稳定性要求更高。

### 12.6.1 缓存优化

缓存的目标是省掉每次重复下载和激活的开销。示例缓存 `~/.reactor` 目录，缓存 key 里混入 `.nrproj` 的哈希——配置一变就换一份缓存。

`~/.reactor` 这个路径是按工具的默认工作目录假设的。实际要缓存什么，取决于工具把许可证信息、临时文件放在哪，这一点以目标版本的实测结果为准。判断标准很简单：缓存之后第一次运行如果仍然要求激活，说明缓存目录选错了。

缓存许可证信息存在安全权衡：缓存通常对整个仓库或组织可见，授权文件放进缓存等于扩大了它的可见范围。托管 runner 上用仓库 Secret 在步骤里临时写入，比把授权放进缓存更合适。

缓存 key 里加工具版本号是必要的。升级 Reactor 后缓存格式可能不兼容，旧缓存会导致难以解释的失败；把版号放进 key，升级时自然换一份新缓存。

{% raw %}
```yaml
# GitHub Actions 示例
- name: Cache .NET Reactor
  uses: actions/cache@v3
  with:
    path: ~/.reactor
    key: ${{ runner.os }}-reactor-${{ hashFiles('**/protection.nrproj') }}
```
{% endraw %}

### 12.6.2 并行构建

矩阵构建把同一份代码在多个配置、多个平台下各跑一遍。示例里的 `configuration` 与 `platform` 是两个维度，组合出六种任务。

这里有一个语义问题要留意：`configuration: [Debug, Release]` 意味着 Debug 也会被保护，而 Debug 产物一般是给开发调试用的，保护之后调试体验反而变差。实际矩阵通常只保留 Release，把平台维度作为唯一变量。

`protection-${{ matrix.platform }}.nrproj` 这行说明按平台使用不同的项目文件——不同平台的程序集引用不同、可用的保护选项也可能不同（例如某些依赖原生代码的功能在 AnyCPU 下不适用）。按平台拆分配置比在命令行里拼条件更清晰。

矩阵任务之间互相独立，适合并行。但构建缓存与 NuGet 缓存如果共用目录，会出现写冲突；CI 平台一般按矩阵维度自动分区，自建执行器上要自己确认。

另外，示例中的 YAML 被夹在一对 raw 标签之间，因为 Jekyll 会把双花括号当成模板语法先解析一遍。写文档遇到同样内容时也要做这层处理，否则构建阶段就会报语法错误。

{% raw %}
```yaml
strategy:
  matrix:
    configuration: [Debug, Release]
    platform: [x86, x64, AnyCPU]

steps:
- name: Protect Assembly
  run: |
    dotNET_Reactor.Console.exe \
      -file "bin/${{ matrix.configuration }}/${{ matrix.platform }}/MyApp.exe" \
      -project "protection-${{ matrix.platform }}.nrproj"
```
{% endraw %}

## 12.7 监控和报告

保护过程是黑盒的话，出问题只能靠猜。报告和统计的作用是把黑盒打开一部分：哪些方法被处理、哪些被跳过、体积变化多少、耗时多长。这些数字既是验收依据，也是性能回归的基线。

### 12.7.1 保护报告生成

`-report` 指定输出文件，`-reportformat` 指定格式（示例用 `html`）。HTML 格式适合归档和人工查看：打开就有总览和明细，不需要额外工具；如果要做自动化比对，机器可读格式更合适，具体支持哪些格式以目标版本的帮助输出为准。

报告的典型用途有三个：发布前确认保护配置真的生效；两次发布之间对比保护覆盖率的变化；排查"某功能在保护后变慢"时，定位具体被加密的方法。

报告包含被保护的方法名和资源名，是敏感信息。它应当作为内部构建制品保存，不要随程序一起分发，也不要把报告提交到公开仓库。

```bash
# 生成 HTML 报告
dotNET_Reactor.Console.exe \
    -file MyApp.exe \
    -report protection-report.html \
    -reportformat html
```

### 12.7.2 统计信息

示例统计里每一项都对应一个可以判断的信号：

| 指标 | 含义 | 异常信号 |
|------|------|----------|
| Total Methods | 程序集方法总数 | 与预期差异大，可能引错产物 |
| Protected Methods | 实际被保护的方法数 | 远低于预期，保护范围被排除规则吃掉 |
| Encrypted Strings | 加密的字符串数量 | 为 0 说明字符串加密没生效 |
| Resource Files | 处理的资源数 | 与项目资源清单不符 |
| Protection Time | 保护耗时 | 突然拉长，可能是压缩级别被调高 |
| File Size | 体积变化 | 增幅过大，可能重复嵌入依赖 |

这些数字最好在 CI 里做阈值检查：保护率低于某条线、体积增幅超过某个比例，就让构建失败。阈值不要照抄文档给出的数字，用自己项目的稳定版本跑几次，取平均值再定。

```
Protection Statistics:
- Total Methods: 1,547
- Protected Methods: 1,234 (80%)
- Encrypted Strings: 567
- Resource Files: 23
- Protection Time: 45 seconds
- File Size: 2.5 MB → 3.1 MB (+24%)
```

## 12.8 版本控制

保护相关的文件分两类：应当进版本控制的（配置、脚本、文档），以及绝对不能进的（许可证文件、保护后的产物、临时日志）。前者是团队共享的资产，后者要么敏感、要么可以重新生成。

版本控制这一节看似琐碎，实际决定了团队换人、换机器、重建流水线时能不能一次跑通。配置和脚本进仓库，保护流程就是可复现的；配置留在某人的机器上，流程就只在那台机器上成立。

### 12.8.1 .gitignore 配置

示例的 .gitignore 有三段，各段意图不同：

- `bin/Protected/` 与 `obj/Protected/` 排除保护后的产物。产物是构建输出，不该进版本库，同一份源码可以随时重新生成；
- `*.nrlog` 与 `*.nrtemp` 排除工具产生的日志与临时文件。它们体积不定、内容每次不同，提交进来只会污染差异；
- `!*.nrproj` 与 `!protection-config.xml` 用取反规则把配置文件重新纳入。注意取反规则的生效前提：如果上层目录整体被忽略，取反对目录内的文件不起作用，需要先让目录本身不被忽略。

一个容易忘记的点是许可证文件。工具目录下通常有授权相关文件，误提交会泄露授权。显式把工具安装目录或授权文件名写进 .gitignore，比依赖"我记得别提交"可靠。

```
# .gitignore
# 排除保护后的文件
bin/Protected/
obj/Protected/

# 排除临时文件
*.nrlog
*.nrtemp

# 包含配置文件
!*.nrproj
!protection-config.xml
```

### 12.8.2 配置文件管理

示例给出的目录结构体现了一个原则：配置按用途分层存放，而不是散落在各项目里。

`src/MyApp/protection.nrproj` 这类放在项目旁边的配置，是项目自身的默认保护策略，跟着项目走。`config/protection-debug.nrproj`、`protection-release.nrproj`、`protection-production.nrproj` 是按环境划分的覆盖配置，解决"同一份代码在不同交付场景用不同强度"的问题。`scripts/` 下放批处理与 PowerShell，负责把这些配置串起来。

这种分法有两个好处。一是环境差异集中可见，想看生产环境到底用了什么保护，直接打开一个文件，不用在命令行里追参数。二是配置可以独立演进，调整 production 配置不影响 debug 配置。

配置文件的命名建议带版本或日期，尤其是交付给外部客户使用的配置。同一个文件名下内容变了，事后无法判断某次发布到底用了哪一版保护策略。

```
推荐结构：
/
├── src/
│   ├── MyApp/
│   │   ├── MyApp.csproj
│   │   └── protection.nrproj
│   └── MyLibrary/
│       ├── MyLibrary.csproj
│       └── protection.nrproj
├── config/
│   ├── protection-debug.nrproj
│   ├── protection-release.nrproj
│   └── protection-production.nrproj
└── scripts/
    ├── protect.bat
    └── protect.ps1
```

## 12.9 本章小结

本章从 IDE 集成一路讲到 CI 流水线，核心是把保护从"人工操作"变成"可重复执行的构建步骤"。可以归纳成四点：

**集成层级选最小可用的那一层。** 个人用 VS 扩展熟悉流程，团队共享用 MSBuild Target 或脚本。层级越高，需要维护的东西越多。

**配置与执行分离。** `.nrproj` 是配置本体，脚本只负责传路径与少量环境差异。把参数堆在命令行里，升级或迁移时一定出问题。

**测试针对保护后的产物。** 原始产物测试通过不能说明任何问题。加载、功能、性能三项检查，缺一项都可能把故障带到用户手里。

**流水线要能判定失败。** 退出码、报告指标、体积阈值，都要能自动判断。靠人看日志的流程，在发布频率上来之后必然出错。

本章介绍了 .NET Reactor 的集成和自动化方案：
- Visual Studio 和 MSBuild 集成
- CI/CD 流程集成
- Docker 容器化
- 自动化测试
- 持续集成最佳实践

通过自动化集成，可以将代码保护无缝融入开发流程。

最后留一条实践提醒：每次升级 Reactor 版本后，把整条流水线在干净环境里完整跑一遍，重点检查工具路径、许可证状态、报告格式这三处。版本升级改掉某个默认值是常见的情况，而这三点正好是流程里最容易被忽略、出问题时又最难定位的环节。
