# 第11章：命令行使用

## 11.1 命令行概述

图形界面适合配置保护策略，命令行适合把配置执行下去。两者的能力边界是一样的：GUI 里勾选的选项最终写进 `.nrproj` 项目文件，命令行读取同一份项目文件，此外还允许用参数临时覆盖部分选项。所以实践中的分工是——用 GUI 调试出满意的保护配置，保存为项目文件，交付流程里只调用命令行。

在 CI 或发布脚本里用命令行，有三个绕不开的现实理由。构建机通常没有交互桌面，自动化流程也不能等人工点按钮；每次发布都需要可复现的参数组合，手点界面无法保证一致性；批量处理几十个程序集时，逐个打开 GUI 不现实。

命令行工具是独立可执行文件（`dotNET_Reactor.Console.exe`），与主程序一起安装在 `Eziriz\.NET Reactor` 目录下。它需要有效的许可证，激活方式与 GUI 相同，这一点在构建服务器上经常被忽略：没做许可证激活的机器上，命令行会以退出码 3 结束，日志里提示许可证无效，而不是给出保护失败的具体原因。

.NET Reactor 提供强大的命令行界面（CLI），支持自动化和批处理操作。

## 11.2 基本语法

命令行的参数形式是"减号 + 参数名 + 空格 + 值"，参数顺序不影响结果。基本形态：

```bash
dotNET_Reactor.Console.exe [options] -file <input> [-targetfile <output>]
```

几个语法层面的约定值得先记牢：

- 参数名区分大小写的情况在不同版本上并不一致，脚本里统一用小写最稳妥。
- 路径含空格时必须整体加双引号。批处理里还要注意 `^"` 与引号嵌套的问题，后面 11.4 会讲。
- 一次调用只处理一个输入程序集。批量处理靠外层脚本循环，而不是给 `-file` 传多个路径。
- `-targetfile` 省略时，输出文件通常覆盖到输入文件同目录的默认命名，具体行为取决于版本的默认输出设置。发布脚本应当显式指定输出路径，避免误改构建产物。
- 不用 `-file` 时可以只用 `-project` 加项目里的输入输出定义，但大多数自动化脚本仍然显式给 `-file`，便于同一个项目文件复用到不同产物上。

```bash
dotNET_Reactor.Console.exe [options] -file <input> [-targetfile <output>]
```

## 11.3 常用参数

### 11.3.1 输入输出

这一组参数决定"处理谁、写到哪、说多少话"：

| 参数 | 作用 | 注意 |
|------|------|------|
| `-file` | 指定输入程序集 | 必填（除非项目文件里已定义） |
| `-targetfile` | 指定输出路径 | 会覆盖同名文件，先清理目录 |
| `-project` | 加载 `.nrproj` 配置 | 与单个选项同时出现时，选项覆盖项目值 |
| `-quiet` | 只输出错误 | 适合 CI，日志靠 `-log` 留存 |
| `-verbose` | 输出处理细节 | 排查保护失败时打开 |

`-quiet` 与 `-verbose` 同时给没有意义，工具按自身的优先级取一个。构建日志很长时，`-verbose` 会把每个被处理的方法类型都打印出来，导致日志膨胀，建议只在定位问题时临时开启。

输出目录要先创建。工具不会递归创建 `-targetfile` 的父目录，父目录不存在时表现为退出码 2 或一条文件未找到的错误。

```bash
# 指定输入文件
-file MyApp.exe

# 指定输出文件
-targetfile MyApp.Protected.exe

# 使用项目文件
-project MyProject.nrproj

# 静默模式
-quiet

# 详细输出
-verbose
```

### 11.3.2 保护选项

保护选项有两类：布尔开关（配 `1`/`0`）和带值的选项（配枚举名）。示例里的 `-obfuscation 1`、`-stringencryption 1`、`-necrobit 1`、`-antidebug 1`、`-antitampering 1` 都是开关；`-obfuscation_level standard` 属于带值选项，取值常见的有 `standard`、`enhanced`、`maximum` 之类的分档。

命令行参数与项目文件的关系需要理解清楚：项目文件是完整配置，命令行参数是覆盖层。只给 `-obfuscation 1` 而不给别的，其余选项沿用项目文件或默认值——这意味着"用命令行拼一套完整保护配置"这种写法很脆弱，换一个版本默认值就可能变。正确做法是把完整策略固化在 `.nrproj` 里，命令行只传与环境相关的差异项。

还有一个顺序问题：Reactor 的保护步骤有内部依赖，字符串加密依赖混淆后的方法结构，NecroBit 又会影响方法体。这不表示参数顺序要跟着写，工具内部有固定的流水线顺序；命令行参数顺序无关，但参数之间的逻辑矛盾（例如关闭混淆却开启依赖混淆的字符串加密）会导致部分选项被跳过，日志里一般会有提示，值得用 `-verbose` 确认。

```bash
# 启用混淆
-obfuscation 1

# 设置混淆级别
-obfuscation_level standard

# 启用字符串加密
-stringencryption 1

# 启用 NecroBit
-necrobit 1

# 启用反调试
-antidebug 1

# 启用防篡改
-antitampering 1
```

## 11.4 批处理脚本

批量保护的核心是"遍历目录、逐个调用、任意一个失败就中断"。Windows 批处理和 PowerShell 都能写，选择依据是目标机器的默认环境：老一些的构建机可能只有 cmd 和 Windows PowerShell 5.1。

### 11.4.1 Windows 批处理

这段脚本的骨架是标准的批处理三部曲：`@echo off` 关回显，`setlocal` 限制变量作用域，`endlocal` 还原环境。逐段看：

- `set REACTOR="C:\Program Files (x86)\..."` 把带空格的路径连引号一起存进变量。批处理的变量在展开时保留引号，所以调用处写 `%REACTOR%` 就够了，不要再套一层引号。
- `if not exist "%OUTPUT_DIR%" mkdir "%OUTPUT_DIR%"` 保证输出目录存在。变量加引号是为了路径含空格时不拆成多个参数。
- `for %%F in (...) do (...)` 遍历两类文件。批处理文件里用双百分号，命令行里直接执行时用单百分号，这是最常见的复制粘贴错误。
- `%%~nxF` 是只取文件名带扩展名，去掉目录。输出到另一个目录时不能直接写 `%%F`，否则会得到 `输出目录\输入目录\文件` 这种畸形路径。
- `if errorlevel 1` 判断退出码是否大于等于 1。批处理的 `errorlevel` 比较语义是"大于等于"，不是"等于"，判断成功用 `errorlevel 0` 的写法并不成立，通常反着写——先判断非零再处理。

这段脚本有两处隐患值得改。其一，`exit /b 1` 在 `for` 循环体里会退出整个批处理，行为符合预期，但如果脚本被别的批处理 `call` 调用，`exit /b` 只退出当前层，上层仍会继续，需要在上层再判断一次。其二，路径里出现 `&`、`^`、`!` 等字符时，即使加了引号也可能被特殊解释，构建机上应避免使用这类目录名。

```batch
@echo off
setlocal

set REACTOR="C:\Program Files (x86)\Eziriz\.NET Reactor\dotNET_Reactor.Console.exe"
set INPUT_DIR=bin\Release
set OUTPUT_DIR=bin\Protected

REM 创建输出目录
if not exist "%OUTPUT_DIR%" mkdir "%OUTPUT_DIR%"

REM 保护所有 DLL 和 EXE
for %%F in ("%INPUT_DIR%\*.exe" "%INPUT_DIR%\*.dll") do (
    echo Protecting %%F...
    %REACTOR% -file "%%F" -targetfile "%OUTPUT_DIR%\%%~nxF" -quiet
    
    if errorlevel 1 (
        echo Failed to protect %%F
        exit /b 1
    )
)

echo All files protected successfully!
endlocal
```

### 11.4.2 PowerShell 脚本

PowerShell 版本比批处理更好维护，参数化、错误处理、对象管道都更清晰。这段脚本的结构：

- `param()` 块声明四个参数，`Mandatory=$true` 让调用方漏传时直接报错，而不是拿到空字符串。
- `Get-ChildItem -Filter "*.exe", "*.dll"` 有语义问题：`-Filter` 只接受一个字符串，传数组会失败或按字符串拼接处理。稳妥写法是两次调用 `Get-ChildItem -Filter *.exe` 与 `-Filter *.dll`，或者用 `-Include` 搭配 `-Recurse`。
- `$args = @(...)` 借用了自动变量名 `$args`。在脚本里 `$args` 是只读的隐式参数集合，复用这个名字轻则覆盖语义、重则赋值失败，建议改成 `$reactorArgs`。
- `& $reactorPath $args` 用调用运算符执行外部程序，并把数组作为参数列表展开。数组里每一项是独立的 argv 元素，含空格的路径也能正确传递。
- `$LASTEXITCODE` 由外部程序设置，是判断保护是否成功的唯一可靠依据。

一个容易忽略的细节是脚本的执行策略。构建机上 `Set-ExecutionPolicy` 若为 Restricted，直接运行 `.ps1` 会报安全错误。CI 场景用参数 `-ExecutionPolicy Bypass` 或改用内联脚本，比修改机器全局策略更合适。

```powershell
# Protect-Assemblies.ps1

param(
    [Parameter(Mandatory=$true)]
    [string]$InputPath,
    
    [Parameter(Mandatory=$true)]
    [string]$OutputPath,
    
    [Parameter(Mandatory=$false)]
    [string]$ProjectFile = "",
    
    [Parameter(Mandatory=$false)]
    [switch]$NecroBit,
    
    [Parameter(Mandatory=$false)]
    [switch]$Verbose
)

$reactorPath = "C:\Program Files (x86)\Eziriz\.NET Reactor\dotNET_Reactor.Console.exe"

# 获取所有程序集
$assemblies = Get-ChildItem -Path $InputPath -Filter "*.exe", "*.dll"

foreach ($assembly in $assemblies) {
    Write-Host "Protecting $($assembly.Name)..." -ForegroundColor Cyan
    
    $args = @(
        "-file", $assembly.FullName,
        "-targetfile", (Join-Path $OutputPath $assembly.Name)
    )
    
    if ($ProjectFile) {
        $args += @("-project", $ProjectFile)
    }
    
    if ($NecroBit) {
        $args += "-necrobit", "1"
    }
    
    if (-not $Verbose) {
        $args += "-quiet"
    }
    
    & $reactorPath $args
    
    if ($LASTEXITCODE -ne 0) {
        Write-Error "Failed to protect $($assembly.Name)"
        exit 1
    }
}

Write-Host "All assemblies protected successfully!" -ForegroundColor Green
```

## 11.5 CI/CD 集成

### 11.5.1 Azure DevOps

这段 YAML 用 PowerShell@2 任务调用脚本，三个 `inputs` 的含义：

- `targetType: 'filePath'` 表示执行一个脚本文件，而不是内联脚本；
- `filePath` 指向仓库里的脚本路径；
- `arguments` 传给脚本的参数，用 `>` 折叠成一行，`$(...) ` 形式的变量由 Azure DevOps 在任务执行前展开。

`Build.BinariesDirectory` 和 `Build.ArtifactStagingDirectory` 是构建代理上的预定义目录，前者适合放编译产物，后者适合放待发布的制品。写保护输出时用 Staging 目录，后面接 PublishBuildArtifacts 任务即可。

这条流水线实际落地的两个前提：代理必须是 Windows（Reactor 的命令行工具是 Windows 可执行文件），并且代理上已有许可证。托管代理每次都是干净环境，因此要在前面加一步安装与激活，或者自建带授权的代理池。

```yaml
# azure-pipelines.yml
steps:
- task: PowerShell@2
  displayName: 'Protect Assemblies'
  inputs:
    targetType: 'filePath'
    filePath: 'scripts/Protect-Assemblies.ps1'
    arguments: >
      -InputPath "$(Build.BinariesDirectory)"
      -OutputPath "$(Build.ArtifactStagingDirectory)/protected"
      -ProjectFile "protection.nrproj"
      -NecroBit
```

### 11.5.2 GitHub Actions

GitHub Actions 的 `run` 块默认用当前 shell，这里显式声明 `shell: powershell`，否则 `&` 调用和反引号续行在 `cmd` 下会被当成别的东西。

命令行里用了反引号续行，这是 PowerShell 的续行符；YAML 里这段整体放在 `| ` 块中，缩进原样保留。三处路径都写了相对路径，说明工作目录是仓库根，因此需要先有构建步骤把程序集放到 `bin\Release`。

Windows 运行器是 `windows-latest`，安装 .NET Reactor 要么在步骤里用安装包静默安装，要么把整套工具目录预先放在自建 runner 上。托管 runner 没有桌面交互，只能走命令行，正好契合本章主题。许可证可以通过仓库 Secret 传入，再在步骤里写入授权文件；不要把授权文件提交进仓库。

失败处理上，建议在后续步骤里检查退出码。`run` 块里任何一条命令返回非零，步骤默认就失败，但 PowerShell 对原生命令的非零退出码不总是传播为步骤失败（取决于 `$ErrorActionPreference` 与版本），显式加一句 `if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }` 最保险。

```yaml
# .github/workflows/protect.yml
- name: Protect with .NET Reactor
  run: |
    $reactor = "C:\Program Files (x86)\Eziriz\.NET Reactor\dotNET_Reactor.Console.exe"
    & $reactor -file "bin\Release\MyApp.exe" `
               -targetfile "protected\MyApp.exe" `
               -project "protection.nrproj" `
               -quiet
  shell: powershell
```

### 11.5.3 Jenkins Pipeline

Jenkins 的 `bat` 步骤在 Windows 节点上执行 cmd 脚本，因此延续符用 `^`，路径里的反斜杠要写两遍。三个单引号 `'''` 是 Groovy 的多行字符串，内部的 `\` 不再转义，所以 `C:\\Program Files` 在 Groovy 层面产出 `C:\Program Files`，交给 cmd 后正好是单个反斜杠。

这段片段只截取了 `stage`，实际使用还要放进 `pipeline { }` 与 `node { }` 里，并指定 Windows 节点标签。Jenkins 的失败判定来自 `bat` 的退出码，返回非零即标记阶段失败，无需额外判断。

共享库场景可以把保护逻辑包成 `protectAssembly(projectFile, input, output)` 这样的 step，各条流水线复用同一实现，避免每个仓库各写一份命令行。

```groovy
// Jenkinsfile
stage('Protect Assemblies') {
    steps {
        bat '''
            "C:\\Program Files (x86)\\Eziriz\\.NET Reactor\\dotNET_Reactor.Console.exe" ^
            -file "bin\\Release\\MyApp.exe" ^
            -targetfile "protected\\MyApp.exe" ^
            -project "protection.nrproj" ^
            -quiet
        '''
    }
}
```

## 11.6 高级用法

### 11.6.1 条件保护

条件保护解决的是"同一条流水线，不同分支用不同保护强度"。示例用环境变量 `BUILD_CONFIGURATION` 做判断，Release 时加 `-necrobit 1`，否则不加。

```bash
if [ "$BUILD_CONFIGURATION" = "Release" ]; then
    NECROBIT="-necrobit 1"
else
    NECROBIT=""
fi

dotNET_Reactor.Console.exe \
    -file MyApp.exe \
    -obfuscation 1 \
    $NECROBIT \
    -targetfile MyApp.Protected.exe
```

写法上有两个细节。变量 `$NECROBIT` 没有加引号，这是有意为之：加引号后空值会变成一个空参数，工具收到空字符串参数可能报"未知参数"。反过来，路径变量必须加引号。同一段脚本里对两类变量采取不同处理，是 shell 编程的常见模式。

这段示例里的 `if` 语法是 POSIX shell，而 Reactor 是 Windows 工具。实际在 Windows 上执行时，要么用 Git Bash、WSL 这类环境，要么改成批处理的 `if "%BUILD_CONFIGURATION%"=="Release"` 或 PowerShell 的 `if ($env:BUILD_CONFIGURATION -eq 'Release')`。示例的价值在于展示"拼参数"的思路，不属于可直接照抄的 Windows 脚本。

```bash
# 根据环境变量决定保护级别
if [ "$BUILD_CONFIGURATION" = "Release" ]; then
    NECROBIT="-necrobit 1"
else
    NECROBIT=""
fi

dotNET_Reactor.Console.exe \
    -file MyApp.exe \
    -obfuscation 1 \
    $NECROBIT \
    -targetfile MyApp.Protected.exe
```

### 11.6.2 并行处理

`ForEach-Object -Parallel` 是 PowerShell 7 才有的能力，Windows PowerShell 5.1 上直接报错。示例把 Reactor 路径写在并行脚本块内部，每一轮各自赋值，避免跨作用域变量问题；如果要在脚本块里引用外部变量，必须用 `$using:` 前缀，这是并行模式和普通管道最大的差别。

`-ThrottleLimit 4` 限制同时运行的实例数。这个值不是越大越好：Reactor 自身在处理单个程序集时已经使用多线程（见第十三章的性能调优），再叠加四路并行会让 CPU 和磁盘同时饱和，整体耗时反而可能上升；更现实的问题是临时文件冲突，多个实例同时写同一个临时目录时偶发失败。

实践中建议：按 CPU 核数取一半作为并行上限，给每个实例指定不同的临时目录，并且先小批量验证一轮，确认编译产物之间没有共享资源再放大并发。

还有一个执行顺序问题：`-Parallel` 里的输出顺序不保证与输入顺序一致，日志按文件落盘比看控制台输出更可靠。

```powershell
# 并行保护多个程序集
$assemblies = Get-ChildItem -Path "bin\Release" -Filter "*.dll"

$assemblies | ForEach-Object -Parallel {
    $reactor = "C:\Program Files (x86)\Eziriz\.NET Reactor\dotNET_Reactor.Console.exe"
    & $reactor -file $_.FullName -targetfile "protected\$($_.Name)" -quiet
} -ThrottleLimit 4
```

## 11.7 错误处理

### 11.7.1 退出代码

脚本判断保护结果，只能依据退出码。文档里列出的约定如下：

| 退出码 | 含义 | 常见原因 |
|--------|------|----------|
| 0 | 成功 | —— |
| 1 | 一般错误 | 参数拼写错误、内部异常 |
| 2 | 文件未找到 | 输入路径错、输出目录不存在 |
| 3 | 许可证无效 | 构建机未激活授权 |
| 4 | 配置错误 | `.nrproj` 损坏或选项冲突 |
| 5 | 保护失败 | 程序集结构不支持、写文件失败 |

批处理里用 `if errorlevel N` 判断，PowerShell 里读 `$LASTEXITCODE`，CI 平台把非零当作步骤失败。需要注意的是，`errorlevel` 语义是"大于等于"，而 `$LASTEXITCODE` 是精确值，写判断逻辑时要区分。

真实排障中，退出码只能把范围缩小到一类问题，具体原因要看日志或加 `-verbose` 重跑。把退出码原样记录到构建日志里，是快速定位问题的第一步。

```
0  - 成功
1  - 一般错误
2  - 文件未找到
3  - 许可证无效
4  - 配置错误
5  - 保护失败
```

### 11.7.2 日志记录

`-log` 把工具输出写进文件，`-verbose` 决定详细程度。两者搭配才有意义：只开 `-log` 得到的是常规信息，出问题时信息量不够；只开 `-verbose` 而日志留在控制台，CI 日志滚动之后查不到。

示例里的检查方式用 `grep -q "ERROR" protection.log`，这是 Unix 写法。Windows 上如果没有 grep，用 PowerShell 的 `Select-String`：

```powershell
if (Select-String -Path protection.log -Pattern "ERROR" -Quiet) {
    Write-Error "Protection failed!"
    exit 1
}
```

日志定位技巧：先搜 `ERROR` 和 `WARNING`，再搜具体文件名。Reactor 的日志会记录每个处理阶段的开始与结束，若某阶段只出现开始不出现结束，说明该阶段崩溃或超时。日志里出现大量 `Skipped` 时，通常是选项冲突或资源被排除，需要回头核对项目配置。

发布流程建议保留每次构建的日志作为制品，与保护后的程序集放在一起。它既是审计记录，也是复现问题的唯一线索。

```bash
# 启用日志
dotNET_Reactor.Console.exe \
    -file MyApp.exe \
    -log protection.log \
    -verbose

# 检查日志
if grep -q "ERROR" protection.log; then
    echo "Protection failed!"
    exit 1
fi
```

## 11.8 本章小结

本章覆盖了命令行工具从参数到自动化的完整用法。核心结论可以归成四条：

**参数是覆盖层，不是配置本体。** 完整策略保存在 `.nrproj` 中，命令行只负责传入环境差异项。把几十个开关堆在命令行里，维护成本会随版本升级迅速失控。

**路径与引号是脚本失败的第一来源。** 含空格的路径必须整体加引号，批处理里的百分号、PowerShell 里的数组展开、Jenkins 里的反斜杠转义，各自有各自的规则，写完后在干净环境的机器上验证一次比读十遍文档更有效。

**退出码是自动化流程的判定依据。** 0 与非 0 的二值判断足够驱动流水线，但定位问题要靠日志和 `-verbose`。构建机上最先要确认的往往是许可证状态，退出码 3 经常被误读为文件问题。

**并行要克制。** Reactor 内部已有多线程，外层再叠加并发时，瓶颈通常落在磁盘与临时文件上，而不是 CPU。

本章介绍了 .NET Reactor 的命令行使用方法，包括：
- 基本命令语法
- 常用参数选项
- 批处理脚本编写
- CI/CD 集成方案
- 错误处理机制

掌握命令行工具可以实现自动化保护流程，提高开发效率。

把命令行接入流水线之后，还有一件容易被忽略的事：保护步骤应当与构建产物一起做版本记录。哪一版程序集用了哪份 `.nrproj`、哪个工具版本、哪个许可证，这三项信息缺一项，出问题时就无法复现。把工具版本打印进构建日志、把项目文件随源码一起纳入版本控制，是成本最低的保障手段。
