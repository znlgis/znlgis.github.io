# 第2章：基础数据结构源码解读（IntPoint、IntRect、DoublePoint）

## 2.1 引言

在任何几何计算库中，**点（Point）** 和 **矩形（Rectangle）** 是最基础的数据结构。它们看似简单，却承载了整个库的设计哲学。在 Clipper1（ClipperLib 6.4.2）中，作者 Angus Johnson 定义了三种基础数据类型：

| 类型 | 坐标类型 | 主要用途 |
|------|----------|----------|
| `IntPoint` | 整数（`cInt` = `Int64`） | 所有多边形顶点的标准表示 |
| `IntRect` | 整数（`cInt` = `Int64`） | 轴对齐包围盒（AABB） |
| `DoublePoint` | 双精度浮点（`double`） | 中间计算、偏移操作中的法线与弧线近似 |

本章将 **逐行解析** 这三个结构体的完整源代码，深入探讨每一个设计决策背后的原因，以及这些看似微小的选择如何影响整个库的正确性与性能。

---

## 2.2 为什么使用整数坐标？——Clipper1 的核心设计哲学

在深入源代码之前，我们必须首先理解 Clipper1 最重要的设计决策之一：**使用整数坐标而非浮点坐标**。

### 2.2.1 浮点数的根本问题

在计算几何中，浮点数运算会带来一系列难以处理的问题：

**1. 精度丢失与累积误差**

IEEE 754 双精度浮点数只有约 15-16 位有效十进制数字。当进行大量连续运算时（例如求交点、裁剪多边形），舍入误差会不断累积，最终导致几何上不一致的结果。

```
示例：
a = 0.1 + 0.2    // 结果：0.30000000000000004，而非精确的 0.3
b = (a == 0.3)    // 结果：false！
```

**2. 比较操作的不确定性**

在多边形裁剪算法中，经常需要判断两个点是否相同、一个点是否在某条边上、两条边是否共线。使用浮点数时，这些比较操作都需要引入一个 **epsilon（容差值）**：

```csharp
// 浮点数比较——需要 epsilon
bool AreEqual(double a, double b, double epsilon = 1e-10)
{
    return Math.Abs(a - b) < epsilon;
}
```

epsilon 的选择是一个两难问题：
- **太大**：会把本不相同的点误判为相同，导致拓扑错误
- **太小**：会把本应相同的点判断为不同，导致漏洞或裂缝

**3. 排序不稳定性**

Vatti 算法的核心是扫描线（scanline），它需要对边（edge）的 X 坐标进行精确排序。浮点数的比较不具有传递性——即 `a ≈ b` 且 `b ≈ c` 不能保证 `a ≈ c`。这会导致排序算法产生不一致的结果，甚至无限循环。

### 2.2.2 整数坐标的优势

使用整数坐标可以完美解决上述所有问题：

| 特性 | 浮点数 | 整数 |
|------|--------|------|
| 精确比较 | ❌ 需要 epsilon | ✅ `a == b` 即可 |
| 排序稳定性 | ❌ 不保证传递性 | ✅ 完全有序 |
| 累积误差 | ❌ 每次运算都有舍入 | ✅ 加减法完全精确 |
| 哈希一致性 | ❌ 浮点误差导致哈希不同 | ✅ 相同值必然相同哈希 |
| 性能 | 取决于平台 | 通常更快（整数运算） |

### 2.2.3 缩放因子模式（Scaling Factor Pattern）

当然，现实世界中的坐标往往不是整数。Clipper1 的使用模式是：

1. **输入时**：将浮点坐标乘以一个缩放因子（例如 1000 或 100000），转换为整数
2. **处理时**：所有裁剪操作在整数域中进行
3. **输出时**：将结果除以相同的缩放因子，还原为浮点坐标

```csharp
// 典型使用模式
double scaleFactor = 1000.0;

// 输入：浮点 → 整数
IntPoint pt = new IntPoint(
    (cInt)(realX * scaleFactor),
    (cInt)(realY * scaleFactor)
);

// ... Clipper 在整数域中执行所有运算 ...

// 输出：整数 → 浮点
double resultX = pt.X / scaleFactor;
double resultY = pt.Y / scaleFactor;
```

缩放因子越大，精度越高，但可用的坐标范围越小。对于 `Int64`，最大值约为 ±9.2×10¹⁸。如果缩放因子为 10⁶，则坐标范围约为 ±9.2×10¹²，对于绝大多数应用来说已经绰绰有余。

### 2.2.4 cInt 类型别名

在源代码文件的顶部，Clipper1 使用 `using` 指令定义了 `cInt` 类型：

```csharp
#if use_int32
  using cInt = System.Int32;
#else
  using cInt = System.Int64;
#endif
```

- **默认模式**（`Int64`）：64 位有符号整数，范围 ±9,223,372,036,854,775,807（约 ±9.2×10¹⁸）
- **`use_int32` 模式**（`Int32`）：32 位有符号整数，范围 ±2,147,483,647（约 ±2.1×10⁹）

32 位模式在某些平台上可能更快（特别是 32 位 CPU），但坐标范围大幅缩小。Clipper1 在文档中明确警告：使用 32 位模式时，坐标的绝对值不应超过 46,340（因为 46,340² ≈ 2.1×10⁹，内部运算中会出现坐标的乘积）。

## 2.3 IntPoint 结构体：完整源码与逐行解析

`IntPoint` 是 Clipper1 中使用最频繁的数据结构。每一个多边形的顶点都是一个 `IntPoint`。整个库围绕这个结构体展开。

### 2.3.1 完整源代码

以下是 `IntPoint` 的完整源代码，包括条件编译的两个变体和运算符重载：

```csharp
#if use_xyz
  public struct IntPoint
  {
    public cInt X;
    public cInt Y;
    public cInt Z;
  
    public IntPoint(cInt x, cInt y, cInt z = 0)
    {
      this.X = x; this.Y = y; this.Z = z;
    }

    public IntPoint(double x, double y, double z = 0)
    {
      this.X = (cInt)x; this.Y = (cInt)y; this.Z = (cInt)z;
    }

    public IntPoint(DoublePoint dp)
    {
      this.X = (cInt)dp.X; this.Y = (cInt)dp.Y; this.Z = 0;
    }

    public IntPoint(IntPoint pt)
    {
      this.X = pt.X; this.Y = pt.Y; this.Z = pt.Z;
    }
  }
#else
  public struct IntPoint
  {
    public cInt X;
    public cInt Y;

    public IntPoint(cInt X, cInt Y)
    {
      this.X = X; this.Y = Y;
    }
    public IntPoint(double x, double y)
    {
      this.X = (cInt)x; this.Y = (cInt)y;
    }

    public IntPoint(IntPoint pt)
    {
      this.X = pt.X; this.Y = pt.Y;
    }
  }
#endif
```

运算符重载部分（位于 `#if` / `#else` 之外，两个变体共享）：

```csharp
  public static bool operator ==(IntPoint a, IntPoint b)
  {
    return a.X == b.X && a.Y == b.Y;
  }

  public static bool operator !=(IntPoint a, IntPoint b)
  {
    return a.X != b.X || a.Y != b.Y;
  }

  public override bool Equals(object obj)
  {
    if (obj == null) return false;
    if (obj is IntPoint)
    {
      IntPoint a = (IntPoint)obj;
      return (X == a.X) && (Y == a.Y);
    }
    else return false;
  }

  public override int GetHashCode()
  {
    //simply IsHashCode IsPoint a IsPoint c;
    return base.GetHashCode();
  }
```

### 2.3.2 结构体声明与字段

#### `public struct IntPoint`

```csharp
public struct IntPoint
```

**关键字 `struct` 而非 `class`：**

这是一个极其重要的设计决策。在 C# 中，`struct` 是 **值类型（value type）**，而 `class` 是 **引用类型（reference type）**。两者的核心区别如下：

| 特性 | struct（值类型） | class（引用类型） |
|------|------------------|-------------------|
| 内存分配 | 栈（stack）或内联（inline） | 堆（heap） |
| 赋值语义 | 复制整个值 | 复制引用（指针） |
| 垃圾回收 | 不需要 GC | 需要 GC |
| null 判断 | 不可为 null（除非 Nullable<T>） | 可为 null |
| 默认相等 | 按值比较 | 按引用比较 |

对于 `IntPoint` 这样的小型数据结构（只有 2-3 个整数字段），使用 `struct` 有显著的性能优势：

1. **无堆分配开销**：一个包含百万个顶点的多边形，每个 `IntPoint` 都直接内联在 `List<IntPoint>` 的内部数组中，无需为每个点单独分配堆内存。
2. **无垃圾回收压力**：值类型随其容器一起释放，不会给 GC 增加跟踪负担。这对于处理大规模几何数据至关重要。
3. **缓存友好性**：连续排列在内存中的点数据具有优秀的空间局部性（spatial locality），能够充分利用 CPU 缓存。

#### 内存布局

在默认的 64 位模式下：

```
IntPoint（无 Z）:
┌──────────────────────┬──────────────────────┐
│       X (Int64)      │       Y (Int64)      │
│      8 字节           │      8 字节           │
└──────────────────────┴──────────────────────┘
总计：16 字节

IntPoint（有 Z，use_xyz 模式）:
┌──────────────────────┬──────────────────────┬──────────────────────┐
│       X (Int64)      │       Y (Int64)      │       Z (Int64)      │
│      8 字节           │      8 字节           │      8 字节           │
└──────────────────────┴──────────────────────┴──────────────────────┘
总计：24 字节
```

在 32 位模式（`use_int32`）下：

```
IntPoint（无 Z）:
┌──────────────┬──────────────┐
│   X (Int32)  │   Y (Int32)  │
│   4 字节      │   4 字节      │
└──────────────┴──────────────┘
总计：8 字节
```

这些大小差异在处理大量顶点时会显著影响内存使用和缓存命中率。

#### 公共字段

```csharp
public cInt X;
public cInt Y;
public cInt Z;  // 仅在 use_xyz 模式下存在
```

注意这里使用了 **公共字段（public fields）** 而非 **属性（properties）**。在现代 C# 编码规范中，通常建议使用属性来封装字段。但对于高频访问的数值类型结构体，直接使用公共字段有以下好处：

1. **零开销访问**：属性虽然在 JIT 编译后通常会被内联，但在调试模式下或某些情况下会产生方法调用开销。
2. **可作为 `ref` 参数**：字段可以直接用 `ref` 传递，而自动属性则不行（在早期 C# 版本中）。
3. **简洁性**：对于一个本质上就是"两个/三个整数打包在一起"的类型，过度封装是不必要的。

这种风格也体现了 Clipper1 的 **Delphi 遗产**——库最初是用 Delphi/Object Pascal 编写的，而 Delphi 中记录类型（record）的字段默认就是公共的。

### 2.3.3 条件编译：`#if use_xyz`

```csharp
#if use_xyz
  // 3D 版本（带 Z 坐标）
#else
  // 2D 版本（标准）
#endif
```

`use_xyz` 是一个 **条件编译符号（conditional compilation symbol）**。它控制 `IntPoint` 是否包含第三个坐标 `Z`。

#### Z 坐标的用途

Z 坐标 **不参与** 任何几何裁剪运算。Clipper1 是一个严格的 2D 裁剪库，所有的交点计算、边排序、多边形填充判断都只使用 X 和 Y。

那么 Z 的意义何在？

Z 坐标用于 **用户自定义数据传播**。当 Clipper 在裁剪过程中创建新的交点时，用户可以通过 `ZFillFunction` 回调来决定新点的 Z 值。这对于以下场景非常有用：

1. **高度数据插值**：如果多边形表示地形，Z 可以存储高度，裁剪后需要插值新点的高度。
2. **索引追踪**：Z 可以存储顶点的原始索引，帮助在裁剪后追溯每个顶点的来源。
3. **颜色/属性传播**：Z 可以编码颜色或其他属性信息。

```csharp
// ZFillFunction 的委托定义
public delegate void ZFillCallback(IntPoint bot1, IntPoint top1,
    IntPoint bot2, IntPoint top2, ref IntPoint pt);
```

当两条边相交产生新点 `pt` 时，Clipper 会调用此回调，传入两条边的端点（`bot1/top1` 和 `bot2/top2`），让用户决定 `pt.Z` 的值。

#### 为什么使用编译时开关而非运行时选项？

如果将 Z 作为可选字段在运行时处理（例如使用 `Nullable<cInt>` 或始终分配 Z），会带来以下代价：

1. **内存浪费**：对于不需要 Z 的应用（绝大多数），每个点多占 8 字节是毫无意义的开销。
2. **性能损失**：每次复制点时都需要多复制一个字段；每次分配 `List<IntPoint>` 时都需要更多内存。
3. **代码复杂度**：运行时检查"是否需要处理 Z"会增加条件分支，降低可预测性。

使用编译时开关（`#if use_xyz`）是一种 **零成本抽象**：
- 不需要 Z 的应用编译出的代码中完全不存在 Z，没有任何额外开销。
- 需要 Z 的应用编译出带 Z 的版本，Z 的处理被编译器硬编码到指令中。

### 2.3.4 构造函数逐行解析

#### 构造函数一：整数参数构造（`use_xyz` 版本）

```csharp
public IntPoint(cInt x, cInt y, cInt z = 0)
{
  this.X = x; this.Y = y; this.Z = z;
}
```

**逐行分析：**

| 代码 | 说明 |
|------|------|
| `public IntPoint(...)` | 公共构造函数 |
| `cInt x, cInt y` | 必选参数：X 和 Y 坐标 |
| `cInt z = 0` | 可选参数：Z 坐标，默认为 0 |
| `this.X = x;` | 将参数 `x` 赋值给字段 `X`。`this.` 用于消除字段与参数同名时的歧义 |
| `this.Y = y;` | 将参数 `y` 赋值给字段 `Y` |
| `this.Z = z;` | 将参数 `z` 赋值给字段 `Z` |

Z 的默认值为 0，这意味着调用者可以用 `new IntPoint(100, 200)` 创建一个 2D 点，Z 自动为 0。这确保了从 2D 代码迁移到 `use_xyz` 模式时的兼容性。

#### 构造函数一：整数参数构造（标准版本）

```csharp
public IntPoint(cInt X, cInt Y)
{
  this.X = X; this.Y = Y;
}
```

标准版本没有 Z 参数，也没有默认参数值。注意这里参数名使用了大写 `X` 和 `Y`——与字段名完全相同。这在 C# 中是合法的，`this.X` 引用字段，而单独的 `X` 引用参数。虽然这种命名方式不太符合 .NET 编码规范（规范建议参数名使用 camelCase），但它确实清晰地表达了意图。

#### 构造函数二：浮点参数构造

```csharp
// use_xyz 版本
public IntPoint(double x, double y, double z = 0)
{
  this.X = (cInt)x; this.Y = (cInt)y; this.Z = (cInt)z;
}

// 标准版本
public IntPoint(double x, double y)
{
  this.X = (cInt)x; this.Y = (cInt)y;
}
```

**关键细节——截断转换（Truncation Cast）：**

`(cInt)x` 执行的是 **截断转换**，即直接丢弃小数部分，而不是四舍五入：

```csharp
(cInt)3.7   == 3    // 不是 4！
(cInt)(-2.9) == -2  // 不是 -3！
(cInt)0.999  == 0   // 不是 1！
```

这意味着如果调用者没有预先进行适当的缩放和四舍五入，可能会丢失精度。更安全的做法是在调用前使用 `Math.Round()`：

```csharp
// 推荐的做法
IntPoint pt = new IntPoint(
    (cInt)Math.Round(x * scale),
    (cInt)Math.Round(y * scale)
);

// 而不是直接传入浮点数
IntPoint pt = new IntPoint(x * scale, y * scale);  // 截断！
```

这个构造函数的存在主要是为了方便——在某些场景下，中间计算会产生浮点结果（例如交点计算），此时可以直接将结果传入构造函数。Clipper1 内部的交点计算代码确实使用了这个构造函数。

#### 构造函数三：从 DoublePoint 转换（仅 `use_xyz` 版本）

```csharp
public IntPoint(DoublePoint dp)
{
  this.X = (cInt)dp.X; this.Y = (cInt)dp.Y; this.Z = 0;
}
```

**逐行分析：**

| 代码 | 说明 |
|------|------|
| `DoublePoint dp` | 接收一个 `DoublePoint` 结构体 |
| `this.X = (cInt)dp.X;` | 将 `dp.X`（`double`）截断转换为 `cInt`，赋值给 `X` |
| `this.Y = (cInt)dp.Y;` | 将 `dp.Y`（`double`）截断转换为 `cInt`，赋值给 `Y` |
| `this.Z = 0;` | Z 坐标设为 0（因为 `DoublePoint` 没有 Z） |

注意 Z 被显式设为 0。这是因为 `DoublePoint` 是一个纯 2D 类型，没有 Z 信息。从 `DoublePoint` 转换时，没有可用的 Z 值，所以默认为 0。

这个构造函数仅在 `use_xyz` 版本中存在。标准版本不需要它，因为标准版本没有 Z 字段，且 `DoublePoint` 到 `IntPoint` 的转换可以通过 `new IntPoint((cInt)dp.X, (cInt)dp.Y)` 显式完成。实际上标准版本中确实缺少这个便捷构造函数——这可能是一个小疏忽，也可能是作者认为标准版本中不需要这种便捷转换。

#### 构造函数四：拷贝构造函数

```csharp
// use_xyz 版本
public IntPoint(IntPoint pt)
{
  this.X = pt.X; this.Y = pt.Y; this.Z = pt.Z;
}

// 标准版本
public IntPoint(IntPoint pt)
{
  this.X = pt.X; this.Y = pt.Y;
}
```

**拷贝构造函数的必要性：**

严格来说，对于 C# 的 `struct`，拷贝构造函数 **不是必需的**——赋值操作符 `=` 会自动执行逐字段复制。即：

```csharp
IntPoint a = new IntPoint(10, 20);
IntPoint b = a;  // 自动复制所有字段，b 是 a 的完全独立副本
```

那么为什么还要提供拷贝构造函数呢？

1. **代码清晰性**：`new IntPoint(pt)` 在某些上下文中比赋值更清晰地表达"创建一个独立副本"的意图。
2. **Delphi 传统**：Delphi 的 record 类型需要手动复制，这个习惯被保留到了 C# 版本中。
3. **与其他语言的一致性**：Clipper1 有 C++、Java、Python 等多个移植版本。在 C++ 中，拷贝构造函数是标准做法。保留它使跨语言的代码结构保持一致。

### 2.3.5 相等运算符：一个重要的设计决策

```csharp
public static bool operator ==(IntPoint a, IntPoint b)
{
  return a.X == b.X && a.Y == b.Y;
}

public static bool operator !=(IntPoint a, IntPoint b)
{
  return a.X != b.X || a.Y != b.Y;
}
```

#### 仅比较 X 和 Y，不比较 Z！

这是一个 **非常重要** 的设计决策：即使在 `use_xyz` 模式下，相等运算符也 **只比较 X 和 Y**，完全忽略 Z 坐标。

**原因：**

1. **Z 是附加数据，不是几何信息**：两个点在几何上是否相同，取决于它们在 2D 平面上的位置（X, Y），而不取决于附加的 Z 数据。
2. **一致性**：Clipper1 的所有几何算法（交点检测、边排序等）都只使用 X 和 Y。如果相等运算符也只看 X 和 Y，则语义完全一致。
3. **实际需求**：在裁剪过程中，同一个位置的点可能来自不同的多边形，携带不同的 Z 值。但在几何上它们是"同一个点"，应该被判定为相等。

这个设计决策虽然合理，但也可能导致意外。如果用户不了解这一点，可能会错误地认为两个 Z 值不同的点是不相等的。

#### 逻辑对偶性

注意 `==` 和 `!=` 的实现完全对偶：

```csharp
==  :  a.X == b.X && a.Y == b.Y    // 两个条件都满足
!=  :  a.X != b.X || a.Y != b.Y    // 任一条件不满足
```

根据 **德摩根定律（De Morgan's Laws）**：

```
NOT (A AND B)  ≡  (NOT A) OR (NOT B)
```

所以 `!=` 的实现确实是 `==` 的逻辑否定，这是正确的。在 C# 中，如果重载了 `==`，就 **必须** 同时重载 `!=`，否则编译器会报错。

### 2.3.6 Equals 方法重写

```csharp
public override bool Equals(object obj)
{
  if (obj == null) return false;
  if (obj is IntPoint)
  {
    IntPoint a = (IntPoint)obj;
    return (X == a.X) && (Y == a.Y);
  }
  else return false;
}
```

**逐行分析：**

| 行 | 代码 | 说明 |
|----|------|------|
| 1 | `public override bool Equals(object obj)` | 重写 `System.Object.Equals`。参数类型必须是 `object` |
| 2 | `if (obj == null) return false;` | 空引用检查。注意：对于值类型，`obj` 是装箱后的引用，可能为 null |
| 3 | `if (obj is IntPoint)` | 类型检查：确保 `obj` 是 `IntPoint` 类型 |
| 4 | `IntPoint a = (IntPoint)obj;` | 拆箱（unboxing）：将 `object` 转回 `IntPoint`。这涉及一次内存复制 |
| 5 | `return (X == a.X) && (Y == a.Y);` | 逐字段比较，与 `==` 运算符一致 |
| 6 | `else return false;` | 如果 `obj` 不是 `IntPoint`，则不相等 |

**性能注意事项：**

由于 `IntPoint` 是值类型，调用 `Equals(object)` 会触发 **装箱（boxing）**——将栈上的值类型复制到堆上的 `object` 包装中。这是一个相对昂贵的操作。在性能敏感的代码中，应尽量使用 `==` 运算符而非 `Equals` 方法。

更好的做法是实现 `IEquatable<IntPoint>` 接口，提供一个类型安全的 `Equals(IntPoint other)` 方法，避免装箱。但 Clipper1 没有这样做——这可能是为了保持代码简洁，或者因为在实际使用中，`Equals` 方法很少被直接调用。

### 2.3.7 GetHashCode 方法

```csharp
public override int GetHashCode()
{
  //simply IsHashCode IsPoint a IsPoint c;
  return base.GetHashCode();
}
```

**分析：**

这个实现简单地委托给了 `base.GetHashCode()`，即 `System.ValueType.GetHashCode()`。这里的注释看起来是编辑残留或自动生成的片段，并不构成有意义的说明。

**`System.ValueType.GetHashCode()` 的问题：**

对于值类型，`base.GetHashCode()` 的默认实现会使用反射来遍历所有字段并计算哈希值。这有两个主要问题：

1. **性能差**：反射非常慢。对于频繁需要哈希的场景（例如放入 `Dictionary` 或 `HashSet`），这会成为瓶颈。
2. **只看第一个字段**：实际上，CLR 的优化版本通常只使用第一个字段来计算哈希。对于 `IntPoint`，这意味着只用 `X` 计算哈希，而忽略 `Y`。这会导致大量哈希冲突——例如，所有 `X` 相同但 `Y` 不同的点都会有相同的哈希值。

一个更好的实现是：

```csharp
public override int GetHashCode()
{
  unchecked
  {
    int hash = 17;
    hash = hash * 31 + X.GetHashCode();
    hash = hash * 31 + Y.GetHashCode();
    return hash;
  }
}
```

然而，在 Clipper1 的实际使用中，`IntPoint` 很少被用作字典的键或放入哈希集合，因此这个次优的实现在实践中影响不大。

## 2.4 IntRect 结构体：完整源码与逐行解析

### 2.4.1 完整源代码

```csharp
  public struct IntRect
  {
    public cInt left;
    public cInt top;
    public cInt right;
    public cInt bottom;

    public IntRect(cInt l, cInt t, cInt r, cInt b)
    {
      this.left = l; this.top = t;
      this.right = r; this.bottom = b;
    }
    public IntRect(IntRect ir)
    {
      this.left = ir.left; this.top = ir.top;
      this.right = ir.right; this.bottom = ir.bottom;
    }
  }
```

### 2.4.2 结构体声明与字段

```csharp
public struct IntRect
{
  public cInt left;
  public cInt top;
  public cInt right;
  public cInt bottom;
```

#### Delphi 风格命名

注意字段名使用了 **小写开头** 的命名：`left`、`top`、`right`、`bottom`。这与 .NET 的命名规范（公共字段应使用 PascalCase，如 `Left`、`Top`）不一致，但与 **Delphi/Windows API** 的 `TRect` 结构体完全对应：

```pascal
// Delphi 中的 TRect
TRect = record
  Left: Integer;
  Top: Integer;
  Right: Integer;
  Bottom: Integer;
end;
```

这再次体现了 Clipper1 的 Delphi 遗产。作者在将代码移植到 C# 时，保留了原始的字段命名风格。

#### 语义定义

`IntRect` 表示一个 **轴对齐包围矩形（Axis-Aligned Bounding Box, AABB）**：

```
(left, top) ─────────────────── (right, top)
      │                               │
      │         IntRect 区域           │
      │                               │
(left, bottom) ──────────────── (right, bottom)
```

其中：
- `left` ≤ `right`（X 轴范围）
- `top` 和 `bottom` 的关系取决于坐标系方向

在 Clipper1 中，Y 轴的方向取决于使用场景。在大多数计算机图形学应用中，Y 轴向下增长，此时 `top` ≤ `bottom`。但 Clipper1 本身不强制约定 Y 轴方向，它只要求 `left` ≤ `right`。

### 2.4.3 构造函数

#### 参数构造函数

```csharp
public IntRect(cInt l, cInt t, cInt r, cInt b)
{
  this.left = l; this.top = t;
  this.right = r; this.bottom = b;
}
```

参数名使用了单字母缩写（`l`、`t`、`r`、`b`），对应 left、top、right、bottom。这种简洁的命名在上下文明确时是可以接受的。

注意构造函数 **不进行任何验证**：不检查 `l ≤ r`，不检查 `t ≤ b`。这是有意为之——作者信任调用者会传入正确的值，避免在性能敏感的代码中增加不必要的检查开销。

#### 拷贝构造函数

```csharp
public IntRect(IntRect ir)
{
  this.left = ir.left; this.top = ir.top;
  this.right = ir.right; this.bottom = ir.bottom;
}
```

与 `IntPoint` 的拷贝构造函数一样，对于 `struct` 类型来说这并非必需（赋值操作自动复制），但提供拷贝构造函数使代码意图更明确。

### 2.4.4 使用场景：GetBounds 方法

`IntRect` 在 Clipper1 中最主要的使用场景是 `ClipperBase.GetBounds()` 方法，该方法计算一组多边形的总体包围盒：

```csharp
public static IntRect GetBounds(Paths paths)
{
  // 初始化为极端值
  IntRect result = new IntRect(
    /*left:*/   cInt.MaxValue,
    /*top:*/    cInt.MaxValue,
    /*right:*/  cInt.MinValue,
    /*bottom:*/ cInt.MinValue
  );

  // 遍历所有路径的所有点，更新包围盒
  foreach (Path path in paths)
    foreach (IntPoint pt in path)
    {
      if (pt.X < result.left)   result.left   = pt.X;
      if (pt.X > result.right)  result.right  = pt.X;
      if (pt.Y < result.top)    result.top    = pt.Y;
      if (pt.Y > result.bottom) result.bottom = pt.Y;
    }

  // 如果结果仍为初始极端值，说明输入为空
  if (result.left == cInt.MaxValue)
    result = new IntRect(0, 0, 0, 0);

  return result;
}
```

包围盒计算在裁剪操作前用于 **快速排除**——如果两个多边形的包围盒不重叠，则它们一定不相交，无需执行昂贵的裁剪算法。

IntRect（64 位模式）：
┌──────────┬──────────┬──────────┬──────────┐
│   left   │   top    │  right   │  bottom  │
│  8 字节   │  8 字节   │  8 字节   │  8 字节   │
└──────────┴──────────┴──────────┴──────────┘
总计：32 字节

## 2.5 DoublePoint 结构体：完整源码与逐行解析

### 2.5.1 完整源代码

```csharp
  public struct DoublePoint
  {
    public double X;
    public double Y;

    public DoublePoint(double x = 0, double y = 0)
    {
      this.X = x; this.Y = y;
    }
    public DoublePoint(DoublePoint dp)
    {
      this.X = dp.X; this.Y = dp.Y;
    }
    public DoublePoint(IntPoint ip)
    {
      this.X = (double)ip.X; this.Y = (double)ip.Y;
    }
  };
```

### 2.5.2 结构体声明与尾部分号

```csharp
public struct DoublePoint
{
  // ...
};   // ← 注意这个分号！
```

结构体定义末尾有一个 **分号**（`;`）。在 C# 中，类或结构体定义后面的分号是可选的，编译器会忽略它。但在 C/C++ 和 Delphi 中，类型定义后面的分号是 **必需的**：

```cpp
// C++ 中必须有分号
struct DoublePoint {
    double X;
    double Y;
};  // 分号是必需的！

// Delphi 中
TDoublePoint = record
    X: Double;
    Y: Double;
end;  // 分号是必需的！
```

这个尾部分号是 Clipper1 **从 Delphi/C++ 移植到 C# 时残留的痕迹**。它不影响编译或运行，但明确地揭示了这段代码的历史渊源。

### 2.5.3 字段

```csharp
public double X;
public double Y;
```

`DoublePoint` 使用 `double`（64 位 IEEE 754 双精度浮点数）而非 `cInt`。这是因为 `DoublePoint` 的用途与 `IntPoint` 不同——它用于需要浮点精度的 **中间计算**，而不是存储最终的多边形顶点。

#### 内存布局

```
DoublePoint：
┌──────────────────────┬──────────────────────┐
│       X (double)     │       Y (double)     │
│      8 字节           │      8 字节           │
└──────────────────────┴──────────────────────┘
总计：16 字节
```

与 `IntPoint`（64 位模式）相同大小，但存储的是浮点值而非整数。

### 2.5.4 构造函数逐行解析

#### 默认参数构造函数

```csharp
public DoublePoint(double x = 0, double y = 0)
{
  this.X = x; this.Y = y;
}
```

**默认参数值：**

与 `IntPoint` 不同，`DoublePoint` 的构造函数为所有参数提供了默认值。这意味着：

```csharp
new DoublePoint()       // X = 0.0, Y = 0.0  —— 原点
new DoublePoint(3.14)   // X = 3.14, Y = 0.0  —— 只指定 X
new DoublePoint(1.0, 2.0) // X = 1.0, Y = 2.0  —— 指定 X 和 Y
```

提供无参数调用的能力使得 `DoublePoint` 可以方便地初始化为原点。这在计算法线向量和偏移向量时非常有用。

注意 `IntPoint` 的标准版本 **没有** 默认参数值——你不能写 `new IntPoint()`。这是因为 C# 的 `struct` 已经有一个隐式的无参构造函数，它将所有字段初始化为默认值（对于 `cInt` 是 0）。但如果你定义了一个带参数的构造函数，C# 不会阻止你同时使用隐式无参构造函数。`DoublePoint` 通过默认参数实现了相同的效果。

#### 拷贝构造函数

```csharp
public DoublePoint(DoublePoint dp)
{
  this.X = dp.X; this.Y = dp.Y;
}
```

与 `IntPoint` 的拷贝构造函数功能完全相同——创建一个独立的副本。同样，对于 `struct` 类型来说不是严格必需的。

#### 从 IntPoint 转换的构造函数

```csharp
public DoublePoint(IntPoint ip)
{
  this.X = (double)ip.X; this.Y = (double)ip.Y;
}
```

**关键细节——宽化转换（Widening Cast）：**

`(double)ip.X` 将 `cInt`（`Int64`）转换为 `double`。这是一个 **宽化转换（widening conversion）**——目标类型能容纳源类型的所有值（几乎）。

但严格来说，这个转换 **不是完全无损的**：`Int64` 有 64 位精度，而 `double` 的尾数只有 53 位。对于绝对值超过 2⁵³（约 9.0×10¹⁵）的整数，转换到 `double` 时会丢失精度。不过在实际使用中，坐标值很少达到这个范围，所以这个转换在实践中是安全的。

与 `IntPoint` 从 `DoublePoint` 转换（窄化、截断）相比，`DoublePoint` 从 `IntPoint` 转换是安全得多的操作。

### 2.5.5 使用场景：ClipperOffset 中的法线计算

`DoublePoint` 在 Clipper1 中最主要的使用场景是 `ClipperOffset` 类，它用于计算多边形的偏移（膨胀/收缩）。偏移操作需要计算每条边的法线向量，这涉及浮点除法和三角函数：

```csharp
// ClipperOffset 中的法线计算（简化示例）
internal List<DoublePoint> m_normals = new List<DoublePoint>();

// 计算每条边的单位法线向量
for (int j = 0; j < len - 1; j++)
{
  double dx = (double)(m_srcPoly[j + 1].X - m_srcPoly[j].X);
  double dy = (double)(m_srcPoly[j + 1].Y - m_srcPoly[j].Y);
  double d = Math.Sqrt(dx * dx + dy * dy);
  // 法线向量：旋转 90 度并归一化
  m_normals.Add(new DoublePoint(dy / d, -dx / d));
}
```

在这个场景中，使用整数运算是不可行的——法线向量是单位向量，分量值在 -1.0 到 1.0 之间，必须使用浮点数。

`DoublePoint` 也用于弧线近似计算中：当偏移操作需要在角点处生成圆弧时，需要计算一系列旋转后的方向向量，这同样需要浮点精度。

## 2.7 Path 和 Paths 类型别名

### 2.7.1 定义

在 Clipper1 的源代码顶部，定义了两个重要的类型别名：

```csharp
using Path = List<IntPoint>;
using Paths = List<List<IntPoint>>;
```

#### 逐行分析

```csharp
using Path = List<IntPoint>;
```

`Path` 是 `List<IntPoint>` 的别名，表示一条 **路径（Path）**——即一系列有序的整数点。在多边形上下文中，一条路径代表一个多边形的轮廓（可以是外轮廓或孔洞轮廓）。

```csharp
using Paths = List<List<IntPoint>>;
```

`Paths` 是 `List<List<IntPoint>>` 的别名，表示 **多条路径的集合**。在实际使用中，`Paths` 可以代表一个带孔洞的多边形（外轮廓 + 多个孔洞轮廓），也可以代表多个独立的多边形。

### 2.7.2 为什么不定义自定义 Path 类？

Clipper1 选择使用 `using` 别名而非自定义类，这是一个值得深思的决策。

**使用 `using` 别名的优点：**

1. **零学习成本**：`Path` 就是一个 `List<IntPoint>`，用户已经熟悉 `List<T>` 的所有 API（`Add`、`Count`、`RemoveAt`、`[]` 索引器等），不需要学习任何新的接口。

2. **完全兼容**：`Path` 可以直接传递给任何接受 `List<IntPoint>` 的方法，也可以使用 LINQ 查询。

3. **无间接层**：没有包装类的开销，直接操作底层 `List<T>`。

**缺点：**

1. **无法添加自定义方法**：例如不能直接给 `Path` 添加 `Area()`、`IsClockwise()` 等方法（需要使用扩展方法或静态方法）。

2. **语义弱**：编译器不会区分 `Path` 和普通的 `List<IntPoint>`，无法在类型系统层面提供安全保障。

3. **作用域限制**：`using` 别名只在当前文件中有效，如果 Clipper1 是多文件项目，每个文件都需要重新声明这些别名。

在 Clipper1 的设计哲学中，**简洁和实用** 优先于 **类型安全和抽象**。这与库的"工具库"定位一致——它提供算法，不强制用户使用特定的数据结构。

### 2.7.3 使用示例

```csharp
// 创建一个三角形路径
Path triangle = new Path();
triangle.Add(new IntPoint(0, 0));
triangle.Add(new IntPoint(100, 0));
triangle.Add(new IntPoint(50, 100));

// 或使用集合初始化器
Path triangle = new Path {
  new IntPoint(0, 0),
  new IntPoint(100, 0),
  new IntPoint(50, 100)
};

// 创建一个带孔洞的多边形
Paths polygon = new Paths();
polygon.Add(outerContour);   // 外轮廓
polygon.Add(hole1);          // 孔洞 1
polygon.Add(hole2);          // 孔洞 2
```

注意 `Path` 是 **开放的**——最后一个点不需要与第一个点重复。Clipper1 会自动将路径视为闭合的（即最后一个点隐式连接到第一个点）。但对于开放路径（用于 `ClipperOffset`），最后一个点不会连接回第一个点。

## 2.8 坐标范围验证常量

### 2.8.1 loRange 和 hiRange

Clipper1 在内部定义了两个常量用于坐标范围验证：

```csharp
internal const cInt loRange = 0x3FFFFFFF;           // = 1,073,741,823
internal const cInt hiRange = 0x3FFFFFFFFFFFFFFFL;  // = 4,611,686,018,427,387,903
```

#### 详细分析

**`loRange`（低范围阈值）：**

```
0x3FFFFFFF = 2³⁰ - 1 = 1,073,741,823 ≈ 1.07 × 10⁹
```

这是一个约 10 亿的值。当坐标的绝对值在这个范围内时，两个坐标值的乘积不会超过 `Int64` 的范围。这是因为：

```
loRange² = (2³⁰ - 1)² ≈ 2⁶⁰ < 2⁶³ - 1 = Int64.MaxValue
```

**`hiRange`（高范围阈值）：**

```
0x3FFFFFFFFFFFFFFF = 2⁶² - 1 = 4,611,686,018,427,387,903 ≈ 4.6 × 10¹⁸
```

这是 `Int64.MaxValue`（2⁶³ - 1 ≈ 9.2×10¹⁸）的一半。坐标的绝对值不应超过此值，因为内部运算（特别是交点计算）中的加减法可能导致溢出。

### 2.8.2 范围检查逻辑

Clipper1 在将多边形添加到裁剪器时会进行坐标范围检查：

```csharp
private void RangeTest(IntPoint Pt, ref bool useFullRange)
{
  if (Pt.X > loRange || Pt.Y > loRange ||
      -Pt.X > loRange || -Pt.Y > loRange)
  {
    useFullRange = true;
    if (Pt.X > hiRange || Pt.Y > hiRange ||
        -Pt.X > hiRange || -Pt.Y > hiRange)
      throw new ClipperException("Coordinate outside allowed range");
  }
}
```

这个方法做了两级检查：

1. **第一级**（`loRange`）：如果坐标超过 `loRange`，设置 `useFullRange = true`，切换到 128 位中间计算模式（使用 `Int128` 辅助类）来避免 64 位乘法溢出。
2. **第二级**（`hiRange`）：如果坐标超过 `hiRange`，直接抛出异常——这些值即使使用 128 位运算也可能导致问题。

这种两级范围检查是一个精巧的设计：
- 对于大多数应用，坐标在 `loRange` 范围内，所有运算都用 64 位整数完成，性能最佳。
- 对于需要更大坐标范围的应用，自动切换到 128 位模式，保证正确性。
- 对于超出安全范围的坐标，立即报错，而不是默默产生错误结果。

### 2.8.3 坐标范围与缩放因子的关系

| 缩放因子 | 有效坐标范围（loRange 内） | 有效坐标范围（hiRange 内） |
|----------|---------------------------|---------------------------|
| 1 | ±1.07×10⁹ | ±4.6×10¹⁸ |
| 10³ | ±1.07×10⁶ | ±4.6×10¹⁵ |
| 10⁶ | ±1.07×10³ | ±4.6×10¹² |
| 10⁹ | ±1.07 | ±4.6×10⁹ |

如表所示，缩放因子越大，精度越高，但坐标范围越小。在选择缩放因子时需要权衡精度和范围。

## 2.9 性能考量：结构体与大规模几何数据

### 2.9.1 值类型的内存连续性

当 `IntPoint` 存储在 `List<IntPoint>`（即 `Path`）中时，由于它是值类型，所有点数据在内存中是 **连续排列** 的：

```
List<IntPoint> 内部数组（64 位模式，无 Z）：
┌────────────┬────────────┬────────────┬────────────┬─── ···
│ X₀ │ Y₀ │ X₁ │ Y₁ │ X₂ │ Y₂ │ X₃ │ Y₃ │
│ 8B │ 8B │ 8B │ 8B │ 8B │ 8B │ 8B │ 8B │
└────────────┴────────────┴────────────┴────────────┴─── ···
```

如果 `IntPoint` 是 `class`（引用类型），则 `List<IntPoint>` 只存储引用（指针），实际的点数据分散在堆的各处：

```
List<IntPoint>（如果是 class）：
┌────┬────┬────┬────┬─── ···     堆上分散的对象：
│ → │ → │ → │ → │             [IntPoint₀] [IntPoint₂]
└──┼─┴──┼─┴──┼─┴──┼─             [IntPoint₁]
   │    │    │    │           [IntPoint₃]
   └────┘    └────┘
   （指向堆上不同位置的引用）
```

连续内存布局带来以下性能优势：

1. **CPU 缓存友好**：现代 CPU 的缓存行（cache line）通常为 64 字节。一个缓存行可以容纳 4 个 `IntPoint`（16 字节/个）。遍历点列表时，缓存命中率极高。
2. **预取器高效**：CPU 的硬件预取器擅长检测连续访问模式，可以提前将数据加载到缓存。
3. **无间接跳转**：不需要通过引用查找实际数据，避免了指针追踪（pointer chasing）导致的缓存未命中。

### 2.9.2 装箱成本

虽然 `struct` 在大多数场景下性能更好，但在某些情况下会触发 **装箱（boxing）**——将值类型包装为引用类型：

```csharp
// 触发装箱的操作
object obj = new IntPoint(10, 20);        // 装箱
IntPoint pt = (IntPoint)obj;               // 拆箱

// 调用 Equals(object) 也会导致参数装箱
bool eq = pt1.Equals((object)pt2);        // pt2 被装箱
```

装箱会在堆上分配一个新对象，并将值复制到其中。拆箱则从堆对象中将值复制回来。这两个操作都有性能开销。

在 Clipper1 的内部实现中，作者非常小心地避免了不必要的装箱操作——使用 `==` 运算符而非 `Equals` 来比较点，使用泛型集合（`List<IntPoint>`）而非非泛型集合（`ArrayList`）。

### 2.9.3 大规模数据的内存估算

对于一个包含 100 万个顶点的多边形（这在 GIS 和 CAD 应用中并不罕见）：

| 模式 | 每点大小 | 总内存（约） |
|------|----------|-------------|
| 64 位，无 Z | 16 字节 | 15.3 MB |
| 64 位，有 Z | 24 字节 | 22.9 MB |
| 32 位，无 Z | 8 字节 | 7.6 MB |

如果 `IntPoint` 是 `class`，每个点还需要额外的对象头（16 字节，在 64 位平台上）和引用（8 字节），总开销约为：

| 模式 | 每点大小（含对象头和引用） | 总内存（约） |
|------|---------------------------|-------------|
| 64 位，无 Z | 16 + 16 + 8 = 40 字节 | 38.1 MB |

使用 `struct` 节省了约 60% 的内存，这在大规模数据处理中意义重大。

## 2.10 已知问题与改进建议

在深入理解这些基础数据结构后，我们可以列出一些已知的不完美之处和可能的改进方向。这并非对作者的批评——Clipper1 是一个久经考验的优秀库——而是为了帮助读者理解设计权衡。

### 2.10.1 GetHashCode 的实现

如前所述，`IntPoint.GetHashCode()` 直接调用 `base.GetHashCode()`，对于值类型来说这不是最优的实现。如果需要将 `IntPoint` 用于字典键或哈希集合，建议外部实现一个 `IEqualityComparer<IntPoint>`：

```csharp
public class IntPointComparer : IEqualityComparer<IntPoint>
{
  public bool Equals(IntPoint a, IntPoint b)
  {
    return a.X == b.X && a.Y == b.Y;
  }

  public int GetHashCode(IntPoint pt)
  {
    unchecked
    {
      int hash = 17;
      hash = hash * 31 + pt.X.GetHashCode();
      hash = hash * 31 + pt.Y.GetHashCode();
      return hash;
    }
  }
}

// 使用自定义比较器
var pointSet = new HashSet<IntPoint>(new IntPointComparer());
```

### 2.10.2 缺少 IEquatable 接口

`IntPoint` 没有实现 `IEquatable<IntPoint>` 接口。实现它可以避免 `Equals` 调用时的装箱开销：

```csharp
public struct IntPoint : IEquatable<IntPoint>
{
  // ...
  public bool Equals(IntPoint other)
  {
    return X == other.X && Y == other.Y;
  }
}
```

### 2.10.3 DoublePoint 缺少运算符重载

`DoublePoint` 没有 `==` 和 `!=` 运算符，也没有重写 `Equals` 和 `GetHashCode`。在实际使用中，`DoublePoint` 主要用于临时计算，很少需要比较，所以这不是一个严重的问题。但如果需要比较两个 `DoublePoint`，用户需要手动逐字段比较。

### 2.10.4 浮点截断而非四舍五入

`IntPoint` 的 `double` 参数构造函数使用截断转换（`(cInt)x`）而非四舍五入。这可能导致系统性偏差——所有值都向零靠近。在实际使用中，建议用户在外部进行四舍五入后再传入整数值。

## 2.11 本章小结

本章深入解析了 Clipper1 中三个最基础的数据结构：`IntPoint`、`IntRect` 和 `DoublePoint`。通过对每一行源代码的详细分析，我们理解了以下核心概念：

1. **整数坐标的设计哲学**：使用整数而非浮点数，消除了 epsilon 比较、累积误差和排序不稳定性等一系列问题。缩放因子模式允许用户在整数域中处理实数坐标。

2. **条件编译的灵活性**：通过 `use_xyz` 和 `use_int32` 编译开关，同一份源代码可以适配不同的使用场景，实现了真正的零成本抽象。

3. **值类型的性能优势**：所有三个类型都是 `struct`，在大规模几何数据处理中提供了显著的内存节省和缓存友好性。

4. **Delphi 遗产的印记**：从字段命名风格到尾部分号，Clipper1 的 C# 版本处处可见其 Delphi/Object Pascal 起源。

5. **实用主义的设计决策**：相等运算符只比较 X/Y 不比较 Z、不实现 `IEquatable<T>`、使用 `using` 别名而非自定义类型——这些决策都体现了"够用就好"的工程哲学。

在下一章中，我们将深入 Clipper1 的核心内部数据结构——`TEdge`（边）、`LocalMinimum`（局部最小值）和 `Scanbeam`（扫描束），它们构成了 Vatti 扫描线算法的基础骨架。
