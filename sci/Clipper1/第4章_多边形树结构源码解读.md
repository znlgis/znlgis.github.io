# 第4章：多边形树结构（PolyNode 与 PolyTree）源码解读

## 4.1 引言

在前面的章节中，我们分析了 Clipper1 的基础数据结构 `IntPoint`、`IntRect`、`DoublePoint`，以及 128 位整数运算 `Int128`。这些数据结构构成了 Clipper 几何计算的数值基础。然而，当我们对多边形执行布尔运算（Union、Intersection、Difference、Xor）之后，得到的结果往往不只是一组简单的多边形坐标——结果中可能包含**嵌套的多边形层次关系**。

考虑一个常见的场景：一个大矩形内部有一个圆形的孔洞（hole），而这个孔洞内部又有一个小方块（岛屿/island）。这种"外轮廓 → 孔洞 → 岛屿 → 孔洞 → ..."的嵌套关系，在计算机图形学中称为**多边形层次结构（Polygon Hierarchy）**。

Clipper 库提供了两种方式来输出布尔运算的结果：

1. **`Paths`（平面列表）**：简单的多边形列表，不包含任何层次信息。
2. **`PolyTree`（多边形树）**：保留完整的父子嵌套关系，能够区分外轮廓与孔洞。

本章将深入剖析 `PolyNode` 和 `PolyTree` 这两个类的源码，它们共同实现了 Clipper 的多边形树结构。我们将逐字段、逐方法地分析每一行代码的设计意图和实现细节。

## 4.2 多边形层次结构的概念模型

### 4.2.1 什么是多边形层次结构？

在二维平面上，多边形之间可能存在**包含关系（containment relationship）**。例如：

- 一个大矩形**包含**一个小圆形 → 小圆形是大矩形的"孔洞"
- 孔洞内部又**包含**一个小三角形 → 小三角形是"岛屿"（被孔洞包围的实心区域）
- 岛屿内部又可以有更深层的孔洞……

这种嵌套关系形成了一棵**树（Tree）**。在 Clipper 中，这棵树的组织规则如下：

| 深度（Depth） | 节点类型 | 含义 |
|:---:|:---:|:---|
| 0 | 根节点（PolyTree 自身） | 虚拟根节点，不包含实际多边形数据 |
| 1 | 外轮廓（Outer Contour） | 最外层的实心多边形 |
| 2 | 孔洞（Hole） | 外轮廓内的空洞区域 |
| 3 | 岛屿（Island） | 孔洞内的实心区域 |
| 4 | 孔洞中的孔洞 | 岛屿内的空洞区域 |
| ... | ... | 以此类推，无限嵌套 |

### 4.2.2 奇偶深度规则（Even-Odd Depth Rule）

Clipper 使用一个简洁的规则来判断一个节点是外轮廓还是孔洞：

- **奇数深度（Odd Depth）**的节点是**外轮廓**（实心区域）
- **偶数深度（Even Depth）**的节点是**孔洞**（空洞区域）

> **注意**：这里的"深度"是从根节点开始计算的。根节点 PolyTree 本身处于深度 0，它是一个虚拟节点，不包含多边形数据。根节点的直接子节点处于深度 1（奇数），因此它们是外轮廓。

为什么是这样？因为根节点（PolyTree）代表的是"整个平面"——一个无限大的"外部空间"。从外部空间进入第一层多边形，就是进入了实心区域（外轮廓）；再进入一层就是进入了空洞区域（孔洞）；再进入一层又回到实心区域（岛屿）……如此交替。

### 4.2.3 树结构可视化示例

下面用 ASCII 艺术图展示一个典型的多边形层次结构：

```
PolyTree (根节点, depth 0, 虚拟节点, 无多边形数据)
├── Outer Polygon A (depth 1, 外轮廓, 非孔洞)
│   ├── Hole 1 in A (depth 2, 孔洞)
│   │   └── Island in Hole 1 (depth 3, 岛屿, 非孔洞)
│   └── Hole 2 in A (depth 2, 孔洞)
└── Outer Polygon B (depth 1, 外轮廓, 非孔洞)
```

对应的几何示意图如下：

```
+=========================================+
|                                         |
|   Outer Polygon A                       |
|                                         |
|   +---------------------------+         |
|   |                           |         |
|   |   Hole 1 in A             |         |
|   |                           |         |
|   |   +-----------+           |         |
|   |   |           |           |         |
|   |   | Island    |           |         |
|   |   |           |           |         |
|   |   +-----------+           |         |
|   |                           |         |
|   +---------------------------+         |
|                                         |

|   |             |                       |

              +==============+
```

在这个例子中：
- **Outer Polygon A** 是一个外轮廓，包含两个孔洞
- **Hole 1** 内部有一个岛屿（**Island**），说明孔洞里面又有实心区域
- **Hole 2** 内部没有嵌套内容
- **Outer Polygon B** 是另一个独立的外轮廓，与 A 平级

## 4.3 PolyNode 完整源码

下面是 `PolyNode` 类的完整源码（来自 ClipperLib 6.4.2 版本的 `clipper.cs` 文件）：

```csharp
  public class PolyNode
  {
      internal PolyNode m_Parent;
      internal Path m_polygon = new Path();
      internal int m_Index;
      internal JoinType m_jointype;
      internal EndType m_endtype;
      internal List<PolyNode> m_Childs = new List<PolyNode>();

      private bool IsHoleNode()
      {
          bool result = true;
          PolyNode node = m_Parent;
          while (node != null)
          {
              result = !result;
              node = node.m_Parent;
          }
          return result;
      }

      public int ChildCount
      {
          get { return m_Childs.Count; }
      }

      public Path Contour
      {
          get { return m_polygon; }
      }

      internal void AddChild(PolyNode Child)
      {
          int cnt = m_Childs.Count;
          m_Childs.Add(Child);
          Child.m_Parent = this;
          Child.m_Index = cnt;
      }

      public PolyNode GetNext()
      {
          if (m_Childs.Count > 0)
              return m_Childs[0];
          else
              return GetNextSiblingUp();
      }

      internal PolyNode GetNextSiblingUp()
      {
          if (m_Parent == null)
              return null;
          else if (m_Index == m_Parent.m_Childs.Count - 1)
              return m_Parent.GetNextSiblingUp();
          else
              return m_Parent.m_Childs[m_Index + 1];
      }

      public List<PolyNode> Childs
      {
          get { return m_Childs; }
      }

      public PolyNode Parent
      {
          get { return m_Parent; }
      }

      public bool IsHole
      {
          get { return IsHoleNode(); }
      }

      public bool IsOpen { get; set; }
  }
```

## 4.4 PolyNode 字段逐一解析

### 4.4.1 m_Parent —— 父节点引用

```csharp
internal PolyNode m_Parent;
```

**作用**：指向当前节点的父节点。

- 对于 PolyTree 根节点，`m_Parent` 为 `null`。
- 对于根节点的直接子节点（外轮廓），`m_Parent` 指向 PolyTree 根节点。
- 对于孔洞节点，`m_Parent` 指向包含它的外轮廓节点。
- 对于岛屿节点，`m_Parent` 指向包含它的孔洞节点。

**访问修饰符为 `internal`**：这意味着 `m_Parent` 只能在 ClipperLib 程序集内部访问。外部用户需要通过公开的 `Parent` 属性来读取父节点。这种设计有两个目的：

1. **封装性**：防止外部代码直接修改父子关系，避免破坏树结构的一致性。
2. **灵活性**：Clipper 库内部的代码（如 `Clipper.Execute()` 和 `ClipperOffset`）需要直接设置 `m_Parent`，因此不能是 `private`。

`m_Parent` 字段没有在声明时初始化（默认值为 `null`），这是因为父节点关系是在 `AddChild()` 方法调用时动态建立的。

### 4.4.2 m_polygon —— 多边形轮廓数据

```csharp
internal Path m_polygon = new Path();
```

**作用**：存储当前节点所代表的多边形的顶点序列。

- `Path` 是 `List<IntPoint>` 的类型别名（`using Path = List<IntPoint>;`）。
- 每个 `IntPoint` 包含 `X` 和 `Y` 两个 `cInt`（即 `Int64`）坐标。
- 对于 PolyTree 根节点，`m_polygon` 为空列表（根节点不代表任何实际的多边形）。
- 对于外轮廓节点，`m_polygon` 包含外轮廓的顶点序列。
- 对于孔洞节点，`m_polygon` 包含孔洞的顶点序列。

**初始化为 `new Path()`**：在声明时就创建了一个空的 `Path` 对象。这意味着 `m_polygon` 永远不为 `null`，后续代码可以直接向其中添加顶点而无需先做空检查。这是一种常见的防御性编程实践。

**通过公开属性 `Contour` 暴露**：外部用户通过 `Contour` 属性读取多边形数据。属性名使用 `Contour`（轮廓）而非 `Polygon`，更准确地描述了其含义——每个节点存储的是一个"轮廓"，整个多边形的完整表示需要结合其所有子孔洞。

### 4.4.3 m_Index —— 在父节点子列表中的索引

```csharp
internal int m_Index;
```

**作用**：记录当前节点在其父节点的 `m_Childs` 列表中的位置索引。

这个字段是 `PolyNode` 中最精巧的设计之一。它的存在使得**兄弟节点的查找**变为 O(1) 操作。在 `GetNextSiblingUp()` 方法中，代码通过 `m_Parent.m_Childs[m_Index + 1]` 直接定位下一个兄弟节点，而不需要遍历父节点的子列表来查找当前节点的位置。

如果没有 `m_Index`，查找下一个兄弟节点需要：
1. 先在 `m_Parent.m_Childs` 中线性搜索当前节点（O(n)）
2. 然后取下一个元素

有了 `m_Index`，直接通过索引访问即可（O(1)）。这对于大规模多边形层次结构的遍历性能至关重要。

**`m_Index` 在 `AddChild()` 中被设置**：`Child.m_Index = cnt;`，其中 `cnt` 是添加前的子节点数量，恰好等于新节点在列表中的索引。

### 4.4.4 m_jointype 和 m_endtype —— ClipperOffset 专用字段

```csharp
internal JoinType m_jointype;
internal EndType m_endtype;
```

**作用**：这两个字段**不是**用于多边形布尔运算（`Clipper.Execute()`）的，而是用于 `ClipperOffset` 类的偏移运算。

- `JoinType` 枚举定义了偏移时拐角的连接方式：`jtSquare`（方角）、`jtRound`（圆角）、`jtMiter`（尖角）。
- `EndType` 枚举定义了开放路径端点的处理方式：`etClosedPolygon`（闭合多边形）、`etClosedLine`（闭合线段）、`etOpenSquare`（开放方角）、`etOpenRound`（开放圆角）、`etOpenButt`（开放平头）。

将这两个字段放在 `PolyNode` 中是一种实用主义的设计——`ClipperOffset` 在内部使用 `PolyNode` 树来组织偏移运算的输入数据，需要为每个节点存储连接类型和端点类型。虽然这两个字段对于纯布尔运算是多余的，但它们的内存开销很小（两个 `int` 值），不会对性能产生显著影响。

### 4.4.5 m_Childs —— 子节点列表

```csharp
internal List<PolyNode> m_Childs = new List<PolyNode>();
```

**作用**：存储当前节点的所有直接子节点。

- 对于根节点（PolyTree），`m_Childs` 包含所有最外层的外轮廓多边形。
- 对于外轮廓节点，`m_Childs` 包含其内部的所有孔洞。
- 对于孔洞节点，`m_Childs` 包含孔洞内部的所有岛屿。

**初始化为 `new List<PolyNode>()`**：与 `m_polygon` 一样，在声明时即创建空列表，保证永远不为 `null`。

**使用 `List<PolyNode>` 而非数组**：因为在构建树结构时，子节点的数量是动态增长的，`List<T>` 提供了高效的动态添加能力。

### 4.4.6 字段可见性总结

| 字段 | 可见性 | 对外暴露方式 | 原因 |
|:---|:---:|:---|:---|
| `m_Parent` | `internal` | `Parent` 属性（只读） | Clipper 内部需要直接写入 |
| `m_polygon` | `internal` | `Contour` 属性（只读） | Clipper 内部需要直接操作顶点列表 |
| `m_Index` | `internal` | 无 | 纯内部实现细节 |
| `m_jointype` | `internal` | 无 | ClipperOffset 专用 |
| `m_endtype` | `internal` | 无 | ClipperOffset 专用 |
| `m_Childs` | `internal` | `Childs` 属性 + `ChildCount` | Clipper 内部需要直接操作子列表 |

## 4.5 IsHoleNode() 算法深度解析

### 4.5.1 源码回顾

```csharp
private bool IsHoleNode()
{
    bool result = true;
    PolyNode node = m_Parent;
    while (node != null)
    {
        result = !result;
        node = node.m_Parent;
    }
    return result;
}
```

### 4.5.2 算法原理

`IsHoleNode()` 方法用于判断当前节点是否代表一个"孔洞"。它的核心思想是：**从当前节点沿 `m_Parent` 链向上遍历到根节点，统计经过的层数，然后根据奇偶性判断是否为孔洞**。

但是这段代码写得非常巧妙——它并没有显式地计算深度再做奇偶判断，而是使用一个布尔变量 `result`，在每经过一层时做一次取反（`!result`）。这本质上等价于对深度做奇偶判断，但代码更简洁。

### 4.5.3 逐步执行分析

让我们用 4.2.3 节中的示例层次结构来逐步分析。假设我们要判断 **"Hole 1 in A"**（深度 2）是否为孔洞：

```
调用链：Hole 1 → Outer Polygon A → PolyTree (root)
```

**第一步：初始化**
```
result = true
node = m_Parent  → 指向 "Outer Polygon A"
```

**第二步：第一次循环（node = "Outer Polygon A"，非 null）**
```
result = !result = !true = false
node = node.m_Parent  → 指向 "PolyTree (root)"
```

**第三步：第二次循环（node = "PolyTree (root)"，非 null）**
```
result = !result = !false = true
node = node.m_Parent  → null（根节点的 m_Parent 为 null）
```

**第四步：循环结束（node == null）**
```
return result  → return true  → "Hole 1 in A" 是一个孔洞 ✓
```

现在让我们验证 **"Outer Polygon A"**（深度 1）：

```
调用链：Outer Polygon A → PolyTree (root)
```

**第一步：初始化**
```
result = true
node = m_Parent  → 指向 "PolyTree (root)"
```

**第二步：第一次循环（node = "PolyTree (root)"，非 null）**
```
result = !result = !true = false
node = node.m_Parent  → null
```

**第三步：循环结束**
```
return result  → return false  → "Outer Polygon A" 不是孔洞 ✓
```

再验证 **"Island in Hole 1"**（深度 3）：

```
调用链：Island → Hole 1 → Outer Polygon A → PolyTree (root)
```

| 步骤 | node 指向 | result 变化 |
|:---:|:---|:---:|
| 初始化 | m_Parent = "Hole 1" | `true` |
| 循环 1 | "Hole 1" → 向上移动 | `!true = false` |
| 循环 2 | "Outer Polygon A" → 向上移动 | `!false = true` |
| 循环 3 | "PolyTree (root)" → 向上移动 | `!true = false` |
| 循环结束 | node = null | 返回 `false` |

结果：`false` → "Island in Hole 1" **不是**孔洞 ✓（它是一个岛屿，即实心区域）

### 4.5.4 数学本质

设从当前节点到根节点（不含当前节点自身）的路径长度为 `L`（即经过的边数，等于遍历经过的节点数）。

- 初始值 `result = true`
- 每次取反相当于乘以 `-1`
- 经过 `L` 次取反后：`result = true` 当且仅当 `L` 为偶数

对于深度为 `d` 的节点（根节点深度为 0）：
- 从该节点的 `m_Parent` 开始遍历，到根节点经过 `d` 个节点（包括根节点）
- 因此 `L = d`（循环执行 `d` 次）

| 深度 d | 循环次数 L | result | IsHole |
|:---:|:---:|:---:|:---:|
| 0 | 0 | true（未翻转） | true（根节点，但根节点不会被查询） |
| 1 | 1 | false | false → 外轮廓 |
| 2 | 2 | true | true → 孔洞 |
| 3 | 3 | false | false → 岛屿 |
| 4 | 4 | true | true → 孔洞 |

**规律**：偶数深度 → `IsHole = true`；奇数深度 → `IsHole = false`。

> **注意**：根节点（PolyTree，深度 0）在逻辑上不代表任何多边形，不会被查询 `IsHole`。其子节点（深度 1）为外轮廓——对应 `IsHole = false`，完全符合预期。

### 4.5.5 时间复杂度

`IsHoleNode()` 的时间复杂度为 **O(d)**，其中 `d` 是节点的深度。在实践中，多边形的嵌套层次很少超过 5-6 层，因此这个方法的性能开销可以忽略不计。

值得注意的是，`IsHole` 不是一个缓存值，而是每次访问时重新计算的。如果需要频繁查询同一节点的 `IsHole` 状态，建议在应用层面做缓存。

### 4.5.6 为什么 IsHoleNode 是 private 而 IsHole 是 public？

```csharp
private bool IsHoleNode()
{
    // ... 实现
}

public bool IsHole
{
    get { return IsHoleNode(); }
}
```

这是一种常见的 C# 设计模式——将实现逻辑封装在 `private` 方法中，通过 `public` 属性对外暴露。这样做的好处是：

1. **接口清晰**：外部用户看到的是一个简洁的 `IsHole` 属性，符合 C# 的属性命名惯例。
2. **实现可替换**：如果将来需要更改判断逻辑（例如改为缓存结果），只需修改 `IsHoleNode()` 的实现，不影响公开接口。
3. **命名语义**：方法名 `IsHoleNode()` 强调"这是一个计算过程"；属性名 `IsHole` 强调"这是节点的一个特征"。

## 4.6 深度优先遍历：GetNext() 与 GetNextSiblingUp()

### 4.6.1 GetNext() 源码解析

```csharp
public PolyNode GetNext()
{
    if (m_Childs.Count > 0)
        return m_Childs[0];
    else
        return GetNextSiblingUp();
}
```

`GetNext()` 实现了**前序深度优先遍历（Pre-order DFS）**的"下一个节点"逻辑：

1. **如果当前节点有子节点**：返回第一个子节点 `m_Childs[0]`。这是深度优先遍历的核心——优先深入子树。
2. **如果当前节点没有子节点**（叶子节点）：调用 `GetNextSiblingUp()` 查找下一个兄弟节点或祖先的兄弟节点。

### 4.6.2 GetNextSiblingUp() 源码解析

```csharp
internal PolyNode GetNextSiblingUp()
{
    if (m_Parent == null)
        return null;
    else if (m_Index == m_Parent.m_Childs.Count - 1)
        return m_Parent.GetNextSiblingUp();
    else
        return m_Parent.m_Childs[m_Index + 1];
}
```

`GetNextSiblingUp()` 是一个**递归方法**，沿着父链向上查找下一个未访问的节点：

**情况 1：`m_Parent == null`**
当前节点是根节点。根节点没有兄弟节点，返回 `null`，表示遍历结束。

**情况 2：`m_Index == m_Parent.m_Childs.Count - 1`**
当前节点是其父节点的**最后一个子节点**（`m_Index` 等于父节点子列表的最后一个有效索引）。这意味着当前层级没有更多兄弟节点了。此时，**递归调用父节点的 `GetNextSiblingUp()`**，继续向上层查找。

**情况 3：其他情况**
当前节点不是最后一个子节点。直接返回下一个兄弟节点 `m_Parent.m_Childs[m_Index + 1]`。

这里就体现了 `m_Index` 字段的价值——通过 `m_Index + 1` 直接计算出下一个兄弟节点的索引，无需遍历查找。

### 4.6.3 遍历过程完整示例

让我们用 4.2.3 节的层次结构来演示完整的遍历过程。为了方便，我们给每个节点编号：

```
PolyTree (root, #0)
├── Outer A (#1)
│   ├── Hole 1 (#2)
│   │   └── Island (#3)
│   └── Hole 2 (#4)
└── Outer B (#5)
```

假设我们从 PolyTree 的 `GetFirst()` 方法开始遍历（`GetFirst()` 返回第一个子节点），遍历代码如下：

```csharp
PolyNode node = polyTree.GetFirst();  // 从第一个子节点开始
while (node != null)
{
    // 处理 node
    Console.WriteLine(node);
    node = node.GetNext();
}
```

**逐步执行**：

| 步骤 | 当前节点 | 动作 | GetNext() 逻辑 | 返回的下一节点 |
|:---:|:---:|:---|:---|:---:|
| 1 | #1 Outer A | 有子节点 → 返回第一个子 | `m_Childs[0]` = #2 | #2 |
| 2 | #2 Hole 1 | 有子节点 → 返回第一个子 | `m_Childs[0]` = #3 | #3 |
| 3 | #3 Island | 无子节点 → 调用 GetNextSiblingUp() | #3 是 #2 的唯一子 → 向上；#2 不是 #1 的最后子 → `m_Parent.m_Childs[m_Index + 1]` | #4 |
| 4 | #4 Hole 2 | 无子节点 → 调用 GetNextSiblingUp() | #4 是 #1 的最后子 → 向上；#1 不是 root 的最后子 → `m_Parent.m_Childs[m_Index + 1]` | #5 |
| 5 | #5 Outer B | 无子节点 → 调用 GetNextSiblingUp() | #5 是 root 的最后子 → 向上；root 的 m_Parent 为 null → return null | null |
| 6 | null | 遍历结束 | — | — |

**遍历顺序**：#1 → #2 → #3 → #4 → #5

这正是**前序深度优先遍历**的顺序——先访问节点自身，然后递归访问其子树。

### 4.6.4 GetNextSiblingUp 的递归展开

让我们详细展开步骤 3 中 `#3 Island` 调用 `GetNextSiblingUp()` 的过程：

```
#3.GetNextSiblingUp():
  m_Parent = #2 (Hole 1)  → 非 null
  m_Index = 0
  m_Parent.m_Childs.Count - 1 = 0  (#2 只有一个子节点)
  m_Index == m_Parent.m_Childs.Count - 1  → true
  → 递归调用 #2.GetNextSiblingUp()

  #2.GetNextSiblingUp():
    m_Parent = #1 (Outer A)  → 非 null
    m_Index = 0
    m_Parent.m_Childs.Count - 1 = 1  (#1 有两个子节点)
    m_Index (0) != m_Parent.m_Childs.Count - 1 (1)  → false
    → 返回 m_Parent.m_Childs[m_Index + 1] = #1.m_Childs[1] = #4 (Hole 2)

→ 最终返回 #4
```

可以看到，递归在找到一个有可用兄弟节点的祖先时停止。

### 4.6.5 为什么不用栈来实现遍历？

深度优先遍历通常需要一个**显式的栈（Stack）**或**递归调用栈**来记录回溯路径。但 `PolyNode` 的遍历不需要额外的栈，因为：

1. **`m_Parent` 指针**提供了从任意节点向上回溯的能力。
2. **`m_Index` 字段**提供了高效的兄弟节点定位。

这种设计的优势是：
- **无额外内存开销**：遍历不需要分配栈或队列。
- **无状态**：每次调用 `GetNext()` 都是独立的，不需要维护迭代器状态。
- **可中断**：可以在遍历过程中随时停止，不需要清理栈。

缺点是：
- **`GetNextSiblingUp()` 最坏情况为 O(d)**：如果当前节点处于树的最深处且是每一层的最后一个子节点，需要递归回溯整棵树的深度。但如前所述，实际的多边形嵌套深度很少超过几层。

## 4.7 AddChild() 方法解析

```csharp
internal void AddChild(PolyNode Child)
{
    int cnt = m_Childs.Count;
    m_Childs.Add(Child);
    Child.m_Parent = this;
    Child.m_Index = cnt;
}
```

`AddChild()` 是构建树结构的核心方法。让我们逐行分析：

### 第 1 行：`int cnt = m_Childs.Count;`

在添加新子节点**之前**，先记录当前子节点的数量。这个值将作为新节点的索引。例如，如果当前有 3 个子节点（索引 0、1、2），那么新添加的子节点应该获得索引 3。

### 第 2 行：`m_Childs.Add(Child);`

将子节点添加到子列表的末尾。`List<T>.Add()` 的平均时间复杂度为 O(1)（当列表不需要扩容时），最坏情况为 O(n)（需要扩容时拷贝整个数组）。

### 第 3 行：`Child.m_Parent = this;`

建立从子节点到父节点的反向引用。`this` 指向当前节点（即调用 `AddChild` 的节点）。这条语句建立了**父子双向关系**中的"子 → 父"方向。

### 第 4 行：`Child.m_Index = cnt;`

设置子节点在父节点子列表中的索引。前面已经记录了 `cnt = m_Childs.Count`（添加前的数量），这恰好是新节点在列表中的位置（0-based 索引）。

### 设计要点

1. **双向关系管理**：`AddChild()` 同时维护了两个方向的关系——父节点的 `m_Childs` 列表和子节点的 `m_Parent` 引用。这确保了树结构的一致性。

2. **索引预计算**：`m_Index` 在添加时就确定了，后续不需要更新。但这也意味着**一旦子节点被添加后，就不能随意删除或重新排序子列表中的其他节点**，否则 `m_Index` 会失效。在 Clipper 的使用场景中，树结构是在布尔运算完成后一次性构建的，不需要动态修改，所以这个限制是可以接受的。

3. **`internal` 访问修饰符**：`AddChild()` 不是公开方法。只有 Clipper 库内部的代码（如 `Clipper.BuildResult2()` 和 `ClipperOffset`）才能调用它来构建树结构。外部用户只能读取已构建好的树，不能修改它。

## 4.8 公开属性详解

### 4.8.1 ChildCount 属性

```csharp
public int ChildCount
{
    get { return m_Childs.Count; }
}
```

返回当前节点的直接子节点数量。这是一个便捷的只读属性，等价于 `Childs.Count`，但语义更明确。`List<T>.Count` 的时间复杂度为 O(1)，因为 `List<T>` 内部维护了一个计数器。

### 4.8.2 Contour 属性

```csharp
public Path Contour
{
    get { return m_polygon; }
}
```

返回当前节点的多边形轮廓数据。注意：返回的是对内部 `m_polygon` 列表的**直接引用**，而非拷贝。这意味着外部代码可以修改返回的 `Path` 中的顶点（例如 `node.Contour.Add(new IntPoint(x, y))`）。这是一种性能优先的设计——避免了不必要的内存拷贝。

### 4.8.3 Childs 属性

```csharp
public List<PolyNode> Childs
{
    get { return m_Childs; }
}
```

返回当前节点的直接子节点列表的引用。与 `Contour` 一样，返回的是直接引用而非拷贝。

### 4.8.4 Parent 属性

```csharp
public PolyNode Parent
{
    get { return m_Parent; }
}
```

返回当前节点的父节点。对于 PolyTree 根节点，返回 `null`。

### 4.8.5 IsHole 属性

```csharp
public bool IsHole
{
    get { return IsHoleNode(); }
}
```

判断当前节点是否为孔洞。每次访问都会重新计算（调用 `IsHoleNode()` 方法）。详见 4.5 节的深度解析。

### 4.8.6 IsOpen 属性

```csharp
public bool IsOpen { get; set; }
```

这是一个自动属性（auto-property），具有公开的 getter 和 setter。

**作用**：标记当前节点是否代表一条**开放路径（Open Path）**。

在 Clipper 中，路径分为两种：
- **闭合路径（Closed Path）**：首尾相连形成封闭的多边形。大多数路径属于此类。
- **开放路径（Open Path）**：首尾不相连的折线。在布尔运算中，开放路径只能作为"主体"（Subject），不能作为"裁剪器"（Clip）。

当 `IsOpen = true` 时，该节点代表的是一条开放路径，而非封闭多边形。此时 `IsHole` 属性的返回值没有实际意义（开放路径不存在"孔洞"的概念）。

## 4.9 PolyTree 完整源码

`PolyTree` 继承自 `PolyNode`，作为多边形树的根节点。以下是完整源码：

```csharp
  public class PolyTree : PolyNode
  {
      internal List<PolyNode> m_AllPolys = new List<PolyNode>();

      public void Clear()
      {
          for (int i = 0; i < m_AllPolys.Count; i++)
              m_AllPolys[i] = null;
          m_AllPolys.Clear();
          m_Childs.Clear();
      }

      public PolyNode GetFirst()
      {
          if (m_Childs.Count > 0)
              return m_Childs[0];
          else
              return null;
      }

      public int Total
      {
          get
          {
            int result = m_AllPolys.Count;
            if (result > 0 && m_Childs[0] != m_AllPolys[0]) result--;
            return result;
          }
      }

  }
```

## 4.10 PolyTree 类深度解析

### 4.10.1 继承关系

```csharp
public class PolyTree : PolyNode
```

`PolyTree` 继承自 `PolyNode`。这意味着 `PolyTree` **本身就是树中的一个节点**——根节点。它拥有 `PolyNode` 的所有字段和方法，包括 `m_Childs`（存储顶层外轮廓多边形）、`m_polygon`（对于根节点为空）、`GetNext()` 等。

这种设计使得根节点和普通节点有统一的接口，简化了树的遍历和处理逻辑。

### 4.10.2 m_AllPolys —— 所有多边形节点的平面列表

```csharp
internal List<PolyNode> m_AllPolys = new List<PolyNode>();
```

**作用**：维护一个包含树中**所有** `PolyNode` 节点的平面列表（不包括根节点自身）。

这个列表的存在有几个关键目的：

1. **内存管理**：`Clear()` 方法通过遍历 `m_AllPolys` 来释放所有节点的引用。
2. **快速计数**：`Total` 属性通过 `m_AllPolys.Count` 直接获取多边形总数，无需遍历整棵树。
3. **节点注册**：Clipper 在执行布尔运算时（`BuildResult2()` 方法），每创建一个新的 `PolyNode` 就将其添加到 `m_AllPolys` 中。这确保了所有节点都被追踪。

**何时添加节点**？在 `Clipper.BuildResult2()` 方法中，Clipper 遍历其内部的 `OutRec`（输出记录）列表，为每个有效的输出多边形创建一个 `PolyNode`，并将其注册到 `m_AllPolys`：

```csharp
// Clipper.BuildResult2() 中的伪代码
foreach (OutRec outRec in m_PolyOuts)
{
    PolyNode pn = new PolyNode();
    polytree.m_AllPolys.Add(pn);  // 注册到平面列表
    // ... 设置 pn 的多边形数据和父子关系 ...
}
```

### 4.10.3 Clear() 方法 —— 清理与内存释放

```csharp
public void Clear()
{
    for (int i = 0; i < m_AllPolys.Count; i++)
        m_AllPolys[i] = null;
    m_AllPolys.Clear();
    m_Childs.Clear();
}
```

`Clear()` 方法负责清空整棵多边形树。让我们逐行分析：

**第 1-2 行：逐一将列表元素设为 null**
```csharp
for (int i = 0; i < m_AllPolys.Count; i++)
    m_AllPolys[i] = null;
```

这一步看似多余——后面已经有 `m_AllPolys.Clear()` 了，为什么还要先逐一设为 `null`？

原因与 **.NET 垃圾回收（GC）** 有关。虽然 `List<T>.Clear()` 会清空列表并将内部数组的元素设为默认值（对于引用类型就是 `null`），但在 .NET 的某些版本（特别是早期版本）中，显式将引用设为 `null` 可以**更快地断开对象图的引用链**，帮助 GC 更早回收不再使用的 `PolyNode` 对象。

此外，`PolyNode` 节点之间通过 `m_Parent` 和 `m_Childs` 形成了**复杂的引用图**。即使清空了 `m_AllPolys`，如果某个外部代码持有某个 `PolyNode` 的引用，通过 `m_Parent` 和 `m_Childs` 链接仍然可以到达整棵树。将 `m_AllPolys[i]` 设为 `null` 至少确保了从 PolyTree 端不再持有这些节点的引用。

**第 3 行：清空 m_AllPolys 列表**
```csharp
m_AllPolys.Clear();
```

`List<T>.Clear()` 将列表的 `Count` 设为 0，并将内部数组的所有元素设为默认值。注意：`Clear()` 不会释放内部数组的内存（不改变 `Capacity`），所以如果后续又要使用这个 PolyTree，不需要重新分配内存。

**第 4 行：清空 m_Childs 列表**
```csharp
m_Childs.Clear();
```

清空根节点的子节点列表。这会断开根节点与所有顶层外轮廓节点之间的引用。

### 4.10.4 GetFirst() 方法

```csharp
public PolyNode GetFirst()
{
    if (m_Childs.Count > 0)
        return m_Childs[0];
    else
        return null;
}
```

返回树中的第一个多边形节点（即第一个顶层外轮廓），如果树为空则返回 `null`。

这个方法与 `PolyNode.GetNext()` 配合使用，实现了遍历整棵树的入口点：

```csharp
// 遍历 PolyTree 的标准模式
PolyNode node = polyTree.GetFirst();
while (node != null)
{
    // 处理当前节点
    ProcessNode(node);
    node = node.GetNext();
}
```

**为什么不直接使用 `polyTree.GetNext()`？**

从理论上说，`polyTree.GetNext()` 也会返回 `m_Childs[0]`（因为根节点有子节点时，`GetNext()` 返回第一个子节点）。但是 `GetFirst()` 的语义更加明确——它表示"获取遍历的起始点"，而 `GetNext()` 表示"获取当前节点之后的下一个节点"。此外，如果树为空，`GetFirst()` 返回 `null`，而 `GetNext()` 也会返回 `null`（通过 `GetNextSiblingUp()` → `m_Parent == null` → `return null`）。

### 4.10.5 Total 属性 —— 最复杂的部分

```csharp
public int Total
{
    get
    {
      int result = m_AllPolys.Count;
      if (result > 0 && m_Childs[0] != m_AllPolys[0]) result--;
      return result;
    }
}
```

`Total` 属性返回多边形树中多边形的总数。看起来很简单——直接返回 `m_AllPolys.Count` 就好了——但为什么有一个特殊的条件判断？

#### 理解这个边界情况

关键在于 `ClipperOffset` 类的工作方式。当 `ClipperOffset` 执行**负偏移（缩小多边形）**操作时，可能会出现一种特殊情况：

在负偏移操作中，`ClipperOffset` 需要在内部创建一个**辅助的外轮廓多边形**，用于将原始多边形"反转"成孔洞。这个辅助多边形会被添加到 `m_AllPolys` 列表中，但**不会**被添加到根节点的 `m_Childs` 列表中（因为它不是最终结果的一部分，只是中间计算需要的）。

在这种情况下：
- `m_AllPolys[0]` 是辅助多边形
- `m_Childs[0]` 是实际结果的第一个多边形
- `m_AllPolys[0] != m_Childs[0]` → `true`
- 因此 `result--`，减去辅助多边形的计数

在正常情况下（非负偏移或无辅助多边形）：
- `m_AllPolys[0]` 和 `m_Childs[0]` 指向同一个节点
- 条件不成立
- `result` 不变

#### 具体场景分析

**场景 1：正常的布尔运算结果**

```
m_AllPolys: [A, B, C, D, E]  (5个多边形)
m_Childs:   [A, B]           (2个顶层外轮廓)

m_Childs[0] == m_AllPolys[0]  (都是 A)  → 不减
Total = 5
```

**场景 2：ClipperOffset 负偏移结果**

```
m_AllPolys: [辅助节点, A, B, C]  (4个节点，含1个辅助)
m_Childs:   [A]                  (1个实际外轮廓)

m_Childs[0] (A) != m_AllPolys[0] (辅助节点)  → 减1
Total = 4 - 1 = 3  (实际多边形数量)
```

这个设计虽然有些隐晦，但它避免了在 `m_AllPolys` 中额外标记"辅助节点"的复杂性，用一个简单的比较就解决了问题。

## 4.11 Paths 与 PolyTree 作为输出格式的对比

Clipper 的 `Execute()` 方法提供了两种重载形式，分别输出 `Paths` 和 `PolyTree`：

```csharp
// 输出为 Paths（平面列表）
public bool Execute(ClipType clipType, Paths solution,
    PolyFillType subjFillType, PolyFillType clipFillType);

// 输出为 PolyTree（树结构）
public bool Execute(ClipType clipType, PolyTree polytree,
    PolyFillType subjFillType, PolyFillType clipFillType);
```

### 4.11.1 对比表

| 特性 | Paths（平面列表） | PolyTree（树结构） |
|:---|:---|:---|
| **数据结构** | `List<List<IntPoint>>` | 嵌套的 `PolyNode` 树 |
| **层次信息** | ❌ 无 | ✅ 完整的父子关系 |
| **孔洞识别** | ❌ 无法直接判断 | ✅ 通过 `IsHole` 属性 |
| **内存开销** | 较小 | 较大（额外的树结构开销） |
| **构建速度** | 较快 | 较慢（需要构建树） |
| **遍历方式** | 简单的 `foreach` | `GetFirst()` / `GetNext()` |
| **适用场景** | 简单绘制、导出 | 需要层次信息的场景 |

### 4.11.2 何时使用 Paths？

- 当你只需要多边形的坐标数据（例如绘制到屏幕、导出为 SVG）时
- 当你确定结果不包含孔洞（例如两个不重叠的多边形求并集）时
- 当性能和内存是首要考虑因素时

```csharp
// 使用 Paths 作为输出
Paths solution = new Paths();
clipper.Execute(ClipType.ctUnion, solution,
    PolyFillType.pftNonZero, PolyFillType.pftNonZero);

// 简单遍历
foreach (Path path in solution)
{
    DrawPolygon(path);
}
```

### 4.11.3 何时使用 PolyTree？

- 当你需要知道哪些多边形是孔洞（例如用于三角化、填充渲染）时
- 当你需要处理嵌套的多边形层次结构时
- 当你需要分别处理外轮廓和内孔洞时

```csharp
// 使用 PolyTree 作为输出
PolyTree polytree = new PolyTree();
clipper.Execute(ClipType.ctUnion, polytree,
    PolyFillType.pftNonZero, PolyFillType.pftNonZero);

// 遍历并区分外轮廓与孔洞
PolyNode node = polytree.GetFirst();
while (node != null)
{
    if (node.IsOpen)
    {
        // 处理开放路径
    }
    else if (node.IsHole)
    {
        // 处理孔洞
        DrawHole(node.Contour);
    }
    else
    {
        // 处理外轮廓
        DrawOuterContour(node.Contour);
    }
    node = node.GetNext();
}
```

## 4.12 PolyTree 辅助函数

Clipper 库提供了几个静态辅助方法，用于从 `PolyTree` 中提取不同类型的路径。这些方法定义在 `Clipper` 类中：

### 4.12.1 PolyTreeToPaths()

```csharp
public static Paths PolyTreeToPaths(PolyTree polytree)
```

**功能**：将整棵 `PolyTree` 转换为 `Paths`（平面列表），包含所有多边形（外轮廓 + 孔洞 + 开放路径）。

**使用场景**：当你先用 `PolyTree` 做了层次分析，然后需要将所有路径转换为平面列表（例如传递给另一个库或导出）时。

```csharp
PolyTree polytree = new PolyTree();

Paths allPaths = Clipper.PolyTreeToPaths(polytree);
```

### 4.12.2 ClosedPathsFromPolyTree()

```csharp
public static Paths ClosedPathsFromPolyTree(PolyTree polytree)
```

**功能**：从 `PolyTree` 中提取所有**闭合路径**（排除开放路径），包括外轮廓和孔洞。

**使用场景**：当布尔运算的输入中同时包含开放路径和闭合多边形时，运算结果的 `PolyTree` 中可能同时包含两种类型。如果你只关心闭合多边形（例如用于填充），可以使用此方法过滤。

```csharp
Paths closedPaths = Clipper.ClosedPathsFromPolyTree(polytree);
```

### 4.12.3 OpenPathsFromPolyTree()

```csharp
public static Paths OpenPathsFromPolyTree(PolyTree polytree)
```

**功能**：从 `PolyTree` 中提取所有**开放路径**（排除闭合多边形）。

**使用场景**：当你需要单独处理布尔运算产生的开放路径时（例如裁剪一条折线后的结果）。

```csharp
Paths openPaths = Clipper.OpenPathsFromPolyTree(polytree);
```

### 4.12.4 辅助函数总结

| 方法 | 提取内容 | 包含外轮廓 | 包含孔洞 | 包含开放路径 |
|:---|:---|:---:|:---:|:---:|
| `PolyTreeToPaths()` | 所有路径 | ✅ | ✅ | ✅ |
| `ClosedPathsFromPolyTree()` | 闭合路径 | ✅ | ✅ | ❌ |
| `OpenPathsFromPolyTree()` | 开放路径 | ❌ | ❌ | ✅ |

## 4.13 内存管理与生命周期

### 4.13.1 引用类型的选择

`PolyNode` 是 `class`（引用类型），而非 `struct`（值类型）。这个选择有充分的理由：

1. **树结构需要引用语义**：树中的节点通过引用互相连接（`m_Parent`、`m_Childs`）。如果 `PolyNode` 是值类型，每次赋值都会产生拷贝，无法维护正确的引用关系。

2. **多态需求**：`PolyTree` 继承自 `PolyNode`，需要面向对象的继承机制。`struct` 不支持继承。

3. **节点共享**：同一个 `PolyNode` 对象在 `m_AllPolys` 和树结构中被同时引用。值类型无法实现这种共享。

### 4.13.2 Clear() 的内存释放策略

如我们在 4.10.3 节中分析的，`Clear()` 方法先逐一将 `m_AllPolys` 中的引用设为 `null`，然后清空列表。这种模式有助于 GC 回收：

```
Clear() 调用前的引用关系：
PolyTree.m_AllPolys → [Node A, Node B, Node C]
PolyTree.m_Childs   → [Node A]
Node A.m_Childs     → [Node B, Node C]
Node B.m_Parent     → Node A
Node C.m_Parent     → Node A

Clear() 调用后的引用关系：
PolyTree.m_AllPolys → [] (空列表)
PolyTree.m_Childs   → [] (空列表)
Node A、B、C 不再被 PolyTree 引用 → 可被 GC 回收
（但 Node A.m_Childs 仍然引用 B 和 C，B 和 C 的 m_Parent 仍然引用 A，
  如果没有外部引用，这组对象会被 GC 作为循环引用一起回收）
```

### 4.13.3 m_AllPolys 存在的必要性

为什么需要 `m_AllPolys` 这个平面列表？直接遍历树结构不也能访问所有节点吗？

原因有三：

1. **构建顺序**：在 `Clipper.BuildResult2()` 中，节点是按照内部 `OutRec` 列表的顺序创建的，不一定按照树的深度优先顺序。`m_AllPolys` 记录了创建顺序，便于后续处理。

2. **O(1) 计数**：`Total` 属性通过 `m_AllPolys.Count` 直接获取多边形总数，无需遍历整棵树（O(n)）。

3. **统一清理**：`Clear()` 方法通过遍历 `m_AllPolys` 可以一次性断开所有引用，无需递归遍历树结构。

### 4.13.4 重复使用 PolyTree

一个 `PolyTree` 对象可以被重复使用于多次 `Clipper.Execute()` 调用。每次调用 `Execute()` 前，Clipper 会在内部调用 `Clear()` 来重置 PolyTree 的状态：

```csharp
PolyTree polytree = new PolyTree();

// 第一次使用
clipper1.Execute(ClipType.ctUnion, polytree, ...);
ProcessResult(polytree);

// 第二次使用（Execute 内部会先 Clear）
clipper2.Execute(ClipType.ctIntersection, polytree, ...);
ProcessResult(polytree);
```

## 4.15 设计模式与编程技巧总结

通过分析 `PolyNode` 和 `PolyTree` 的源码，我们可以归纳出以下设计模式和编程技巧：

### 4.15.1 组合模式（Composite Pattern）

`PolyNode` 和 `PolyTree` 体现了经典的**组合模式**：
- `PolyNode` 既是"叶子"（没有子节点的多边形），也是"容器"（包含子节点的多边形）。
- `PolyTree` 是特殊的根容器，继承自 `PolyNode`，与普通节点具有统一的接口。
- 客户代码可以一致地处理单个节点和整棵子树。

### 4.15.2 内部迭代器模式

`GetFirst()` 和 `GetNext()` 组合实现了一种简单的**内部迭代器**，无需分配额外的迭代器对象：

```csharp
for (PolyNode n = tree.GetFirst(); n != null; n = n.GetNext())
{
    // 处理每个节点
}
```

### 4.15.3 索引缓存优化

`m_Index` 字段是一种**空间换时间**的优化——用额外的 `int` 字段（4 字节）换取 O(1) 的兄弟节点查找时间，避免了 O(n) 的线性搜索。

### 4.15.4 封装与可见性控制

- 字段使用 `internal` 修饰符，允许库内部代码直接访问，同时对外部用户隐藏实现细节。
- 公开的只读属性提供了安全的对外接口。
- 构建方法（`AddChild()`）是 `internal` 的，防止外部代码破坏树结构的一致性。

### 4.15.5 防御性初始化

`m_polygon` 和 `m_Childs` 在声明时就初始化为空的集合对象，避免了 `NullReferenceException` 的风险。这是一种值得推广的最佳实践。

## 4.16 本章小结

本章深入剖析了 Clipper1 库中多边形层次结构的实现——`PolyNode` 和 `PolyTree` 两个类。

**核心要点回顾**：

1. **PolyNode** 是多边形树的节点类，包含多边形轮廓数据、父子关系、以及深度优先遍历的支持方法。

2. **PolyTree** 继承自 `PolyNode`，作为树的根节点，额外维护了一个所有节点的平面列表 `m_AllPolys`。

3. **IsHoleNode()** 通过沿父链遍历并翻转布尔值来判断节点是否为孔洞，体现了奇偶深度规则。

4. **GetNext() + GetNextSiblingUp()** 实现了无需额外内存的前序深度优先遍历，`m_Index` 字段使兄弟查找达到 O(1)。

5. **Total 属性** 中的特殊条件处理了 `ClipperOffset` 负偏移时添加的辅助节点。

6. **Paths 与 PolyTree** 是 Clipper 提供的两种输出格式，分别适用于不需要和需要层次信息的场景。

在下一章中，我们将进入 Clipper 库的核心——**边（Edge）数据结构和扫描线算法**的源码解析，了解 Clipper 如何高效地执行多边形布尔运算。
