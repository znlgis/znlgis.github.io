### 3.1.3 依赖关系

各层的依赖关系遵循**单向依赖原则**：

- CLI → Engine, Steps, Models
- Engine → Steps, Backends, Models, Utils
- Steps → Models, Utils
- Backends → Models
- Models → 无外部依赖
- Utils → 无外部依赖

## 3.2 模块职责划分

### 3.2.1 CLI 层 (`cli.py`)

CLI 层基于 Click 框架实现，是用户与 GeoPipeAgent 交互的入口。

```python
# cli.py 中定义的命令（基于 Click）
@click.group()
def cli():
    """GeoPipeAgent - AI-Native GIS Pipeline Framework"""
    pass

@cli.command()
def run(): ...           # 执行流水线

@cli.command()
def validate(): ...      # 验证流水线

@cli.command()
def list_steps(): ...    # 列出步骤

@cli.command()
def describe(): ...      # 描述步骤详情

@cli.command()
def info(): ...          # 显示系统信息

@cli.command()
def backends(): ...      # 显示可用后端

@cli.command()
def generate_skill_doc(): ...   # 生成 Skill 文档

@cli.command()
def generate_skill(): ...       # 生成 Skill 文件
```

CLI 层的职责：
- 解析命令行参数
- 调用 Engine 层执行操作
- 格式化输出结果

### 3.2.2 Engine 层 (`engine/`)

Engine 层是框架的核心，负责流水线的完整生命周期管理。

| 模块 | 文件 | 职责 |
|------|------|------|
| **Parser** | `parser.py` | 将 YAML 文件解析为 `PipelineDefinition` 对象 |
| **Validator** | `validator.py` | 验证流水线定义的合法性 |
| **Executor** | `executor.py` | 按顺序执行流水线中的每个步骤 |
| **Context** | `context.py` | 管理变量和步骤输出，解析引用表达式 |
| **Reporter** | `reporter.py` | 将执行结果聚合为 JSON 报告 |

### 3.2.3 Steps 层 (`steps/`)

### 3.2.4 Backends 层 (`backends/`)

Backends 层实现了 5 种 GIS 处理后端的统一抽象：

| 文件 | 后端 | 实现基础 |
|------|------|---------|
| `base.py` | 抽象基类 | 定义 `GeoBackend` 接口 |
| `native_python_backend.py` | native_python | GeoPandas + Shapely |
| `gdal_cli.py` | gdal_cli | ogr2ogr 命令行调用 |

| `qgis_process.py` | qgis_process | QGIS Processing CLI |
| `pyqgis_backend.py` | pyqgis | PyQGIS Python API |

### 3.2.5 Models 层 (`models/`)

Models 层定义了框架的核心数据结构：

| 文件 | 类 | 用途 |
|------|---|------|
| `pipeline.py` | `PipelineDefinition` | 流水线定义（name, steps, description, crs, variables, outputs） |
| `pipeline.py` | `StepDefinition` | 步骤定义（id, use, params, when, on_error, backend） |
| `result.py` | `StepResult` | 步骤执行结果（output, stats, metadata, issues） |
| `qc.py` | `QcIssue` | 质检问题（rule_id, severity, feature_index, message, geometry, details） |

### 3.2.6 Utils 层 (`utils/`)

| 文件 | 用途 |
|------|------|
| `logging.py` | 结构化日志，统一日志格式 |
| `safe_eval.py` | 安全表达式求值，使用 AST 白名单防止代码注入 |

## 3.3 数据流与执行流程

### 3.3.1 完整执行流程

当用户执行 `geopipe-agent run pipeline.yaml` 时，框架内部的完整数据流如下：

```
步骤1: CLI 解析命令行参数
       │
       ▼
步骤2: Parser.parse_yaml(file_path)
       │  读取 YAML 文件
       │  构建 PipelineDefinition
       │    ├── name, description, crs
       │    ├── variables: dict
       │    ├── steps: list[StepDefinition]
       │    └── outputs: dict
       ▼
步骤3: Validator.validate(pipeline_def)
       │  检查步骤 ID 合法性 ([a-z0-9_-])
       │  检查步骤 ID 唯一性
       │  检查 use 字段是否注册
       │  检查参数引用有效性
       │  检查输出引用有效性
       ▼
步骤4: Executor.execute_pipeline(pipeline_def, var_overrides)
       │  创建 PipelineContext
       │  ├── 初始化 variables（合并 CLI --var 覆盖）
       │  ├── 初始化 _step_outputs = {}
       │  │
       │  遍历每个 StepDefinition:
       │  │
       │  ├── 1. 评估 when 条件
       │  │      └── safe_eval.py 安全求值
       │  │
       │  ├── 2. 解析参数引用
       │  │      ├── ${var} → variables 值
       │  │      └── $step_id.attr → _step_outputs 值
       │  │
       │  ├── 3. 获取/选择后端
       │  │      └── BackendManager.get(preferred)
       │  │
       │  ├── 4. 构建 StepContext
       │  │      └── params, backend, pipeline_context
       │  │
       │  ├── 5. 调用步骤函数
       │  │      └── step_func(step_context) → StepResult
       │  │
       │  ├── 6. 存储结果
       │  │      └── _step_outputs[step_id] = result
       │  │
       │  └── 7. 错误处理
       │         ├── on_error: fail → 抛出异常终止
       │         ├── on_error: skip → 跳过继续
       │         └── on_error: retry → 重试最多3次
       ▼
步骤5: Reporter.build_report(results)
       │  生成 JSON 报告
       │  ├── pipeline 元信息
       │  ├── steps 执行结果
       │  ├── qc_summary 质检汇总
       │  └── outputs 声明输出
       ▼
步骤6: 输出 JSON 报告到 stdout
```

### 3.3.2 解析阶段详解

`Parser.parse_yaml()` 的核心逻辑（`engine/parser.py`）：

```python
def parse_yaml(file_path: str) -> PipelineDefinition:
    # 1. 读取 YAML 文件
    with open(file_path) as f:
        raw = yaml.safe_load(f)

    # 2. 提取 pipeline 节点
    pipeline_raw = raw["pipeline"]

    # 3. 构建 StepDefinition 列表
    steps = []
    for step_raw in pipeline_raw["steps"]:
        step = StepDefinition(
            id=step_raw["id"],
            use=step_raw["use"],
            params=step_raw.get("params", {}),
            when=step_raw.get("when"),
            on_error=step_raw.get("on_error", "fail"),
            backend=step_raw.get("backend"),
        )
        steps.append(step)

    # 4. 构建 PipelineDefinition
    return PipelineDefinition(
        name=pipeline_raw["name"],
        steps=steps,
        description=pipeline_raw.get("description"),
        crs=pipeline_raw.get("crs"),
        variables=pipeline_raw.get("variables", {}),
        outputs=pipeline_raw.get("outputs", {}),
    )
```

### 3.3.3 验证阶段详解

`Validator.validate()` 执行的检查项（`engine/validator.py`）：

| 检查项 | 说明 | 错误类型 |
|--------|------|---------|
| 步骤 ID 格式 | 必须匹配 `[a-z0-9_-]+` | `ValidationError` |
| 步骤 ID 唯一性 | 不允许重复 ID | `ValidationError` |
| 步骤注册检查 | `use` 字段必须对应已注册步骤 | `ValidationError` |
| 参数引用检查 | `$step_id` 引用必须指向前序步骤 | `ValidationError` |
| 输出引用检查 | `outputs` 中的引用必须有效 | `ValidationError` |

### 3.3.4 执行阶段详解

`Executor.execute_pipeline()` 的核心逻辑（`engine/executor.py`）：

```python
def execute_pipeline(self, pipeline: PipelineDefinition,
                     var_overrides: dict = None) -> dict:
    # 1. 创建上下文
    context = PipelineContext(
        variables={**pipeline.variables, **(var_overrides or {})}
    )

    results = []

    # 2. 遍历步骤
    for step_def in pipeline.steps:
        # 2a. 评估 when 条件
        if step_def.when:
            condition = context.resolve(step_def.when)
            if not safe_eval(condition):
                continue  # 跳过此步骤

        # 2b. 解析参数中的引用
        resolved_params = context.resolve(step_def.params)

        # 2c. 获取后端
        backend = self.backend_manager.get(step_def.backend)

        # 2d. 构建 StepContext
        step_ctx = StepContext(
            params=resolved_params,
            backend=backend,
            pipeline_context=context,
        )

        # 2e. 执行步骤（含重试逻辑）
        try:
            result = self._execute_step(step_def, step_ctx)
            context.store_output(step_def.id, result)
            results.append((step_def.id, result))
        except Exception as e:
            self._handle_error(step_def, e, results)

    # 3. 构建报告
    return Reporter.build_report(pipeline, results)
```

## 3.4 步骤注册与发现机制

### 3.4.1 自动发现机制

GeoPipeAgent 在 `__init__.py` 中使用 `pkgutil.walk_packages` 自动扫描和导入 `steps/` 目录下的所有模块：

```python
# src/geopipe_agent/__init__.py
import pkgutil
import importlib

# 自动发现并导入 steps 下的所有子模块
package = importlib.import_module("geopipe_agent.steps")
for importer, modname, ispkg in pkgutil.walk_packages(
    path=package.__path__,
    prefix=package.__name__ + ".",
):
    importlib.import_module(modname)
```

这意味着当导入 `geopipe_agent` 包时，所有 `steps/` 下的模块会被自动导入，其中使用 `@step` 装饰器注册的函数会自动注册到全局步骤注册表中。

### 3.4.2 `@step` 装饰器

`@step` 装饰器定义在 `steps/registry.py` 中，它将一个普通函数注册为流水线步骤：

```python
# steps/registry.py
from dataclasses import dataclass, field
from typing import Callable, Any

@dataclass
class StepInfo:
    id: str                    # 步骤唯一标识，如 "vector.buffer"
    func: Callable             # 步骤执行函数
    name: str                  # 人类可读名称
    description: str           # 详细描述
    category: str              # 类别（从 id 前缀自动推导）
    params: list               # 参数定义列表
    outputs: list              # 输出定义列表
    backends: list = field(default_factory=list)  # 支持的后端
    examples: list = field(default_factory=list)  # 用法示例

# 全局步骤注册表
_registry: dict[str, StepInfo] = {}

def step(id: str, name: str, description: str,
         params: list, outputs: list,
         backends: list = None, examples: list = None):
    """步骤注册装饰器"""
    def decorator(func: Callable):
        # 从 id 前缀自动推导类别
        category = id.split(".")[0]  # "vector.buffer" → "vector"
        info = StepInfo(
            id=id,
            func=func,
            name=name,
            description=description,
            category=category,
            params=params,
            outputs=outputs,
            backends=backends or [],
            examples=examples or [],
        )
        _registry[id] = info
        return func
    return decorator
```

### 3.4.3 步骤定义示例

一个典型的步骤定义：

```python
# steps/vector/buffer.py
from geopipe_agent.steps.registry import step

@step(
    id="vector.buffer",
    name="Buffer",
    description="Create buffer zones around geometries",
    params=[
        {"name": "input", "type": "geodataframe", "required": True,
         "description": "Input geometries"},
        {"name": "distance", "type": "number", "required": True,
         "description": "Buffer distance"},
        {"name": "resolution", "type": "integer", "required": False,
         "default": 16, "description": "Buffer resolution"},
    ],
    outputs=[
        {"name": "output", "type": "geodataframe",
         "description": "Buffered geometries"},
    ],
    backends=["native_python", "gdal_cli", "gdal_python"],
    examples=[
        {
            "id": "buffer_example",
            "use": "vector.buffer",
            "params": {"input": "$load_data", "distance": 100},
        }
    ],
)
def buffer(ctx):
    """执行缓冲区操作"""
    gdf = ctx.param("input")
    distance = ctx.param("distance")
    resolution = ctx.param("resolution", default=16)

    # 使用后端执行
    result_gdf = ctx.backend.buffer(gdf, distance, resolution=resolution)

    return StepResult(output=result_gdf, stats={"count": len(result_gdf)})
```

### 3.4.4 类别自动推导

步骤的类别（category）从 `id` 前缀自动推导：

```
步骤 ID              推导出的类别
─────────────────────────────────
io.read_file      →  io
vector.buffer     →  vector
raster.read       →  raster
analysis.overlay  →  analysis
network.shortest  →  network
qc.check_geometry →  qc
```

这种设计确保了步骤分类的一致性，也使得 `list-steps` 命令能够按类别分组显示。

## 3.5 后端抽象与多态

### 3.5.1 GeoBackend 抽象基类

`backends/base.py` 定义了统一的后端接口：

```python
# backends/base.py
from abc import ABC, abstractmethod

class GeoBackend(ABC):
    @abstractmethod
    def name(self) -> str:
        """返回后端名称"""
        ...

    @abstractmethod
    def is_available(self) -> bool:
        """检测后端是否可用"""
        ...

    @abstractmethod
    def buffer(self, gdf, distance, **kwargs):
        """缓冲区操作"""
        ...

    @abstractmethod
    def clip(self, gdf, mask, **kwargs):
        """裁剪操作"""
        ...

    @abstractmethod
    def reproject(self, gdf, crs, **kwargs):
        """重投影操作"""
        ...

    @abstractmethod
    def dissolve(self, gdf, by, **kwargs):
        """融合操作"""
        ...

    @abstractmethod
    def simplify(self, gdf, tolerance, **kwargs):
        """简化操作"""
        ...

    @abstractmethod
    def overlay(self, gdf, other, how, **kwargs):
        """叠加分析"""
        ...
```

### 3.5.2 后端实现对比

| 操作 | native_python | gdal_cli | gdal_python |
|------|--------------|----------|-------------|
| `buffer()` | `gdf.buffer(d)` | `ogr2ogr -dialect SQLite` | `OGR Layer.Buffer()` |
| `clip()` | `gpd.clip(gdf, mask)` | `ogr2ogr -clipsrc` | `OGR Layer.Clip()` |
| `reproject()` | `gdf.to_crs(crs)` | `ogr2ogr -t_srs` | `osr.CoordinateTransformation` |
| `dissolve()` | `gdf.dissolve(by)` | `ogr2ogr -dialect SQLite` | SQL `GROUP BY` |
| `simplify()` | `gdf.simplify(t)` | `ogr2ogr -simplify` | `OGR Geometry.Simplify()` |
| `overlay()` | `gpd.overlay(how)` | `ogr2ogr -dialect SQLite` | `OGR Layer.Union()` |

### 3.5.3 BackendManager

`BackendManager` 负责管理后端的注册、检测和选择：

```python
class BackendManager:
    def __init__(self):
        self._backends = {
            "native_python": NativePythonBackend(),
            "gdal_cli": GdalCliBackend(),
            "gdal_python": GdalPythonBackend(),
            "qgis_process": QgisProcessBackend(),
            "pyqgis": PyQgisBackend(),
        }

    def available_backends(self) -> list[str]:
        """返回所有可用后端的名称列表"""
        return [
            name for name, backend in self._backends.items()
            if backend.is_available()
        ]

    def get(self, preferred: str = None) -> GeoBackend:
        """获取后端实例，优先使用指定后端"""
        if preferred:
            backend = self._backends.get(preferred)
            if backend and backend.is_available():
                return backend
            raise BackendNotAvailableError(preferred)

        # 未指定时，按优先级返回第一个可用后端
        for name in ["native_python", "gdal_cli", "gdal_python",
                      "qgis_process", "pyqgis"]:
            backend = self._backends[name]
            if backend.is_available():
                return backend

        raise NoBackendAvailableError()
```

## 3.6 上下文与数据传递

### 3.6.1 PipelineContext

`PipelineContext`（`engine/context.py`）是流水线级别的上下文，管理变量和步骤输出：

```python
class PipelineContext:
    def __init__(self, variables: dict = None):
        self.variables: dict = variables or {}
        self._step_outputs: dict = {}

    def store_output(self, step_id: str, result: StepResult):
        """存储步骤执行结果"""
        self._step_outputs[step_id] = result

    def get_output(self, step_id: str) -> StepResult:
        """获取步骤执行结果"""
        if step_id not in self._step_outputs:
            raise VariableResolutionError(f"Step '{step_id}' not found")
        return self._step_outputs[step_id]

    def resolve(self, value):
        """解析值中的变量引用和步骤引用"""
        if isinstance(value, str):
            # 解析 ${var} 变量引用
            value = self._substitute_variables(value)
            # 解析 $step_id.attr 步骤引用
            value = self._resolve_step_ref(value)
        elif isinstance(value, dict):
            return {k: self.resolve(v) for k, v in value.items()}
        elif isinstance(value, list):
            return [self.resolve(item) for item in value]
        return value
```

### 3.6.2 StepContext

`StepContext` 是步骤级别的上下文，封装了步骤函数执行所需的所有信息：

```python
class StepContext:
    def __init__(self, params: dict, backend: GeoBackend,
                 pipeline_context: PipelineContext):
        self._params = params
        self.backend = backend
        self.pipeline_context = pipeline_context

    def param(self, name: str, default=None):
        """获取参数值"""
        return self._params.get(name, default)

    def input(self, name: str = "input"):
        """获取输入数据（param 的快捷方式）"""
        return self.param(name)

    @property
    def params(self) -> dict:
        """获取所有参数"""
        return self._params
```

### 3.6.3 数据传递示例

```yaml
steps:
  - id: load              # 步骤1
    use: io.read_file
    params:
      path: "data.shp"

  - id: buffer            # 步骤2
    use: vector.buffer
    params:
      input: $load        # 引用步骤1的完整输出
      distance: 100

  - id: clip              # 步骤3
    use: vector.clip
    params:
      input: $buffer      # 引用步骤2的完整输出
      mask: $load         # 也可以引用步骤1
```

数据传递的内部机制：

```
执行 load 步骤：
  → result = StepResult(output=GeoDataFrame(...))
  → context._step_outputs["load"] = result

执行 buffer 步骤：
  → 解析 "$load" → context.get_output("load") → StepResult
  → 如果是 $step_id 简写，直接返回 result.output
  → 如果是 $step_id.output，返回 result.output
  → 如果是 $step_id.stats，返回 result.stats
```

## 3.7 错误处理体系

### 3.7.1 异常类层次结构

`errors.py` 定义了 GeoPipeAgent 的异常体系：

```
GeoPipeAgentError (基类)
├── ParseError              # YAML 解析错误
├── ValidationError         # 流水线验证错误
├── StepExecutionError      # 步骤执行错误
├── BackendNotAvailableError # 后端不可用
├── NoBackendAvailableError  # 无可用后端
├── VariableResolutionError  # 变量解析错误
└── StepNotFoundError        # 步骤未注册
```

### 3.7.2 AI 友好的错误信息

GeoPipeAgent 的错误信息设计为 AI 可理解的格式：

```python
class StepNotFoundError(GeoPipeAgentError):
    def __init__(self, step_use: str):
        # 提供清晰的错误信息和修复建议
        available = list(_registry.keys())
        message = (
            f"Step '{step_use}' is not registered. "
            f"Available steps: {', '.join(sorted(available))}"
        )
        super().__init__(message)
```

这种设计使得 AI 在接收到错误信息后能够：
1. 理解错误原因
2. 知道如何修复
3. 自动重新生成正确的流水线

### 3.7.3 执行阶段的错误处理

```python
# executor.py 中的错误处理逻辑
def _handle_error(self, step_def, error, results):
    match step_def.on_error:
        case "fail":
            raise StepExecutionError(step_def.id, error)
        case "skip":
            # 记录跳过信息，继续执行下一步
            results.append((step_def.id, StepResult(
                output=None,
                metadata={"skipped": True, "error": str(error)}
            )))
        case "retry":
            # 重试逻辑，最多 MAX_RETRIES=3 次
            for attempt in range(MAX_RETRIES):
                try:
                    result = self._execute_step(step_def, step_ctx)
                    break
                except Exception:
                    if attempt == MAX_RETRIES - 1:
                        raise StepExecutionError(step_def.id, error)
```

## 3.8 设计模式分析

### 3.8.1 策略模式 (Strategy Pattern)

**应用场景**：多后端支持

```
┌──────────────┐        ┌──────────────────┐
│ GeoBackend   │◄───────│ BackendManager   │
│  (接口)      │        └──────────────────┘
└──────────────┘
       ▲
       │ implements
       ├── NativePythonBackend
       ├── GdalCliBackend
       ├── GdalPythonBackend
       ├── QgisProcessBackend
       └── PyQgisBackend
```

每个后端实现了相同的接口（`buffer`、`clip`、`reproject` 等），执行器在运行时通过 `BackendManager` 选择合适的"策略"。这样添加新后端只需实现 `GeoBackend` 接口，无需修改执行器代码。

### 3.8.2 装饰器模式 (Decorator Pattern)

**应用场景**：步骤注册

```python
@step(id="vector.buffer", name="Buffer", ...)
def buffer(ctx):
    ...
```

`@step` 装饰器在不修改函数本身逻辑的情况下，将其注册到全局步骤注册表中，并附加了丰富的元信息（参数定义、输出定义、支持的后端等）。

### 3.8.3 管道模式 (Pipeline Pattern)

**应用场景**：流水线执行

```
Step 1 ──output──▶ Step 2 ──output──▶ Step 3 ──output──▶ Report
```

每个步骤的输出通过 `PipelineContext` 传递给后续步骤，形成数据处理管道。这是框架最核心的设计模式。

### 3.8.4 注册表模式 (Registry Pattern)

**应用场景**：步骤注册与查找

全局 `_registry` 字典维护所有已注册步骤的映射关系，通过 `id` 快速查找对应的 `StepInfo`：

```python
_registry: dict[str, StepInfo] = {
    "io.read_file": StepInfo(...),
    "vector.buffer": StepInfo(...),
    "qc.check_geometry": StepInfo(...),
    ...
}
```

### 3.8.5 模板方法模式 (Template Method Pattern)

**应用场景**：执行器的步骤执行流程

`Executor` 定义了步骤执行的固定流程（评估条件 → 解析参数 → 选择后端 → 执行 → 存储结果），而具体的步骤逻辑由各步骤函数实现。

### 3.8.6 上下文对象模式 (Context Object Pattern)

**应用场景**：`PipelineContext` 和 `StepContext`

将步骤执行所需的所有信息封装在上下文对象中，避免了大量参数传递，也使得步骤函数的接口保持简洁统一。
