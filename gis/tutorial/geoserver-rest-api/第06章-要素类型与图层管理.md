# 第06章：要素类型与图层管理

数据存储配好之后，GeoServer 还不会自动把库里的每张表变成能出图的图层。矢量数据要经过两次登记：先把数据源中的表登记成要素类型（FeatureType），再把要素类型挂到图层（Layer）上。两步在 REST 接口里属于两个不同的资源集合，请求体、返回码和失败原因都不一样。实际项目里常见的"要素类型建好了，WMS 却看不到图层"，多数是漏了第二步，或者图层默认被设成了不启用。

本章按 REST 资源模型把这条链路拆开：两个资源各有哪些字段、各自对应哪个端点、创建和更新时服务端会做哪些校验，以及发布失败后先看哪里。读完应当能独立写出一段可以重复执行的发布脚本，而不是在管理页面里手工点一遍。

## 6.1 要素类型和图层的关系

要素类型描述的是"数据源里有什么"。它记录表名或视图名（nativeName）、发布时对外使用的名字（name）、几何字段和坐标系，以及从数据源读出来的属性结构。GeoServer 不存要素本身，只保存这份描述；每次 WFS 请求或地图渲染，它都按描述回到数据源取数据。

图层描述的是"这份数据怎么对外提供"。它引用一个要素类型，另外带上默认样式、是否启用、缓存策略、权限规则和 WMS/WFS 的服务设置。同一个要素类型可以被多个图层引用，比如同一份行政区数据，一个图层用面状样式、另一个图层用标签样式；反过来，一个图层只能指向一个要素类型。

在 GeoServer 中：
- **要素类型（FeatureType）**：数据存储中的实际数据表或数据集
- **图层（Layer）**：发布的地图服务，可以配置样式、缓存等

关系：要素类型 → 图层 → OGC 服务（WMS、WFS、WCS）

这条链路里每层都有独立的命名。要素类型在 GeoServer 内的全名带工作空间前缀，写作 workspace:type；WMS 的 LAYERS 参数、WFS 的 typeName 用的都是这个全名，而不是数据源里的表名。发布时 name 和 nativeName 允许不同：nativeName 必须和数据源里的名字严格一致（区分大小写，视图名也一样），name 是公开名，改它不需要动数据库。

还有一点容易忽略：要素类型发布成功只说明 GeoServer 读到了表结构，不代表图层已经启用。图层对象上的 enabled 决定它是否出现在服务文档和地图请求里，新建时通常默认为启用，但用脚本手工 PUT 过一份只带部分字段的 JSON 后，这个值可能被覆盖成 false，排查"服务文档里没有图层"时应当先看这里。

## 6.2 FeatureTypeService 核心功能

读要素类型用 GET，新建用 POST 打到要素类型集合。列表端点是 GET /rest/workspaces/{workspace}/datastores/{store}/featuretypes.json，GeoServer 返回带包装的 JSON：顶层是 featureTypes 对象，里面的 featureType 数组才是条目。客户端把这层包装拆掉，直接返回 FeatureType 数组，调用方不必关心原始 JSON 结构。工作空间或数据存储任意一级名字写错，服务端返回 404，而不是空数组。

CreateFeatureTypeAsync 对应 POST 同一个集合端点，请求体同样包一层 featureType。服务端插入之前会连一次数据源、读表结构：几何列、字段类型、原生坐标系都由它探测后补全；客户端传的 SRS 是声明坐标系，和原生坐标系（nativeCRS）是两回事。只有数据本身没有坐标系、或者需要在发布时换一种说法解释坐标，才需要填 SRS。

```csharp
// 获取要素类型列表
var featureTypes = await featureTypeService.GetFeatureTypesAsync("workspace", "datastore");

// 发布要素类型为图层
var featureType = new FeatureType
{
    Name = "cities",
    NativeName = "cities",
    Title = "世界城市",
    Abstract = "世界主要城市数据",
    Enabled = true,
    SRS = "EPSG:4326"
};
await featureTypeService.CreateFeatureTypeAsync("workspace", "datastore", featureType);
```

这段示例里 Name 和 NativeName 相同，都取表名，是最省事的写法。Title 和 Abstract 会进入 WMS Capabilities 和 WFS 服务描述，给人看，可以写中文；Name 会出现在 URL 和 typeName 里，尽量只用字母、数字和下划线。Enabled 设为 true 才对外提供，SRS 声明数据是 EPSG:4326。

调用之后值得再 GET 一次要素类型，确认服务端探测出的几何类型和字段数量符合预期。这一步能提前暴露两类问题：表里没有几何列，或者几何列的类型不被识别，要素类型仍会创建成功，但渲染时出不来图；声明的 SRS 和数据实际坐标不符，图层画得出来却整体偏移。

创建不是幂等的。同一个名字重复 POST，GeoServer 会返回错误（常见 409 或 500），脚本重试前应当先 Get 探测；需要"存在则更新"的语义，就自己写成 GET 成功走 PUT、404 才 POST 的分支。

## 6.3 图层管理

图层端点分两种粒度：GET /rest/layers.json 返回实例上所有工作空间的图层清单，GET /rest/layers/{workspace}:{name}.json 取单个图层。路径里的冒号不能省，只写图层名会得到 404。列表返回的条目通常只有名字和链接，要拿样式、要素类型引用这些细节，还得逐个取。

更新图层要留意 PUT 的语义。GeoServer 的 REST 把 PUT 当整体替换：先 GET 出完整表示，改需要改的字段，再原样 PUT 回去。样例里只改 DefaultStyle 就提交整个 layer 对象，前提是 layer 变量来自刚才的 GET；如果自己 new 一个只填几个字段的对象再 PUT，没填的字段可能被置空或恢复默认值，enabled 和要素类型引用都可能丢。

样式引用存的是名字，不是样式对象。DefaultStyle 只保存一个指向样式资源的引用，样式内容本身通过样式端点单独维护，所以换图层样式只需要改引用，不必重传 SLD。

```csharp
// 获取所有图层
var layers = await layerService.GetLayersAsync();

// 获取特定图层
var layer = await layerService.GetLayerAsync("workspace:cities");

// 更新图层配置
layer.DefaultStyle = new StyleReference { Name = "custom_style" };
await layerService.UpdateLayerAsync("workspace:cities", layer);

// 删除图层
await layerService.DeleteLayerAsync("workspace:cities", recurse: true);
```

删除接口的 recurse 参数控制删除是否向下传递。传 true 时，服务端会连同该图层依赖的要素类型等资源一起处理；不同 GeoServer 版本对"连带删除范围"的细节不完全一致，生产环境使用前应当先在测试实例上确认一次。只想撤掉一个发布、保留数据源里的表时，选 false 更稳妥。

批量维护时不要在图循环里逐个 GET。图层列表接口一次能拿到全量名字，把需要处理的图层名收集起来，再按需并发取详情，能省掉大量往返。更新完成后重新取一次图层表示，确认 defaultStyle 指向的样式名确实生效——样式名写错时图层更新可能仍然成功，渲染却退回默认样式，不容易发现。

## 6.4 图层发布完整流程

这一节把前面的单个操作串成一条发布流程。顺序有依赖：要素类型必须挂在已存在的工作空间和数据存储下，所以先确认工作空间；图层由要素类型发布派生，所以第二步是创建要素类型。示例里的 LayerPublisher 只覆盖了工作空间检查和要素类型创建，数据存储是否存在、要素类型是否已存在、发布后要不要设样式，都留给调用方。

WorkspaceExistsAsync 是一次 GET 探测，返回 false 才创建。这在批量导入时能省掉大量重复创建，但要注意并发：两个进程同时判断"不存在"再同时创建，第二个会失败。更稳的做法是直接创建并捕获"已存在"的错误，或者在工作空间这一层用固定的初始化流程串行执行。

ProjectionPolicy 设为 FORCE_DECLARED，表示忽略数据源原生坐标系，强制按声明的 SRS 解释坐标。数据确实没有正确坐标系、或者已经被外部工具转成声明坐标系时用得上；数据本身带正确 SRS 时不要加这一项，强制声明会让原本正确的坐标被再次解释，位置整体偏移。

```csharp
public class LayerPublisher
{
    private readonly WorkspaceService _workspaceService;
    private readonly DataStoreService _dataStoreService;
    private readonly FeatureTypeService _featureTypeService;

    public async Task<bool> PublishLayerAsync(
        string workspaceName,
        string dataStoreName,
        string tableName,
        string layerTitle)
    {
        // 1. 确保工作空间存在
        if (!await _workspaceService.WorkspaceExistsAsync(workspaceName))
        {
            await _workspaceService.CreateWorkspaceAsync(workspaceName);
        }

        // 2. 发布要素类型
        var featureType = new FeatureType
        {
            Name = tableName,
            NativeName = tableName,
            Title = layerTitle,
            Enabled = true,
            SRS = "EPSG:4326",
            ProjectionPolicy = "FORCE_DECLARED"
        };

        await _featureTypeService.CreateFeatureTypeAsync(
            workspaceName, dataStoreName, featureType);

        Console.WriteLine($"图层 {layerTitle} 发布成功!");
        return true;
    }
}
```

发布完成至少验证三件事：取一次要素类型，看几何类型和字段是否和数据库一致；取一次图层，确认 enabled 为 true、defaultStyle 指向预期样式；再发一个小的 WMS GetMap 或 WFS GetFeature 请求，确认服务真的能出结果。前两步只证明配置写进去了，第三步才证明数据取得到。

失败回滚要自己补。要素类型创建成功后，如果后面的样式设置或权限配置失败，GeoServer 里会留下一个半成品发布。稳妥的做法是记录本次新建的要素类型名，异常时按要素类型 DELETE 回收；回收前确认没有其他图层引用它。

还有一类错误不在代码里：数据存储指向的数据库连不上。这时 POST 要素类型会返回 5xx，异常文本里通常带着数据源驱动的报错。遇到 5xx 先到数据存储端点做一次 reset，确认连接参数和网络，再回头重试发布。

## 6.5 本章小结

学习了：
1. 要素类型与图层的区别和联系
2. 如何发布数据为图层
3. 图层属性配置
4. 完整的图层发布流程

把这一章压成一条检查清单：数据存储能连上；nativeName 与数据源里的对象名逐字一致；要素类型创建后几何列和坐标系被正确探测；图层引用的是正确的要素类型，enabled 为 true，defaultStyle 指向存在的样式；最后用 WMS 和 WFS 各请求一次。任何一步失败，先判断是哪一层资源不存在，再决定是重建还是修配置，不要直接删数据存储重来——那会连带清掉下面的要素类型和图层。
