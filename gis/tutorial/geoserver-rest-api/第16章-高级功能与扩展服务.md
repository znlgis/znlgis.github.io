# 第16章：高级功能与扩展服务

这一章的接口有一个共同前提：它们大多来自 GeoServer 的扩展插件，不是核心自带的功能。调用之前先确认目标实例装了对应插件，可以用 about 端点看已加载的模块，也可以直接请求扩展端点：插件没装时通常返回 404，而不是明确的"未启用"错误。

扩展接口的形态也比前几章自由。有的是一次性请求，有的是先建任务再上传再执行的多步流程；有的读写文件，有的依赖外部服务（S3、密钥库）。下面逐个说清楚每个服务解决什么问题、调用顺序是什么、失败时先看哪里。

## 16.1 数据导入服务

ImporterService 提供了批量导入数据的高级功能。

直接 POST 要素类型适合"数据已经放在服务器能访问的位置"的场景。数据还在本地、格式又比较杂（Shapefile 压缩包、GeoPackage、CSV）时，用导入服务更省事：它负责接收文件、识别格式、把数据落到工作空间的数据存储里，整个过程以任务的形式管理。

导入是异步的。CreateImportTaskAsync 返回的 taskId 只是任务编号，任务此时还没有数据、也没有开始执行；上传文件、执行导入是后续两个独立步骤。三步之间任何一步失败，任务会停在对应状态，脚本要能查询任务状态并根据状态决定继续、重试还是放弃。

```csharp
var importerService = factory.CreateImporterService();

// 创建导入任务
var importTask = new ImportTask
{
    TargetWorkspace = "myWorkspace",
    TargetStore = "myDataStore"
};

var taskId = await importerService.CreateImportTaskAsync(importTask);

// 上传文件到导入任务
var zipFile = File.ReadAllBytes("data.zip");
await importerService.UploadFileToTaskAsync(taskId, zipFile);

// 执行导入
await importerService.ExecuteImportAsync(taskId);
```

这段流程对应三个端点：创建任务、向任务上传文件、触发执行。上传环节要注意文件类型和压缩方式，Shapefile 要打包成 zip 再传，散装文件服务端没法识别；上传接口通常还要求指定文件类型参数，写错时任务能创建成功，执行阶段才报"无法识别的格式"。

执行之后不要立刻认为导入完成。执行调用返回只代表任务开始运行，真正的结果要轮询任务状态或查询任务详情。任务失败时，错误信息里一般会带数据源读取失败的原因，比如字段类型超出预期、编码不对、压缩包内缺少必需文件，按这些线索修数据比反复重试有效。

导入失败会在数据目录留下临时文件或半成品存储。定期清理任务和临时目录，避免磁盘被历史数据占满。

## 16.2 TransformService - 坐标转换

坐标转换端点解决的是"给定一个点和两个坐标系，算出另一个点"的小计算需求，不需要建图层、也不需要 WMS。典型用途是前端点击地图后把屏幕坐标换算到业务坐标系，或者把用户输入的经纬度转成投影坐标去查数据库。

请求里三个要素不能少：源 CRS、目标 CRS、坐标。CRS 的写法要与 GeoServer 认识的一致，EPSG:4326 这种带前缀的写法通用，直接写 4326 有的版本也认，但不要依赖。坐标顺序是容易出错的地方：同样的数字，按经度纬度还是纬度经度解释，结果差得很远。GeoServer 的 REST 参数一般按 x、y 顺序，即经度在前、纬度在后，和 EPSG:4326 官方定义的轴序（纬度在前）相反，调用前务必确认一次。

```csharp
var transformService = factory.CreateTransformService();

// 转换坐标
var result = await transformService.TransformAsync(
    new CoordinateTransformRequest
    {
        SourceCRS = "EPSG:4326",
        TargetCRS = "EPSG:3857",
        Coordinates = new[] { 116.4074, 39.9042 }
    });

Console.WriteLine($"转换后坐标: {result.X}, {result.Y}");
```

转换结果的可信度取决于目标坐标系的原点、单位和范围。EPSG:3857 是 Web 墨卡托，单位是米，适合网页地图；把经纬度直接当米去参与距离计算，会得到完全错误的结论。转换之后检查一下数值范围，比如 Web 墨卡托的 x 应在正负两千万米左右，明显超出说明前面某一步用错了坐标系。

批量转换时不要一个点发一次请求。能一次传多个点的接口尽量批量传，不能批量就在客户端用本地坐标转换库做，把 GeoServer 留给它擅长的渲染和查询。

## 16.3 URLCheckService - URL验证

GeoServer 配置数据存储或远程 WMS 时经常要填 URL，填错了要等到第一次请求才发现。URLCheckService 让服务端主动去访问一个地址，提前确认它是否可达、返回什么状态。配置远程数据源、级联 WMS、外部图标之前先跑一次检查，能省掉不少"保存成功但用不了"的困惑。

检查结果只有有效和无效两种，背后可能是完全不同的原因：DNS 解析不了、连接被防火墙挡住、目标返回 404、证书过期、需要认证。看到无效时，先拿到更详细的错误信息（如果接口返回），再按网络、目标服务、证书的顺序排查。

服务端发出的请求受它所在网络的限制。内网地址在服务器上通、在你的电脑上不通，反过来也一样。检查结果要结合部署环境理解。

```csharp
var urlCheckService = factory.CreateURLCheckService();

// 验证外部URL
var isValid = await urlCheckService.CheckURLAsync("https://example.com/wms");
Console.WriteLine($"URL 有效性: {isValid}");
```

URL 检查不能替代真正的连通性验证。地址可达不代表返回的内容符合预期，级联 WMS 还要求对方返回合法的 Capabilities 文档。检查通过之后，仍然要用一次实际请求确认服务类型、版本、图层列表是否正确。

对可以访问任意地址的服务器来说，URL 检查本身也是一个安全边界。生产环境应当限制它能访问的地址范围，避免被用来探测内网。

## 16.4 KeystoreService - 密钥存储

密钥库（keystore）存放证书和私钥，用在 HTTPS 服务端、客户端证书认证、以及需要签名的场景。GeoServer 的密钥库端点可以列出当前配置的密钥库、查看类型和别名，也可以上传新的密钥库文件。文件名、密码、类型三者必须匹配，JKS 和 PKCS12 的格式不能混。

密钥库的密码和私钥密码是两回事，很多操作失败就败在只填了一个。上传时接口要求的参数在文档里写得很细，按类型准备对应格式的文件，再用列表接口确认别名出现，是最省时间的验证方式。

生产环境不要把密钥库文件提交到代码仓库，也不要用示例密码。证书有有效期，过期前要更换，换证书时注意服务端配置里引用的别名是否同步更新。

```csharp
var keystoreService = factory.CreateKeystoreService();

// 获取密钥库信息
var keystores = await keystoreService.GetKeystoresAsync();

foreach (var keystore in keystores)
{
    Console.WriteLine($"密钥库: {keystore.Name}");
    Console.WriteLine($"类型: {keystore.Type}");
}
```

密钥库属于低频但高风险的操作。改错了可能导致 HTTPS 不可用，排查时先看服务端日志里的证书加载错误，再看密钥库端点返回的别名和类型是否和预期一致。改之前备份原文件是基本操作。

## 16.5 Blobstore Service - Blob存储

GeoServer 默认把配置和数据存在本地磁盘。Blob 存储扩展允许把一部分内容（比如缓存瓦片、资源文件）放到 S3 或其他对象存储里，多节点部署时共享同一份数据，也方便扩容。前提是装了对应的存储插件，并配好访问凭证。

创建配置时几个字段最关键：Name 是之后引用这个存储用的名字，Type 决定用哪个插件，Configuration 里的键随类型不同而不同。S3 一般要 bucket、prefix、region，凭证则走 GeoServer 的凭据管理或环境变量，尽量不要把密钥写进请求体。

创建后先用列表接口确认存储出现在配置中，再让需要它的功能引用这个名字。引用名字写错时，相应功能会退回默认的本地存储，问题不会立刻暴露。

```csharp
var blobstoreService = factory.CreateBlobstoreService();

// 配置S3 Blob存储
var s3Config = new BlobstoreConfig
{
    Name = "s3_storage",
    Type = "S3",
    Configuration = new Dictionary<string, object>
    {
        ["bucket"] = "my-geoserver-bucket",
        ["prefix"] = "tiles/",
        ["region"] = "us-west-2"
    }
};

await blobstoreService.CreateBlobstoreAsync(s3Config);
```

对象存储的权限要单独配置。GeoServer 进程需要有桶的读写权限，只给读会写不进缓存，只给写又读不回文件。配置完以后用一个上传、再读回的动作验证一遍，比只看创建接口返回成功可靠。

多节点共享存储时，一致性和延迟要纳入考虑。对象存储不是本地磁盘，列目录和读小文件的延迟更高，把高频访问的内容全部挪过去可能拖慢渲染。按数据类型区分：缓存瓦片适合放对象存储，样式和配置仍留在本地或数据库。

## 16.6 本章小结

本章学习了GeoServer的高级功能和扩展服务，包括数据导入、坐标转换、URL验证、密钥管理和Blob存储。

这几类扩展的共同点是"按需启用、依赖配置"。调不通时先确认插件是否安装、端点是否存在，再确认配置里的名字、路径、凭证是否和服务端一致。它们不像核心的图层接口那样有稳定的错误语义，多数失败只能从服务端日志里找原因，所以部署时把日志级别调合适、把扩展的初始化步骤写进部署脚本，比事后排查省事。

扩展功能也带来运维成本：数据导入会产生临时文件，密钥库涉及证书更新，对象存储增加外部依赖。引入之前想清楚是否真的需要——很多需求用核心接口加一次数据预处理就能满足。
