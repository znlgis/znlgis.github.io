# 第17章：错误处理与最佳实践

前几章的示例都在演示"怎么调通"，这一章往回退一步，讨论脚本真正上线后要面对的问题：网络会抖、服务会重启、权限会过期、磁盘会满。GeoServer 的 REST 接口是普通的 HTTP 服务，客户端能做的事和调用任何 HTTP API 没有本质区别——区分可重试错误与不可重试错误、控制并发、记录足够的上下文、把配置和凭据从代码里挪出去。

下面按异常处理、性能、日志、配置、安全、监控、部署检查的顺序展开。每条都给出可以照抄的代码骨架，重点在说明取舍：什么情况下该重试、并发开多大、日志记到什么程度。

## 17.1 异常处理策略

在业务代码里到处写 try/catch 是失败的做法：每处都要判断状态码、决定重试几次、记录什么日志，最后必然出现十几份略有差异的重复逻辑。把重试和错误分类收敛到一个地方，业务方法只负责构造请求和处理成功结果，失败路径统一走这个包装。

分类要做对才有意义。5xx 是服务端或数据源的问题，可能过一会儿恢复，值得重试；429 是限流，等一段时间再试通常有效；4xx 里的 404、400、401、403 重试多少次结果都一样，直接抛给上层处理更快。重试次数别设太大，三次已经能覆盖大部分瞬时抖动，再多重试只会拖长故障恢复时间。

### 17.1.1 统一异常处理

示例里的 ExecuteWithRetryAsync 用指数退避控制重试间隔：第 i 次失败后等 delayMs 乘上 i，第二次比第一次等得久。真实实现里通常再加一点随机抖动，避免多个客户端在同一时刻重试形成尖峰。IsRetriable 只把 5xx 和 429 当可重试错误，其余原样抛出。

用 C# 的异常过滤器 when (IsRetriable(ex)) 而不是在 catch 里 if 判断，好处是过滤器返回 false 时异常不会被这个 catch 吃掉，会继续向上抛，调用栈保留得更完整。网络层的 HttpClient 超时通常表现为 TaskCanceledException，而不是 GeoServerRequestException，需要单独处理。

```csharp
public class GeoServerExceptionHandler
{
    public static async Task<T> ExecuteWithRetryAsync<T>(
        Func<Task<T>> operation,
        int maxRetries = 3,
        int delayMs = 1000)
    {
        for (int i = 0; i < maxRetries; i++)
        {
            try
            {
                return await operation();
            }
            catch (GeoServerRequestException ex) when (IsRetriable(ex))
            {
                if (i == maxRetries - 1) throw;
                await Task.Delay(delayMs * (i + 1));
            }
        }
        throw new InvalidOperationException("Unreachable");
    }

    private static bool IsRetriable(GeoServerRequestException ex)
    {
        return ex.StatusCode >= 500 || ex.StatusCode == 429;
    }
}
```

## 17.2 性能优化最佳实践

GeoServer 客户端的主要性能瓶颈通常不在 CPU，而在连接数和服务端处理能力。一次发布几百个图层，如果每个请求都开一个新连接、并发全开，服务端线程池很快被占满，后面的请求排队直到超时。限制并发比提高并发更常带来收益。

另一个常见问题是 HttpClient 的创建方式。每次请求 new 一个 HttpClient 会耗尽本地端口；正确做法是复用同一个实例，或者用 IHttpClientFactory 管理生命周期。第03章已经讲过封装的实现，这里只强调一点：连接复用和并发上限要一起配，缺一个都会出问题。

### 17.2.1 连接池管理

SemaphoreSlim 在这里充当并发闸门：同时最多 10 个操作进入临界区。上限取多少要看服务端配置和压测结果，没有万能值。一般从 5 到 10 起调，观察请求排队时间和错误率；服务端 CPU 还没满、但客户端排队明显，说明可以适当放宽。

用静态 SemaphoreSlim 意味着整个进程共享这个额度，包括不同业务模块发起的调用。模块之间可能互相影响：批量导入占满了额度，健康检查也拿不到槽位。流量分级明显的系统，按用途拆成几个额度更合理。

```csharp
public class GeoServerConnectionPool
{
    private static readonly SemaphoreSlim _semaphore = new(10, 10);

    public static async Task<T> ExecuteAsync<T>(Func<Task<T>> operation)
    {
        await _semaphore.WaitAsync();
        try
        {
            return await operation();
        }
        finally
        {
            _semaphore.Release();
        }
    }
}
```

### 17.2.2 批量操作优化

批量操作有两种策略：串行执行和分批并发。串行最简单，速度最慢；全量并发最快，但容易把服务端打垮，也会让失败重试变得难以控制。分批并发是折中：每批固定数量同时执行，批与批之间留出间隔，服务端始终处在可控压力下。

示例里批大小是 5，批间隔 1 秒。这两个数字要根据实际场景调整：创建图层涉及数据源读取，比较重，批小一点；读取元数据的批量请求很轻，批可以大。间隔的作用是给服务端留出清理和 GC 的时间，不是必需的，但在资源紧张的环境里能明显降低错误率。

```csharp
public class BatchOperationOptimizer
{
    public async Task<Dictionary<string, bool>> CreateMultipleLayersAsync(
        List<Layer> layers,
        int batchSize = 5)
    {
        var results = new Dictionary<string, bool>();
        
        for (int i = 0; i < layers.Count; i += batchSize)
        {
            var batch = layers.Skip(i).Take(batchSize);
            var tasks = batch.Select(async layer =>
            {
                try
                {
                    await _layerService.CreateLayerAsync(layer);
                    return (layer.Name, true);
                }
                catch
                {
                    return (layer.Name, false);
                }
            });

            var batchResults = await Task.WhenAll(tasks);
            foreach (var (name, success) in batchResults)
            {
                results[name] = success;
            }

            // 批次间延迟，避免服务器过载
            if (i + batchSize < layers.Count)
            {
                await Task.Delay(1000);
            }
        }

        return results;
    }
}
```

## 17.3 日志记录最佳实践

日志要能回答三个问题：发生了什么操作、用了多长时间、失败时错误是什么。示例里的 LoggedOperationAsync 用 Stopwatch 计时，成功和失败各记一条，异常对象一起传给日志框架，堆栈不会丢。

只记操作名不够。同一个"创建图层"可能对应几十个图层，日志里得带图层名或请求标识，否则事后翻日志只能看到一串相同的文字。推荐在操作名里带上关键参数，或者用结构化日志的占位符把参数单独记录，便于检索。

耗时日志要注意采样。高频调用每次都记会淹没真正有用的信息，正常情况可以只记 debug 级，超过阈值再记 warn。把耗时阈值做成配置项，不同环境用不同标准。

```csharp
public class GeoServerLogger
{
    private readonly ILogger _logger;

    public async Task<T> LoggedOperationAsync<T>(
        string operationName,
        Func<Task<T>> operation)
    {
        var sw = Stopwatch.StartNew();
        _logger.LogInformation($"开始执行: {operationName}");

        try
        {
            var result = await operation();
            sw.Stop();
            _logger.LogInformation(
                $"完成: {operationName}, 耗时: {sw.ElapsedMilliseconds}ms");
            return result;
        }
        catch (Exception ex)
        {
            sw.Stop();
            _logger.LogError(ex,
                $"失败: {operationName}, 耗时: {sw.ElapsedMilliseconds}ms");
            throw;
        }
    }
}
```

## 17.4 配置管理最佳实践

配置从环境变量读，是十二要素应用的基本要求。同一份程序要能在开发、测试、生产三套环境里跑，差别只在环境变量，不能靠改代码或换配置文件。GeoServer 的地址、账号、超时时间都属于配置，硬编码在代码里的后果是每次换环境都要重新编译。

环境变量方式也有局限：密码放在环境变量里，进程列表和崩溃转储都可能泄露它。更稳的做法是接密钥管理服务，或者至少限制环境变量的可见范围。示例里给了默认值，生产环境应当把默认值当成错误处理——没配就启动失败，比带着默认密码连到错误的地方安全。

读取之后必须校验。URL 格式、超时是否为正数、账号密码是否为空，这些检查放在启动阶段做，比等到第一次请求失败再排查省事得多。校验失败直接抛异常，让部署流程明确失败。

```csharp
public class ConfigurationManager
{
    public static GeoServerClientOptions LoadConfiguration()
    {
        // 从环境变量加载
        var options = new GeoServerClientOptions
        {
            BaseUrl = Environment.GetEnvironmentVariable("GEOSERVER_URL")
                     ?? "http://localhost:8080/geoserver",
            Username = Environment.GetEnvironmentVariable("GEOSERVER_USER")
                      ?? "admin",
            Password = Environment.GetEnvironmentVariable("GEOSERVER_PASSWORD")
                      ?? "geoserver",
            TimeoutSeconds = int.Parse(
                Environment.GetEnvironmentVariable("GEOSERVER_TIMEOUT") ?? "30")
        };

        // 验证配置
        ValidateConfiguration(options);

        return options;
    }

    private static void ValidateConfiguration(GeoServerClientOptions options)
    {
        if (string.IsNullOrEmpty(options.BaseUrl))
            throw new ArgumentException("BaseUrl is required");

            throw new ArgumentException("BaseUrl must be a valid URL");

        if (string.IsNullOrEmpty(options.Username))
            throw new ArgumentException("Username is required");
    }
}
```

## 17.5 安全最佳实践

GeoServer 的管理接口权限很大，一个泄露的账号可以改配置、删图层、读所有数据。客户端代码里出现明文密码，是最常见的低级风险：代码进仓库、镜像被拉取、日志打印请求体，任何一个环节都会把密码带出去。

权限要最小化。发布脚本只需要数据存储和图层相关的权限，就用专门的账号，不要直接拿 admin。GeoServer 的角色系统支持按工作空间授权，给每个租户、每类任务建独立账号，泄露时影响范围小得多。

### 17.5.1 凭据管理

```csharp
// 不要在代码中硬编码凭据
// ❌ 错误做法
var options = new GeoServerClientOptions
{
    Username = "admin",
    Password = "geoserver" // 硬编码密码
};

// ✅ 正确做法
var options = new GeoServerClientOptions
{
    Username = Environment.GetEnvironmentVariable("GEOSERVER_USER"),
    Password = Environment.GetEnvironmentVariable("GEOSERVER_PASSWORD")
};
```

### 17.5.2 HTTPS 使用

生产环境必须走 HTTPS，这一点没有讨论余地。Basic 认证的密码在 HTTP 下是 Base64 编码传输，等于明文；中间人只要拿到一个请求就能复用凭据。内网也不是安全区，横向移动的攻击者拿到的往往就是内网凭据。

客户端校验服务端证书是默认行为，不要为了"方便"关掉证书校验。自签证书的环境，把 CA 证书装进信任链，而不是在代码里跳过验证。反过来，服务端也应当只信任明确的客户端证书，而不是放行所有来源。

```csharp
// 生产环境始终使用 HTTPS
var options = new GeoServerClientOptions
{
    BaseUrl = "https://geoserver.example.com/geoserver", // 使用HTTPS
    Username = GetSecureUsername(),
    Password = GetSecurePassword()
};
```

## 17.6 监控和告警

监控的价值在于"出问题时有人在看"。只把指标画在面板上，没人盯着等于没有；真正起作用的是阈值告警和通知渠道。告警要分级：服务完全不可用发紧急通知，内存偏高记一条工单，两者混在一起会让人对告警失去反应。

告警内容要包含定位信息。只说"GeoServer 离线"没法处理，附上实例地址、检测时间、最近一次成功请求的时间，收到通知的人才能直接上手。告警频率也要控制，同一个故障在恢复前持续告警，会迅速消耗值班人的注意力；设置抑制窗口，同一实例的同类告警在十分钟内只发一次。

```csharp
public class MonitoringService
{
    public async Task MonitorSystemHealthAsync()
    {
        var checker = new SystemHealthChecker();
        var report = await checker.CheckHealthAsync();

        {
            await SendAlertAsync("GeoServer 离线");
        }

        if (report.MemoryUsagePercent > 90)
        {
            await SendAlertAsync($"内存使用率过高: {report.MemoryUsagePercent}%");
        }

        foreach (var error in report.Errors)
        {
            await SendAlertAsync($"系统错误: {error}");
        }
    }

    private async Task SendAlertAsync(string message)
    {
        // 发送告警通知（邮件、短信、企业微信等）
        _logger.LogCritical(message);
        // 实现具体的告警逻辑
    }
}
```

## 17.7 部署清单

上线前跑一遍自动化检查，比依赖人工核对可靠。检查项要能被机器判定：连接能不能通、账号有没有权限、数据目录里该在的文件在不在、缓存配置有没有指到不存在的路径。检查结果输出成结构化列表，哪一项失败一目了然。

清单不是一次性的。每次改配置、升级版本、迁移服务器都要重跑。把清单脚本放进部署流水线，失败就中断发布，能挡住大部分低级问题。

### 17.7.1 生产部署检查

示例里的五个检查项覆盖了主要风险面：配置正确、连接可用、权限足够、资源齐全、缓存有效。实际项目可以继续加：HTTPS 是否启用、证书是否快过期、磁盘剩余空间、数据源连接池大小、备份任务是否在跑。

检查失败时的行为要事先想好。连接测试失败说明服务不可用，应当直接阻断发布；缓存配置检查失败可能只影响性能，不一定要阻断。给每项检查标上严重级别，流水线按级别决定是中断还是只告警。

```csharp
public class DeploymentChecklist
{
    public async Task<ChecklistResult> RunPreDeploymentChecksAsync()
    {
        var result = new ChecklistResult();

        // 1. 验证配置
        result.AddCheck("配置验证", ValidateConfiguration());

        // 2. 测试连接
        result.AddCheck("连接测试", await TestConnectionAsync());

        // 3. 验证权限
        result.AddCheck("权限验证", await ValidatePermissionsAsync());

        // 4. 检查资源
        result.AddCheck("资源检查", await CheckResourcesAsync());

        // 5. 验证缓存配置
        result.AddCheck("缓存配置", await ValidateCacheConfigAsync());

        return result;
    }
}
```

## 17.8 本章小结

把这一章的内容归纳成几条可以直接执行的规则：可重试错误只包括 5xx 和 429，重试用指数退避并加上限；并发用信号量限制在服务端能承受的范围，批量操作分批执行；每次重要操作记录操作名、耗时和失败原因；配置和凭据从环境变量或密钥服务读取，启动时校验；生产环境强制 HTTPS，账号按最小权限分配；健康检查覆盖进程、资源和外部依赖三个层面；上线前跑自动化检查。

本章学习了：
1. 异常处理和重试策略
2. 性能优化最佳实践
3. 日志记录和监控
4. 配置和安全管理
5. 部署前检查清单

还有两条经验。第一，代码里的示例（比如重试次数、并发上限、阈值）都只是起点，真实参数要拿压测数据定，不要照抄。第二，排障时先确认事实再看配置：服务版本对不对、请求有没有到达服务端、返回的状态码是什么，这三项确认完，再去看代码逻辑。
