# 第17章 - 性能优化与最佳实践

## 17.1 渲染优化

OpenLayers 的渲染开销来自三块：要素数量（每帧要处理多少个图形）、样式复杂度（每个图形要画多少条指令）、重绘频率（一帧画几次）。优化就是在这三个维度上做减法。加机器、换浏览器解决不了根本问题，因为瓶颈通常在主线程的 JavaScript 与 Canvas 绘制路径上。

先建立基线再动手：用浏览器性能面板录制一段操作，看 `postrender` 一帧耗时多少、哪些函数占比最高；用 `map.getSize()` 与实际要素数量估算密度。没有基线就开始调参数，改完不知道有没有效果，也很难判断哪个改动起作用。

### 17.1.1 图层优化

`renderMode: 'image'` 让矢量图层先渲染到一张离屏图片再贴到主画布。它把“每个要素一条绘制指令”合并成“一次贴图”，要素特别多（几万以上）时效果明显，平移缩放更流畅。代价是每次地图变化都要重画整张图，要素少、变化频繁的场景反而更慢；另外基于 DOM 的拾取在 image 模式下仍然可用，但像素级的精细定位会受影响。

`updateWhileAnimating` 与 `updateWhileInteracting` 是一对开关：默认 false 时，视图动画或交互期间不重绘矢量图层，等停稳后再画。这能避免拖动时每帧重算所有要素，代价是拖动过程中矢量会“拖影”或暂时消失。要素数量大时保持 false 是必要的；要素少、要求跟手时可以打开。

`renderBuffer` 是图层绘制时的缓冲像素，默认 100。绘制区域比可视范围四周各扩 100 像素，平移时可以直接复用刚画好的部分，减少重绘。值越大越平滑，但每次绘制的区域也越大，内存占用上升。地图容器小、要素密集时把它调小到 50 甚至 0，可以降低单次绘制的开销。

`minResolution` 与 `maxResolution` 控制图层在什么缩放级别显示。用途有两类：一是性能，小比例尺下不渲染细节图层，省掉大量不可见的绘制；二是规范，某些要素在小比例尺下根本不应出现。注意这两个参数的单位是“分辨率”（地图单位/像素），不是缩放级别，数值方向与直觉相反：分辨率越大比例尺越小。

```javascript
// 使用 renderMode: 'image' 优化大量矢量数据
const optimizedLayer = new VectorLayer({
  source: vectorSource,
  renderMode: 'image', // 渲染为图像，减少重绘
  updateWhileAnimating: false,
  updateWhileInteracting: false
});

// 设置渲染缓冲区
const layer = new VectorLayer({
  source: vectorSource,
  renderBuffer: 100 // 默认100像素
});

// 图层分辨率限制
const layer = new VectorLayer({
  source: vectorSource,
  minResolution: 10,  // 分辨率 < 10 时不渲染
  maxResolution: 1000 // 分辨率 > 1000 时不渲染
});
```

### 17.1.2 样式优化

样式函数会被非常频繁地调用：每个可见要素、每次渲染都要调一次。在函数里 `new Style()`、`new Fill()`、`new Stroke()` 是最常见的性能杀手，几万个要素时每帧创建几十万个对象，GC 压力直接体现为卡顿。`styleCache` 把相同样式缓存起来复用，是成本最低的优化。

缓存键的选择决定了命中率。示例用要素的 `type` 属性做键，前提是同一类型的要素样式完全一致；如果样式还依赖数值大小、选中状态、时间，键里必须包含这些维度，否则会出现“不同类型显示成同一颜色”的错误。缓存不需要手动清理，样式种类是有限的，内存占用可控。

`simpleStyle` 去掉了 `stroke`，注释说减少渲染开销。描边确实比填充贵——填充一次绘制，描边在多数实现里要描一圈轮廓，边数多时开销明显。但去掉描边会影响可读性，浅色底图上纯填充的点几乎看不见。正确的取舍是按缩放级别切换，而不是一律去掉。

样式还可以用 `ol/style/Style` 的 `zIndex` 控制绘制顺序，用 `declutter: true` 让标签自动避让。`declutter` 能显著改善密集标签的可读性，代价是每次渲染都要做碰撞检测，标签多时开销上升。开启前确认要素数量在可控范围。

```javascript
// 样式缓存
const styleCache = {};

function getCachedStyle(type) {
  if (!styleCache[type]) {
    styleCache[type] = new Style({
      image: new Circle({
        radius: 6,
        fill: new Fill({ color: getColor(type) })
      })
    });
  }
  return styleCache[type];
}

const layer = new VectorLayer({
  source: vectorSource,
  style: (feature) => getCachedStyle(feature.get('type'))
});

// 简化样式
const simpleStyle = new Style({
  image: new Circle({
    radius: 4,
    fill: new Fill({ color: 'blue' })
  })
  // 不使用 stroke，减少渲染开销
});
```

### 17.1.3 WebGL 渲染

Canvas 2D 在几万个点以上就会明显吃力，WebGL 能把这个量级提到十万级甚至更高。`WebGLPointsLayer` 用 GPU 批量绘制点，样式用一个描述对象而不是 `Style` 实例，支持大小、颜色、透明度、旋转等属性的表达式。它适合海量点数据（POI、监测站、轨迹点），不适合需要复杂符号或频繁修改单个要素样式的场景。

`style.symbol` 里的 `symbolType` 支持 `circle`、`square`、`triangle`、`image` 等；`size`、`color`、`opacity` 都可以写成表达式对象（比如按属性值设色），表达式语法与 Mapbox 风格类似。颜色写 `'red'` 这样的字符串可以，但复杂配色建议用表达式，便于按数据驱动。

WebGL 图层的限制要提前知道：不支持 `Select` 交互直接拾取（需要自己实现像素拾取或借助 `forEachFeatureAtPixel` 的兼容层）、不支持样式里的自定义 Canvas 绘制、在某些集显或移动设备上可能因 WebGL 上下文限制而失效。引入前先确认目标浏览器与设备。

同类的 WebGL 图层还有 `WebGLVectorLayer`（可以画线和面）与 `WebGLTileLayer`（栅格）。选用原则是“数据量大且样式简单”：样式一复杂，WebGL 的准备工作量与兼容成本就会超过收益。

```javascript
import WebGLPointsLayer from 'ol/layer/WebGLPoints';

// 大量点数据使用 WebGL
const webglLayer = new WebGLPointsLayer({
  source: vectorSource,
  style: {
    symbol: {
      symbolType: 'circle',
      size: 8,
      color: 'red',
      opacity: 0.8
    }
  }
});
```

## 17.2 数据优化

渲染优化的收益有上限，数据量的削减才是根本。一个 5 万个顶点的面，无论怎么调样式参数都比一个 500 个顶点的面慢。数据优化分两个方向：减少顶点（简化、抽稀）和减少要素（聚合、按比例尺过滤），前者降单要素成本，后者降要素数量。

### 17.2.1 数据简化

`geometry.simplify(tolerance)` 用 Douglas-Peucker 算法减少顶点，容差单位是地图单位。这个操作会**修改几何本身**（返回新几何但基于原坐标计算），频繁调用会有可观的计算开销。示例第二段把简化写进样式函数，并在函数里 `feature.setGeometry(simplified)`——这是有问题的：样式函数每帧都会被调用，几何会被反复简化，同时修改要素又触发重绘，形成循环。

正确的做法是在数据加载后做一次简化，按比例尺准备多个版本：小比例尺用粗简化版本，大比例尺用原始数据，用 `minResolution`/`maxResolution` 图层或在 `loadend` 里切换数据源。简化一次、使用多次，才是省时间的做法。

容差怎么定？经验是按当前分辨率取几倍：视野分辨率 10 米/像素时，容差取 20 到 50 米，肉眼几乎看不出差异；容差超过分辨率的 10 倍，形状会明显变形。对线状要素（道路、河流）可以放宽，对面状要素（地块、建筑）要保守，因为面积和形状是业务属性。

```javascript
// 几何简化
const simplifiedGeometry = geometry.simplify(tolerance);

// 根据缩放级别简化
const layer = new VectorLayer({
  source: vectorSource,
  style: (feature, resolution) => {
    const geom = feature.getGeometry();
    const simplified = geom.simplify(resolution * 10);
    feature.setGeometry(simplified);
    return style;
  }
});
```

### 17.2.2 聚合

点聚合把距离相近的点合并成一个带计数的聚合点，缩放级别越大聚合越少，直到完全展开。它是解决“十万个点堆在一起看不清”的标准手段，同时把渲染要素数从原始点数降到屏幕上的聚合点数，性能与可读性双赢。

`distance` 是聚合半径（像素），`minDistance` 是只在聚合结果超过这个距离时才重新计算，用于减少抖动。两个值都在像素空间，与投影无关。`Cluster` 源对外表现为一个普通矢量源，样式函数里通过 `feature.get('features')` 拿到被聚合的要素数组，数量大于 1 时画聚合样式，等于 1 时画单个要素样式。

示例在 `change:resolution` 里动态改 `distance`：缩放越大距离越小，最终为 0 表示不聚合。`setDistance` 会触发源重新聚合并重绘，频繁缩放时这个调用会很多，应当做防抖或者只在 `moveend` 时调整。`getZoom()` 返回可能为小数（视图正在动画），用它做分支判断时注意阈值附近的抖动。

聚合会改变拾取语义：点击聚合点拿到的是聚合后的要素，不是原始要素之一。交互代码要从 `feature.get('features')` 里取原始要素再处理，直接当普通点用会导致属性空白或者报错。

```javascript
import Cluster from 'ol/source/Cluster';

// 点聚合
const clusterSource = new Cluster({
  source: vectorSource,
  distance: 50,
  minDistance: 20
});

// 动态聚合距离
map.getView().on('change:resolution', () => {
  const zoom = map.getView().getZoom();
  const distance = zoom < 10 ? 80 : zoom < 14 ? 40 : 0;
  clusterSource.setDistance(distance);
});
```

### 17.2.3 数据加载策略

`loadingstrategy` 决定 `VectorSource` 什么时候去请求数据。`all` 是默认值，只请求一次；`bbox` 按当前视野范围请求，适合数据量大、只关心当前区域的场景；`tile` 把范围切成瓦片逐块请求，适合需要平滑加载的大范围数据源。选错策略的后果是“要么一次加载太多、要么拖动时空白”。

`bbox` 与 `tile` 都需要 `loader` 或 `url` 函数来真正发出请求。示例里 `loader: loadFeatures` 只给了函数名，函数本身的实现不在片段中——它接收 `(extent, resolution, projection, success, failure)` 五个参数，必须调用 `success(features)` 或 `failure(error)` 来结束这次加载，否则该范围会一直是“加载中”，后续同范围请求被阻塞。

`tile(createXYZ({ tileSize: 512 }))` 创建的是按 512 像素瓦片划分的加载策略。选择瓦片尺寸要与服务端的服务能力匹配：服务端按固定瓦片切图时用它的尺寸，自定义接口可以自由选。瓦片尺寸越大，单次请求的数据越多、请求总数越少。

分页加载用于“一次取不完”的场景：循环按页请求、`addFeatures` 追加，直到某一页不足 `pageSize` 为止。这段代码有两个隐患：`hasMore = features.length === pageSize` 在数据总量恰好是整数倍时会多发一次空请求（无害），但 `vectorSource` 在循环期间会反复触发 `addfeature` 事件，界面如果监听这些事件做刷新，会卡住；另一个是循环没有上限保护，服务端忽略分页参数时 `hasMore` 永远是 true，形成死循环。加一个最大页数限制。

```javascript
import { bbox, tile } from 'ol/loadingstrategy';
import { createXYZ } from 'ol/tilegrid';

// BBOX 加载
const bboxSource = new VectorSource({
  loader: loadFeatures,
  strategy: bbox
});

// 瓦片加载
const tileSource = new VectorSource({
  loader: loadFeatures,
  strategy: tile(createXYZ({ tileSize: 512 }))
});

// 分页加载
async function loadWithPagination(extent, resolution) {
  const pageSize = 1000;
  let page = 0;
  let hasMore = true;
  
  while (hasMore) {
    const features = await fetchFeatures(extent, page, pageSize);
    vectorSource.addFeatures(features);
    hasMore = features.length === pageSize;
    page++;
  }
}
```

## 17.3 内存优化

地图应用的内存泄漏大多来自“引用了已卸载的对象”：事件监听没有注销、定时器没有清理、数据源清空了但要素还被别的数组引用着。长时间运行的看板类页面，几小时不刷新就卡顿，基本都是这个原因。

### 17.3.1 清理资源

移除图层用 `map.removeLayer(layer)`，图层从地图上消失但对象还在内存里；如果不再使用，还应当清空数据源，让要素可以被回收。`layer.getSource().clear()` 清空要素，数据源对象本身保留，需要彻底释放时把图层与数据源的引用都置空。`map.removeLayer` 不会自动销毁图层，反复创建、移除图层而不清理数据源，内存会持续增长。

`ol/Observable` 的 `on` 方法返回一个监听键（key），用 `unByKey(key)` 可以精确注销一个监听。这比 `un(type, listener)` 方便，因为不需要保存 listener 的函数引用；`un` 要求传同一个函数对象，匿名函数注册后就无法注销，只能靠 `unByKey`。事件监听的数是内存泄漏的高发点。

`destroyMap` 遍历所有图层、清空数据源，然后 `map.setTarget(null)`。`setTarget(null)` 把地图从 DOM 上摘下来，停止渲染循环，释放 WebGL 上下文相关资源。这是卸载地图的标准做法。示例里判断了 `source && source.clear`，因为部分图层（如 GroupLayer）没有 `clear` 方法，直接调用会抛错。

`setTarget(null)` 之后如果还持有地图对象的引用，地图本身及其图层不会被回收；页面组件卸载时把 `map` 引用也置空。如果应用里有多个地图实例反复创建，最好确认旧实例确实被 GC 回收，用 `WeakRef` 或内存面板验证。

```javascript
// 及时移除不用的图层
map.removeLayer(oldLayer);
oldLayer.getSource().clear();

// 清理事件监听
import { unByKey } from 'ol/Observable';

const key = map.on('click', handler);
// 使用后移除
unByKey(key);

// 销毁地图
function destroyMap() {
  map.getLayers().forEach(layer => {
    const source = layer.getSource();
    if (source && source.clear) {
      source.clear();
    }
  });
  map.setTarget(null);
}
```

### 17.3.2 瓦片缓存

瓦片源会把加载过的瓦片缓存在内存里，避免回看时重复请求。`XYZ` 源的 `cacheSize` 控制缓存瓦片数，默认 2048；缓存越大回看越流畅，内存占用也越大。一张 256×256 的瓦片解码后约占 256 KB，2048 张就是 500 MB 量级，移动设备上默认值偏大。

`source.getTileCache().clear()` 清空全部缓存，用于切换数据源或释放内存。注意清空后当前视野的瓦片也会被丢弃，画面会短暂空白并重新加载；只在确实需要回收时调用，不要放进渲染循环。

瓦片缓存的收益与操作模式有关：用户频繁在固定区域来回平移时，大缓存命中率高；一路向前的浏览（比如沿公路前进）命中率低，缓存只是占用内存。按业务场景设置 `cacheSize`，比一律用默认值更合理。

```javascript
// 控制瓦片缓存大小
const source = new XYZ({
  url: '...',
  cacheSize: 512 // 默认 2048
});

// 清理瓦片缓存
source.getTileCache().clear();
```

## 17.4 交互优化

地图上大量的事件是高频的：指针移动每秒几十次，视图变化在动画期间每帧一次。每个事件都直接触发业务逻辑，很快就会把主线程占满。防抖（debounce）与节流（throttle）是两种最基本的控制手段，理解它们的区别比记住实现更重要。

### 17.4.1 防抖节流

防抖是“等事件停下来再做”：每次触发都重置定时器，只有静默超过 `wait` 毫秒才真正执行。它适合“最终状态才有意义”的场景，比如地图移动结束后加载数据——中间过程加载了也会被下一次移动覆盖，纯属浪费。`moveend` 本身已经是移动结束事件，再包一层防抖主要防的是连续快速拖动产生的密集 `moveend`。

节流是“固定间隔最多做一次”：第一次立即执行，之后在 `limit` 毫秒内的触发被丢弃。它适合“过程中需要持续反馈”的场景，比如鼠标移动时更新坐标显示、悬停高亮。节流保证有反馈，又不会让回调把帧占满。

两个实现都用闭包保存状态，`func.apply(this, args)` 保留了调用时的 `this` 与参数，直接写 `func(...args)` 会丢失 `this`，在类方法里会报错。防抖的定时器需要在组件销毁时 `clearTimeout`，否则卸载后回调仍会执行并访问已销毁的地图。这是最容易漏掉的清理项。

移动端上 `pointermove` 更密集，`limit` 可以设到 100 毫秒以上；桌面端 50 毫秒的节流已经足够流畅。事件处理器里如果要计算距离、面积，宁可在节流之后再算，也不要算完再丢弃结果。

```javascript
// 防抖
function debounce(func, wait) {
  let timeout;
  return function(...args) {
    clearTimeout(timeout);
    timeout = setTimeout(() => func.apply(this, args), wait);
  };
}

// 地图移动防抖
map.on('moveend', debounce(() => {
  loadDataForExtent();
}, 300));

// 节流
function throttle(func, limit) {
  let inThrottle;
  return function(...args) {
    if (!inThrottle) {
      func.apply(this, args);
      inThrottle = true;
      setTimeout(() => inThrottle = false, limit);
    }
  };
}

// 鼠标移动节流
map.on('pointermove', throttle((event) => {
  updateTooltip(event);
}, 50));
```

### 17.4.2 异步处理

查询类操作应当异步执行并且要有加载状态。`showLoading()` / `hideLoading()` 放在 `try/finally` 里，保证请求失败时也能关掉 Loading——这是最常见的“转圈圈转不停”的来源。`finally` 不处理错误，异常会继续向上抛，如果调用方没有 catch，控制台会出现未处理拒绝。

异步之后还有一个并发问题：用户连续点击，多个请求同时在飞，后发的请求可能先返回，界面显示的是旧数据。解决办法是给每次请求编号，回调时只处理最新编号；或者用 `AbortController` 取消上一次请求。示例没有处理这个，快速连点时会看到结果闪烁。

Web Worker 用来把重计算移出主线程。`worker.postMessage` 传递大数据时会做结构化克隆，几兆的要素数组克隆本身就有开销，频繁传递反而更慢。更高效的方式是传 `ArrayBuffer`（可转移对象，零拷贝），在 worker 里解析后再把结果转移回来。

Worker 里的代码不能访问 DOM 与地图对象，只能处理纯数据。示例里 worker 返回 `features` 后直接 `addFeatures`，要求返回的对象已经是 OpenLayers 可识别的要素结构；通常在 worker 里解析 GeoJSON 文本，返回坐标数组与属性，主线程再构造要素。Worker 用完要 `terminate()`，否则线程常驻。

```javascript
// 异步要素查询
map.on('singleclick', async (event) => {
  showLoading();
  
  try {
    const features = await queryFeaturesAsync(event.coordinate);
    showResults(features);
  } finally {
    hideLoading();
  }
});

// Web Worker 处理大量数据
const worker = new Worker('dataProcessor.js');

worker.postMessage({ type: 'process', data: largeDataset });

worker.onmessage = (event) => {
  const features = event.data;
  vectorSource.addFeatures(features);
};
```

## 17.5 最佳实践

前面几节是“怎么让地图跑得快”，这一节是“怎么让代码能维护”。地图应用的复杂度很容易失控：图层创建、事件绑定、数据请求、弹窗交互全堆在一个文件里，几百行之后没人敢改。按职责拆模块，是唯一能让代码活过三个版本的办法。

### 17.5.1 代码组织

示例给出的目录结构很朴素：`map/index.js` 统一导出，`map/layers/` 放各类图层的工厂函数，`map/interactions/` 放交互，后续还可以有 `map/controls/`、`map/utils/`。核心思想是“每个模块负责创建一类对象，返回句柄，不直接操作全局地图”。

图层工厂函数接收配置、返回图层实例，调用方决定何时 `addLayer`。这样同一套工厂可以在多个页面复用，也可以在测试里单独构造。工厂函数里不要执行副作用（发请求、绑定全局事件），副作用留给调用方，模块才可预测。

模块之间通过参数传递依赖，而不是共享全局变量。地图实例作为参数一路传下去，虽然啰嗦，但能清楚看到谁依赖谁；把 `map` 挂到 `window` 上省事，代价是任何模块都能改它，出问题无从追查。

```javascript
// 模块化组织
// map/index.js
export { createMap } from './createMap';
export { layers } from './layers';
export { interactions } from './interactions';

// map/layers/basemap.js
export function createBasemapLayer(type) {
  // ...
}

// map/layers/business.js
export function createBusinessLayer(config) {
  // ...
}
```

### 17.5.2 错误处理

地图的错误大多是异步的：瓦片请求失败、数据接口超时、解析异常。同步的 `try/catch` 抓不到它们，必须在事件或 Promise 链上处理。`tileloaderror` 在单张瓦片加载失败时触发，`featuresloaderror` 在矢量源加载失败时触发，两者都是源对象上的事件，不是地图上的。

`tileloaderror` 的 `event.tile` 是失败的瓦片对象，`getTileCoord()` 返回它的层级与行列号。这个信息用来判断是“服务端整体挂了”还是“个别瓦片缺失”：整屏报错说明服务不可用，零星报错可能是数据边界或切片缺失。根据情况决定是否重试、降级到备用源。

`window.onerror` 捕获同步错误与未处理的 Promise 拒绝（部分浏览器分开处理，`onunhandledrejection` 是单独的事件）。错误上报时把地图状态（中心点、缩放级别、图层列表）一起带上，复现问题时这些信息比堆栈更有用。上报前做脱敏，不要把用户坐标、业务数据发到第三方。

```javascript
// 瓦片加载错误
source.on('tileloaderror', (event) => {
  console.error('瓦片加载失败:', event.tile.getTileCoord());
});

// 矢量数据加载错误
source.on('featuresloaderror', () => {
  showError('数据加载失败');
});

// 全局错误处理
window.onerror = (message, source, lineno, colno, error) => {
  console.error('地图错误:', error);
  // 上报错误
};
```

### 17.5.3 调试技巧

把 `map` 挂到全局，便于在控制台里直接调用方法、查看状态。`window.ol` 挂的是整个命名空间，可以用来在控制台里试验 API，比如 `ol.proj.fromLonLat([116.4, 39.9])`。这段代码放在开发环境判断里，生产构建时被 tree-shaking 掉，不会泄漏内部对象。

`import.meta.env.DEV` 是 Vite 提供的环境变量，Webpack 对应的是 `process.env.NODE_ENV !== 'production'`，不同构建工具写法不同。用错时条件永远为真或永远为假，调试代码可能被打进生产包，或者开发环境里根本没挂上。

`postrender` 里打印 `performance.now()` 得到的是绝对时间，不是渲染耗时；要测耗时需要在开始渲染时记一个时间戳，在 `postrender` 里相减。OpenLayers 没有直接提供渲染耗时事件，常见做法是包一层 `map.renderSync()` 计时，或者用浏览器性能面板。

FPS 计数的实现是每秒统计一次 `postrender` 次数，逻辑上正确，但 OpenLayers 只在需要时渲染（`setTarget(null)`、不可见标签页、没有变化时都不渲染），所以它统计的是“渲染帧率”而非“屏幕刷新率”。画面静止时 FPS 会远低于 60，这是正常的，不代表性能有问题。

```javascript
// 挂载到全局便于调试
if (import.meta.env.DEV) {
  window.map = map;
  window.ol = ol;
}

// 性能监控
map.on('postrender', () => {
  console.log('渲染时间:', performance.now());
});

// FPS 监控
let frameCount = 0;
let lastTime = performance.now();

map.on('postrender', () => {
  frameCount++;
  const now = performance.now();
  if (now - lastTime >= 1000) {
    console.log('FPS:', frameCount);
    frameCount = 0;
    lastTime = now;
  }
});
```

## 17.6 本章小结

优化的顺序建议固定为：先量化（性能面板 + FPS + 要素计数），再减数据（简化、聚合、按比例尺过滤），然后减绘制（样式缓存、renderMode、WebGL），接着降频率（防抖节流、按需渲染），最后才是调参数。每一步都记录前后数据，才能判断收益来自哪里。

工程层面的三条底线：资源要能释放（监听、定时器、数据源），错误要能看见（加载失败、解析失败、请求超时），状态要能复现（把地图状态打进日志）。做到这三条，性能问题与线上故障至少能定位到大致范围，不至于靠猜。

本章介绍了性能优化与最佳实践：

1. **渲染优化**：图层配置、样式缓存、WebGL
2. **数据优化**：简化、聚合、加载策略
3. **内存优化**：资源清理、缓存控制
4. **交互优化**：防抖节流、异步处理
5. **最佳实践**：代码组织、错误处理、调试

### 关键要点

- 大量点数据使用 WebGL 渲染
- 样式缓存避免重复创建
- 合理使用聚合减少渲染量
- 防抖节流优化频繁事件
