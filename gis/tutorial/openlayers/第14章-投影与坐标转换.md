# 第14章 - 投影与坐标转换

## 14.1 投影基础

投影是地图开发里最容易出错、也最难在出问题后定位的一环。坐标数值错了不会抛异常，地图照常渲染，只是位置偏了几百公里、图形被拉伸、或者叠加的两层完全对不上。OpenLayers 用投影对象统一管理坐标系，绝大多数转换 API 都要求明确“从哪个投影到哪个投影”，这个设计就是为了逼开发者把坐标的来源和去向想清楚。

默认视图投影是 `EPSG:3857`（Web Mercator），不是 `EPSG:4326`（WGS84 经纬度）。这个默认值决定了：所有给 `View`、`fromLonLat`、`transform` 之外的原生坐标都应当是 3857 的米制坐标。很多人在示例里看到 `fromLonLat` 就以为 OpenLayers 用经纬度，实际上它只是一个便捷转换函数，内部仍然转到 3857。

### 14.1.1 常用投影

`getProjection('EPSG:4326')` 取到一个投影对象，属性比想象中丰富。`getCode()` 是 EPSG 编码，用于判断和日志；`getUnits()` 返回 `'m'`、`'degrees'` 这类单位字符串，量算、比例尺、缓冲区半径都要按它换算；`getExtent()` 是投影的合法坐标范围，Web Mercator 的范围是 `[-20037508.34, -20037508.34, 20037508.34, 20037508.34]`，超出这个范围的点会渲染到地图外；`isGlobal()` 表示投影能否覆盖全球，Web Mercator 在高纬度会失真到不可用，但在编码意义上仍是全球投影。

`getProjection` 对未注册的编码返回 `null`，不会抛异常。自定义投影没有调用 `register(proj4)` 或 `addProjection` 时，这里拿到的就是 null，后续对 null 调用方法才会报错，错误点离真正原因很远。判断投影是否存在，是排查自定义投影问题的第一步。

EPSG:4326 与 EPSG:3857 的区别不只是单位：4326 是等经纬度投影，一度经度和一度纬度代表的实地距离不同（纬度方向随纬度变化）；3857 是等角圆柱投影，把球面投影到平面上，保证方向正确、面积严重变形（格陵兰看起来比非洲还大）。用 Web Mercator 做面积统计会得到离谱的结果，量算必须转回经纬度用球面公式，或者投影到等积坐标系。

```javascript
import { get as getProjection, transform, fromLonLat, toLonLat } from 'ol/proj';

// 内置投影
const wgs84 = getProjection('EPSG:4326');      // WGS84 经纬度
const webMercator = getProjection('EPSG:3857'); // Web Mercator

// 投影信息
console.log('代码:', webMercator.getCode());
console.log('单位:', webMercator.getUnits());        // 'm'
console.log('范围:', webMercator.getExtent());
console.log('是否全球:', webMercator.isGlobal());
```

### 14.1.2 坐标转换

`fromLonLat` 与 `transform` 是同一件事的两个入口：前者固定从 4326 转到视图投影（默认 3857，可通过第二个参数指定），后者允许显式指定源和目标投影。两者都返回新数组，不修改输入；内部做了投影定义查找和转换函数准备，第一次调用有额外开销，之后的批量转换会快一些。

`toLonLat` 是 `fromLonLat` 的反向操作，同样默认目标是 4326。它常用于把地图事件里的 `event.coordinate`（3857）转成经纬度展示或提交给后端。返回的数组是 `[经度, 纬度]`，与 GeoJSON 的顺序一致，与很多国内文档里“纬度, 经度”的写法不一致，跨系统对接时要对齐。

`transformExtent` 转换一个范围。范围在 3857 下是矩形，转到 4326 之后仍然是矩形，但对应的实地范围会变形——投影之间不是线性变换，矩形的四个角点转换后再取包围盒，会得到比真实范围略大的结果。做精确的范围查询时，应当把范围转到数据所在投影后再查，而不是依赖两个矩形近似相等。

`geometry.transform(from, to)` 是**原地修改**几何对象，与前面几个返回新数组的函数不同。示例里直接调用，原几何就被改了；如果这个几何还挂在某个要素上，要素的坐标也跟着变。OpenLayers 的 `geometry.transform` 内部会销毁旧的坐标缓存，修改之后要素渲染随之更新。只想转换一份副本时，先 `feature.clone()` 再对克隆体调用，14.4 节的工具类就是这么做的。

```javascript
// 经纬度 → Web Mercator
const mercatorCoord = fromLonLat([116.4074, 39.9042]);

// Web Mercator → 经纬度
const lonLatCoord = toLonLat([12958752.49, 4853167.35]);

// 通用转换
const coord = transform(
  [116.4074, 39.9042],
  'EPSG:4326',
  'EPSG:3857'
);

// 范围转换
import { transformExtent } from 'ol/proj';
const extent = transformExtent(
  [115, 39, 118, 41],
  'EPSG:4326',
  'EPSG:3857'
);

// 几何转换
geometry.transform('EPSG:4326', 'EPSG:3857');
```

## 14.2 自定义投影

OpenLayers 内置常用投影，但中国测绘常用的 CGCS2000 高斯投影分带、北京 54、西安 80 等并不都在默认列表里。引入 proj4 并注册到 OpenLayers，是让这些投影能用起来的标准做法。注册之后，`transform`、`fromLonLat`、`View` 的 `projection` 选项都能识别这些编码，与内置投影没有区别。

### 14.2.1 使用 Proj4

顺序很关键：先 `proj4.defs(code, definition)` 注册定义，再 `register(proj4)` 把 proj4 接入 OpenLayers，最后才能 `getProjection(code)`。反过来先 `register` 再 `defs`，那些定义也能被识别（proj4 是全局的），但 OpenLayers 的投影缓存可能在 register 时就建立，自定义编码是否生效取决于版本。按“defs → register → 使用”的顺序写，兼容性最好。

`register(proj4)` 全局只需要调用一次。在模块里重复调用不会报错，但会让每次查找多绕一圈。通常放在项目初始化模块里，由入口文件引入。如果应用使用了多个 OpenLayers 实例（微前端场景），每个实例打包出了自己的 `ol/proj`，需要分别 register，这是微前端里很隐蔽的一个坑。

定义字符串用的是 proj4 的语法，不是 WKT。`+proj=tmerc` 表示横轴墨卡托，`+lat_0=0 +lon_0=117` 是原点纬度和中央经线，`+k=1` 是比例因子，`+x_0=500000 +y_0=0` 是东伪偏移与北伪偏移。高斯-克吕格投影的坐标带号前缀（如 40 带写成 `40500000`）不属于投影定义，`+x_0` 仍是 500000；带号要在数据或业务层单独处理，直接拿带号前缀的坐标去转换会东移 400 多个带号的距离。

CGCS2000 的椭球是 GRS80（`+ellps=GRS80`），与 WGS84 的椭球参数差异在毫米级，日常 Web 地图可以视为等价，但高精度测绘成果不能混用。北京 54 用的克拉索夫斯基椭球参数与 WGS84 差异明显，且需要七参数转换，示例里的 `+towgs84=15.8,-154.4,-82.3,0,0,0,0` 是一个常见的粗略参数，实际项目必须用测绘部门提供的本地参数，否则偏差可达几十米。

```javascript
import { register } from 'ol/proj/proj4';
import proj4 from 'proj4';

// 定义 CGCS2000
proj4.defs('EPSG:4490', '+proj=longlat +ellps=GRS80 +no_defs');

// 定义高斯投影
proj4.defs('EPSG:4527', 
  '+proj=tmerc +lat_0=0 +lon_0=117 +k=1 +x_0=500000 +y_0=0 +ellps=GRS80 +units=m +no_defs'
);

// 注册到 OpenLayers
register(proj4);

// 使用
const cgcs2000 = getProjection('EPSG:4490');
```

### 14.2.2 中国常用投影

这一节的几段定义是工程里最常被复制粘贴的内容，需要知道每段的来由。`EPSG:4490` 是 CGCS2000 的地理坐标系，`+proj=longlat` 表示地理坐标，单位是度；它和 `EPSG:4326` 数值上几乎一致，编码不同，混用会导致“看起来一样但对不上”的困惑。

`EPSG:4527` 与 `EPSG:4528` 都是 CGCS2000 高斯投影，中央经线分别是 117° 和 120°。中国 3 度带从东经 75° 起，每 3 度一带，中央经线为 117° 对应第 39 带（`117 = 3 × 39`），北京在此带内；120° 对应第 40 带，上海附近。带号与中央经线的关系是 `中央经线 = 3 × 带号`，用这个公式可以推出任意一带的定义，不必背表。

`+x_0=500000` 是东伪偏移，把中央经线处的横坐标从 0 平移到 500000，避免出现负坐标；`+y_0=0` 是北伪偏移，北半球不需要。`+k=1` 是中央经线处的比例因子，高斯投影在国家基本比例尺地形图中常用 1，UTM 才用 0.9996。这两套体系不要混用参数。

北京 54 的 `+towgs84` 七参数表达了从北京 54 到 WGS84 的基准转换。`+ellps=krass` 是克拉索夫斯基椭球。严格来说，七参数是分区域的，全国用同一组参数会有残余误差；示例里的参数只能算“能跑通”的演示值。西安 80 用 `+ellps=IAU76`，IAU76 与西安80 的 IAG75 椭球并不相同，这处定义在高精度场景下不可靠，实际应以测绘部门发布的定义为准。

```javascript
// CGCS2000 经纬度
proj4.defs('EPSG:4490', '+proj=longlat +ellps=GRS80 +no_defs');

// CGCS2000 高斯投影（3度带）
// 中央经线 117°（北京区域）
proj4.defs('EPSG:4527', 
  '+proj=tmerc +lat_0=0 +lon_0=117 +k=1 +x_0=500000 +y_0=0 +ellps=GRS80 +units=m +no_defs'
);

// 中央经线 120°（上海区域）
proj4.defs('EPSG:4528',
  '+proj=tmerc +lat_0=0 +lon_0=120 +k=1 +x_0=500000 +y_0=0 +ellps=GRS80 +units=m +no_defs'
);

// 北京54
proj4.defs('EPSG:4214', 
  '+proj=longlat +ellps=krass +towgs84=15.8,-154.4,-82.3,0,0,0,0 +no_defs'
);

// 西安80
proj4.defs('EPSG:4610', '+proj=longlat +ellps=IAU76 +no_defs');

register(proj4);
```

## 14.3 坐标偏移处理

在国内做 Web 地图，绕不开三套坐标：WGS84（GPS 原始坐标）、GCJ-02（国测局加密坐标，高德、腾讯使用）、BD-09（百度在 GCJ-02 上再次偏移的坐标）。同一地点在三套坐标下的经纬度相差几百米，直接混用会出现“GPS 定位点偏移到马路对面”“从高德拿的点和从自家底图差一条街”这类问题。

这三套坐标之间的转换不属于投影变换，proj4 处理不了，必须用专门的算法。下面的代码是公开流传的实现，理解它的结构比记住公式更重要：正向转换用一组三角函数的组合算出偏移量，逆向转换没有解析解，只能用近似。

### 14.3.1 火星坐标（GCJ-02）

`wgs84ToGcj02` 的计算分三步：用 `transformLat`、`transformLng` 两个函数根据经纬度算出一个偏移量（单位是某种中间量，不是度），再把偏移量按纬度做尺度修正，最后叠加到原坐标上。`a = 6378245.0` 是克拉索夫斯基椭球长半轴，`ee = 0.00669342162296594323` 是第一偏心率平方——这套算法沿用了北京 54 的椭球参数，是历史原因，不代表精度最优。

`transformLat`、`transformLng` 里的多项式与正弦项是拟合出来的扰动函数，没有严格的几何意义。它们保证了偏移量在空间上连续、平滑，不会出现跳变，从而让相邻点的相对位置保持合理。`Math.sqrt(Math.abs(x))` 这类写法在坐标接近 0 时起到平滑作用，删掉任意一项都会让偏移分布变形。

算法在中国境外不适用。境外坐标不做偏移，原样返回，这是公开实现里的通用约定；示例没有做境外判断，把纽约的经纬度传进去也会被加一个偏移。需要处理境外数据时，在函数开头加一个粗略的范围判断（经度 72 到 138、纬度 0 到 56 之外直接返回原值）。

`gcj02ToWgs84` 用“正向一次再取差值补偿”的方式近似求逆：把输入的 GCJ 坐标当作 WGS 做一次正向偏移，得到 `mLng, mLat`，再用 `lng * 2 - mLng` 反推。这是不动点迭代的一次近似，误差通常在米级，对 Web 地图够用；需要更高精度时循环迭代两到三次，或者用查表/牛顿法求解。把它当成精确逆变换是常见的误解，叠加多级转换时误差会累积。

```javascript
// WGS84 → GCJ-02
function wgs84ToGcj02(lng, lat) {
  const a = 6378245.0;
  const ee = 0.00669342162296594323;
  
  let dLat = transformLat(lng - 105.0, lat - 35.0);
  let dLng = transformLng(lng - 105.0, lat - 35.0);
  
  const radLat = lat / 180.0 * Math.PI;
  let magic = Math.sin(radLat);
  magic = 1 - ee * magic * magic;
  const sqrtMagic = Math.sqrt(magic);
  
  dLat = (dLat * 180.0) / ((a * (1 - ee)) / (magic * sqrtMagic) * Math.PI);
  dLng = (dLng * 180.0) / (a / sqrtMagic * Math.cos(radLat) * Math.PI);
  
  return [lng + dLng, lat + dLat];
}

// GCJ-02 → WGS84
function gcj02ToWgs84(lng, lat) {
  const [mLng, mLat] = wgs84ToGcj02(lng, lat);
  return [lng * 2 - mLng, lat * 2 - mLat];
}

function transformLat(x, y) {
  let ret = -100.0 + 2.0 * x + 3.0 * y + 0.2 * y * y + 0.1 * x * y + 0.2 * Math.sqrt(Math.abs(x));
  ret += (20.0 * Math.sin(6.0 * x * Math.PI) + 20.0 * Math.sin(2.0 * x * Math.PI)) * 2.0 / 3.0;
  ret += (20.0 * Math.sin(y * Math.PI) + 40.0 * Math.sin(y / 3.0 * Math.PI)) * 2.0 / 3.0;
  ret += (160.0 * Math.sin(y / 12.0 * Math.PI) + 320 * Math.sin(y * Math.PI / 30.0)) * 2.0 / 3.0;
  return ret;
}

function transformLng(x, y) {
  let ret = 300.0 + x + 2.0 * y + 0.1 * x * x + 0.1 * x * y + 0.1 * Math.sqrt(Math.abs(x));
  ret += (20.0 * Math.sin(6.0 * x * Math.PI) + 20.0 * Math.sin(2.0 * x * Math.PI)) * 2.0 / 3.0;
  ret += (20.0 * Math.sin(x * Math.PI) + 40.0 * Math.sin(x / 3.0 * Math.PI)) * 2.0 / 3.0;
  ret += (150.0 * Math.sin(x / 12.0 * Math.PI) + 300.0 * Math.sin(x / 30.0 * Math.PI)) * 2.0 / 3.0;
  return ret;
}
```

### 14.3.2 百度坐标（BD-09）

BD-09 是在 GCJ-02 基础上再叠加一层极坐标偏移：`z` 是点到原点的距离加上一个正弦扰动，`theta` 是极角加上一个余弦扰动，最后再叠加固定的 `0.0065`、`0.006` 平移量。这层变换是纯数学的，正向、逆向都有解析表达式，所以 `bd09ToGcj02` 是精确逆变换，不像 GCJ-02 的逆向那样是近似。

`Math.PI * 3000.0 / 180.0` 是把角度转成弧度后再放大的系数，实现里所有三角函数都乘了 3000 这个量级，作用是让扰动在小范围内快速变化。这些常数是逆向工程出来的，没有公开的官方推导，改变任何一项都会让结果偏离。网上的实现版本很多，常数一致才能互相验证。

`wgs84ToBd09` 与 `bd09ToWgs84` 都是两次转换的组合，注意组合顺序：WGS 先转 GCJ 再转 BD；反向先 BD 转 GCJ 再转 WGS。中间那次 GCJ 逆变换是近似的，所以 `wgs84ToBd09` 再 `bd09ToWgs84` 回来不会精确回到原点，往返误差在米级。业务上要求往返一致时，应保存原始坐标而不是依赖转换链。

百度地图的瓦片本身使用 BD-09，把 WGS84 数据直接叠加到百度底图上会整体偏移几百米。使用 OpenLayers 加载百度瓦片时，除了坐标转换，还要处理百度的瓦片编号规则（它不用标准 XYZ 的 TMS 方案），这一点在第 08 章瓦片服务里讲过，两者要配套改，只改坐标仍然对不上。

```javascript
// GCJ-02 → BD-09
function gcj02ToBd09(lng, lat) {
  const x = lng;
  const y = lat;
  const z = Math.sqrt(x * x + y * y) + 0.00002 * Math.sin(y * Math.PI * 3000.0 / 180.0);
  const theta = Math.atan2(y, x) + 0.000003 * Math.cos(x * Math.PI * 3000.0 / 180.0);
  
  return [z * Math.cos(theta) + 0.0065, z * Math.sin(theta) + 0.006];
}

// BD-09 → GCJ-02
function bd09ToGcj02(lng, lat) {
  const x = lng - 0.0065;
  const y = lat - 0.006;
  const z = Math.sqrt(x * x + y * y) - 0.00002 * Math.sin(y * Math.PI * 3000.0 / 180.0);
  const theta = Math.atan2(y, x) - 0.000003 * Math.cos(x * Math.PI * 3000.0 / 180.0);
  
  return [z * Math.cos(theta), z * Math.sin(theta)];
}

// WGS84 → BD-09
function wgs84ToBd09(lng, lat) {
  const gcj = wgs84ToGcj02(lng, lat);
  return gcj02ToBd09(gcj[0], gcj[1]);
}

// BD-09 → WGS84
function bd09ToWgs84(lng, lat) {
  const gcj = bd09ToGcj02(lng, lat);
  return gcj02ToWgs84(gcj[0], gcj[1]);
}
```

## 14.4 投影工具类

零散的转换函数在实际项目里很快会变成一堆重复代码：这里 `fromLonLat`、那里 `transform`、另一个文件又抄了一遍 GCJ 公式。把它们收进一个工具类，统一入口、统一单位、统一返回格式，是最小成本的治理。下面的 `CoordinateTransformer` 就是这么做的，静态方法意味着不需要实例化，调用方直接引用类名。

```javascript
class CoordinateTransformer {
  static wgs84ToMercator(lon, lat) {
    return fromLonLat([lon, lat]);
  }
  
  static mercatorToWgs84(x, y) {
    return toLonLat([x, y]);
  }
  
  static wgs84ToGcj02(lon, lat) {
    return wgs84ToGcj02(lon, lat);
  }
  
  static gcj02ToWgs84(lon, lat) {
    return gcj02ToWgs84(lon, lat);
  }
  
  static wgs84ToBd09(lon, lat) {
    return wgs84ToBd09(lon, lat);
  }
  
  static bd09ToWgs84(lon, lat) {
    return bd09ToWgs84(lon, lat);
  }
  
  static gcj02ToMercator(lon, lat) {
    const wgs84 = this.gcj02ToWgs84(lon, lat);
    return fromLonLat(wgs84);
  }
  
  static bd09ToMercator(lon, lat) {
    const wgs84 = this.bd09ToWgs84(lon, lat);
    return fromLonLat(wgs84);
  }
  
  static transformFeatures(features, fromProj, toProj) {
    return features.map(feature => {
      const cloned = feature.clone();
      cloned.getGeometry().transform(fromProj, toProj);
      return cloned;
    });
  }
}

// 使用示例
const mercator = CoordinateTransformer.gcj02ToMercator(116.4074, 39.9042);
```

## 14.5 本章小结

坐标问题的排查顺序可以固定下来：先打印坐标数值，看量级判断投影（经纬度在 -180 到 180，Web Mercator 在千万级，高斯投影在百万级并带 500000 偏移）；再确认两边的投影定义是否都已注册；然后用 `transform` 显式转换一次，看位置是否正确；最后才怀疑偏移算法。多数“地图错位”在第一、二步就能定位，不需要碰 GCJ 公式。

本章介绍了投影与坐标转换：

1. **投影基础**：WGS84、Web Mercator
2. **坐标转换**：fromLonLat、toLonLat、transform
3. **自定义投影**：Proj4 注册
4. **坐标偏移**：GCJ-02、BD-09 转换
5. **工具类**：统一转换接口

### 关键要点

- OpenLayers 默认使用 EPSG:3857
- 使用 Proj4 注册自定义投影
- 处理国内地图坐标偏移问题
