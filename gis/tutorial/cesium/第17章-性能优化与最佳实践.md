# 第17章：性能优化与最佳实践

## 17.1 性能优化原则

三维 GIS 的性能问题有明确的层次，按代价从大到小排：数据量（同时加载多少瓦片、多少实体）、绘制调用次数（多少个独立的图元集合）、每帧的 CPU 计算（遍历、拾取、坐标转换）、后处理与光照（全屏计算的次数与分辨率）、内存与显存（纹理、几何体缓存）。优化的顺序应该是先减数据、再合批次、然后砍每帧计算、最后才动画面效果。反过来做，经常是把画质调低了一档，帧率只涨了两帧，因为大头根本没碰到。

判断瓶颈在哪一层，靠的是量化数据而不是感觉。浏览器自带的性能面板能看到主线程在做什么；Cesium 自己的帧率显示能看出是稳定低帧还是间歇卡顿——间歇卡顿多半是数据加载或 GC，稳定低帧多半是绘制或填充率。先把这两类分开，再往下查。

### 17.1.1 性能瓶颈分析

`viewer.scene.debugShowFramesPerSecond = true` 打开右上角的帧率面板，面板上除了 FPS 还显示每帧的毫秒数。60 FPS 对应 16.7 毫秒，30 FPS 对应 33 毫秒，两者之间的差距是“能不能再做一件事”的预算。面板本身的 HTML 节点带有 `cesium-performanceDisplay-fps` 类名，运行期读取它就能把帧率接到自己的监控里去，本章 17.3.1 的动态 LOD 就是这么做的。

`viewer.extend(Cesium.viewerCesium3DTilesInspectorMixin)` 给 Viewer 挂上 3D Tiles 检查器，打开后能逐个瓦片看包围盒、几何误差、纹理内存、请求队列。排查“为什么这个模型加载不出来”“为什么视角一转就狂请求”时，这是最直接的工具；生产环境记得去掉，检查器本身有不小的开销。

`performance.memory` 是 Chrome 的非标准扩展，其他浏览器上可能不存在，示例里先做存在性判断是对的。它反映的是 JS 堆的占用，不包括纹理和几何体占用的显存——而后者恰恰是三维场景里最容易失控的部分。判断显存压力更可靠的办法是看 `scene.context` 相关的统计，或者观察长时间运行后帧率是否持续下降。用 `setInterval` 定时采样时，输出的对象应当序列化后再打印，否则控制台里看到的是引用，展开时数值已经变了。

```javascript
// 启用性能监控
viewer.scene.debugShowFramesPerSecond = true;

// 扩展 3D Tiles Inspector
viewer.extend(Cesium.viewerCesium3DTilesInspectorMixin);

// 内存监控
setInterval(() => {
    if (performance.memory) {
        console.log('内存使用:', {
            usedJSHeapSize: (performance.memory.usedJSHeapSize / 1024 / 1024).toFixed(2) + ' MB',
            totalJSHeapSize: (performance.memory.totalJSHeapSize / 1024 / 1024).toFixed(2) + ' MB'
        });
    }
}, 5000);
```

## 17.2 渲染优化

默认情况下 Cesium 以浏览器的刷新率持续重绘，即使画面完全静止。对交互式地图这是必要的——相机随时可能移动；对“加载后只做展示”的大屏、报表截图、内嵌卡片，持续重绘意味着风扇常转、笔记本掉电。按需渲染就是让引擎在没事可做的时候停下来，只在场景真的发生变化时画一帧。

### 17.2.1 按需渲染

`requestRenderMode = true` 打开按需模式，`maximumRenderTimeChange = Infinity` 表示时间流逝本身不触发重绘。这两行要一起看：`maximumRenderTimeChange` 的默认值是 0.5 秒，含义是“即使没有其他变化，时间每走过这个间隔也要重绘一帧”——因为时钟在走、光照和大气可能跟着变。把它设为 Infinity，就等于告诉引擎时间变化不再算作变化，画面只在你调用 `requestRender()` 或场景内部检测到修改时才更新。

代价是任何“引擎认为不构成变化”的状态都会留在屏幕上。手工改 `entity.point.color`、切换 `entity.show` 通常能触发重绘，但修改材质实例的内部 uniform、直接操作 canvas 纹理、或者外部数据驱动了自定义着色器，引擎并不知道，必须手动调用 `scene.requestRender()`。这一条忘了，现象就是“数据明明变了，画面没动”。

`viewer.entities.collectionChanged.addEventListener(requestRender)` 是最省事的兜底：实体集合有增减就请求一帧。它不覆盖“已有实体的属性被修改”的情况，那类修改需要自己包一层 setter，在赋值后调用 `requestRender`。

按需模式还有个细节：`requestRender` 只是“请求在下一次渲染循环画一帧”，连续调用多次会被合并，不会抖成动画。相机的惯性移动、图层的淡入淡出这类引擎内部动画会自行请求渲染，不需要外部干预。

```javascript
// 启用按需渲染模式
viewer.scene.requestRenderMode = true;
viewer.scene.maximumRenderTimeChange = Infinity;

// 手动请求渲染
function requestRender() {
    viewer.scene.requestRender();
}

// 数据变化时请求渲染
viewer.entities.collectionChanged.addEventListener(requestRender);
```

### 17.2.2 Primitive vs Entity

Entity 是面向业务的抽象：加入一个 `point` 属性，Cesium 在背后把它转换成 `PointPrimitiveCollection`，并接上 Property 系统、拾取、`availability`、时间轴。Primitive 是面向渲染的抽象：直接操作几何体与集合，没有 Property 包装，不参与时间系统，拾取要靠自己实现。

两者的性能差距来自数量级。一万个 Entity 是上万个包装对象、上万个属性求值、多个批次之间的调度；一万个 `PointPrimitive` 只占一个 `PointPrimitiveCollection`，一次绘制调用可以画掉。示例里十万个点用 Entity 写，页面基本会卡死；用 PointPrimitiveCollection 则能在普通显卡上流畅运行。

选型不必二选一。静态底图要素（POI、监测站、海量设备）用 Primitive 批量画，需要点击查询时自己做拾取；交互频繁、数量可控的要素（选中高亮、拖拽编辑、动态属性）用 Entity，开发成本低得多。两者可以共存，靠图层管理组件统一开关。

`PointPrimitiveCollection` 的 `add` 返回单个 `PointPrimitive`，之后可以改它的 `show`、`color`、`position`；要整体更新先 `removeAll()` 再重建，比逐个 remove 快。构造时传 `{ debugShowBoundingVolume: false }` 之外的参数很少用到，重点是把点放进同一个集合，而不是集合的配置。

```javascript
// Entity（简单但性能较低）
// 适合：< 1000 个对象，需要拾取，需要动态属性
viewer.entities.add({
    position: Cesium.Cartesian3.fromDegrees(lon, lat),
    point: { pixelSize: 10 }
});

// Primitive（性能更高）
// 适合：> 1000 个对象，静态数据
const pointCollection = new Cesium.PointPrimitiveCollection();
for (let i = 0; i < 100000; i++) {
    pointCollection.add({
        position: Cesium.Cartesian3.fromDegrees(
            100 + Math.random() * 30,
            20 + Math.random() * 20
        ),
        pixelSize: 5,
        color: Cesium.Color.RED
    });
}
viewer.scene.primitives.add(pointCollection);
```

### 17.2.3 批量操作

每次 `entities.add` 都会让集合派发一次变更事件，触发 `EntityCollection` 与底层图元集合的同步。加一个是无感的开销，加一万个就是一万次同步，在循环里逐条添加的代码会明显卡住主线程。`suspendEvents()` 把期间的事件攒起来，`resumeEvents()` 时一次性合并派发，同步只做一遍。

`try / finally` 是必须的：循环里抛异常（坐标非法、属性类型不对）时，如果没走 `resumeEvents`，实体集合会一直处于挂起状态，后续所有添加都不再触发同步，表现为“数据在内存里但画面永远不动”。这种状态极难排查，加 finally 的成本很低。

示例里的经度、纬度用了外部变量 `lon`、`lat`，这在真实代码里通常写成从数据数组解构的 `feature.geometry.coordinates`。批量操作期间不要混入需要立即生效的 UI 更新，事件被挂起时这些更新不会触发；把界面刷新放到 `resumeEvents` 之后。

```javascript
// 挂起事件进行批量操作
const entities = viewer.entities;
entities.suspendEvents();

try {
    for (let i = 0; i < 10000; i++) {
        entities.add({
            position: Cesium.Cartesian3.fromDegrees(lon, lat),
            point: { pixelSize: 5 }
        });
    }
} finally {
    entities.resumeEvents();
}
```

## 17.3 数据优化

三维场景的数据量通常远大于二维，优化空间也主要在这里。原则是“按屏幕需要加载”：视野里看不见的不请求，看得见的按精度分级加载，已经加载的按内存上限淘汰。3D Tiles 的设计本身就是围绕这条原则做的，参数调优的本质是在画质、流量、内存三者之间找平衡点。

### 17.3.1 3D Tiles 优化

`maximumScreenSpaceError` 是最核心的一个参数：瓦片在屏幕上投影的误差超过阈值时才加载更精细的子瓦片。默认 16，调大意味着容忍更大的误差，加载的瓦片更少、画面更粗；调到 4 以下几乎只有近景会加载，内存和带宽压力陡增。这个值不是“越小越好”，它的合理取值取决于数据类型和显示距离，倾斜摄影通常 16 到 24，精细单体模型可以到 8。

`maximumMemoryUsage` 是瓦片缓存的上限，单位 MB，默认 512。浏览器里瓦片的几何与纹理都占用内存，超限时引擎会淘汰最久未用的瓦片再重新加载，形成“转一圈回来又要重新下”的循环。移动端把它压到 128 到 256 是常见做法，桌面端可以放宽到 1024。

`skipLevelOfDetail` 允许跳过中间层级直接加载更粗或更细的瓦片，`skipLevels` 指定跳几层，配合 `baseScreenSpaceError` 使用可以在相机快速移动时显著减少请求数，代价是画面可能出现短暂的精度跳变。`cullWithChildrenBounds` 用子瓦片的包围盒做剔除，减少父瓦片可见但子瓦片全不可见时的无效遍历；`cullRequestsWhileMoving` 在相机移动中推迟请求，`cullRequestsWhileMovingMultiplier` 越大越保守。

`preloadWhenHidden` 决定隐藏的 tileset 是否继续预加载，`preloadFlightDestinations` 在相机飞行途中预取终点视野的瓦片，`preferLeaves` 优先加载叶子节点。这些开关互有取舍，没有一套值适配所有数据，实践中先用默认值跑一遍，看检查器里的请求队列与内存曲线，再逐项调整。

示例后半段按帧率动态调 `maximumScreenSpaceError` 的思路是自适应的常见做法，但代码本身有几处需要留意：每帧都改参数会让请求策略持续震荡，应当加冷却时间或只在帧率连续低于阈值若干帧后才调整；`parseFloat` 读到的 DOM 文本在面板未渲染时可能是空字符串，得到 NaN 后一路乘下去参数就坏了；`maximumScreenSpaceError` 没有上限保护，长时间卡顿时会一路放大到画面完全不可用。把调整幅度限制在 8 到 32 之间，并记录上一次调整时间，稳定性会好很多。

```javascript
const tileset = await Cesium.Cesium3DTileset.fromUrl(url, {
    // LOD 优化
    maximumScreenSpaceError: 16,        // 增大可降低精度提高性能
    maximumMemoryUsage: 512,            // 限制内存
    
    // 跳级加载
    skipLevelOfDetail: true,
    skipLevels: 1,
    
    // 剔除优化
    cullWithChildrenBounds: true,
    cullRequestsWhileMoving: true,
    cullRequestsWhileMovingMultiplier: 60.0,
    
    // 预加载
    preloadWhenHidden: false,
    preloadFlightDestinations: true,
    preferLeaves: false
});

// 动态调整（根据帧率）
let lastFPS = 60;
viewer.scene.postRender.addEventListener(() => {
    const fps = viewer.scene.debugShowFramesPerSecond ? 
        parseFloat(document.querySelector('.cesium-performanceDisplay-fps').textContent) : 60;
    
    if (fps < 30 && tileset.maximumScreenSpaceError < 64) {
        tileset.maximumScreenSpaceError *= 1.1;
    } else if (fps > 55 && tileset.maximumScreenSpaceError > 4) {
        tileset.maximumScreenSpaceError *= 0.95;
    }
});
```

### 17.3.2 影像优化

`globe.tileCacheSize` 控制影像瓦片在内存里保留的数量，默认 100。数值越大，回看已经浏览过的区域越不容易重新请求，但内存占用随瓦片数量线性增长；把整颗地球都缓存下来是不现实的，应根据业务区域大小设定，几百的量级比较常见。

`Cesium.RequestScheduler.maximumRequestsPerServer` 限制同一域名并发请求数，默认 6，与浏览器的连接数限制接近。调大能提升瓦片加载吞吐，但超过浏览器实际上限后请求会排队，反而增加延迟；瓦片服务分布在多个域名（CDN 分片）时，真正的并发是“每域名上限乘以域名数”。

减少图层数是最有效的影像优化。每个影像图层都是一套独立的瓦片请求与合成开销，叠三四层在线影像后，同样的视角下请求数翻几倍。示例里 `removeAll` 再 `add` 一个主图层的做法适合底图切换，但要注意 `removeAll` 会连 `baseLayer` 一起删掉，删除后必须重新添加至少一个图层，否则地球变成黑球。

```javascript
// 限制瓦片缓存
viewer.scene.globe.tileCacheSize = 100;

// 限制最大请求数
Cesium.RequestScheduler.maximumRequestsPerServer = 6;

// 减少影像图层数
// 移除不需要的图层
viewer.imageryLayers.removeAll();
viewer.imageryLayers.addImageryProvider(primaryImagery);
```

### 17.3.3 地形优化

`globe.maximumScreenSpaceError` 是地形（以及默认的全球表面）的渲染误差阈值，默认 2，值越大越粗。把它从 2 调到 4，地形三角形数量大约降到四分之一，山区和大范围浏览时提升明显，代价是山脊变得圆钝、陡崖出现拉扯。做展示型应用可以放宽，做量测、坡度分析类应用不要动，精度直接影响计算结果。

不需要起伏时，用 `new Cesium.EllipsoidTerrainProvider()` 把地形换成光滑椭球，省掉全部地形瓦片请求与网格细分。示例这样写会把原来的地形服务整个替换掉，之后想恢复得保存原 provider 的引用再赋回去；`viewer.terrainProvider` 的 setter 会触发重建，频繁切换会有卡顿。

`globe.loadingDescendantLimit` 限制同一父瓦片向子瓦片下探的并发数，数值小能抑制峰值请求、让加载更平滑，数值大则近景细化更快。它和瓦片服务端的承载能力相关，服务端限流严格时把它调小可以避免大量请求超时被判失败。

```javascript
// 降低地形精度
viewer.scene.globe.maximumScreenSpaceError = 4;

// 禁用地形（如果不需要）
viewer.terrainProvider = new Cesium.EllipsoidTerrainProvider();

// 限制地形级别
viewer.scene.globe.loadingDescendantLimit = 20;
```

## 17.4 内存管理

三维应用的泄漏大多来自“删了数据但没删引用”。`viewer.entities.removeAll()`、`dataSources.removeAll(true)`、`scene.primitives.removeAll()` 会从渲染管线里移除对象，但如果业务代码里还留着它们的引用（数组、Map、事件回调的闭包），对象就不会被回收。清理函数要配合业务侧的状态一起清，只清 Cesium 这一半，内存曲线仍然会缓慢上涨。

`dataSources.removeAll(true)` 的第二个参数 `destroy` 决定是否一并销毁数据源；设为 false 只移除不销毁，之后还能重新 add 回来，但内存不释放。加载 GeoJSON、CZML 的场景反复切换时，这个参数漏掉或传错是内存增长的主要原因。

`viewer.destroy()` 是唯一能彻底释放 WebGL 上下文的入口，它会销毁所有图元、数据源、事件监听，并把 canvas 从 DOM 上摘下来。单页应用里组件卸载时必须调用，且只能调用一次——示例里的 `isDestroyed()` 判断就是防重复调用。销毁之后再访问 `viewer.scene` 会抛异常，组件里所有持有 viewer 引用的地方都要在销毁前置空。

除了这三个入口，还要检查自己注册的监听：`ScreenSpaceEventHandler`、`clock.onTick`、`scene.preRender`、`camera.changed` 都不会随 viewer 销毁自动解除（挂在 scene 上的会，挂在全局对象上的不会）。把这些都写进组件的 `destroy` 方法里，组件重复挂载时才不会出现回调翻倍执行。

```javascript
// 及时销毁不用的资源
function cleanupResources() {
    // 清除实体
    viewer.entities.removeAll();
    
    // 清除数据源
    viewer.dataSources.removeAll(true);
    
    // 清除图元
    viewer.scene.primitives.removeAll();
    
    // 清除地面图元
    viewer.scene.groundPrimitives.removeAll();
}

// 销毁 Viewer
function destroyViewer() {
    if (viewer && !viewer.isDestroyed()) {
        viewer.destroy();
    }
}
```

## 17.5 最佳实践

前面几节讲的是“怎么让引擎跑得快”，这一节讲“怎么让代码不给自己添麻烦”。三维项目常见的失败模式不是性能技巧不够，而是代码组织混乱导致无法定位问题：初始化逻辑、数据加载、图层管理、交互工具全堆在一个 main.js 里，出了问题是哪一步造成的都说不清。

### 17.5.1 项目结构

示例的目录划分对应四层职责：`components` 是可挂载、可销毁的界面单元（地图容器、图层面板、量测工具条），`layers` 是数据图层的封装（每个图层负责自己的加载、样式、显隐与销毁），`tools` 是交互工具（拾取、编辑、量算），`utils` 是无状态函数（坐标转换、格式化、请求封装）。`config` 单独放配置，避免服务地址、初始视角这类常量散落在代码里。

`public/assets` 与 `public/data` 的分工是资源与数据分开：模型、纹理、图标等随构建产物发布的静态资源放 assets，业务数据（GeoJSON、3D Tiles 的 json、瓦片索引）放 data。实际部署时数据往往在独立的静态服务器或对象存储上，config 里应当只保留一个基地址，便于区分开发与生产环境。

图层的封装值得单独强调。一个可维护的图层模块至少暴露 `add()`、`remove()`、`setVisible()`、`destroy()` 四个方法，并在内部持有自己创建的 entity、primitive、数据源和事件监听，销毁时统一清理。上层只管调用这四个方法，不直接碰 `viewer`，换引擎、换实现时改动面才可控。

```
cesium-project/
├── src/
│   ├── main.js
│   ├── config/          # 配置文件
│   ├── components/      # 组件
│   ├── layers/          # 图层管理
│   ├── tools/           # 工具类
│   └── utils/           # 工具函数
├── public/
│   ├── assets/          # 静态资源
│   │   ├── models/      # 3D模型
│   │   └── textures/    # 纹理
│   └── data/            # 数据文件
└── package.json
```

### 17.5.2 代码规范

`Cesium3DTileset.fromUrl` 是异步的，用 `await` 拿结果比回调链清晰，`try / catch` 捕获加载失败——网络错误、模型格式错误、服务端 404 都会走到 catch 里。加载失败后把错误显示给用户，比在控制台打一行日志有用得多，尤其是数据地址由后端下发、前端无法确认其有效性的场景。

`await viewer.zoomTo(tileset)` 会让相机飞到数据范围，代价是改变了用户当前视角。批量加载多个模型时逐个 zoomTo 会让镜头来回乱飞，正确做法是全部加载完再统一计算总包围盒，飞一次。

`MyComponent` 演示了事件监听的生命周期管理：构造函数里创建 `ScreenSpaceEventHandler`，`init` 里注册回调，`destroy` 里销毁 handler 并置空。`this.removeCallbacks` 数组在示例里没有真正用起来，但它代表的模式是对的——把所有需要手动解除的监听登记在一个数组里，销毁时统一遍历执行，避免漏掉某一条。

`handler.destroy()` 会解除该 handler 上注册的所有输入动作，所以不需要逐个 `removeInputAction`；但如果同一个 handler 被复用、只想移除其中一个动作，就必须精确移除。置空引用是为了让垃圾回收能识别出这个对象已经不再使用，也防止重复调用 destroy。

```javascript
// 使用异步/等待
async function loadData() {
    try {
        const tileset = await Cesium.Cesium3DTileset.fromUrl(url);
        viewer.scene.primitives.add(tileset);
        await viewer.zoomTo(tileset);
    } catch (error) {
        console.error('加载失败:', error);
    }
}

// 清理事件监听
class MyComponent {
    constructor(viewer) {
        this.viewer = viewer;
        this.handler = new Cesium.ScreenSpaceEventHandler(viewer.canvas);
        this.removeCallbacks = [];
    }
    
    init() {
        // 保存回调以便清理
        const callback = (e) => this.onClick(e);
        this.handler.setInputAction(callback, Cesium.ScreenSpaceEventType.LEFT_CLICK);
    }
    
    destroy() {
        if (this.handler) {
            this.handler.destroy();
            this.handler = null;
        }
    }
}
```

### 17.5.3 错误处理

`window.onerror` 捕获同步错误与资源加载错误，`onunhandledrejection` 捕获没有 catch 的 Promise 拒绝。两者的 `return false` 表示继续执行默认处理，也就是仍然在控制台打印；返回 true 会抑制浏览器默认输出，排查阶段不要这么做。

`viewer.scene.renderError` 在渲染循环内部抛错时触发。三维场景的渲染错误往往不是一次性的——着色器编译失败、上下文丢失之后，后续每一帧都会继续报错，控制台瞬间刷满。回调里应当做两件事：限制日志频率（比如只打印前三条），以及给用户一个可恢复的提示（刷新页面、降级到二维、切换到兼容模式）。

上下文丢失（context lost）在移动端和长时间运行的页面上并不罕见，显卡驱动切换、系统休眠都可能触发。Cesium 有对 `webglcontextlost` 的内部处理，但自定义着色器与外部纹理不会自动恢复；在 `renderError` 之外再监听 canvas 的 `webglcontextrestored`，把自定义资源重建一遍，能减少“切出去再切回来就白屏”的概率。

```javascript
// 全局错误处理
window.onerror = function(message, source, lineno, colno, error) {
    console.error('全局错误:', { message, source, lineno, colno, error });
    return false;
};

// Promise 错误处理
window.onunhandledrejection = function(event) {
    console.error('未处理的 Promise 错误:', event.reason);
};

// CesiumJS 错误处理
viewer.scene.renderError.addEventListener(function(scene, error) {
    console.error('渲染错误:', error);
});
```

## 17.6 本章小结

性能优化的落地顺序建议是：先用帧率面板和检查器确认瓶颈在数据、绘制还是每帧计算；数据层先砍瓦片与实体数量，再调 `maximumScreenSpaceError` 和内存上限；绘制层把海量静态要素换成 Primitive 集合，批量添加时挂起事件；帧计算层检查有没有在 `onTick`、`preRender` 里做重活；最后才是关后处理、降阴影、减光源。每一步都记录优化前后的数值，凭感觉调参通常只记住了“我改过什么”，没记住“有没有用”。

本章介绍了性能优化与最佳实践：

1. **性能监控**：帧率、内存监控
2. **渲染优化**：按需渲染、Primitive
3. **数据优化**：3D Tiles、影像、地形
4. **内存管理**：资源清理、销毁
5. **最佳实践**：项目结构、代码规范
