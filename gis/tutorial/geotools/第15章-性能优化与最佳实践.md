# 第15章 - 性能优化与最佳实践

## 15.1 性能优化概述

GeoTools 的性能问题有个特点：多数不是“哪一行代码写得慢”，而是“用错了层次”。同一个查询，交给数据库做是毫秒级，在内存里遍历几十万要素是几十秒；同一个要素，流式处理占用几十兆堆内存，全量装进 List 再处理就可能 OOM。优化的第一步是判断当前的瓶颈在数据访问、内存、空间计算还是渲染，然后决定把工作下推到哪一层。

上面那张图把常见瓶颈分了四类，实际排查时按这个顺序走：先看有没有把能用索引的查询做成了全表扫描（数据访问），再看有没有把大结果集全量堆在内存里（内存管理），再看几何运算是不是在做 O(n²) 的两两比较（空间计算），最后才是渲染参数和样式解析。顺序反了，往往在渲染上花很多时间调整，真正的瓶颈还在数据层。

## 15.2 数据访问优化

数据访问是所有优化的第一优先级，因为它的损耗是数量级的。`getFeatures()` 不带参数时会把图层的全部字段、全部要素都读出来，几十万条记录在客户端建出几十万个对象，然后你只用了其中两个字段——这种浪费在生产代码里非常常见，而且改动成本很低：加一个 `Query`、指定字段、加过滤条件。

### 15.2.1 使用查询优化

`query.setPropertyNames("name", "population")` 做的是属性投影：只把这两列从数据源读出来，其他字段不参与。对 Shapefile 和数据库都有效，数据库上会翻译成 `SELECT name, population FROM ...`，减少网络传输和对象构造。注意投影之后要素的 Schema 变了，只剩这两列加上几何列，后续按名字取不到其他字段，`getAttributeCount` 也会变小。

分页用 `setStartIndex(offset)` 和 `setMaxFeatures(pageSize)` 组合。这两个参数能否真正下推到数据源，取决于驱动：PostGIS 会翻译成 `LIMIT/OFFSET`，Shapefile 则在内存里跳过前 offset 条。后者在 deep paging（offset 很大）时性能会线性下降，因为每条记录都要读出来再丢掉。数据量大又需要随机翻页时，用主键游标（`WHERE id > last_id LIMIT n`）比 offset 翻页稳定。

`source.getCount(Query.ALL)` 取总数，同样不一定下推，Shapefile 上会把整个文件扫一遍。分页循环里每页都调一次 count 就更糟了，应当在循环外取一次。如果数据在查询期间可能变化，总数与实际分页结果不一致，这是分页的固有问题，业务上要接受或改用快照。

`ff.bbox(ff.property("the_geom"), minX, minY, maxX, maxY, "EPSG:4326")` 构造空间过滤器。这里的坐标系必须和数据源一致：PostGIS 表是 4326 就传 4326，是 3857 就传 3857。传错时 GeoTools 会尝试重投影，结果可能对但性能差，也可能因为坐标系定义缺失直接抛异常。属性名 `"the_geom"` 是数据源里几何列的实际名字，不同数据源不一样，取 `source.getSchema().getGeometryDescriptor().getLocalName()` 更稳。

示例最后两个方法只有声明没有实现，`SimpleFeatureCollection selected` 和 `filtered` 都是未使用的局部变量。实际代码里应当把结果消费掉，并且用完关闭迭代器；如果只是把 `getFeatures` 的结果拿去遍历，记得用 try-with-resources 包住 `features()`。

```java
public class QueryOptimization {
    
    // 只获取需要的属性
    public static void propertySelection(SimpleFeatureSource source) throws Exception {
        Query query = new Query(source.getSchema().getTypeName());
        
        // 不好：获取所有属性
        // SimpleFeatureCollection all = source.getFeatures();
        
        // 好：只获取需要的属性
        query.setPropertyNames("name", "population");
        SimpleFeatureCollection selected = source.getFeatures(query);
    }
    
    // 使用分页
    public static void paginatedQuery(SimpleFeatureSource source, 
            int pageSize) throws Exception {
        
        int total = source.getCount(Query.ALL);
        
        for (int offset = 0; offset < total; offset += pageSize) {
            Query query = new Query(source.getSchema().getTypeName());
            query.setStartIndex(offset);
            query.setMaxFeatures(pageSize);
            
            SimpleFeatureCollection page = source.getFeatures(query);
            processPage(page);
        }
    }
    
    // 使用空间过滤器缩小范围
    public static void spatialFilter(SimpleFeatureSource source,
            Envelope bounds) throws Exception {
        
        FilterFactory2 ff = CommonFactoryFinder.getFilterFactory2();
        
        Filter bboxFilter = ff.bbox(
            ff.property("the_geom"),
            bounds.getMinX(), bounds.getMinY(),
            bounds.getMaxX(), bounds.getMaxY(),
            "EPSG:4326"
        );
        
        Query query = new Query(source.getSchema().getTypeName(), bboxFilter);
        SimpleFeatureCollection filtered = source.getFeatures(query);
    }
    
    private static void processPage(SimpleFeatureCollection page) {
        // 处理分页数据
    }
}
```

### 15.2.2 连接池配置

连接池参数的键名由具体的 DataStore 实现定义，不是 GeoTools 内核统一的约定。`DataStoreFinder.getDataStore(Map)` 会把参数交给第一个声称能处理 `dbtype` 的工厂，工厂自己解析这些键。示例里的 `max connections`、`min connections`、`fetch size`、`Loose bbox` 都是 PostGIS 数据存储的常用键，但不同版本对键名大小写、空格的容忍度不同，升级 GeoTools 后要在测试环境验证一遍。

连接数不是越大越好。`max connections` 设成 20，意味着这个 DataStore 最多占用数据库 20 个连接；一个应用里创建多个 DataStore、或者多台应用服务器连同一个库，很容易把数据库的 `max_connections` 打满，之后所有连接请求都超时。经验值是单实例 5 到 20，按并发查询数配置，并给数据库留出余量。`connection timeout` 控制等待连接的秒数，设太大时故障场景下请求会长时间挂起，设太小则正常峰值时误判为超时。

`fetch size` 影响 JDBC 驱动每次从服务端取多少行。设成 1000 比默认的整结果集一次取回省内存，但不等于“流式”，真正的流式读取需要驱动支持游标并关闭自动提交。`preparedStatements` 开启预编译语句缓存，对参数化查询频繁执行的场景有收益；`Loose bbox` 让 PostGIS 用 `&&` 运算符做包围盒粗筛，比精确的 `ST_Intersects` 快，配合后续精确判断使用。

生产环境不要把密码硬编码在代码里，示例里明文写 `passwd` 只是为了展示参数位置。连接参数通常来自配置文件或环境变量，`DataStoreFinder` 的 Map 在运行时构造即可。另外 `createOptimizedPostGIS` 返回的 DataStore 是长生命周期对象，应当作为单例持有，随应用关闭时在 `ServletContextListener` 一类的钩子里 `dispose`；每次请求新建一个会瞬间耗光连接池。

```java
public class ConnectionPoolConfig {
    
    public static DataStore createOptimizedPostGIS() throws Exception {
        Map<String, Object> params = new HashMap<>();
        
        // 基本连接
        params.put("dbtype", "postgis");
        params.put("host", "localhost");
        params.put("port", 5432);
        params.put("database", "gisdb");
        params.put("user", "postgres");
        params.put("passwd", "password");
        
        // 连接池优化
        params.put("max connections", 20);     // 根据并发量调整
        params.put("min connections", 5);      // 保持最小连接
        params.put("connection timeout", 10);  // 减少等待时间
        params.put("validate connections", true);
        params.put("Test while idle", true);
        
        // 查询优化
        params.put("fetch size", 1000);        // 批量获取
        params.put("Loose bbox", true);        // 宽松边界框
        params.put("preparedStatements", true);// 预编译语句
        params.put("encode functions", true);  // SQL 函数下推
        
        return DataStoreFinder.getDataStore(params);
    }
}
```

## 15.3 内存管理

GeoTools 的对象分两类：纯内存对象（几何、属性）和持有底层资源的对象（数据源、迭代器、事务）。前者靠 GC，后者必须显式关闭。混淆这两类会导致两种典型故障：迭代器不关，连接和文件句柄泄漏，跑一段时间后报“too many open files”；数据源不 dispose，Web 应用热部署时旧类加载器被引用住，内存里堆着几份旧版本，表现为每次重部署内存涨一截。

### 15.3.1 资源释放

`correctResourceHandling` 给出了标准的两层释放结构：内层用 try-with-resources 管迭代器，外层用 finally 管数据源。迭代器实现了 `AutoCloseable`，离开 try 块自动调用 `close()`，即使循环里抛异常也会关；数据源放在 finally 里，保证无论成功失败都 `dispose()`。两层都要有，缺一层就会泄漏一类资源。

`FileDataStoreFinder.getDataStore(file)` 对同一个文件多次调用可能返回同一个实例（内部有缓存），此时在 finally 里 `dispose` 会让后续使用者拿到已关闭的数据源。是否缓存取决于数据源类型和版本，稳妥的做法是数据源集中创建、集中释放，不要在方法内部反复开关。Web 环境下把 DataStore 放在应用级单例里，随应用关闭统一 dispose。

`fc.accepts(visitor, null)` 是另一种遍历方式，把迭代器的创建与关闭交给框架，调用方只写 `visit` 方法。它的好处是不容易忘关迭代器，代码也更短；代价是只能做单遍遍历，无法在遍历中途 break 出来（要中断得抛异常），也无法把要素收集起来延迟处理。适合“每个要素做一件事”的统计、导出类需求。

第二个参数是 `ProgressListener`，传 null 表示不汇报进度。遍历大量要素时传入监听器可以拿到进度，也能响应取消。visitor 抛出的异常会被包装成 `IOException` 一类抛出，在 `visit` 里做可能失败的操作时要注意异常处理策略——是跳过这一条继续，还是整体中断。

```java
public class ResourceManagement {
    
    // 正确的资源释放模式
    public static void correctResourceHandling(File file) throws Exception {
        FileDataStore store = FileDataStoreFinder.getDataStore(file);
        
        try {
            SimpleFeatureSource source = store.getFeatureSource();
            SimpleFeatureCollection fc = source.getFeatures();
            
            // 使用 try-with-resources 自动关闭迭代器
            try (SimpleFeatureIterator iter = fc.features()) {
                while (iter.hasNext()) {
                    SimpleFeature feature = iter.next();
                    // 处理要素
                }
            }  // 自动关闭
            
        } finally {
            store.dispose();  // 确保释放数据源
        }
    }
    
    // 使用 FeatureVisitor 避免手动管理迭代器
    public static void useVisitor(SimpleFeatureCollection fc) throws Exception {
        fc.accepts(new FeatureVisitor() {
            @Override
            public void visit(Feature feature) {
                // 处理要素
            }
        }, null);
    }
}
```

### 15.3.2 大数据处理

`streamProcessing` 用分页把任意规模的数据切成固定大小的批次，逐批处理，任意时刻内存里只有一个批次。这是大数据量下唯一可靠的模式，比“全量查出来再循环”安全得多。分页的 `pageSize` 是内存与请求次数的折中：1000 到 10000 是常见区间，太小则请求次数多、开销大，太大则单批内存高。

循环终止条件用 `count == pageSize` 判断是否还有下一页，这个判断有个边界问题：数据总量恰好是 `pageSize` 的整数倍时，最后一批满了，还会再查一次空结果，多一次请求但结果正确；数据在分页过程中被增删时，某个中间页可能不足 `pageSize`，循环会提前结束而漏掉后面的数据。对静态数据（导出、批处理）没问题，对实时变化的数据要加基于主键的游标。

`hasMore = count == pageSize` 在 count 为 0 时自然结束，不会死循环。但 `offset += count` 的写法在数据有删除时会跳过记录：第一页读了 1000 条，中间删了 100 条，第二页从 offset 1000 开始，原本的第 1001 条已经前移到 901 位，被跳过。同样的问题在 offset 分页里普遍存在，意识到这一点比修补更重要。

示例里注释掉的 `System.gc()` 是一个反面示例，保留在注释里提醒不要用是对的。显式调用 `System.gc()` 只是建议 JVM 回收，真实执行时间不可控，频繁调用会让吞吐量骤降。判断内存问题应当看 GC 日志和堆转储，而不是靠手动触发。

```java
public class LargeDataHandling {
    
    // 流式处理
    public static void streamProcessing(SimpleFeatureSource source,
            FeatureProcessor processor) throws Exception {
        
        int pageSize = 1000;
        int offset = 0;
        boolean hasMore = true;
        
        while (hasMore) {
            Query query = new Query(source.getSchema().getTypeName());
            query.setStartIndex(offset);
            query.setMaxFeatures(pageSize);
            
            SimpleFeatureCollection batch = source.getFeatures(query);
            int count = 0;
            
            try (SimpleFeatureIterator iter = batch.features()) {
                while (iter.hasNext()) {
                    processor.process(iter.next());
                    count++;
                }
            }
            
            hasMore = count == pageSize;
            offset += count;
            
            // 可选：显式触发 GC
            // System.gc();
        }
    }
    
    public interface FeatureProcessor {
        void process(SimpleFeature feature);
    }
}
```

## 15.4 空间索引优化

空间索引把“与某个范围相交的要素有哪些”从全表扫描变成局部查找。JTS 提供两种：`STRtree` 是静态的批量加载索引，建好后查询最快，适合数据不变或变化很少的场景；`Quadtree` 支持插入与删除，适合要素频繁增删的场景，单次操作的常数开销比 STRtree 大。选错的代价不明显，但在高并发或大数据量时会暴露出来。

### 15.4.1 选择合适的索引

建 STRtree 分三步：`insert(envelope, item)` 逐个加入、`build()` 建树、`query(envelope)` 查询。`build` 之后再 insert 是无效的，部分版本会抛异常，另一些版本静默忽略——无论哪种，结果都不可靠。索引建好之后是只读结构，要更新就重建整个树，重建成本与要素数量成正比，所以它适合“一次建、多次查”的场景。

`Quadtree` 的用法更接近普通集合：`insert` 随时可以调，`query` 随时可用，删除用 `remove`。代价是每次插入都可能触发节点分裂，内存占用比 STRtree 高，查询也略慢。要素增删频繁（比如实时车辆位置）时用 Quadtree；批量导入后只查不改时用 STRtree。GeoTools 里还有一类 `SpatialIndex` 接口的封装，屏蔽了具体实现，需要时可换实现。

`queryWithIndex` 演示了索引查询的标准两步：先用 `index.query(queryGeom.getEnvelopeInternal())` 拿候选（只比包围盒），再对每个候选做精确的 `intersects` 判断。只有第二步是精确的，漏掉它结果会多出一堆“包围盒相交但几何不相交”的要素；只做第一步则结果偏大，在某些业务里可以接受（宁多勿漏），但要明确这是有意的取舍。

索引里存什么对象，决定了查询返回什么。示例存 `SimpleFeature`，返回也是 `SimpleFeature`；如果存 `Geometry`，返回就得按几何处理。同一棵树里不要混存不同类型，查询时的类型转换会抛 `ClassCastException`，而错误抛在循环深处，排查成本高。

```java
public class SpatialIndexOptimization {
    
    // 构建 STRtree（适合静态数据）
    public static STRtree buildSTRtree(SimpleFeatureCollection fc) throws Exception {
        STRtree index = new STRtree();
        
        try (SimpleFeatureIterator iter = fc.features()) {
            while (iter.hasNext()) {
                SimpleFeature feature = iter.next();
                Geometry geom = (Geometry) feature.getDefaultGeometry();
                index.insert(geom.getEnvelopeInternal(), feature);
            }
        }
        
        index.build();  // 必须调用
        return index;
    }
    
    // 构建 Quadtree（适合动态数据）
    public static Quadtree buildQuadtree(SimpleFeatureCollection fc) throws Exception {
        Quadtree index = new Quadtree();
        
        try (SimpleFeatureIterator iter = fc.features()) {
            while (iter.hasNext()) {
                SimpleFeature feature = iter.next();
                Geometry geom = (Geometry) feature.getDefaultGeometry();
                index.insert(geom.getEnvelopeInternal(), feature);
            }
        }
        
        return index;
    }
    
    // 使用索引查询
    public static List<SimpleFeature> queryWithIndex(STRtree index, 
            Geometry queryGeom) {
        
        List<?> candidates = index.query(queryGeom.getEnvelopeInternal());
        
        List<SimpleFeature> result = new ArrayList<>();
        for (Object obj : candidates) {
            SimpleFeature feature = (SimpleFeature) obj;
            Geometry geom = (Geometry) feature.getDefaultGeometry();
            
            // 精确检查
            if (queryGeom.intersects(geom)) {
                result.add(feature);
            }
        }
        
        return result;
    }
}
```

## 15.5 渲染优化

服务端渲染（比如生成 WMS 图片）的耗时由三块构成：数据查询、几何处理与样式解析、Java2D 绘制。前两块前面已经讲过，这里关注第三块。`StreamingRenderer` 的渲染提示（hints）能在不改业务代码的前提下影响后两块的行为，代价是显示质量。

### 15.5.1 渲染参数调优

`StreamingRenderer.OPTIMIZE_FTS_RENDERING_KEY` 打开按样式批量绘制的优化，把同一符号的多个要素合并处理，减少状态切换。`SCALE_COMPUTATION_METHOD_KEY` 设为 `SCALE_ACCURATE` 表示精确计算比例尺，对比例尺相关的样式规则（下一节）准确；如果地图范围固定、比例尺不变，用近似算法更省时间。`LINE_WIDTH_OPTIMIZATION_KEY` 优化线宽处理，`LABEL_CACHE_KEY` 为标注准备缓存实现，避免每次重算文字布局。

`RENDERING_BUFFER` 是渲染缓冲，表示在地图视野之外额外渲染多少像素。预渲染视野外一圈，平移时可以复用已经画好的内容，减少闪烁与重绘；代价是每次绘制面积变大。裁屏图（固定范围出图）把它设小甚至为 0 能省时间，交互式地图服务保持 30 到 100 之间比较平衡。

`setJava2DHints` 里的两个设置是画质与速度的直接取舍：关闭抗锯齿（`VALUE_ANTIALIAS_OFF`）让线条边缘出现锯齿，但绘制速度明显提升；`VALUE_RENDER_SPEED` 让 Java2D 选择偏速度的渲染管线，`VALUE_RENDER_QUALITY` 则相反。生成瓦片底图时可以关抗锯齿，生成打印地图时应该打开。

提示参数不是越多越好，每个优化在特定数据上都有反效果。例如要素数量少、样式简单时，批量绘制的调度开销可能大于收益。调整顺序建议是：先保证查询只取必要数据，再调渲染参数，最后才考虑降画质；反过来做，画质降了、速度没提升多少。

```java
public class RenderingOptimization {
    
    public static StreamingRenderer createOptimizedRenderer() {
        StreamingRenderer renderer = new StreamingRenderer();
        
        Map<Object, Object> hints = new HashMap<>();
        
        // 优化选项
        hints.put(StreamingRenderer.OPTIMIZE_FTS_RENDERING_KEY, Boolean.TRUE);
        hints.put(StreamingRenderer.SCALE_COMPUTATION_METHOD_KEY,
            StreamingRenderer.SCALE_ACCURATE);
        hints.put(StreamingRenderer.LINE_WIDTH_OPTIMIZATION_KEY, Boolean.TRUE);
        hints.put(StreamingRenderer.LABEL_CACHE_KEY, new LabelCacheImpl());
        
        // 缓冲区
        hints.put(StreamingRenderer.RENDERING_BUFFER, 50);
        
        renderer.setRendererHints(hints);
        
        // Java2D 优化
        RenderingHints java2dHints = new RenderingHints(null);
        java2dHints.put(RenderingHints.KEY_ANTIALIASING,
            RenderingHints.VALUE_ANTIALIAS_OFF);  // 关闭抗锯齿提高速度
        java2dHints.put(RenderingHints.KEY_RENDERING,
            RenderingHints.VALUE_RENDER_SPEED);
        
        renderer.setJava2DHints(java2dHints);
        
        return renderer;
    }
}
```

### 15.5.2 按比例尺控制

比例尺规则让同一图层在不同缩放级别显示不同符号：远看只要一个 4 像素的小圆点，近看才需要描边、渐变、标注。这样做既省绘制开销，也符合制图规范——小比例尺下密集的细节只会糊成一片。`Rule.setMinScaleDenominator` 与 `setMaxScaleDenominator` 定义规则的生效区间，比例尺分母越大表示越“远”。

两条规则的区间要首尾相接：小比例尺规则 `min = 100000`，表示比例尺分母大于等于 10 万时生效；大比例尺规则 `max = 100000`，表示分母小于 10 万时生效。分界点 100000 只落在一个规则里取决于实现对该端点的开闭定义，如果两条规则都包含 100000，该比例尺下会两个符号叠加显示；如果都不包含，就会出现一条“无符号”的断层。经验做法是给其中一条的边界值错开 1，或者把边界设在业务上不会出现的比例尺上。

规则按顺序匹配，第一个匹配的规则生效。同一 `FeatureTypeStyle` 里可以放多条规则，用 `Filter` 按属性区分，用比例尺按层级区分，两个维度可以组合。规则数量增长会影响样式匹配的性能，几十条以内无感，上百条时应当合并或拆分图层。

示例里的 `SLD.createPointSymbolizer` 是 GeoTools 提供的便捷工具方法，参数分别是形状、颜色、大小或形状、填充、描边、描边宽度、大小。它适合演示，正式样式一般用 `StyleFactory` 逐个属性构造，或者直接解析 SLD/XML，便于和 GeoServer 的样式共用。

```java
public class ScaleBasedRendering {
    
    public static Style createScaleDependentStyle() {
        StyleFactory sf = CommonFactoryFinder.getStyleFactory();
        FilterFactory2 ff = CommonFactoryFinder.getFilterFactory2();
        
        // 小比例尺（远视）- 简化符号
        Rule smallScaleRule = sf.createRule();
        smallScaleRule.setMinScaleDenominator(100000);
        smallScaleRule.symbolizers().add(createSimpleSymbol());
        
        // 大比例尺（近视）- 详细符号
        Rule largeScaleRule = sf.createRule();
        largeScaleRule.setMaxScaleDenominator(100000);
        largeScaleRule.symbolizers().add(createDetailedSymbol());
        
        FeatureTypeStyle fts = sf.createFeatureTypeStyle();
        fts.rules().add(smallScaleRule);
        fts.rules().add(largeScaleRule);
        
        Style style = sf.createStyle();
        style.featureTypeStyles().add(fts);
        
        return style;
    }
    
    private static Symbolizer createSimpleSymbol() {
        // 创建简化符号
        return SLD.createPointSymbolizer("circle", Color.RED, 4);
    }
    
    private static Symbolizer createDetailedSymbol() {
        // 创建详细符号
        return SLD.createPointSymbolizer("circle", Color.RED, Color.BLACK, 0.5f, 10);
    }
}
```

## 15.6 最佳实践

这一节的代码模式看起来琐碎，但每一条都对应过真实故障。资源不关会泄漏，批量操作不开事务会让每次写入都提交一次，工厂重复创建有解析开销，CRS 反复 decode 在高频调用里变成热点。这些模式不需要记住全部，把模板抄进项目的基础类里，后续开发自然继承。

### 15.6.1 代码模式

`batchOperations` 的关键是 `Transaction`。GeoTools 的写入默认是自动提交，每个 `addFeatures` 就是一次事务；一万条要素逐条加就是一万次提交，数据库上表现为磁盘 IO 打满。显式开一个事务、每 1000 条提交一次，能把提交次数降到个位数，吞吐量提升非常明显。注意 `super` 之外还有 `commit()` 的时机：每批 commit 之后事务仍可继续使用，`close()` 要放在 finally。

`transaction.rollback()` 只在异常时调用，回滚的是当前未提交批次；已经 commit 的前几批不会回滚。如果要“全部成功或全部失败”，就不能分批 commit，只能把所有批次放在同一个事务里——但那样又会长时间占用连接与锁，大批量导入时通常不这么要求。这是典型的取舍，按业务语义选择。

三个静态工厂对象（`GeometryFactory`、`FilterFactory2`、`StyleFactory`）都是线程安全的，创建一次全局复用即可。`CommonFactoryFinder` 每次调用都要走 SPI 查找，开销比想象中大，放在循环里会变成热点。把它们声明为 `static final` 是最简单的优化。

`CRS_CACHE` 用 `ConcurrentHashMap.computeIfAbsent` 缓存 `CRS.decode` 的结果。CRS 解析涉及 WKT 文本解析和数据库查找，耗时可到毫秒级，高频坐标转换时不缓存会有明显开销。用 `computeIfAbsent` 而不是先 get 再 put，能避免并发下的重复解析。注意缓存键要包含坐标系定义的完整信息，只用 EPSG 编码做键时，不同版本对同一编码的解析结果可能不同，热更新场景要清缓存。

```java
public class BestPractices {
    
    // 1. 始终关闭资源
    public void properResourceHandling(DataStore store) {
        try {
            // 使用 store
        } finally {
            store.dispose();
        }
    }
    
    // 2. 使用批量操作
    public void batchOperations(SimpleFeatureStore store,
            List<SimpleFeature> features) throws Exception {
        
        Transaction transaction = new DefaultTransaction("batch");
        store.setTransaction(transaction);
        
        try {
            int batchSize = 1000;
            for (int i = 0; i < features.size(); i += batchSize) {
                int end = Math.min(i + batchSize, features.size());
                List<SimpleFeature> batch = features.subList(i, end);
                
                DefaultFeatureCollection fc = new DefaultFeatureCollection();
                fc.addAll(batch);
                store.addFeatures(fc);
                
                transaction.commit();
            }
        } catch (Exception e) {
            transaction.rollback();
            throw e;
        } finally {
            transaction.close();
        }
    }
    
    // 3. 重用工厂实例
    private static final GeometryFactory GEOMETRY_FACTORY = 
        JTSFactoryFinder.getGeometryFactory();
    private static final FilterFactory2 FILTER_FACTORY = 
        CommonFactoryFinder.getFilterFactory2();
    private static final StyleFactory STYLE_FACTORY = 
        CommonFactoryFinder.getStyleFactory();
    
    // 4. 缓存常用对象
    private static final Map<String, CoordinateReferenceSystem> CRS_CACHE = 
        new ConcurrentHashMap<>();
    
    public CoordinateReferenceSystem getCRS(String code) throws Exception {
        return CRS_CACHE.computeIfAbsent(code, k -> {
            try {
                return CRS.decode(k);
            } catch (Exception e) {
                throw new RuntimeException(e);
            }
        });
    }
}
```

### 15.6.2 性能监控

`timeOperation` 用 `System.currentTimeMillis()` 计时，精度在毫秒级，对分钟级的批量任务够用，对微秒级的单次调用不够。需要更细的精度时用 `System.nanoTime()`，它返回单调时间，不受系统时钟调整影响；两者都不能用来测绝对时间，只能测差值。

计时代码本身要放在 try/finally 里，否则操作抛异常时不会打印耗时，而异常路径往往正是最需要看耗时的地方。示例没有包 finally，实际使用时补上。多个操作嵌套计时时，用同一个 `System.nanoTime()` 基准算相对耗时，比各自取开始时间更一致。

`memoryUsage` 读取 JVM 堆的使用量、已分配量、最大量。`used` 在 GC 前后会剧烈波动，单次采样说明不了问题，要在固定间隔下连续采样观察趋势。`maxMemory` 是堆上限，接近上限时触发 Full GC，表现为响应时间出现周期性尖峰。真正定位内存问题要看堆转储，`jmap`、`jcmd` 或者给 JVM 加 `-XX:+HeapDumpOnOutOfMemoryError`，让它在 OOM 时自动落盘。

监控数据要写进日志而不是只打印到控制台，生产环境的控制台输出会被回收或丢失。把耗时、内存、要素数量这类指标按固定格式打日志，便于后续用日志平台做聚合和告警。

```java
public class PerformanceMonitoring {
    
    public static void timeOperation(String name, Runnable operation) {
        long start = System.currentTimeMillis();
        operation.run();
        long end = System.currentTimeMillis();
        
        System.out.printf("%s: %d ms%n", name, end - start);
    }
    
    public static void memoryUsage() {
        Runtime runtime = Runtime.getRuntime();
        
        long total = runtime.totalMemory();
        long free = runtime.freeMemory();
        long used = total - free;
        long max = runtime.maxMemory();
        
        System.out.printf("内存使用: %d MB / %d MB (最大 %d MB)%n",
            used / 1024 / 1024,
            total / 1024 / 1024,
            max / 1024 / 1024);
    }
}
```

## 15.7 本章小结

衡量优化是否有效，只看一个指标没用：吞吐量提升可能是靠更大内存换的，响应变快可能是靠更粗的渲染换的。每次调优记录三组数：耗时、堆内存峰值、结果精度（或画质）。三组都在可接受范围内，优化才算成立。

还有一个容易被忽视的层面：配置与数据本身。数据没有建空间索引、坐标系定义缺失、字段类型是字符串存数字，这些问题在代码层面怎么写都优化不掉，先做数据治理比改代码收益大。一个 `ogrinfo -al -so` 或者数据库的 `EXPLAIN` 就能看出来，成本很低，应该养成习惯。

本章详细介绍了 GeoTools 的性能优化和最佳实践：

1. **数据访问优化**
   - 属性投影
   - 分页查询
   - 连接池配置

2. **内存管理**
   - 资源释放
   - 流式处理

3. **空间索引**
   - STRtree vs Quadtree
   - 索引使用

4. **渲染优化**
   - 渲染参数
   - 比例尺控制

5. **最佳实践**
   - 代码模式
   - 性能监控

### 关键要点

- 始终正确关闭资源
- 使用空间索引提高查询效率
- 批量操作减少事务开销
- 重用工厂实例
- 按比例尺调整渲染复杂度
