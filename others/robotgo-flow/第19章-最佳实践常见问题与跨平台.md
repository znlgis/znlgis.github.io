# 第19章 - 最佳实践、常见问题与跨平台

作为教程的收尾章，本章汇总 robotgo-flow 使用中的最佳实践、常见问题排查（FAQ）以及跨平台方面的现状与限制，帮助你把工作流做得更稳、更可维护，也帮助你在遇到问题时快速定位。

## 19.1 最佳实践

### 19.1.1 工作流组织

- **按业务语义分步**：每个 `step` 对应一个有意义的业务阶段（如「登录」「填表」「提交」），而非把所有动作堆在一步。这样日志清晰，`--from N` 恢复也更自然；
- **给步骤起好名字**：`name` 会显示在进度中，取「登录系统」这类可读名称，而非「step1」；
- **一步一职责**：单个 step 内的动作应围绕同一目标，避免过长；
- **善用 `description`**：为工作流和步骤写清楚意图，方便他人（和未来的你）维护。

### 19.1.2 模板管理

- **统一目录**：所有模板放 `templates/`，用相对路径引用，便于迁移；
- **命名语义化**：`btn_login.png`、`input_user.png` 比 `1.png`、`2.png` 好得多；
- **在目标环境截图**：模板要在实际运行的机器、相同分辨率与 DPI 下截取，避免匹配失败；
- **截取要精准**：只截包含目标且相对独特的最小区域，既准又快；
- **随工作流一起版本管理**：把 YAML 与 `templates/` 一起纳入 Git，保证可复现。

### 19.1.3 等待与稳定性

- **永远显式等待**：切换页面/弹窗后，用 `wait` 等目标出现，而非用固定 `sleep` 赌时间；
- **双重等待更稳**：先 `wait_gone` 等加载动画消失，再 `wait` 等目标就绪；
- **合理设置超时**：`element_timeout` 太短易误报失败，太长会拖慢失败反馈，按网络/系统速度调（示例常用 10~15 秒）；
- **少用 sleep**：仅在没有可靠视觉信号时才用 `sleep` 兜底。

### 19.1.4 容错策略

- **开发期用 `abort`**：快速暴露问题，配合 `--debug` 定位；
- **生产期按需 `retry`/`continue`**：偶发性失败用 `retry`（配 `max_retries`）；非关键步骤失败可 `continue`；
- **利用错误截图**：失败时框架自动截图，是排障第一手材料。

### 19.1.5 人类行为模拟

- **面向风控场景开启**：需要「像真人」的场景启用 `human`，普通内部工具可关闭以求速度；
- **适度即可**：`speed`、`mistake_rate` 不宜过度，否则拖慢且可能引入非预期输入；
- **注意 `mistake_rate` 副作用**：打字纠错会产生额外击键，对某些即时校验的输入框需谨慎。

### 19.1.6 安全与凭据

- **敏感输入用 `mask`**：密码类输入务必设 `mask: true`；
- **不要硬编码密码**：用 `inputs` 运行时输入或 `prompt` 交互获取，避免把明文写进 YAML 提交到仓库；
- **最小权限**：自动化账号只授予必要权限。

## 19.2 常见问题排查（FAQ）

下表汇总常见问题、可能原因与解决方案：

| 现象 | 可能原因 | 解决方案 |
| --- | --- | --- |
| 模板始终匹配不到 | 分辨率/DPI/缩放与截图时不同 | 在目标环境重新截取；检查系统缩放设置 |
| 偶尔匹配不到 | 页面未加载完成 | 加 `wait`/`wait_gone`；调大 `element_timeout` |
| 点击位置偏移 | 显示缩放导致坐标偏差 | 统一 DPI；用模板匹配代替固定坐标 |
| 中文/特殊字符乱码 | 编码问题 | 框架已内置编码转换；确认 YAML 保存为 UTF-8 |
| type 输入丢字 | 输入过快或焦点未就位 | 启用 human 放慢；先 `wait` 确认输入框就绪 |
| 浏览器动作无效 | 焦点不在浏览器 | 先点击浏览器窗口获取焦点；确认目标是活动窗口 |
| 编译失败（CGO） | 缺少 MinGW-w64 GCC | 按第 2 章安装 MSYS2/GCC，配置 PATH |
| WPF 界面打不开 | 缺少 .NET 10 / 未编译 | 安装 .NET 10 SDK；用 `build.ps1` 构建 |
| 验证码/确认框没弹出 | 用了 `run` 但期望自动 | `prompt`/`confirm` 本就需人工；全自动流程需去掉这些动作 |
| `--from N` 后行为异常 | 前置步骤未执行，状态不对 | `--from` 要求手动把系统置于对应前置状态 |

排查通用思路：

1. **加 `--debug`**：逐步截图，观察在哪一步、什么界面出问题；
2. **看错误截图**：失败瞬间的画面往往直接说明原因；
3. **缩小范围**：用 `--from`/拆分步骤定位到最小可复现单元；
4. **验证模板**：把疑似失效的模板重新截取再试。

## 19.3 跨平台现状与限制

robotgo-flow **目前是 Windows-only** 的框架。虽然其底层 `go-vgo/robotgo` 本身支持跨平台，但 robotgo-flow 在实现中使用了一些 Windows 特有的能力，导致暂不能直接跨平台运行。

### 19.3.1 Windows 特有依赖

框架中依赖的 Windows 专有 API/行为主要包括：

- **窗口/进程相关**：如 `robotgo.FindIds`、`robotgo.ActivePid` 等在不同平台行为不一致；
- **按键状态检测**：`GetAsyncKeyState` 等是 Windows 特有；
- **修饰键差异**：不同平台的 alt/ctrl 等修饰键语义存在差异；
- **WPF 前端**：托盘应用基于 .NET WPF，本身即 Windows 专属；
- **构建脚本**：`build.ps1` 为 PowerShell 脚本，编译链（MinGW-w64/MSYS2）也以 Windows 为目标。

### 19.3.2 迁移到其它平台的思路

若要将 robotgo-flow 移植到 macOS/Linux，大致需要：

1. **抽象平台相关能力**：把窗口查找、按键状态、修饰键等封装到平台接口后，分平台实现；
2. **替换 Windows 专有调用**：为 macOS/Linux 提供等价实现（robotgo 多数基础能力可跨平台复用）；
3. **替换前端**：WPF 前端需换成跨平台 UI（如 Avalonia、Electron、Web），仍走 `serve` 的 JSON-Line 协议；
4. **调整构建**：为目标平台准备对应的 CGO 工具链与构建脚本；
5. **充分测试**：图像匹配在不同平台的 DPI/色彩管理下可能有差异，需回归验证。

### 19.3.3 现阶段建议

在官方提供跨平台支持之前，建议：

- 生产使用固定在 **Windows** 环境；
- 关注上游仓库更新，若跨平台需求强烈可参与贡献（见第 17 章二次开发）。
