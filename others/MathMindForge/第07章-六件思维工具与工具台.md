# 第07章 - 六件思维工具与工具台

六件工具（pattern / rule / construct / knob / probe / counter）是《数思工坊》的「可操作证据」来源：玩家每做一次判断，都要落成一个结构化动作，判定器读的正是这些动作留下的产物。但 2026-11 的第五轮改造（去卡片化）把「工具台」这一层整个拆掉了——**关卡里不再有工具卡、卡头与手风琴**，玩家打开一关看到的就是这一关的题面与作答面。

这一章讲两件事：六件工具各自是什么能力，以及它们在关卡里如何被渲染成真正承载答案的面板（`AnswerDock` 的映射表），第四轮删掉的「运行 / 采集 / 抽样 / 清除」按钮又是怎么变成自动执行的。

## 7.1 三层分工：toolkit、toolkit-ui 与外壳

六件工具横跨三个包，边界很硬：**纯逻辑不带 Vue、Vue 组件不带 Phaser、外壳不碰工具内部**。

| 层 | 包 | 里面有什么 | 禁止什么 |
|---|---|---|---|
| 纯逻辑 | `@mmf/toolkit` | `pattern/` 的规则与校验、`shared/rng.ts`、`shared/stats.ts` | 禁止 `vue`、`phaser`、`Math.random()`、`Date.now()` |
| 视图 | `@mmf/toolkit-ui` | `AnswerDock.vue`、11 块作答面板、`ArgumentBoard.vue` | 不 import Phaser，不直接写存档 |
| 宿主 | `apps/site` | 只引 `AnswerDock` 与 `ArgumentBoard`，负责布局、自动判题、存档、音效 | 不写着色/校验逻辑 |

`@mmf/toolkit` 的入口只有一行，因为它只导出模式工具：

```ts
// packages/toolkit/src/index.ts（全文）
export * from './pattern/index';
```

但 `shared/` 里有另两个入口：`@mmf/toolkit/shared` 导出 `mulberry32` / `hashString` / `digest` 与 `wilsonInterval` / `clamp` / `round2`。抽出来是因为它们与具体工具无关，又被多处复用：

```ts
// packages/toolkit/src/shared/rng.ts（节选）
/** 可注入种子的确定性 RNG；纯逻辑层唯一允许的随机来源。 */
export function mulberry32(seed: number): () => number {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6d2b79f5) >>> 0;
    let t = a;
    t = Math.imul(t ^ (t >>> 15), t | 1);
    t ^= t + Math.imul(t ^ (t >>> 7), t | 61);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

export function digest(value: unknown): string {
  // JSON.stringify(undefined / 函数 / symbol) 返回 undefined 而不是字符串；
  // 产物摘要来自玩家输入，缺字段是常态，这里退成空串，避免取 .length 时整次提交崩掉。
  const text = JSON.stringify(value) ?? '';
  return hashString(text).toString(16).padStart(8, '0');
}
```

这条「纯逻辑层唯一允许的随机来源」不是文档约定，而是 eslint 硬规则——同一份配置里禁止了 `Math.random` 与 `Date.now`：

```js
// eslint.config.js（节选）
{
  files: ['packages/toolkit/src/**/*.ts', 'packages/templates/src/**/*.logic.ts'],
  rules: {
    'no-restricted-properties': ['error',
      { object: 'Math', property: 'random', message: '纯逻辑层禁止 Math.random，请注入种子。' },
      { object: 'Date', property: 'now', message: '纯逻辑层禁止 Date.now，请注入 now。' },
    ],
    'no-restricted-imports': ['error', { paths: [
      { name: 'phaser', message: '纯逻辑层禁止 Phaser。' },
      { name: 'vue', message: '纯逻辑层禁止 Vue。' },
    ]}],
  },
},
```

这条禁令换来的是可测性：`packages/toolkit/src/shared/rng.test.ts`、`stats.test.ts`、`pattern/index.test.ts` 都能直接在 Node 里跑，不需要 jsdom、不需要 canvas、不需要等 Phaser 初始化。工具面板里那层「Vue 组件」则一律薄——读快照、派发动作、把结果画成按钮或表格，不自己算判定。

## 7.2 从 ToolDock 到 AnswerDock：工具卡这一层被删掉了

第三轮及以前，关卡右栏挂的是 `ToolDock`：它按内容 JSON 里的 `tools` 数组渲染 2~3 张可折叠「工具卡」，卡头写着「模式卡」「规则卡」「构造块」「参数旋钮」「数据采集器」「反例探测器」，同一时刻只展开一张（手风琴），默认开第一张，换关时回到第一张。折叠用 `v-show` 而不是 `v-if`，为的是保住填了一半的输入。

第五轮把这一层整体删掉了。现在的宿主只挂 `AnswerDock`：

```vue
<!-- apps/site/src/views/WorkshopView.vue（节选） -->
<!-- pattern / rule：答案在画布上，这里不渲染卡片；保留 host 容器给模板挂载上下文用。 -->
<div v-else ref="host" class="hidden" aria-hidden="true" />
<div v-if="hasAnswerArea" ref="host" data-testid="level-dock" class="min-h-0 flex-1 overflow-y-auto p-2.5">
  <div :class="splitLayout ? '' : 'mx-auto w-full max-w-3xl'">
    <AnswerDock v-if="runtime && detail" :tools="detail.tools" :runtime="runtime" :detail="detail" :locale="locale" />
    <ArgumentBoard
      v-if="runtime && detail?.template === 'argue' && liveSnapshot"
      :runtime="runtime"
      :snapshot="liveSnapshot"
      :detail="detail"
      :t="translator"
    />
  </div>
</div>
```

右侧整列是否出现，由两个 computed 决定：

```ts
/**
 * 本轮简化：关卡里不再有「工具卡」这一层。
 * pattern / rule 的答案就在画布上，右侧只留失败提示与动作条；
 * 其余模板的答案面板直接平铺（argue 用论证板）。
 */
const hasAnswerArea = computed(() => {
  const template = detail.value?.template;
  return template !== undefined && template !== 'pattern' && template !== 'rule';
});
/** 画布 + 作答面板并排；pattern / rule 只有画布，整块宽度留给它。 */
const splitLayout = computed(() => module.value?.manifest.hasCanvas === true && hasAnswerArea.value);
```

也就是说：**pattern / rule 两关的右栏整块消失，画布占满整宽**；其余模板没有画布，作答区被拉满宽度居中（`max-w-3xl`）。不做 `v-show` 折叠之后，也就不存在「先展开卡片再操作」这一击——20 关的交互预算因此普遍下调一档（第 18 章）。

删掉的组件共 8 个：`ToolDock`、`PatternTool`、`RuleTool`、`ConstructTool`、`DominoTool`、`InvariantProbeTool`、`MetricsTool`、`QueueMetricsTool`。新增的 `AnswerDock` 只做一件事：**把工具规格映射到真正承载答案的面板**。

```ts
// packages/toolkit-ui/src/AnswerDock.vue（节选）
/**
 * 工具规格 → 真正承载答案的面板。表里没有的一律不渲染：
 * pattern / rule 由画布作答，domino / invariant probe 这类「沙盒工具」不再出现在答案区。
 */
function panelOf(spec: ToolSpecLike): string | null {
  if (spec.kind === 'construct') {
    const mode = spec.config.mode;
    if (mode === 'payment') return 'payment';
    if (mode === 'network') return 'network';
    if (mode === 'schedule') return 'schedule';
    if (mode === 'frontier') return 'frontier';
    if (mode === 'distribution') return 'distribute';
    return null;
  }
  if (spec.kind === 'counter') return 'counter';
  if (spec.kind === 'knob') return 'knob';
  if (spec.kind === 'probe') {
    const mode = spec.config.mode;
    if (mode === 'tally') return 'tally';
    if (mode === 'sampling') return 'sampling';
    if (mode === 'inference') return 'inference';
    if (mode === 'sample') return 'sample';
    return null;
  }
  return null;
}
```

这张映射表就是去卡片化后的「工具台」：**工具不再是一个个可折叠的盒子，而是关卡里那块能直接作答的地方**。组件仍是按 `spec.kind` + `spec.config.mode` 两级分发，但分发目标从「工具卡」换成了「答案面」；`v-else` 兜底那句「这个工具暂时还没接上」也随组件删除而消失——`panelOf` 返回 `null` 时不渲染任何东西，不会再出现占位文。

`AnswerDock` 的 props 仍然是四样：`tools` / `runtime` / `detail` / `locale`。三个决定值得说：

- **订阅在组件里做，不在外壳做**：`AnswerDock` 自己 `subscribe` 运行时快照并在 `onBeforeUnmount` 里 `unsubscribe()`。订阅与组件同生共死，外壳不需要转发快照。
- **`shallowRef` 而不是 `ref`**：快照是整棵替换的只读视图（里面还有 Map 派生的数组），深层响应式既没必要也容易把大对象代理一遍。
- **`locale` 变化时重建 translator**：`createTranslator` 绑死了表，换语言必须换 translator 实例；用 `watch` 而不是每次渲染 `createTranslator`，避免每帧建对象。

```ts
const snapshot = shallowRef<RunSnapshot>(props.runtime.snapshot());
const unsubscribe = props.runtime.subscribe((next) => {
  snapshot.value = next;
});

const translator = shallowRef<Translator>(createTranslator(props.locale));
watch(
  () => props.locale,
  (locale) => {
    translator.value = createTranslator(locale);
  },
);
```

工具规格里的 `kind` / `mode` 和内容 JSON 一一对应：`construct` 有 `placement`（占位）/ `payment` / `domino` / `distribution` / `network` / `schedule` / `frontier` 七种 mode，`probe` 有 `sample`（默认）/ `tally` / `metrics` / `invariant` / `queue` / `sampling` / `inference` 七种 mode——但去卡片化之后，七种视觉形态里**只有真正承载答案的那些会被渲染**：`domino` 与 `invariant` 不再有面板，`metrics` / `queue` 只剩旋钮（指标并进旋钮面板）。

## 7.3 六件工具：动作、产物、失败类

动作是工具唯一能改变世界的方式，全部集中定义在 `packages/game-kit/src/runtime.ts` 的 `ActionPayloadMap` 里。下表按工具列出实际驱动的动作；契约里还登记了少数保留动作（例如 `rule/run`），模板当前统一走宿主的 `run`，所以没有列进表里：

| 工具 | 动作 | 产物 | 失败类（模板 `FAILURE_CLASSES`） |
|---|---|---|---|
| `pattern` 规律反推 | `pattern/inspect`、`pattern/setCycle`、`pattern/preview`、`pattern/commit`、`construct/place` | `pattern-rule`（`{tokens, period, transform}`）+ `repair-set` | `pattern-no-observation` / `pattern-rule-invalid` / `pattern-cycle-wrong` / `pattern-repair-incomplete` / `pattern-mismatch` / `pattern-transfer-failed` |
| `rule` 画路线 | `rule/place`、`rule/remove`、`rule/move`、`rule/commit`（运行走统一 `run`） | `program`（`ProgramBlock[]`） | `rule-empty` / `rule-wall` / `rule-loop` / `rule-missed-item` |
| `construct` 摆构造 | `construct/place`、`construct/remove` | `placement-set` / `distribution` / `network-selection` / `schedule` / `frontier-costs` / `counterexample` | `construct-not-optimal` / `construct-overpay`，另有按 mode 划分的 `distribution-*` / `network-*` / `schedule-*` / `frontier-*` 等 |
| `knob` 调参数 | `knob/set`、`knob/run`、`knob/compare`、`knob/reset`、`knob/commit` | `params`（`{values}`）+ `RunMetrics` | `sim-not-run` / `sim-budget` / `sim-coverage` / `sim-wait` / `sim-overfit-seed` |
| `probe` 采样与下结论 | `probe/sample`、`probe/clear`、`probe/focus`、`probe/claim`、`probe/tally` | `dataset` + `claim`（`ClaimInput`） | `probe-sample-small` / `probe-not-collected` / `probe-claim-mismatch` / `probe-tally-wrong` |
| `counter` 构造反例 | `counter/edit`、`counter/test`、`counter/annotate`、`counter/commit` | `counterexample`（`CounterPatch`） | `counter-invalid` / `counter-wrong-premise` / `counter-not-tested` |

这张表背后有一条纪律：**先加类型、再加处理分支、最后才让 UI 派发**。动作表里没有的类型不能出现在组件里，否则 `autoplay` 与真实操作就不再是同一条路径。

要注意「表里列了动作」不等于「界面上有对应按钮」。去卡片化之后，UI 只派发承载答案的那几个动作：pattern 画布派发 `construct/place`（规律由填法反推，不再派发 `pattern/setCycle` / `pattern/preview` / `pattern/commit`），rule 画布派发 `rule/place`（没有积木面板与程序列表），其余模板由面板直接派发 `construct/*`、`knob/*`、`probe/*`、`counter/*`。契约里的旧动作留着，是为了让 `autoplay`、审计与历史内容仍走同一条运行时路径，不是给 UI 留后门。

工具的产物不是「答案」，而是**结构化证据**。以 pattern 为例：

```ts
// packages/toolkit/src/pattern/index.ts（节选）
export interface PatternRule {
  tokens: string[];
  period: number;
  transform: PatternTransform;
}

export interface PatternArtifact {
  patternRule: PatternRule;
  repair: PatternRepair[];
}
```

`repair` 是玩家在缺口上放的块（`{index, token}` 数组），`patternRule` 是从填法反推出来的规律。第五轮之后玩家不再「先声明规律再补块」，画布每填一格，运行时就用 `deriveRuleFromRepairs` 从已填缺口反推一条能解释它的候选规律；反推命中就写进产物，反推不中则 `rule = null`、submit 走 repair-only 校验，报具体错格。这个设计在第 8 章展开。

## 7.4 作答面板逐个看：11 块面板各答什么题

`AnswerDock` 的映射表落到具体组件上，就是下面这 11 块。它们没有卡头、没有展开收起，进入关卡即平铺：

| 面板 | 组件 | 出现在哪类关卡 | 玩家在面板上做什么 |
|---|---|---|---|
| `payment` | `PaymentTool.vue` | `g46-algorithm-payment` | 点面额往台面放硬币，金额与枚数实时上屏 |
| `network` | `NetworkTool.vue` | `g79-structure-network` | 在 SVG 路网图上点边，连通块/成本/关键接入实时亮灯 |
| `schedule` | `ScheduleTool.vue` | `g79-algorithm-schedule` | 在课表网格上点格排课，冲突格与偏好分实时更新 |
| `frontier` | `FrontierTool.vue` | `g1012-algorithm-frontier` | 用 +/- 改边权，贪心与最优代价当场对比 |
| `distribute` | `DistributeTool.vue` | `k-modeling-share`、`g13-modeling-pack` | 给每个容器加/减物品，一键「照这样分」 |
| `counter` | `CounterTool.vue` | `g46-algorithm-payment`（反例部分） | 改目标金额与面额，再点一条失效前提 |
| `knob` | `KnobTool.vue` | 排队/调度/胜率实验室 | 调数字旋钮，指标随改随算 |
| `tally` | `TallyTool.vue` | `k-data-tally`、`g13-data-weather` | 填四类计数，再点一个「最多/最少」结论 |
| `sampling` | `SamplingTool.vue` | `g79-data-sampling` | 看两批样本比例，点结论 |
| `inference` | `InferenceTool.vue` | `g1012-data-inference` | 看两组区间，选「哪组更高/差异不明确」 |
| `sample` | `SampleTool.vue` | `g1012-modeling-winrate` | 看胜率与 Wilson 区间，点结论（采样由旋钮自动跑出） |

两个特例值得单独说明。pattern / rule 两关**没有任何作答面板**：答案就在画布上，进关看到的是失败横幅、画布与底部动作条，右侧整列不存在。argue 三关则由宿主单独渲染 `ArgumentBoard`，`AnswerDock` 不渲染工具——它是「论证的提交面」，不是第七件工具，7.7 节展开。

`panelOf` 返回 `null` 的规格一律不渲染，这条规则同时承担了「删掉的工具不再复活」的职责：`domino`（多米诺沙盒）、`invariant`（不变量探测面板）、`metrics`、`queue` 这些 mode 即使内容里还登记着 `tools` 条目，也不会在界面上重新长出一块面板。

## 7.5 自动执行：删掉「运行 / 采集 / 抽样 / 清除」之后

第四轮的交互简化做了一件事：**把「让系统跑一下 / 显示一下」的按钮全部删掉，改成进入面板即自动执行**，只保留答案输入本身。这是「去卡片化」之前的一步，但两者叠在一起才完成现在的交互面：

| 位置 | 删掉的额外操作 | 改成 |
|---|---|---|
| 宿主底部 | 「完成」 | 填完自动判；答对自动进下一关 |
| 宿主完成面板 | 「下一关 / 再玩一次 / 回星图」三选一 | 0.9s 成功遮罩后自动跳；存档失败才停在面板 |
| tally | 「全部倒出来」「采集一把」 | 进入面板自动倒出整筐，直接填数字 |
| sampling | 「抽两批」「再抽 N 个」「倒回袋里」 | 进入面板自动抽两批，直接点结论 |
| simulate / duel | 「运行」「跑满 N 局」 | 参数一改就自动运行，指标立刻上屏 |
| argue | 引导文案里的「再点完成」 | 选完依据即判 |
| payment | 「清除」 | 点答案即判 |

实现上有两处细节值得抄下来，它们决定了「自动执行」不会跟自动判题打架。

第一，**自动动作放在宏任务里**。`TallyTool` 与 `SamplingTool` 的注释写得很直白：

```ts
// packages/toolkit-ui/src/TallyTool.vue（节选）
/**
 * 自动倒筐放在宏任务里：autoplay 调试路径整段在微任务里跑完，
 * 不能让它和自动倒筐抢同一个运行时（否则自动播放的第一次采集会被判「已采完」）。
 */
```

`sampling` 同理：「自动抽样放在宏任务里，不能让它和自动抽样抢同一个运行时（否则自动播放的样本序列会被多抽两批打乱）」。这条对 e2e 与审计都关键——`autoplay` 通关路径和玩家真实点击路径必须落到同一个状态，否则 A8 与 A11 会各自看到不同的世界。

第二，**「重来」之后自动动作要再跑一次**。`TallyTool` 的 `collected` 回到 0 时会再自动倒一次，`SamplingTool` 的批次与总数回到 0 时会再自动抽两批；玩家不用重新去找那个已经不存在的按钮。

自动执行还带出一条门禁：**面板必须真的变化**。`e2e/ui-smoke.spec.ts` 在关键动作前后各取一次面板文本，断言两者不同——专拦两类问题：死按钮（点了屏幕完全不变）与「运行完没反馈」（调完参数指标区还是旧值）。自动执行把「按钮」删了，但「动作 → 可见结果」这条链不能断。

## 7.6 防点选：每件工具都有一道「不做事就过不去」的坎

《数思工坊》的通关条件不是「选对选项」，所以每件工具都必须让「点一下蒙对」变得无效。反刷题审计（`scripts/audit-levels.ts`）里 A1/A1b/A2/A4/A11 几条就是查这个：A1 要求无工具提交必须被拒且给出缺失证据、A1b 要求空壳/错误产物被结构反馈拒绝、A2 要求动作空间里存在非选择动作、A4 要求负例真的触发声明的失败类、A11 要求 autoplay 通关后 `answerComplete` 为真。

六件工具各自的「坎」：

| 工具 | 坎的具体实现 |
|---|---|
| `pattern` | 只填不声明也能判，但填法必须能被可见格推出的某条候选规律解释；迁移门还会把「没有可翻译规律的空壳」判 `pattern-transfer-failed` |
| `rule` | 必须交出一段可执行程序并真的跑出结果；画布画路线产出的是展开版程序，拿不到 `simple` 印章 |
| `construct` | 必须真的摆放；判定按登记物品/站点/课次重算，不信任产物自报的 `total` |
| `knob` | 必须真的运行出指标；达标还要换种子仍达标（`sim-overfit-seed`） |
| `probe` | 结论必须绑定本次采样（`probe-not-collected`）；样本太小或结论与数据对不上会判 `probe-sample-small` / `probe-claim-mismatch` |
| `counter` | 必须自己构造实例并测出一个让贪心失效的例子，还得指出它推翻了哪条前提（`counter-wrong-premise`） |

界面层面的「坎」也做了对应改造，最典型的是反例探测器：

```ts
/** 编辑即自动测：玩家不用再点一次"测试贪心"。 */
async function autoTest(): Promise<void> {
  const result = await props.runtime.dispatch({ type: 'counter/test', payload: {} });
  if (!result.ok) error.value = result.message ? props.t.t(result.message) : null;
}

/** 失效前提是一排 chip：点一下就指出（不需要下拉展开、也不需要再点提交）。 */
async function choosePremise(id: string): Promise<void> {
  if (busy.value || !lastTest.value?.passed) return;
  // …dispatch({ type: 'counter/annotate', payload: { premiseId: id } })
}
```

注意 `choosePremise` 的守卫：`!lastTest.value?.passed` 时 chip 全部禁用——**还没测出一个真正让贪心失效的例子，就先别让你指认前提**。这道顺序约束把「先猜结论再凑证据」堵掉了。

参数旋钮的坎在「必须跑」上，但「跑」已经自动化：改参数即触发运行，`knob/run` 由面板代玩家派发，判定读的仍是运行记录而不是参数值本身。数据采集器同理：`probe/sample` 产生 `dataset`，`probe/claim` 提交的结论会被拿去和这份 dataset 比对，对不上就是 `probe-claim-mismatch`。

## 7.7 论证板：argue 的提交面，不是第七件工具

`ArgumentBoard.vue` 常常被误当成「第七件工具」。它不是：它不声明自己的 `ToolSpec`、不出现在 `tools` 数组里，只在 `template === 'argue'` 的关卡里由宿主额外渲染；第五轮之后更是**只留它一块**——多米诺沙盒与不变量探测面板都被删了。

它的四个字段（主张 / 依据 / 证据 / 适用范围）并不是四个输入框。当前实现把输入压到了最小：**玩家只选一条依据，其余三格由运行时推出来**：

```ts
/**
 * 一切显示都从快照派生：没有本地表单状态，所以重玩/换关不会把上一轮的旧选择带回来。
 * 主张与范围不再由玩家填：选一条依据，运行时就把「不可能铺满 → 1×2 多米诺铺满」推出来。
 */
const warrant = computed(() => argument.value?.warrant ?? '');
const claim = computed(() => argument.value?.claim ?? '');
const scope = computed(() => argument.value?.scope ?? '');
```

点一条依据时，它先让运行时真的去数棋盘（`probe/sample`），再写依据（`argue/setWarrant`）：

```ts
async function pick(next: string): Promise<void> {
  if (busy.value) return;
  busy.value = true;
  error.value = null;
  try {
    // 一次点击 = 一次输入：先把黑白格真的数出来（观察证据），再写一条依据。
    // 沿用旧实现里把统计与论证拆成两个按钮，会逼玩家先点 probe 再回来点依据。
    const sampled = await props.runtime.dispatch({ type: 'probe/sample', payload: {} });
    if (!sampled.ok) { /* error ... */ return; }
    const result = await props.runtime.dispatch({ type: 'argue/setWarrant', payload: { warrant: next } });
    if (!result.ok) error.value = result.message ? props.t.t(result.message) : null;
  } finally {
    busy.value = false;
  }
}
```

这一步很关键：如果论证板只写「依据 = 染色法」而不真的去数棋盘，它就退化成选择题。先 `probe/sample` 再 `argue/setWarrant`，意味着证书里的每个数字都有一次真实的工具调用作依据。

界面上还会就地给出「这条依据在这张棋盘上到底能不能下结论」，例如染色法要比较黑白格数是否相等、奇偶/面积要看总格数是否奇数——这是把同一条数学事实翻成人话，真正的判定仍以运行时的 `validateArtifact` 为准。选一条依据就是一次完整作答：`answerComplete` 当场变 true，宿主 500ms 后自动判题。

`ArgumentBoard` 的产物是 `argument`（`ArgumentSnapshot`），失败类是 `argue-claim-unsupported` / `argue-warrant-unsupported` / `argue-invariant-false` / `argue-evidence-missing` / `argue-scope-wrong`。

## 7.8 answerComplete：工具面板与自动判题的交界

第四轮删掉「完成」按钮之后，宿主靠快照里的一个布尔量决定「什么时候判」：`RunSnapshot.answerComplete`。契约在 `packages/game-kit/src/runtime.ts` 与 `packages/templates/src/shared/runtime.ts` 两处：

- `RunSnapshot.answerComplete?: boolean`：玩家的答案是否已经填完整；
- `RuntimeAdapter.answerComplete?(state): boolean`：模板自己实现，缺省 false。

**它不判对错**——对错永远由 `validate` 决定。answerComplete 只决定「什么时候允许自动判题」：

| 模板 / 模式 | 关卡 | answerComplete=true 的条件 |
|---|---|---|
| pattern | k-structure-pattern-path、g13-structure-symmetry | 所有缺口都已填上（规律由填法反推，不再要求已提交） |
| rule | k-algorithm-train、g13-algorithm-route | 程序非空，且跑出结果（撞墙/绕圈，或已到终点） |
| construct / distribution | k-modeling-share、g13-modeling-pack | 每一类物品都分完 |
| construct / network | g79-structure-network | 已选边数 ≥ 站点数 − 1 |
| construct / schedule | g79-algorithm-schedule | 每个课次都排进时段 |
| construct / frontier | g1012-algorithm-frontier | 真的改过至少一条边 |
| construct / payment | g46-algorithm-payment | 反例已指出前提 + 台面硬币总额 ≥ 目标（或已放满上限） |
| experiment / tally | k-data-tally、g13-data-weather | 整筐采完 + 统计条已记录 + 结论已选 |
| experiment / duel | g1012-modeling-winrate | 参数凑满 + 采样结果已出 + 结论已选 |
| experiment / sampling | g79-data-sampling | 样本非空 + 结论已选 |
| experiment / inference | g1012-data-inference | 结论已选 |
| simulate / dispatch、queue | g79-modeling-dispatch、g46-modeling-queue | 自动运行结果就绪 |
| argue | 三关 | 依据已选（证据/主张/范围由运行时派生） |

有了这个谓词，宿主的自动判题才不会「在玩家还在填的时候误报」：

```ts
/** 玩家停手多久后自动判题：太短会在"还在填"时误报，太长会让人觉得没反应。 */
const AUTO_JUDGE_DELAY_MS = 500;
/** 答对后成功遮罩停留多久再进下一关（instant 模式是 e2e 用的快进）。 */
const AUTO_NEXT_DELAY_MS = 900;

function scheduleAutoJudge(usage: number): void {
  clearAutoJudge();
  autoJudgeTimer = window.setTimeout(() => {
    autoJudgeTimer = null;
    void autoJudge(usage);
  }, AUTO_JUDGE_DELAY_MS);
}
```

判定顺序仍是「先结构校验、再报缺步骤」，答错原因走顶部红色横幅（`failure-banner`）；判过就不再重复判（`autoJudgedUsage`），玩家一改答案才会重新判。这条链的末端是 `level:complete` 事件与存档（第 16 章）。

界面上玩家能看到的东西只有三样：顶部失败横幅、画布或作答面板、底部一行「填完自动判题 / 重来」提示条（`data-testid="level-auto-judge"`）。e2e 里「20 关都没有完成按钮」的用例就是断言 `level-submit` 数量为 0、`level-auto-judge` 可见。

## 7.9 工具面板里的 i18n：两种文案来源并存

工具面板的文案有两个来源，理解这个分裂有助于读懂现有代码。

第一类是**正式 i18n key**。内容 JSON 里 `tools[i].titleKey = 'tool.pattern.title'`、`descriptionKey = 'tool.pattern.desc'`；去卡片化之后，卡头不渲染了，但这两个 key 仍留在内容与 i18n 表里——星图关卡卡片、思维日志、家长报告显示的工具标签读的正是它们（第 15 章）。`content:check` 也要求这两个字段非空，所以它们不能删。

第二类是**面板内的短句**，仍直接写中文（工具组件里有注释写明「面板文案是 toolkit-ui 里的中文短句」）。`CounterTool` 这类组件会把 `t` 传进来并统一走 `translate()`，有的能查表、有的查不到就回退原文：

```ts
// packages/toolkit-ui/src/CounterTool.vue（节选）
/** 始终读取当前的 t，避免语言切换后拿到旧翻译器。 */
function translate(key: string, params?: MessageParams): string {
  return props.t.t(key, params);
}
```

为什么每个组件都写一个 `translate()` 包装而不是直接 `props.t.t`：`props` 是响应式的，渲染时读 `props.t` 才能拿到最新 translator；如果解构成局部变量 `const { t } = props`，语言切换后仍是旧实例。

这条缺口在 i18n 包里用兜底表补了一半：`zh-source.ts` 是「中文源串 → 英文」映射，正式 `en.ts` 优先，查不到再查兜底表，再查不到回退中文（宁可中文也不白屏）：

```ts
// packages/i18n/src/index.ts（节选）
/**
 * 英文表 = 正式 en 表 + "中文源串 → 英文"兜底表。
 * 后者兜住历史遗留的"以中文句子当 key"（内容 feedback / 模板失败文案），
 * 让英文界面不再漏出中文；正式 key 优先，避免兜底表盖掉真实文案。
 */
const EN: Record<string, string> = { ...zhSourceEn, ...en };
```

所以现状是：**切英文后界面基本干净，但作答面板里仍有硬编码中文**。这不是遗漏，而是 `docs/05` 里登记过的待办（「内容 i18n 化」），`content:check` 对这类 key 只记警告。写新面板时应该走 `titleKey` / `descriptionKey` 那条路，别再往组件里塞中文字符串。

## 7.10 工具与画布的协作：一个 runtime，两个消费者

有画布的模板（`pattern` / `rule`）里，作答面板与 Phaser 场景是同一个运行时的两个消费者——去卡片化之后，pattern / rule 的「面板」退化成画布本身，但这条协作关系没有变：

```text
玩家点画布格子 ──▶ 场景 dispatch(construct/place 或 rule/place) ──▶ runtime 状态变化
                                                      │
                              runtime.subscribe 通知 ──┤──▶ AnswerDock / 论证板重渲染（其余模板）
                                                      └──▶ 场景重画（签名比对后才重画）
```

两侧都不持有状态副本：面板读 `snapshot.toolState`，场景读同一份快照。场景侧还有一条性能纪律——先算 signature，没变就不重画：

```ts
// packages/templates/src/pattern/scene.ts（节选）
private render(snapshot: RunSnapshot): void {
  const signature = this.signatureOf(snapshot);
  if (signature === this.lastSignature) return;
  this.lastSignature = signature;
  // …重新绘制整条带子
}
```

这对「每点一格都派发一个动作」的交互是必须的：没有签名比对，改一个字母也要重画整条带子与所有文本对象。

无画布的模板（`construct` / `simulate` / `experiment` / `argue`）里，作答面板就是全部界面。宿主的 `mount()` 是空的，`AnswerDock` 被拉满宽度居中（`max-w-3xl`），这也是为什么 `manifest.hasCanvas` 这个字段存在——它决定宿主是否渲染 canvas 容器、给作答区多少宽度。

## 7.11 小结

- 三层分工：`@mmf/toolkit` 纯逻辑（禁 Vue/Phaser/Math.random/Date.now）、`@mmf/toolkit-ui` 视图组件、外壳只做布局、自动判题与存档。
- 关卡里没有「工具卡」这一层：`ToolDock` 的卡头与手风琴已删，`AnswerDock` 按 `kind` + `config.mode` 把工具规格映射到 11 块真正承载答案的面板；pattern / rule 不渲染面板，argue 只渲染论证板。
- 六件工具的动作名集中在 `ActionPayloadMap`，产物是结构化证据（`pattern-rule` / `program` / `placement-set` / `params` / `dataset+claim` / `counterexample`），失败类由模板 `FAILURE_CLASSES` 定义。
- 第四轮删掉了「运行 / 采集 / 抽样 / 清除」等仪式按钮，改成进入面板自动执行（自动倒筐、自动抽两批、改参即运行、编辑即测），并靠宏任务避免与 autoplay 抢运行时。
- 防点选不是文案口号：pattern 的填法要能被候选规律解释，counter 要先测出反例才能指认前提，knob 判定读运行记录，probe 的结论必须绑定本次采样。
- `answerComplete` 只回答「填完了没有」，不判对错；宿主停手 500ms 自动判题、答对 0.9s 后自动进下一关，A11 审计兜底。
- `ArgumentBoard` 是 argue 模板的提交面，不是第七件工具；玩家只选一条依据，且必须先真的数出棋盘数据。
- 工具面板 i18n 是两种来源并存：`titleKey` 留给外围元数据，面板内仍有中文短句；`zh-source.ts` 兜底让英文界面不漏中文。
