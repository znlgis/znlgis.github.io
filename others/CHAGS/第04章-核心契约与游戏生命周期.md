# 第04章 - 核心契约与游戏生命周期

## 4.1 契约层的位置

`packages/game-kit` 是整个仓库里最薄、也最重要的包：它只有三个文件（`contract.ts` 178 行、`math.ts` 24 行、一行 `index.ts`），不含 Phaser、不含浏览器 API，两侧都依赖它：

- **游戏侧**：每个游戏包只认识 `GameContext` 与 `GameModule`，不知道外壳长什么样、进度存在哪里；
- **外壳侧**：Vue 只通过 `registry` + `mount(ctx)` 使用游戏，不知道任何具体玩法。

这样做的直接收益是**两边可以并行开发、独立替换**：换外壳（比如做微信小游戏壳）不用动游戏；加游戏不用动外壳。

```
packages/game-kit/src/contract.ts
├─ GameManifest      # 游戏自述：id / 标题 / 版本 / 模板 / 设计分辨率 / 年龄（6 个字段）
├─ GameEventMap      # 事件表：场景、幕、故事听完、选择、完成、卡片、退出
├─ Stars / ReviewState / EntryProgress / SaveData   # 存档类型
├─ PlatformServices  # 平台出口：storage / audio / lifecycle / share / telemetry / now
├─ GameContext       # 游戏运行时拿到的一切：容器、内容、服务、语言、调试开关
├─ DebugOptions      # autoplay / storyInstant / cardHold
└─ GameModule        # 游戏的对外接口：mount / unmount / pause / resume
```

## 4.2 GameManifest：只剩 6 个真的有人读的字段

```ts
export interface GameManifest {
  id: string;
  title: string;
  version: string;
  template: TemplateId;
  designSize: { width: number; height: number };
  ageRange: [number, number];
}
```

这份接口在 2026-10-18 被**削掉了一半**：以前还有 `orientation` / `sessionSeconds` / `skills` / `curriculum` / `assets` 五个字段，全仓 0 读取（只有游戏测试顺手断言过），却要 53 个 manifest 各抄一遍 —— 其中 `curriculum.figures` 已经悄悄漂移了 3 处，没有任何测试会发现。描述性信息（朝代 / 人物 / 技能）的唯一事实来源是内容 JSON，manifest 不再重复。

一个真实例子（`games/pangu/src/manifest.ts`，全文 12 行）：

```ts
import type { GameManifest } from '@chags/game-kit';
import { DESIGN } from '@chags/templates/layout';

export const manifest: GameManifest = {
  id: 'pangu',
  title: '盘古开天辟地',
  version: '0.1.0',
  // 撑天那一段是 tap（点满一万八千年），不是已经删掉的 grow 模板
  template: 'tap',
  designSize: { width: DESIGN.width, height: DESIGN.height },
  ageRange: [7, 10],
};
```

三处值得注意的细节：

1. **`template` 必须是 `TEMPLATE_IDS` 里的真实 id**。它在 `content` 包里有唯一定义，契约层只做再导出；写错一个字，`pnpm typecheck` 就报错。盘古这一行曾经写着早已删除的 `'grow'`，而当时没有任何测试会发现 —— 这就是 `registry.test.ts` 那 5 条交叉断言被补上的原因（第 13 章）。
2. **`designSize` 从 `@chags/templates/layout` 取 `DESIGN`（750×1334）**，不写 `@chags/templates` 主 barrel。这一点不是洁癖：主 barrel 会把 24 个场景一起拖进 chunk，而 `layout.ts` 是纯常量、与 Phaser 无关，所以还能在 Node 里被单测导入。
3. **`id` 必须与内容 JSON 的 `id` 一致**，外壳用它把「内容」与「游戏包」对起来：`loadEntry(id, locale)` 找不到内容会抛 `找不到游戏内容：<id>`。两边的对应关系由 `registry.test.ts` 强制。

## 4.3 GameContext：游戏运行时拿到的一切

```ts
export interface GameContext {
  container: HTMLElement;
  manifest: GameManifest;
  content: ContentEntry;             // ★ 已经是目标语言的翻译结果
  services: PlatformServices;        // 存档 / 音频 / 生命周期 / 分享 / 遥测
  locale: Locale;                    // 'zh-CN' | 'en'
  reducedMotion: boolean;            // prefers-reduced-motion
  debug?: DebugOptions;              // ?autoplay / ?story / ?card（仅开发与自动化）
  completedBefore: boolean;          // 这条内容之前通关过没有（决定能否「跳过故事」）
  emit<K extends keyof GameEventMap>(type: K, payload: GameEventMap[K]): void;
  requestExit(reason?: 'quit' | 'replay'): void;
}
```

四个设计点值得展开：

1. **`content` 是已经翻译好的**。外壳先取摘要、再按条目加载详情、再合并当前语言的译文补丁，最后交给游戏 —— 所以游戏代码里**不存在语言分支**（第 11 章）。
2. **`services` 是唯一的环境出口**。游戏禁止直接碰 `localStorage` / `fetch` / `wx.*`，需要用什么都从 context 上拿。
3. **`completedBefore` 是「跳过故事」的唯一开关**。首次必须听完（故事是正片），二周目才允许跳过 —— 两个方向都由外壳从存档里读出来，游戏只需要读这个布尔值。
4. **`requestExit(reason)` 区分「退出」与「再来一次」**：`'replay'` 时 `PlayView` 会原地卸载并重新挂载这一局，不刷新页面、不回大厅。

`debug` 的三个开关也在这份契约里定死（`DebugOptions`）：`autoplay`（自动通关）、`storyInstant`（跳过「听完才能继续」的等待）、`cardHold`（自动通关后停在典故卡上）。三者的解析入口只有一个 —— `shell/createGameContext.ts` 的 `readDebugOptions()`，并且只在开发服务器或 `navigator.webdriver` 下生效。

## 4.4 PlatformServices：平台出口的接口形状

```ts
export interface PlatformServices {
  storage: ProgressStore;
  audio: AudioBus;
  lifecycle: LifecycleBus;
  share(opts: ShareOptions): Promise<void>;
  telemetry: Telemetry;
  now(): number;
}
```

各子接口的要点（全部逐字来自 `contract.ts`）：

```ts
export interface ProgressStore {
  load(): Promise<SaveData>;
  save(data: SaveData): Promise<void>;
}

/** 朗读的结果：真的念完了 / 这台设备念不出来（静音、没装语音包、无头浏览器） */
export type SpeechOutcome = 'ended' | 'unavailable';

export interface SpeechHandle {
  /**
   * 念完、或者确认念不出来时 resolve —— 两种情况都必须 resolve，
   * 否则故事页会永远停在"正在听"上。玩法里的旁白可以完全忽略它。
   */
  readonly done: Promise<SpeechOutcome>;
}

export interface AudioBus {
  unlock(): Promise<void>;                      // iOS / 微信必须由用户手势触发解锁
  play(key: SfxKey): void;                      // 六种合成音效
  tone(freq: number, durationMs: number): void; // 指定音高的一声（进度"听得见"）
  speak(text: string, locale: Locale): SpeechHandle;
  stopSpeech(): void;
  setMuted(muted: boolean): void;
  isMuted(): boolean;
}

export interface LifecycleBus {
  onPause(cb: () => void): () => void;
  onResume(cb: () => void): () => void;
}
```

`speak()` 从 2026-10-15 起返回 `SpeechHandle` 而不是 `void`：这是「故事必须听完」这条产品规则的技术落点 —— 故事页要等 `done` 才放行，而 `unavailable`（静音、无语音包、无头浏览器）也必须 resolve，否则那些设备上会永远卡在「正在听」。这条契约在第 15 章还会再提一次。

`SfxKey` 只有六个：`tap` / `correct` / `wrong` / `splash` / `unlock` / `complete`，全部由 WebAudio 振荡器实时合成（零音频文件），见第 9 章。

注意 `now()`：所有需要计时的地方（长按进度、等待玩法、空闲提示、会话时长）都通过 `services.now()` 而不是 `Date.now()`。这样时钟可注入、可测试，而且和「逻辑层禁用 `Date.now`」的 lint 规则相互配合。

## 4.5 GameEventMap：事件就是「可观测性协议」

```ts
export interface GameEventMap {
  'session:start': { at: number };
  'scene:enter': { scene: string };
  'beat:enter': { beatId: string };
  /** 这一幕的旁白真的听完了 —— 故事页的小手到这一刻才出现 */
  'story:ready': { beatId: string };
  'choice:made': { beatId: string; choiceId: string; correct: boolean; latencyMs: number };
  'level:complete': {
    levelId: string;
    stars: 0 | 1 | 2 | 3;
    mistakes: number;
    correct: number;
    total: number;
    durationMs: number;
  };
  'card:unlocked': { entryId: string; cardId: string };
  /** replay = 孩子点了「再来一次」：外壳会原地重开这一局，而不是回游戏馆 */
  'session:exit': { reason: 'complete' | 'quit' | 'background' | 'replay'; progress: number };
}
```

两处与旧版本不同的地方：

- 新增 `story:ready`：翻页动画不能用来判断「听完了没有」，因为动画与语音是两条独立的时间线。有了这个事件，无头验证与端到端测试才能**确定性地**翻页；
- 删除了 `hint:used`：它在契约里声明了很久，但全仓没有任何地方 emit 它 —— 声明了却没人发的死事件，比没有更糟（契约过期本身就是文档债务）。

这些事件是四个消费者共用的协议：

| 消费者 | 用途 |
|---|---|
| 外壳（`PlayView`） | 收到 `level:complete` 时写入星星与复习评级，并给玩耍时长 `+1 局` |
| 调试桥 | 每次 `emit` 追加到 `window.__chags.events`（生产环境也开着，因为不含个人信息） |
| 端到端测试 | 用 `events(page)` 断言流程走到了哪一步 —— 不靠像素、不靠时序猜测 |
| 遥测 | `Telemetry.track` 只做本地缓冲，绝不上报 |

契约还规定了事件的**粒度约定**：`beat:enter` 的 `beatId` 被各模板复用来报告关键节点 —— story 报告每一幕；substitution 报告 `aboard` / `mark` / `substitute` / `weighed`；tap 报告 `milestone:<id>` 与 `complete`；place / sort 报告每个槽位 / 物品的 id；reward 报告 `card:unlocked` 与 `level:complete`。端到端测试因此可以写「到河边时**尚未**通关」「三条里程碑**按序各出现一次**」这类断言。

## 4.6 GameModule：生命周期四件套

```ts
export interface GameModule {
  manifest: GameManifest;
  mount(ctx: GameContext): Promise<void>;
  unmount(): Promise<void>;
  pause(): void;
  resume(): void;
}
```

生命周期的正确性依赖宿主（Vue）与游戏（Phaser）两边配合：

| 时机 | 宿主（PlayView） | 游戏（defineGame 产物） |
|---|---|---|
| 进入路由 | 动态 `import` 游戏包 | — |
| 挂载前 | `await progress.init()` 读档 | — |
| 挂载 | `mount(await createGameContext(...))` | `new Phaser.Game({ scenes: [story, ...stages, reward] })` |
| 切后台 | `platform.lifecycle.onPause` → `pause()` + `stopSpeech()` | `game.loop.sleep()` |
| 回前台 | `onResume` → `resume()` | `game.loop.wake()` |
| 点「再来一次」 | `restart()`：先 `unmount()`，再 `start()`（**带幂等锁**） | 旧的 `destroy(true)`、新建一个实例 |
| 离开路由 | `await unmount()` + 停朗读 | `game.destroy(true)` 并置空 |

`pause()` / `resume()` 实现得很朴素 —— `loop.sleep()` / `loop.wake()`，但它们是**必须存在的钩子**：安卓壳里切后台、原生返回键、将来微信小游戏的后台切换都要用到。宿主的 `disposed` 标记与 `game.destroy(true)` 同样关键，否则 HMR 或路由切换会叠出多个 canvas 与 RAF 循环（第 16 章有复现记录）。

「再来一次」这一格值得单独说：`PlayView.restart()` 在 2026-10-20 加了幂等锁 `restarting`。原因是「卸载 → 重新挂载」之间有一小段空窗，孩子连点两下就会在同一个容器里挂出两个 Phaser 实例（两块 canvas 叠着、输入只落在最上面那块），表现是「点了没反应」。同一批修复里还顺手在退出时停朗读 —— 否则回大厅后旁白还在念。

## 4.7 defineGame：三段式装配

绝大多数游戏包的 `index.ts` 只有二三十行，因为「分幕故事 + 玩法 + 典故卡」这三段外加上面整张生命周期表的处理，被收进了 `defineGame()`（`packages/templates/src/defineGame.ts`）：

```ts
export interface GameplayStage {
  /** 分幕故事之后进入哪一幕 */
  entry: string;
  /** 中间的玩法场景（一到多个） */
  scenes: Phaser.Types.Scenes.SceneType[];
}

export interface GameDefinition {
  manifest: GameManifest;
  /**
   * 分幕插图：每个典故自己画。
   * **契约只画两幕**：index 只有 0 / 1 —— 内容 schema 已把 story 锁成 length(2)。
   */
  drawBeat?: (
    g: Phaser.GameObjects.Graphics,
    index: 0 | 1,
    rect: { x: number; y: number; w: number; h: number },
  ) => void;
  gameplay: (ctx: GameContext, session: SessionState) => GameplayStage;
}

export function defineGame(definition: GameDefinition): GameModule {
  let game: Phaser.Game | null = null;

  return {
    manifest: definition.manifest,

    async mount(ctx: GameContext): Promise<void> {
      const session = createSessionState(ctx.services.now());
      const stage = definition.gameplay(ctx, session);

      game = createPhaserGame(ctx, {
        scenes: [
          createStoryScene(ctx, {
            beats: ctx.content.story,
            nextSceneKey: stage.entry,
            drawBeat: definition.drawBeat,
          }),
          ...stage.scenes,
          createRewardScene(ctx, {
            entryId: ctx.content.id,
            title: ctx.content.title,
            pinyin: ctx.content.pinyin,
            moral: ctx.content.moral,
            keywords: ctx.content.keywords,
            source: ctx.content.source,
            session,
            transfer: ctx.content.transfer,
            thinkingTag: ctx.content.thinkingTag,
          }),
        ],
      });
    },

    async unmount(): Promise<void> {
      game?.destroy(true);
      game = null;
    },

    pause(): void { game?.loop.sleep(); },
    resume(): void { game?.loop.wake(); },
  };
}
```

三个细节：

- **`drawBeat` 的 `index` 是 `0 | 1`**。53 个游戏的 `art.ts` 全是「第 0 幕 / 其它幕」分叉，schema 也已把 `story` 锁成 `length(2)` —— 契约与数据双保险。真要写第三幕，先扩契约，而不是在 `art.ts` 里加 `index === 2` 分支（那样会直接 typecheck 报错）。
- **`createRewardScene` 多接了 `transfer` / `thinkingTag`**：三十六计的每一计都要在卡面上给出「今天可以怎么用」与思维标签，这两个字段从摘要一路透传到卡面。
- **`nextSceneKey` 与 `reveal` 的默认值已收敛**：多数游戏包不再传这两个参数，由 `layout.ts` 的 `resolveEnding()` 统一默认成 `SCENE_KEYS.reward` 与 `ctx.content.keyMoment.reveal`。这一轮净删了 97 行「抄默认值」的代码，也把「抄错默认值」这类 bug 从结构上消掉了。

于是「一个典故」在游戏包里只剩两件事：**怎么画分幕、玩法场景怎么拼**。盘古的例子（`games/pangu/src/index.ts`）：

```ts
import { defineGame, SCENE_KEYS } from '@chags/templates/core';
import { createPlaceScene } from '@chags/templates/place';
import { createTapScene } from '@chags/templates/tap';
import { drawBeat, drawOrb, drawPiece } from './art';
import { placeLevel, tapLevel } from './logic';
import { manifest } from './manifest';
import { createChaosScene } from './scenes/chaos';
import { drawHoldFinale, drawHoldStage } from './scenes/hold';

export default defineGame({
  manifest,
  drawBeat,

  gameplay: (ctx, session) => ({
    entry: SCENE_KEYS.chaos,
    scenes: [
      // 开：连点蛋壳，混沌炸开（这个场景是盘古专属，不进模板库）
      createChaosScene(ctx, { nextSceneKey: SCENE_KEYS.tap, tapsToBreak: 4 }),
      // 撑：把天一点点顶上去，撑够一万八千年
      createTapScene(ctx, { level: tapLevel(ctx.content), session, nextSceneKey: SCENE_KEYS.place,
        titleKey: 'scene.hold', drawStage: drawHoldStage, drawFinale: drawHoldFinale }),
      // 化：把自己一件件放回世界
      createPlaceScene(ctx, { level: placeLevel(ctx.content), session, drawPiece, drawOrb }),
    ],
  }),
});
```

注意 import 全部走**子路径**（`@chags/templates/core` / `place` / `tap`），不是主 barrel —— 这是运行时入口纪律，写错了体积会立刻变大（第 2 章）。

## 4.8 asLevel：生产包里不跑 zod

关卡脚本的类型从哪来？内容 JSON 是 `unknown`，模板要的是强类型。历史做法是运行时 `Schema.parse(...)`，代价是把 zod 与全部模板 schema 拖进每一个游戏 chunk（实测 116 KB 原始 / 32.8 KB gzip，而它只在开发时有用）。

现在的做法是**把校验挪到构建期**：

```ts
// packages/game-kit/src/math.ts
/** 把关卡脚本断言成模板的关卡类型 */
export function asLevel<T>(script: unknown): T {
  return script as T;
}

// games/pangu/src/logic.ts
import { stageScript } from '@chags/content';
import type { ContentEntry } from '@chags/content';
import type { PlaceLevel, TapLevel } from '@chags/templates/schemas';
import { asLevel } from '@chags/game-kit';

/** 纯逻辑：不碰 Phaser，可以直接单测 */
export function tapLevel(content: ContentEntry): TapLevel {
  return asLevel<TapLevel>(stageScript(content, 'tap'));
}
```

正确性由三处保证：`pnpm content:check`（53 条 × 中英 × 模板 schema，CI 与发版都跑）、单测负例（直接对 schema 断言）、开发服务器里 `defineGame.mount()` 的 DEV 分支会动态 import schema 再校验一次。`stageScript()` 本身也在这一轮被搬到摘要层 —— 它以前住在 `entries/detail.ts`，53 个游戏包的 `logic.ts` 为了调它去 import `@chags/content/full`，结果每个游戏 chunk 都静态拖着全部详情（83 KB gzip）。

## 4.9 存档类型：星星与评级共用 0..3

```ts
/** 0..3 的三档评价：**星星与复习评级共用** */
export type Stars = 0 | 1 | 2 | 3;

export interface ReviewState {
  level: number;
  dueAt: number | null;
  lastGrade: Stars | null;
  reviews: number;
}

export interface EntryProgress {
  entryId: string;
  stars: Stars;
  completions: number;
  lastPlayedAt: number | null;
  review: ReviewState;
}

export const SAVE_SCHEMA_VERSION = 1;

export interface SaveData {
  schemaVersion: number;
  /** 每条内容的进度，键是内容 id。字段名刻意保留 `allusions`：改名会让所有老存档读不出来 */
  allusions: Record<string, EntryProgress>;
  updatedAt: number;
}
```

两个命名上的历史包袱被**刻意保留**：

- `SaveData.allusions` 没有跟着内容层「allusions → entries」的改名一起改。存档字段改名会让所有老玩家的星星凭空消失 —— 内容侧重命名只动类型与目录，不动存档结构。
- `Stars` 同时承担「这一局玩得怎么样」（只增不减，给孩子看）与「记得牢不牢」（决定下次复习间隔）两个语义。2026-10-16 之前只有前一个语义在用；现在 `level:complete` 里的 `correct / total` 被折算成评级，唯一例外是纯动手、不记对错的模板（`total` 为 0）退回用星星 —— 这是**有意的兜底**，不是权宜之计（第 10 章）。

## 4.10 一次完整运行的时序

把上面所有零件拼起来，一位玩家从大厅点进「盘古开天辟地」到回到大厅的时序是：

```
HallView      点整张卡（或卡上的「开始玩」）→ navigate('/play/pangu')
router        hash 变化 → useRoute 更新
PlayView      await progress.init()          ← 深链也要先读档
              registry['pangu']() 动态 import（独立 chunk）
              createGameContext(manifest, host, locale, hooks, completedBefore)
                ├─ content = loadEntry('pangu', locale)   ← 摘要 + 详情 + 译文
                ├─ services = platform（IndexedDB/WebAudio/TTS）
                └─ debug = readDebugOptions()             ← 仅 dev / webdriver
              mod.mount(ctx)
defineGame    createStoryScene + [chaos, tap, place] + createRewardScene
              new Phaser.Game({ scene: [...] })

story scene   session:start → beat:enter:b1 → story:ready:b1 → 翻页 → b2
chaos scene   连点 4 次 → beat:enter:burst → tap
tap scene     连点 40 次 → 里程碑 → beat:enter:complete → place
place scene   6 个光球归位 → beat:enter:<slotId> ×6 → reward
reward scene  card:unlocked + level:complete → 显示典故卡（再来一次 / 收下）
              「收下」→ session:exit(complete) → ctx.requestExit()
PlayView      hooks.onExit → navigate('/') → onBeforeUnmount → stopSpeech + unmount()
defineGame    game.destroy(true)
外壳           level:complete 时已写入 ProgressManager → IndexedDB（刷新后仍在）
```

这条链路上的每一个事件名、每一次跳转，在端到端测试里都有断言（第 13 章），这就是「可观测」的含义：**流程的每一步都是协议的一部分，而不是实现细节**。

## 4.11 契约如何强制三条铁律

回到第一章的三条架构铁律，看看契约在工程上如何兜底：

| 铁律 | 契约/工程手段 |
|---|---|
| 逻辑与渲染分离 | 模板提供 `*.logic.ts` 纯函数；lint 在 `*.logic.ts` 禁止 `Math.random` 与 `Date.now`；`asLevel` 让判定文件不依赖 zod |
| 游戏不碰环境 | `GameContext.services` 是唯一出口；游戏包里没有 `localStorage` / `fetch` 的直接引用；`now()` 替代 `Date.now` |
| 无头直达 | `DebugOptions` 三个开关 + 各模板的 `runAutoplay` 分支 + `window.__chags` 观测桥，且只在 dev / webdriver 生效 |

## 4.12 小结

- `game-kit` 是两侧共同依赖的契约：`GameManifest` 自述、`GameContext` 注入、`GameModule` 生命周期、`GameEventMap` 观测协议；
- manifest 只留 6 个真的有人读的字段，「描述性信息以内容 JSON 为唯一事实来源」；
- `story:ready` 让「听完才能继续」变成可断言的事件；`requestExit('replay')` 让「再来一次」不用回大厅；
- `defineGame()` 把「故事 + 玩法 + 典故卡 + 生命周期」标准化，游戏包只回答「怎么画、怎么拼」；
- `asLevel` 把 zod 从生产包里请出去，校验落在构建期与单测里；
- 宿主（Vue）与游戏（Phaser）之间只通过契约交互，`shallowRef`、`destroy(true)`、`disposed`、`restarting` 是宿主侧的四条硬性纪律。
