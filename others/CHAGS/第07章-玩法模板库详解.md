# 第07章 - 玩法模板库详解

## 7.1 从十部到五十三部：模板库现在要回答的问题

模板库的公式没有变：

> **一个游戏 = 若干模板（骨架）+ 一份内容 JSON（血肉）+ 专属美术与叙事（气质）+ 约 20% 定制代码。**

变的是规模。本章写第一版时是 17 个典故、约 10 个模板；现在合集里有 **53 部游戏**（典故 17 + 三十六计 36），模板 id 有 **26 个**，内容里声明的关卡段一共 **55 段**。规模变了，问题的性质也变了：典故那 17 部靠"复用"省钱；三十六计 36 部在省钱的同时还得**不撞车** —— 三十六计每一计都是一个独立机制，36 个点子不能有 20 个长得像。

这一轮做对的三件事，是本章的主线：

1. **模板按交互原语建模，不按题材建模。** `siege` 不是"围魏救赵模板"，是"正面推不动就去动他非救不可的地方"；因此它能装围魏救赵、釜底抽薪、关门捉贼、上屋抽梯四计。26 个模板 id 里，14 个是三十六计期长出来的，却撑起了 **33 种模式**。
2. **扩展用"加模式"，不动老判定。** 六辑下来同一条规矩重复了五次：新模式的判定单独写、`templateSchemas` 用 `z.union([...])` 并集登记、场景工厂用重载分派 —— 老模式那条路径一行不改。
3. **模板按需加载。** 一局只用得到一到两个场景，模板层因此拆成 `core` + 每模板一个子路径，打开一局不再把 24 个场景一起下下来。

先看目录现状（`packages/templates/src/`）：

```text
packages/templates/src/
├─ core.ts              # defineGame + layout + session：每局都要的那一点点
├─ defineGame.ts        # 三段式装配（第 04 章）：story → 玩法 → reward
├─ layout.ts            # 750×1334 设计坐标 + SCENE_KEYS + resolveEnding
├─ session.ts           # 一局状态（total / correct / mistakes）+ 星星规则
├─ gains.ts             # 两个"判定与 schema 共用"的小函数
├─ schemas.ts           # 26 个模板 id 的关卡 schema + templateSchemas 注册表
├─ reward.ts / index.ts
├─ cli/check-content.ts # pnpm content:check 的入口
├─ story.ts             # 分幕绘本（53 部共用开场，不走模板 id）
└─ 24 个场景工厂：
   substitution  tap  place  aim  sort  trace  wait  mark  split  burrow
   ruse  siege  borrow  stillness  window  show  twoline  read  matchup
   probe  lure  chase  swap  chain
   每个模板一份 *.logic.ts（纯函数）+ 一份 *.logic.test.ts
```

> **本章口径（其它章节引用请以此为准）**：模板 id **26 个**（`TEMPLATE_IDS`）；其中 **24 个**有独立的场景工厂与场景 chunk，`beacon`（烽火戏诸侯）与 `butcher`（庖丁解牛）只有 schema 登记、场景写在游戏包里；另有 `story`（共用开场，不走模板 id）与盘古专属的 `chaos`（连模板 id 都没有）。游戏 **53 部**，内容里共 **55 段** `game.stages`。

## 7.2 三个导入层次：core / 场景子路径 / 主 barrel

这是本轮对模板层最大的一次结构性改动，动机写在 `packages/templates/src/core.ts` 的文件头注释里：

```ts
/**
 * 模板包的核心入口：**每个游戏都要的那一点点**。
 *
 * 以前 53 个游戏都从 '@chags/templates' 这个大 barrel 里取 defineGame / SCENE_KEYS / 场景工厂，
 * barrel 又把 24 个模板场景全部再导出 —— 打包器因此把**全部场景**放进共享 chunk：
 * 打开任意一局都要下约 90 KB gzip 的模板代码，而它其实只用到其中 1–2 个场景。
 *
 * 现在分两档：
 * - 核心（这里）：defineGame + 布局常量 + 一局状态 —— 每局都需要的公共部分；
 * - 场景：'@chags/templates/<id>' 子路径，一个游戏只 import 自己用到的。
 * 主 barrel 仍然保留（Node 侧测试与类型用），但游戏包的**运行时** import 已改走子路径。
 */
```

三种导入方式各有明确用途，混用就会把体积吃回去：

| 导入方式 | 拿到什么 | 谁在用 | 代价 |
|---|---|---|---|
| `@chags/templates/core` | `defineGame` / `SCENE_KEYS` / `DESIGN` / `resolveEnding` / `SessionState` | 53 个游戏包的 `index.ts` 与 `art.ts`（`manifest.ts` 多走 `@chags/templates/layout`，同一层） | 几 KB，每局都要 |
| `@chags/templates/<id>` | 一个场景工厂 + 该模板的画法常量（如 `SIEGE` / `SWAP`） | 每个游戏只 import 自己那一到两个 | 单独成 chunk |
| `@chags/templates`（主 barrel） | 全部场景 + 全部类型 | 单测与类型引用；`import type` 被完全抹掉 | 绝不用于运行时 |

`package.json` 的 `exports` 把这件事写死了 —— 少写一个子路径，那个模板就只能在类型层面被用到（节选，`...` 表示省略若干行）：

```json
"exports": {
  ".": "./src/index.ts",
  "./layout": "./src/layout.ts",
  "./core": "./src/core.ts",
  "./substitution": "./src/substitution.ts",
  "./tap": "./src/tap.ts",
  ...
  "./schemas": "./src/schemas.ts",
  "./session": "./src/session.ts",
  "./gains": "./src/gains.ts"
}
```

一个副作用值得记下来：某个游戏的 `art.ts` 里只要出现一句 `import { DESIGN } from '@chags/templates'`，整条 barrel 就会被拉进那个 chunk（`import type` 例外，它会被类型擦除）。这类地方现状都改走了 `core`；`games/**/src/logic.test.ts` 里也留着注释「这里刻意不 import 主 barrel：那个入口会拉进 Phaser」。

### 7.3.3 数出来的账

两张表的"已用于"就是最终口径：模板清单与 `packages/templates/src` 一一对应，游戏与 `games/` 下的目录一一对应（计策的包名是计名拼音：`mantian-guohai` ↔ 瞒天过海、`zou-weishang` ↔ 走为上）。把上面的账数一遍：

- 53 部游戏里 **51 部**用了模板场景；**2 部**是纯专属场景（烽火、庖丁）。盘古另有 `chaos` 一段专属，但它后面还接了两段模板。
- 场景工厂共被调用 **56 次**（53 部 + 盘古多两段 + 大禹多一段），减去 `chaos` 那一次，正好对应内容里的 **55 段** `game.stages`（含 `beacon` / `butcher` 两段）。
- `tap` 是复用面最广的模板（5 部），`siege` 是模式最多的模板（4 个），`chain` 是唯一一个"三种模式各占一部游戏、且都不是同一题材"的模板。

## 7.4 模板的通用形状与共用契约

所有模板都是同一套模式：**工厂函数返回场景类**（下面是曹冲称象的签名，函数体里 `return class SubstitutionScene extends BaseScene { … }`），配置里除了数据，全是"由游戏包提供的绘制回调"。

```ts
export function createSubstitutionScene(
  ctx: GameContext,
  cfg: SubstitutionConfig,
): Phaser.Types.Scenes.SceneType {
```

通用配置字段：

| 字段 | 作用 |
|---|---|
| `level` | 已过 zod 解析的关卡脚本（来自内容 JSON） |
| `session` | 一局共享状态；`recordAttempt` 是"这一下算不算做对"的唯一入口 |
| `nextSceneKey` | 可选。**不传就是回典故卡**（`SCENE_KEYS.reward`） |
| `titleKey` / `title` | 顶栏标题：界面文案键，或计策自己的计名（三十六计的 `scene.*` 文案没登记，直接传内容标题） |
| `reveal` | 可选。不传就取 `ctx.content.keyMoment.reveal`（关键抉择点的揭晓语） |
| `drawXxx` 回调 | 画面全外置：`drawStage` / `drawPiece` / `drawOrb` / `drawWorld` / `drawFinale` … |
| `onXxx` 回调 | 游戏接管某一瞬间（里程碑、诱饵点击、归位语音），处理完调 `api.done()` / `api.resume()` |
| `finaleHoldMs` | 收尾演出停留多久（无头验证时会一起压缩） |

`nextSceneKey` 与 `reveal` 的默认值收在 `layout.ts` 里，以前 53 个 `index.ts` 每份手抄这两行：

```ts
export function resolveEnding<T extends { reveal?: string; nextSceneKey?: string }>(
  ctx: GameContext,
  cfg: T,
): { reveal: string; nextSceneKey: string } {
  return {
    reveal: cfg.reveal ?? ctx.content.keyMoment.reveal,
    nextSceneKey: cfg.nextSceneKey ?? SCENE_KEYS.reward,
  };
}
```

三条贯穿所有模板的行为规则（第一条在三十六计期变得更重要）：

1. **逐帧重画**：需要动起来的模板每帧调用 `drawStage(g, metrics)`，游戏包在这一个回调里画整个世界，而不是维护一堆 Sprite 引用；
2. **autoplay 走同一代码路径**：无头验证不模拟点击，而是调用与真实操作相同的内部方法（`runAutoplay()` 内联在场景里，或喂同一个 `holding` / `stirring` 状态）。第五辑之后这条被写成硬要求：**不许另写一条"自动通关"分支**；
3. **零失败**：放错、划歪、点错都不结束、不扣星、不锁操作，弹回原位继续试。错只影响两件事：这一局拿几颗星（`starsFor`）与下次复习间隔。

判定为什么一定要外置，`gains.ts` 的文件头给了个很实在的理由：

```ts
/**
 * 玩法判定要用、schema 的 refine 也要用的两个小函数。
 *
 * 它们原来住在 schemas.ts 里：于是 siege.logic / matchup.logic（生产代码）为了一个纯函数
 * 去 import 整个 schema 模块，连带把 zod 与全部模板 schema 拖进游戏 chunk（约 33 KB gzip）。
 * 拆出来之后：schema 的 refine 与玩法判定 import 同一份实现，生产包里却只有这几行。
 */
```

模板层现在有 **25 个 `*.logic.test.ts` / 636 条 `it()`**：判定全部是纯函数，node 里直接跑，不加载 Phaser。这也是"单测能守住玩法"的前提 —— 没有这一层，36 计的判定只能靠 e2e 撞。

## 7.5 story：分幕绘本，必须听完

53 部游戏共用同一个开场：一屏一个画面、一句话，**点哪都行**，没有"下一幕"按钮。由 `defineGame` 装配，游戏包只画插图：

```ts
export interface StoryConfig {
  beats: StoryBeat[];
  nextSceneKey: string;
  /**
   * 分幕插图：**契约只画两幕**，index 只有 0 / 1。
   *
   * 内容 schema 已把 story 锁成 length(2)（packages/content/src/schema.ts），
   * 第 3 幕会先在 pnpm content:check 构建期报错；真要三幕，先扩这份契约
   * （以及 game-kit 的 Art 渲染约定），而不是让第 3 幕静默复用第 2 幅图。
   */
  drawBeat?: (
    g: Phaser.GameObjects.Graphics,
    index: 0 | 1,
    rect: { x: number; y: number; w: number; h: number },
  ) => void;
}
```

「听完才能翻页」是这个模板最硬的一条规则，算法抽成了纯函数（`packages/templates/src/story.logic.ts`）：

```ts
const CHARS_PER_SECOND: Record<Locale, number> = { 'zh-CN': 5, en: 14 };
/** 再短的一句也要停一下：孩子得有时间把画面和这句话对上 */
export const MIN_NARRATION_MS = 2200;
/** 再长的旁白也有上限：卡住比念不完更糟 */
export const MAX_NARRATION_MS = 24000;

/** 这段话"念一遍"大概要多久；没有语音可用时，它就是这一幕的最低停留时间 */
export function narrationMs(text: string, locale: Locale): number {
  const chars = text.trim().length;
  if (chars === 0) return 0;
  const speed = CHARS_PER_SECOND[locale] ?? CHARS_PER_SECOND['zh-CN'];
  const raw = (chars / speed) * 1000;
  return Math.round(Math.min(MAX_NARRATION_MS, Math.max(MIN_NARRATION_MS, raw)));
}
```

三种设备都要兜住：有语音就等它真的念完；没有语音（静音、没装语音包、无头浏览器）按"读一遍"的时间等；语音引擎迟迟不回报时由看门狗（`gateWatchdogMs` = 朗读时长 × 1.8 + 2.5 秒）放行。**"念完了"还要可信**（`speechTrusted`）：无头浏览器与刚被 cancel 的朗读会立刻回报 `ended`，那不是听完了，是根本没出声。

实现上有三个坑，都是被 e2e 撞出来的：

- **350ms 连点锁的起点曾经写错**：锁从"点击区建好"起算，而"这一幕念完"与点击区建好是同一瞬间 —— 孩子在听到念完那一刻抬手就点，正好落在锁里，护盾已销毁，于是既不翻页也不提示。现在锁从**上一次真的翻页**起算（`isTapArmed(now, lastAdvanceAt)`，见第 08 章）。
- **二周目的「跳过」按钮必须在 `listenFirst` 之后创建**：`listenFirst` 会给整屏加一层点击区（点早了只回一句"先听完"），先建的按钮会被那层盖住、点不到。
- **`drawBeat` 的 index 只有 0 / 1**：契约收窄后类型就是 `0 | 1`，第 3 幕在 `content:check` 就报错，别在 `art.ts` 里加 `index === 2` 分支。

## 7.6 substitution：等量代换（1 部）

曹冲称象是唯一使用 `substitution` 的游戏，也是"一个模板讲一个思维方法"最完整的例子。内部状态机四步：

```text
称重（drag）：想直接称 → 拖大象上秤 → 秤被压垮
mark：大象上船 → 水痕出现 → 点船身刻一刀
substitute：大象下船 → 从岸边石堆拖石头上船，直到水痕回到水面
weigh：石头一块块搬上秤，读数累加
done：等式成立（大象 = 3300）
```

判定是三个纯函数（`packages/templates/src/substitution.logic.ts`）：

```ts
/** 重物上船时刻下的水痕位置（0=刚碰到水，1=完全没入） */
export function markRatio(level: SubstitutionLevel): number {
  return clamp01(level.heavy.weight / level.capacity);
}

/** 当前载重对应的吃水比例 */
export function depthRatio(total: number, level: SubstitutionLevel): number {
  return clamp01(total / level.capacity);
}

export function judge(total: number, level: SubstitutionLevel): WeighVerdict {
  const diff = total - level.heavy.weight;
  if (Math.abs(diff) <= level.tolerance) return 'match';
  return diff < 0 ? 'light' : 'heavy';
}
```

关卡里没有"答案数字"，只有物理量：`capacity`（船的载重上限）、`heavy.weight`（大象）与 `stones[]`（每块石头有 `value` 与 `radius`，半径决定拖拽手感）。曹冲这份数据是 `heavy.weight = 3300`、`capacity = 3600`、`tolerance = 80` —— 六块大石凑不出 3300，必须把大石和中石搭起来。

无头验证与卡住提示共用同一个"下一步该搬哪块"（`nextStoneFor`）：

```ts
/**
 * 该往船上再搬哪一块。
 * 无头验证（?autoplay=1）用它把一局走完；卡住时的兜底提示也可以用它。
 *
 * 规则：先挑"加上去不会冲过容差"的最大一块 —— 大石头步数少；
 * 一块都放不下（再放就一定偏重）时挑最小的一块，尽量贴近目标。
 * 这一条正是"光搬大石头凑不出来"的关卡所必需的：只搬最大的那种，
 * 会在偏轻与偏重之间来回跳，永远对不上水痕。
 */
export function nextStoneFor(total: number, level: SubstitutionLevel): StoneDef | undefined {
  if (level.stones.length === 0) return undefined;
  const ceiling = level.heavy.weight + level.tolerance;
  const fits = level.stones.filter((stone) => total + stone.value <= ceiling);
  if (fits.length > 0) {
    return fits.reduce((best, stone) => (stone.value > best.value ? stone : best));
  }
  return level.stones.reduce((best, stone) => (stone.value < best.value ? stone : best));
}
```

schema 侧还有一条「内容写错不让孩子发现」的规则：`SubstitutionLevelSchema` 用有界完全背包在构建期验证「这些石头能不能凑出容差内的重量」，凑不出直接拒绝这份内容。三条 refine 的原文：

```text
重物重量不能超过载重上限
水痕之上要留出容差空间，否则一定判"太沉"
用这些石头凑不出重物的重量（容差内无解），关卡不可通关
```

## 7.7 tap：一个循环，五个世界（5 部）

`tap` 是复用面最大的模板：盘古撑天、精卫填海、夸父追日、愚公移山、大禹筑堤共用同一套循环，五段画面毫不相干。秘密全在配置接口与"画面完全外置"：

```ts
export interface TapStageMetrics {
  width: number;
  height: number;
  /** 原始进度 0..1 */
  progress: number;
  /** 缓动后的进度 —— 画面按这个画，才有"越到后面越吃力"的感觉 */
  eased: number;
  /** 当前累计值 */
  value: number;
  complete: boolean;
}
```

进度有两条：`progress` 给判定和计数气泡，`eased` 给画面 —— 阻力越大，后半程看起来越过瘾（`packages/templates/src/tap.logic.ts`）：

```ts
/** 画面用的缓动进度：resistance 越大，后半程显得越吃力 */
export function easedProgress(value: number, level: TapLevel): number {
  return Math.pow(progressFor(value, level), 1 + level.resistance);
}
```

两个模式：

- `mode: 'tap'`：每次点击 `+stepValue`。schema 强制 `targetValue % stepValue === 0`，否则永远点不满 —— `tap 模式下 targetValue 必须是 stepValue 的整数倍`。
- `mode: 'hold'`：按住推进（夸父）。这里有一条来自真机的教训：**按墙钟算，不累加帧间隔** —— Phaser 在帧率低时会钳制 `delta`，慢机器上"按住 6 秒"累积不到 6 秒的进度，而旧安卓手机正是目标用户。

**里程碑**是 tap 最有表现力的一环：愚公的三条里程碑（智叟出现、换代 ×2）在推进到指定进度时暂停循环，把控制权交给游戏包，处理完（等玩家点一下）再 `api.resume()`。每条里程碑触发时发 `beat:enter:milestone:<id>` 事件 —— 这不是可选项：没有事件，把暂停逻辑删掉测试也会全绿，所以事件是让里程碑可观测、可测试的协议。

其他细节：

- 计数气泡固定在底部（`TAP.counterY = 1256`），画面变化时它不动；长按模式显示前必须 `Math.round()`，否则会出现 `814.967999999994`；
- 音调随进度上升（`audio.tone(300 + eased * 520, 90)`）—— 进度是"听得见"的；
- `comboLevel` 只影响表现（音调、星光），不影响数值，保证通关次数确定可测；
- 小手在玩家"会了"之后收起，**卡住 6 秒把小手找回来**并显示提示；这条对两种模式都生效（曾经只写在连点分支里，导致夸父永远不提示）。

## 7.9 aim：按线段判定，外加距离阶梯（2 部）

箭很快，必须按"这一帧扫过的线段"判定，否则会直接穿过目标（`packages/templates/src/aim.logic.ts`）：

```ts
/** 点到线段的最短距离：箭很快，必须按"这一帧扫过的线段"判定，否则会穿过去 */
export function distanceToSegment(p: AimPoint, a: AimPoint, b: AimPoint): number {
  const dx = b.x - a.x;
  const dy = b.y - a.y;
  const lengthSq = dx * dx + dy * dy;
  if (lengthSq === 0) return Math.hypot(p.x - a.x, p.y - a.y);
  let t = ((p.x - a.x) * dx + (p.y - a.y) * dy) / lengthSq;
  t = Math.min(1, Math.max(0, t));
  return Math.hypot(p.x - (a.x + t * dx), p.y - (a.y + t * dy));
}
```

命中判定再按"沿弹道最先碰到"取一个 —— 中间的 `projectionT` 只算投影位置，谁在前谁先中：

```ts
/**
 * 这一帧里被命中的目标。
 * 命中半径内可能有多个，取**沿弹道最先碰到的那一个** —— 这才是箭的语义；
 * 只按垂直距离取最近会在几发并排时选错。
 */
export function firstHit(
  from: AimPoint,
  to: AimPoint,
  targets: readonly AimTargetPoint[],
  radius: number,
  /** 可选：每个目标自己的命中半径（百步穿杨：越远的那片柳叶越小） */
  radiusOf?: (target: AimTargetPoint) => number,
): string | null {
  let best: string | null = null;
  let bestT = Number.POSITIVE_INFINITY;
  for (const target of targets) {
    if (distanceToSegment(target, from, to) > (radiusOf ? radiusOf(target) : radius)) continue;
    const t = projectionT(target, from, to);
    if (t < bestT) {
      best = target.id;
      bestT = t;
    }
  }
  return best;
}
```

`AimApi` 允许游戏接管后续：`aliveIds()` / `revive(id)` / `lock(ms)` / `redraw()` / `complete()`。后羿的"射九留一"全在这套 API 上：射到只剩一个 → 大地回春，延时 2.4 秒收工，给好奇的孩子再射一箭的机会；把最后一个也射了 → 天黑、提示、`api.revive(id)` 把太阳放回来。零惩罚，自己撞一次就懂了。

百步穿杨用的是同一个模板的 **`ladder` 模式**：靶子按距离一档一档往后退，越远那片柳叶的命中半径越小（`radiusOf`）。schema 侧盯住两件事 —— `goalCount 必须小于目标总数 —— 否则就没有"留一个"的余地了`、`一个靶子只能出现在一档里`。

## 7.10 sort：先尝后分（1 部）

`sort` 的基础是"把东西分进对的那一堆"，但神农尝百草需要更强的机制：**先尝后分**。数据结构直接强制了教学核心（`packages/templates/src/sort.logic.ts`）：

```ts
/**
 * "先尝后分"：这件东西还没尝过吗？
 * 没有 probe 的关卡永远返回 false —— 分类玩法可以不带品尝步骤，直接用。
 */
export function needsTaste(
  level: SortLevel,
  item: SortItem,
  tastedIds: string[],
): boolean {
  return level.probe !== undefined && !tastedIds.includes(item.id);
}
```

「想分类，先自己试一口」这条规矩写在 schema 里，内容写错在构建期就报：

```ts
.refine((l) => l.probe === undefined || l.items.every((i) => i.tastedKind !== undefined), {
  message: '有"先尝后分"却没有给每件东西写 tastedKind —— 尝完什么都看不出来',
  path: ['items'],
});
```

流程图：

```text
拿起东西（未品尝）→ 嘴边发光 → 拖到嘴边 → onTaste 演出（游戏画表情/落叶）
  → 记录 tasted → 重新画成"尝过的样子"（靠图案不靠文字）
拿起东西（已品尝）→ 该去的那块木牍发光 → 拖入 → 缩小留在木牍上 → 计数
全部归位 → drawFinale（药书上的字一片片亮起来）→ reveal
```

`onTaste(item, api)` 让游戏接管品尝表现，完成后调 `api.done()` 继续。`sort.logic.ts` 还提供 `binAt` / `binFor` / `placedIn` / `nextUntasted` / `probeHit`，卡住提示与无头自动都建立在它们之上。

## 7.11 trace：只判顺序，不判手感（2 部）

`trace` 的判定是"有没有按顺序到过锚点"，不是"画得像不像"（`packages/templates/src/trace.logic.ts`）：

```ts
/**
 * 往前推进一格 —— **只前进，不后退**：
 * 划歪了、划回去了都不会把已经过的锚点退掉，孩子不会因为手抖丢进度。
 *
 * prev 用来挡"瞬移"（手指抬起后落在别处，不该算一条河道），
 * 但它只是防作弊，不是精度要求：同一笔里慢机器的稀疏采样也照样能过。
 */
export function advanceTrace(
  level: TraceLevel,
  cursor: TraceCursor,
  point: TracePoint,
  prev?: TracePoint,
): TraceCursor {
  const segment = currentSegment(level, cursor);
  if (!segment) return cursor;
  if (prev && Math.hypot(point.x - prev.x, point.y - prev.y) > level.maxGap) return cursor;

  const target = currentTarget(level, cursor);
  if (!target) return cursor;
  if (Math.hypot(point.x - target.x, point.y - target.y) > target.radius) return cursor;

  if (cursor.anchor < segment.anchors.length) {
    return { segment: cursor.segment, anchor: cursor.anchor + 1 };
  }
  return { segment: cursor.segment + 1, anchor: 0 };
}
```

配置把"这个世界长什么样"与"这一帧画什么"分开：`drawWorld` 只画一次（洪水、山、村庄），`drawStage` 每帧按 `TraceStageMetrics` 重画（水位、流水、露出来的土地、`metrics.path` 里已划出的轨迹），`onSegmentDone` 接管"划完一段"的演出，`stroke` 决定河道长什么样（默认泥土外沿 + 水色内芯）。

大禹治水用三段河道（`ditch` 田间 → `mountain` 山间 → `sea` 入海），每段 4 个锚点（半径 62）与一个终点（半径 72）；`maxGap` 是 200，手指两帧之间跳得再远也不会被当成一条河道。每划完一段触发「三过家门」的演出，并配了 **1.5s / 2.4s 双重兜底** —— 补间被打断也绝不让玩家卡在门口。第 36 计走为上整关复用它，只换文案与画面：三段 = 退避三舍。

## 7.12 chain：一条链上的三种顺序（3 部）

`chain` 装了三计，三份配置互不牵动，共用一个场景键，按 `level.mode` 分派：

三种顺序，三种"来不及"：

- `pass`（第 24 计假道伐虢）：先谈成借路，再按顺序取下关口，最后回师 —— **顺序不能跳**；
- `step`（第 30 计反客为主）：每一步先求允许，允许只持续 `grantMs`，过期作废要重新求。schema 把体验底线写死了：`允许只持续 600ms 以内 —— 那就变成比手速了`；
- `domino`（第 35 计连环计）：先点火种，再一环一环接；每一环有时限，断了回岸边重来。数据来自 `packages/content/src/entries/lianhuan-ji.game.json`：

关卡数据是三段：一处 `ignite`（岸边火种）、3–5 个 `links`（每环一个坐标与半径）、一个 `windowMs`（每环的时限），另加 `breakLine` 与 `hint` 两句文案。连环计那份是 4 环 × 2200ms。

## 7.13 siege：四个模式，一个场景键（4 部）

`siege` 是"模板长出模式"这条路线最典型的样本：围魏救赵（vital）先上线，后面三辑各加一个模式，四个模式共用同一套手感常量与同一条收尾流程。

```ts
/** 四个模式的配置合起来 —— createSiegeScene 按 level.mode 分派 */
export type SiegeConfig =
  | SiegeVitalConfig | SiegeSupportConfig | SiegeCloseConfig | SiegeLadderConfig;

/**
 * 打要害 / 抽支撑 / 断退路 —— 三个模式说的是同一句话：
 * 不跟他正面硬碰，去动他撑不住的地方。
 *
 * 按 `level.mode` 分派到各自的场景。三个模式共用同一套手感常量（SIEGE）
 * 与同一条收尾流程（结算 → 揭晓语 → 下一幕）；**vital（第 2 计围魏救赵）
 * 那条路径一个字没动** —— 它只是被 mode 判断包起来了。
 */
export function createSiegeScene(
  ctx: GameContext,
  cfg: SiegeConfig,
): Phaser.Types.Scenes.SceneType {
  if (isSupportConfig(cfg)) return createSiegeSupportScene(ctx, cfg);
  if (isCloseConfig(cfg)) return createSiegeCloseScene(ctx, cfg);
  if (isLadderConfig(cfg)) return createSiegeLadderScene(ctx, cfg);
  return createSiegeVitalScene(ctx, cfg);
}
```

判别式藏在 `cfg.level.mode` 里（两层），所以显式写了三个类型守卫（`isSupportConfig` / `isCloseConfig` / `isLadderConfig`，形如 `return cfg.level.mode === 'support'`），让每条分支里的 `cfg` 收窄成对应那一份，不用强转。

四个模式各一句话：

| 模式 | 计策 | 一句话 | 关键回调 |
|---|---|---|---|
| `vital` | 2 围魏救赵 | 正面怎么推都推不动，去点他非救不可的要害 | `onRelieve` / `onFrontTap` / `onFrame` |
| `support` | 19 釜底抽薪 | 不跟火硬碰，从底下把柴一根根抽走，抽到根上那根火势骤降 | `onPull` |
| `close` | 22 关门捉贼 | 抢在贼跑掉之前关上所有出口，没关完他就跑了（重来） | `onClose` |
| `ladder` | 28 上屋抽梯 | 一级级搭好梯子，等他走到位再抽梯；抽早了只是他掉回来 | `onBuild` / `onDrop` |

schema 侧盯的是"这一关是不是太磨人 / 不可能"：`点完所有要害之后，正面还要推 40 次以上 —— 这一关太磨人`、`把所有柴抽光火也灭不了 —— 这一关不可能过`、`把所有门关一遍的时间比贼跑掉的时间还长 —— 这一关不可能过`。四条 refine 的句式几乎一样，因为它们的判断方式也一样：**把玩家可能的最优路径算一遍，算不通就拒绝这份内容**。

## 7.14 window：窗口的开法与造法（3 部）

同为"时机"，三种"窗口"的来源完全不同，所以是三份配置、一个场景键。`WindowConfig` 里除了 `drawWorld` / `onTapJob` / `drawFinale`，还有两条只属于 `glimpse` 的字段：`tripLine`（一趟走完、要重走一遍时说的话）与 `tripHoldMs`（换趟时站住喘口气的时长）。

```ts
/**
 * 时机窗口：两种玩法共用一个场景键（SCENE_KEYS.window），按 level.mode 分派。
 * - fire（趁火打劫）/ glimpse（顺手牵羊）：窗口按时间开合 —— 既有路径，一行未改；
 * - stir（混水摸鱼）：窗口是**自己搅出来的** —— 点水面搅浑，浑水里才摸得到鱼。
 */
// 两个重载 + 一个并集的实现：老模式的调用处（传的是内联箭头函数）由第一个重载
// 做上下文类型推导，不用担心并集让回调参数变成 any —— 既有游戏包一行都不用改。
export function createWindowScene(
  ctx: GameContext,
  cfg: WindowConfig,
): Phaser.Types.Scenes.SceneType;
export function createWindowScene(
  ctx: GameContext,
  cfg: WindowStirConfig,
): Phaser.Types.Scenes.SceneType;
export function createWindowScene(
  ctx: GameContext,
  cfg: WindowConfig | WindowStirConfig,

  if (cfg.level.mode === 'stir') return createStirWindowScene(ctx, cfg as WindowStirConfig);
  return createTimedWindowScene(ctx, cfg as WindowConfig);
}
```

- `fire`（第 5 计趁火打劫）：火只烧一阵，窗口里干活，错过就等下一轮；
- `glimpse`（第 12 计顺手牵羊）：每隔一轮路过一个机会，一趟走完重走一遍（零惩罚），所以要 `travelMs`；
- `stir`（第 20 计混水摸鱼）：窗口不是等来的，是**搅出来的** —— 每一搅让水浑一档，浑到 `muddyAt` 以上才抓得动鱼，水一清鱼就摆尾滑走。

schema 用两条互斥的 refine 把数据口径统一了：`fire 模式没有"一趟走完"这回事，不要写 travelMs`、`fire / glimpse 模式没有"搅水"，不要写 stir`。这两条看着像洁癖，其实是防"复制上一份关卡脚本改两个字"。

## 7.15 borrow：借力与借名（2 部）

```ts
/**
 * 借力 / 借名号：两种玩法共用一个场景键（SCENE_KEYS.borrow），按 level.mode 分派。
 * - force（借刀杀人）：支点 + 力源凑够 needed，才抬得起来 —— 既有路径，一字未改；
 * - banner（借尸还魂）：把旧旗竖到旗杆上，旗能召回多少人，散掉的人就回来多少。
 */
export function createBorrowScene(
  ctx: GameContext,
  cfg: BorrowConfig | BorrowBannerConfig,
): Phaser.Types.Scenes.SceneType {
  if (cfg.level.mode === 'banner') return createBannerScene(ctx, cfg as BorrowBannerConfig);
  return createForceBorrowScene(ctx, cfg as BorrowConfig);
}
```

`force` 的关卡数据是"力不够"这件事本身（`packages/content/src/entries/jiedao-sharen.game.json`）：`load` 重 40、`needed` 是 30，而 `self` 只有 1 点力，三处 `source` 分别是 12 / 18 / 14 点，另有一处 `fulcrum`（力 0，但没有它整关不成立）。

难的不是力气，而是**把绳子连对**：自己那 1 点力只是让你体会「不够」，真正抬起来要靠支点与力源。schema 用四条 refine 守住这一关立不立得住：`没有支点：杠杆总得有个垫脚的地方`、`至少要有一个"自己出力"的选项 —— 不然孩子体会不到"自己不够"`、`光靠自己就够力了 —— "借力"这件事就不成立了`、`把所有力源都借来也不够 —— 这一关无解`。

`banner`（第 14 计借尸还魂）换了一个维度：旗上写着能召回多少人（`rally` 点），竖旗之后那么多人一步步走回旗杆下。这一关的落点是"名号能把人聚起来"，不是把人一个个抓回来 —— 所以点到一个还没回来的散人只是搭句话（`onCall`），零惩罚。

## 7.16 matchup：排法本身就是玩法（2 部）

```ts
/**
 * 配对编排：两种玩法共用一个场景键（SCENE_KEYS.matchup），按 level.mode 分派。
 * - pair（李代桃僵）：三匹马对三场，怎么排决定输赢 —— 既有路径，一行未改；
 * - order（远交近攻）：一圈势力，按"近的先解决、远的先结好"的顺序点过去。
 */
export function createMatchupScene(
  ctx: GameContext,
  cfg: MatchupConfig,
): Phaser.Types.Scenes.SceneType;
export function createMatchupScene(
  ctx: GameContext,
  cfg: MatchupOrderConfig,
): Phaser.Types.Scenes.SceneType;
export function createMatchupScene(
  ctx: GameContext,
  cfg: MatchupConfig | MatchupOrderConfig,
): Phaser.Types.Scenes.SceneType {
  if (cfg.level.mode === 'order') return createOrderMatchupScene(ctx, cfg as MatchupOrderConfig);
  return createPairMatchupScene(ctx, cfg as MatchupConfig);
}
```

`pair`（第 11 计李代桃僵）是**编排**玩法：三匹马、三场对手，`roster[场次] = 马的下标`，排法是纯数据；`power` 相等算输，赢两场即胜。这一关能不能赢不该等孩子打到一半才发现，所以构建期用 `bestMatchupWins` 穷举六种配对验算 —— `六种配对都赢不到 needWins 场 —— 这一关不可能赢`。这个函数与玩法判定共用同一份实现，它住在 `gains.ts`（见 7.18）。

`order`（第 23 计远交近攻）把"排法"换成"次序"：一圈势力围着地图中央，**近的先解决、远的先结好**。正确顺序写在关卡里（`sequence`），refine 要求它把每个势力刚好排一次，并且 `既要有"近的"也要有"远的" —— 否则这一计没有取舍`。点错不是惩罚，只是原样返回并记一次 `mistakes`，小手挪回该点的那一个。

## 7.17 其余十三个模板：一张表与三条共识

没在上一节展开的 13 个模板，一句话一个：

| 模板 | 交互原语 | 模式 → 计策/典故 | 一句话要点 |
|---|---|---|---|
| `wait` | 以不推进为玩法 | 太公钓鱼、9 隔岸观火 | 按墙钟算；诱惑有 `penaltyCap`，不存在等不到头；最后一件事是动作（收钩） |
| `mark` | 在会动的世界上做记号 | 刻舟求剑 | 会漂走的面必须一开始压在剑落水处；刻完 1.2s 才开船，给孩子看一眼 |
| `split` | 总量不变的两份分配 | 朝三暮四、34 苦肉计 | 高兴门槛写进数据；绳子两端必须在同一条绳上（y 相同） |
| `burrow` | 预留退路 + 威胁封堵 | 狡兔三窟 | 危险一次堵住的洞数必须小于洞口总数，否则怎么挖都躲不过 |
| `ruse` | 伪装与误导 | `hide` → 1；`divert` → 6 | hide 换外壳、divert 看时机；正确外壳只能有一个 |
| `stillness` | 最难的动作是不动 | `bide` → 4；`feign` → 27；`calm` → 32 | 三种"不能动"：鼓响时出手、试探期点击、他盯着时点哪里 |
| `show` | 维持不存在的东西 | `draw` → 7；`borrow` → 29 | 影子会淡要不停补笔；借旗挂满支点凑够规模 |
| `twoline` | 明线 + 暗线抢同一根手指 | `stack` → 8；`plant` → 33 | 明线掉不下来就没张力；空档不足 0.9s 就变成比手速 |
| `read` | 从好话里识破动作的破绽 | `inspect` → 10 | 只教识破，点空零惩罚；破绽必须按 `atMs` 递增排 |
| `probe` | 用一次试探换一条信息 | `knock` → 13；`spot` → 18；`hint` → 26 | 敲草丛会惊蛇（代价不能变成必输：穷举 120 种敲法证明每步都还有解） |
| `lure` | 放饵换空档，给砖换玉 | `decoy` → 15；`trade` → 17；`favor` → 31 | 按住才记账、松手即断；看守在路上时放饵无效 |
| `chase` | 追而不逼 | `hold` → 16 | 距离要待在 `keepMin..keepMax` 区间；逼太近时体力回得比掉得还快就是没张力 |
| `swap` | 换成"样子一样"的替身 | `shell` → 21；`beam` → 25 | 检查者每隔一会儿抬头看一次；beam 换一根要比两次清点的间隔更快 |

三条跨模板的共识值得单独说：

1. **"代价"不能变成"必输"。** `probe.knock` 的收益伴随风险（敲到蛇会把邻近的草一起搅乱），于是单测**穷举全部 120 种敲击顺序**，证明每一步之后都还有解。这是"零失败"在概率空间里的版本：惩罚可以叠加，但任何时刻都得留一条出路。
2. **"连续"要真的连续。** `lure.decoy` 按住才记账、松手即断，而且看守在路上时放饵无效（防连点把空档续成无限）。这类模板的判定不看"点了没"，看"过程长得对不对"。
3. **无头验证不许另开一条路。** `chase` 的 autoplay 与真实按住共用同一个 `holding` 状态；`stillness` 的三个模式各有一份 `effectiveXxxLevel` 把时长压短，但喂进去的判定函数一模一样。

## 7.18 三件地基：layout / session / gains

**`layout.ts`** 是模板层唯一的坐标事实来源：`DESIGN = { width: 750, height: 1334 }`，以及 e2e 直接复用的 `SCENE_KEYS`（29 个键：`story` / `reward` / `chaos` / `beacon` / `butcher` + 24 个模板场景键）。给按钮与卡片用的常量也在这里，例如 `REWARD.done = { x: 375, y: 1190 }` —— 自动化用例直接按坐标点。各模板的手感常量同样集中：`PLACE.dropForgive = 52`、`SORT.tasteMs = 1000`、`TRACE.channelWidth = 32`、`WAIT.fallbackMs = 16000`、`MARK.carveHoldMs = 1200`、`BURROW.digForgive = 44`、`SPLIT.dividerRadius = 58`。

**`session.ts`** 是"零惩罚"与"星星"之间的桥：

```ts
/**
 * 记一次尝试 —— 场景里"这一下算不算做对"只走这一个口子。
 *
 * total 是"试了几次"，correct 是"成了几次"，mistakes 是"错了几次"：
 * - ok = true：total + 1、correct + 1；
 * - ok = false：total + 1、mistakes + 1（做错也是一次尝试）。
 *
 * 以前 20 个模板只在成功时把 total 与 correct 一起 +1，于是 correct / total 恒为 1：
 * 复习评级（PlayView 按答对率算）永远满分；星星只看 mistakes，也就永远是 3 颗。
 * 失败也记进 total 之后，两条线才恢复真实。
 *
 * "零惩罚"的口径没有变：做错不会结束这一局、不会锁住操作、不会扣掉已经拿到的星星；
 * 它只影响这一局拿几颗星（starsFor）与下次复习间隔（PlayView 的 reviewGrade）。
 */
export function recordAttempt(session: SessionState, attempt: { ok: boolean }): void {
  session.total += 1;
  if (attempt.ok) session.correct += 1;
  else session.mistakes += 1;
}
```

星星规则：错 ≤ 1 次三星、≤ 3 次两星、再多一星 —— 门槛刻意宽松，**没有 0 星**。对小朋友来说，"这次没拿满星"就够难受了。

**`gains.ts`** 只有两个函数，存在的理由是体积（见 7.4 的引文）：`siegeGain(resistance)` 给 siege 与关卡验算共用同一份"推一下能推进多少"，`bestMatchupWins(horses, rivals)` 穷举三匹马的全部六种配对、返回最多能赢几场 —— 玩法判定与 schema 的 refine 都调它，所以"这一关不可能赢"与"孩子真打不赢"永远是同一句话。

## 7.19 数据登记：zod schema 与 templateSchemas

模板层的第二份"事实来源"是 `packages/templates/src/schemas.ts`：26 个 id 的关卡 schema + 一张注册表。注册表是 `Record<TemplateId, z.ZodType>` —— **少登记一个在 typecheck 就报**（`TemplateId` 的唯一来源是 `packages/content/src/schema.ts` 的 `TEMPLATE_IDS`，`game-kit` 只做再导出；下为节选，`...` 表示省略若干条）：

```ts
/** 模板 id → 关卡脚本 schema。新增模板时在这里登记，content:check 自动生效。 */
export const templateSchemas: Record<TemplateId, z.ZodType> = {
  substitution: SubstitutionLevelSchema,
  tap: TapLevelSchema,
  place: PlaceLevelSchema,
  ...
  // siege / matchup 第四辑长出了新模式：老模式那份 schema 一个字没改，这里按并集登记
  siege: z.union([SiegeLevelSchema, SiegeSupportSchema, SiegeCloseSchema, SiegeLadderSchema]),
  // borrow 有两种模式：force（借刀杀人，既有）与 banner（借尸还魂）——
  // 两份 schema 分开写（force 那份一个字没改），这里按并集登记给构建期体检用。
  borrow: z.union([BorrowLevelSchema, BorrowBannerLevelSchema]),
  stillness: z.union([StillnessLevelSchema, StillnessFeignSchema, StillnessCalmSchema]),
  ...
  chain: z.union([ChainLevelSchema, ChainStepSchema, ChainDominoSchema]),
};
```

`z.union([...])` 这个写法是六辑下来的关键决定：**加一个模式只是并集里多一项**，两边不用碰彼此的字段，也不会让老内容的校验语义发生变化。代价是判别要显式写守卫（`isSupportConfig` 之类），但那是类型层面的事，运行期只多一次 `cfg.level.mode` 比较。

`content:check` 就是拿这张表逐段校验的（`packages/templates/src/cli/check-content.ts`）：遍历每条内容的 `game.stages`，取 `templateSchemas[stage.template]`，没有就报"未知玩法模板，请在 schemas.ts 登记"，有就 `safeParse(stage.levelScript)` 并把每条 issue 的路径与 message 打出来。双语补丁合并之后还会再跑一遍 —— 所以英文漏翻一个 `hint` 也在这里挂。

`schemas.ts` 现在有 **127 条 refine**，每条的 message 都是写给内容作者看的一句话，而不是给程序员看的英文断言。这一层的价值在于：**内容写错在构建期就报，不让孩子在游戏里发现**。几条有代表性的：

| 模板 | refine 原文 | 守住什么 |
|---|---|---|
| `substitution` | 用这些石头凑不出重物的重量（容差内无解），关卡不可通关 | 可通关性 |
| `tap` | tap 模式下 targetValue 必须是 stepValue 的整数倍，否则永远点不满 | 整除 |
| `sort` | 有"先尝后分"却没有给每件东西写 tastedKind —— 尝完什么都看不出来 | 教学核心 |
| `aim` | goalCount 必须小于目标总数 —— 否则就没有"留一个"的余地了 | 玩法余地 |
| `burrow` | 有危险一次堵住的洞口数不少于洞口总数 —— 这一局无论怎么挖都躲不过去 | 必败检测 |
| `chain` | 允许只持续 600ms 以内 —— 那就变成比手速了 | 适龄底线 |
| `probe` | 每一处安全的草丛都落在某条蛇的惊吓范围里 —— 一敲就会被搅乱，这一关可能无解 | 无解检测 |
| `matchup` | 六种配对都赢不到 needWins 场 —— 这一关不可能赢 | 无解检测 |

## 7.20 游戏专属场景：40% 定制的落点

模板覆盖不了一次性机制时，场景写进游戏包 —— 但**数据仍然登记在模板层**。当前三个例子：

- **盘古的开蛋**（`games/pangu/src/scenes/chaos.ts`）：连点 4 次蛋壳，裂缝一道道出现，最后炸开；亮粒子上升、暗块下沉，用画面完成"阳清为天，阴浊为地"。它**连模板 id 都没有** —— `chaos` 不在 `TEMPLATE_IDS` 里，内容 `game.stages` 也只写 `tap` 与 `place`；
- **烽火的点烽火**（`games/fenghuo/src/scenes/beacon.ts`）：点一次火 → 火光一座座传向天边 → 信任少一格；
- **庖丁的解牛**（`games/paoding/src/scenes/butcher.ts`）：顺缝推块 + 刀口状态。

后两个有模板 id（`beacon` / `butcher`），但模板层只有 schema，没有场景工厂：

```ts
/**
 * beacon 关卡（烽火戏诸侯专用）：
 * 场景本身留在这个游戏包里（像盘古的开蛋场景一样），但**数据在这里登记**，
 * 这样双语内容校验、翻译体检、schema 体检都会覆盖到它。
 */
```

判据很清楚：**这段数据要不要被 `content:check` 校验？** 要，就必须有模板 id 与 schema；场景在哪写是工程选择，不是契约选择。所以 `chaos` 不登记（它的数据是常量，不来自内容），`beacon` / `butcher` 登记（塔数、骨块数、提示语都是内容作者写的）。

## 7.21 新增一个模板的检查清单

当已有模板都装不下一个典故的核心玩法时才新增模板。以新增 `match` 为例（这个名字 2026-10-18 已从契约里删掉，这里只当占位）：

1. **定 id**：在 `packages/content/src/schema.ts` 的 `TEMPLATE_IDS` 加 `'match'`。这一份是唯一来源，内容 schema 用 `z.enum` 校验，写错模板构建期就报；
2. **定 schema**：在 `packages/templates/src/schemas.ts` 写 `MatchLevelSchema`，把"教学核心"写成 refine（参考 sort 的"先尝后分"、substitution 的背包校验）；
3. **注册**：加进 `templateSchemas`。从这一刻起 `content:check` 开始校验所有使用它的内容（含双语合并后的二次校验）；
4. **登记场景键**：`layout.ts` 的 `SCENE_KEYS` 加 `match: 'match'`；需要新坐标常量一并加进来（e2e 会复用）；
5. **写纯逻辑**：`match.logic.ts`（判定、进度、并集去重计数），**不 import Phaser、不用 `Math.random` / `Date.now`**（eslint 拦）；
6. **写单测**：`match.logic.test.ts` 覆盖判定与边界，并把"一局真的走得完"写成一条性质（照 `runAutoplay` 的同一条路）；
7. **写场景工厂**：`match.ts`，工厂 + `drawXxx` 回调外置 + 卡住提示 + 逐帧/事件驱动；多模式用 `level.mode` 分派，**老模式那条路径保持一行不改**；
8. **加子路径导出**：`packages/templates/package.json` 的 `exports` 加 `"./match": "./src/match.ts"`（不加这一行，游戏包只能用 `import type`）；
9. **导出与改名**：`packages/templates/src/index.ts` 导出，注意与现有同名导出显式改名（文件里已有 `stillnessPhaseAt` / `windowTapsNeeded` 等多个先例）；
10. **内容**：写 `levelScript`、双语补丁两半、四处登记（摘要 / 详情 / 摘要译文 / 详情译文），并在 `game.stages` 里声明 `{ template: 'match', levelScript }`；
11. **游戏包**：运行时 import 走 `@chags/templates/match`，不要走 barrel；`apps/site/src/registry.ts` 加一行懒加载；
12. **端到端**：`e2e/` 加一条真实指针操作 + 一条 `?autoplay=1` 无头通关（必须走与真实操作同一条判定路径），再跑 `pnpm verify`（六项）与 `pnpm e2e`。

反过来，如果只是给已有模板加一个模式，清单短得多：**schema 单独写 + 并集登记 + 配置用重载分派 + 老模式判定一行不动 + 新模式自己的单测**。六辑下来这条路径重复了五次，成本已经可预测。

## 7.22 兼容真机行为与「只加不改」的坑

模板层踩过的坑，按"会在真机上表现出来"排序：

1. **墙钟，不累加帧间隔。** Phaser 在帧率低时会钳制 `delta`，慢机器上"按住 6 秒"累积不到 6 秒。tap 的 `hold`、wait 的等待、mark 的漂船、window 的窗口全部按 `ctx.services.now()` 算。
2. **命中的是线段，不是点。** aim 的箭一帧能跨过半个屏幕，只按点距判定会穿过去；`firstHit` 还按"沿弹道最先碰到"取目标，否则几发并排时选错。
3. **输入锁的起点必须绑在"真的翻页"上。** 350ms 锁从点击区建好起算，会让孩子"听完立刻点"落在锁里 —— 既不翻页也不提示。现在由 `isTapArmed(now, lastAdvanceAt)` 判定，并抽成纯函数加了单测（详见第 08 章与第 16 章）。
4. **计数要去重。** place 的 `['sun','sun']`、sort 的同一件东西放两次，都曾经被算成两件。
5. **落点宽容度是产品需求，不是技术妥协。** `PLACE.dropForgive = 52`、`TRACE.hintRing = 18`、`BURROW.digForgive = 44`：手指粗的孩子也要点得到。命中区与 `TOUCH_PAD` 的取舍见第 08 章。
6. **触摸与手势。** 一次手势只认一根手指（`createGestureGuard`），drag 记住 `pointerId`；`trace` / `swap` / `borrow` / `twoline` / `aim` 都已改造。多指同时按下时 Phaser 默认只保留一个活跃指针，第二个 `touchstart` 会被整条丢弃。
7. **收尾演出必须有兜底。** 大禹的「三过家门」1.5s + 2.4s 双保险、wait 的 `fallbackMs = 16000`、story 的 `gateWatchdogMs`：补间被打断、语音不回报、玩家就是不点 —— 任何一种都不能把这一局钉死。
8. **扩展不许碰老模式。** 这条规矩在六辑里重复了五次：`window` 的 `fire`、`siege` 的 `vital`、`borrow` 的 `force`、`show` 的 `draw`、`chain` 的 `pass`、`swap` 的 `shell`、`probe` 的 `knock`/`spot`、`stillness` 的 `bide` —— 加新模式时这些路径与它们的单测**删改 0 行**（`git diff` 逐行确认）。第六辑收官时，34 / 36 复用的 `split` / `trace` 两个模板在 `git status` 里完全干净。
9. **体积。** 模板场景与内容都按需加载：首屏 54.1 KB gzip（2026-10-18 实测，不含 Phaser 与内容详情），点开一局的全部新增流量约 226 KB gzip（其中 220.6 KB 是裁剪版 Phaser），二十四套场景、五十三条内容各自成 chunk。数字以 `pnpm size` 为准。

顺带修正两条本章早前的结论：`quiz` 模板已经**删除**（到期复习改由外壳的 DOM 页面实现，同一个功能不留两份实现，见第 10 章）；`beacon` 不再是"唯一的数据登记型专属场景"，现在有三个，写法已经统一。

## 7.23 小结

- 模板层现在是 **26 个 id**：24 个有独立场景工厂与 chunk，`beacon` / `butcher` 只有 schema 登记；`story` 是 53 部共用的开场、不走 id，`chaos` 是盘古专属、连 id 都没有。它们撑起 **53 部游戏**（17 典故 + 36 计）、**55 段**内容关卡；
- 模板按**交互原语**建模，而不是按题材：14 个计策模板长出 **33 种模式**，另有 3 计整关复用典故期模板（9 用 `wait`、34 用 `split`、36 用 `trace`）；
- 扩展走"只加不改"：新模式单独写 schema、`templateSchemas` 按 `z.union` 并集登记、场景工厂用重载分派，老模式判定与单测删改 0 行 —— 五次重复下来，这条路线的成本已经可预测；
- 教学核心写进 schema：可通关（substitution 的背包校验、matchup 的六种配对验算）、先尝后分（sort）、只进不退（trace）、永远等得到（wait）、整除（tap）、不许变成比手速（chain / stillness / twoline 的时长下限）；
- 兼容真机行为的坑都有注释与单测兜底：墙钟计时、命中线段扫描、输入锁起点、去重计数、落点宽容度、收尾兜底；
- 专属场景允许"一次性机制"，但**数据必须登记**，保证 `content:check`、翻译体检、schema 体检全覆盖。
