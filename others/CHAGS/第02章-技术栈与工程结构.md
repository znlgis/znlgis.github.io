# 第02章 - 技术栈与工程结构

## 2.1 版本基线

CHAGS 使用 pnpm workspace 管理多包，所有版本以各 `package.json` 为准。当前基线如下（`^` 表示允许小版本升级）：

| 包 | 版本 | 作用 |
|---|---|---|
| phaser | ^4.2.1（构建时用裁剪版） | 游戏引擎 |
| vue | ^3.5.44 | 应用外壳 |
| pinia | ^4.0.3 | 外壳状态管理 |
| @vitejs/plugin-vue | ^6.0.10 | SFC 编译 |
| vite | ^8.3.4 | 构建（Rolldown 内核） |

## 2.2 两个「锁版本」背后的实测原因

### TypeScript 锁在 5.9.3，而不是最新的 7.x

TypeScript 7（Go 原生编译器）移除了 `./lib/tsc` 子路径导出，而 `vue-tsc` 依赖它。实测 `typescript@7.0.2 + vue-tsc@3.3.13` 会直接报错：

```
ERR_PACKAGE_PATH_NOT_EXPORTED: './lib/tsc' is not defined by "exports"
```

并且查询 dist-tags 确认当时**不存在**支持 TS 7 的 vue-tsc 版本。换回 `typescript@5.9.3` 后同一份代码立即正常工作。5.9.3 同时满足 `vue-tsc >= 5.0.0`、`typescript-eslint < 6.1.0`、`pinia >= 5.6.0` 三方 peer 范围，是当前唯一「全绿」的版本。

代价是暂时享受不到原生编译器约一个量级的类型检查提速；等 vue-tsc 跟进后升级只是改一行版本号，代码零改动。

### 安卓打包要 JDK 17–24，绕开 JDK 25

Gradle 8.14 只支持到 JDK 21 左右的区间，用 JDK 25 会报 `Unsupported class file major version 69`。CI 里 `release.yml` 用 `actions/setup-java@v5` 固定 `java-version: '21'`；本地则由 `scripts/build-apk.mjs` 在常见安装目录里找一个可用的 JDK（也可用环境变量 `CHAGS_JDK` 指定），不需要手动切换 `JAVA_HOME`。这是「本机环境差异」这一类问题的典型处置方式：把判断写进脚本，而不是写进文档让人记。

## 2.3 为什么是 Phaser 4 + Vue 3.5 的组合

| 方案 | 合集适配度 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **Phaser 4** | ★★★★★ | 纯代码/TS、MIT、生态成熟、包可控 | 无编辑器，UI 要自己写 | ✅ 主选 |
| Phaser 3 | ★★★★☆ | 教程最多 | 已是上一代 | 备选 |
| Cocos Creator | ★★★☆ | 小游戏一键发布 | 编辑器资产 AI/CI 不友好，包体大 | 备选 |
| PixiJS | ★★☆ | 渲染性能好 | 只是渲染器，游戏框架要从零造 | ✗ |
| Godot / Unity Web | ★★ / ★ | 开发体验好 | Web 导出体积大、移动端 H5 兼容差 | ✗ |
| 纯 DOM/CSS | ★★★（仅问答类） | 最轻、可 SEO | 复杂交互做不动 | 仅用于图鉴、复习、家长页 |

选 Phaser 4 的核心原因与 1.2 节的产品约束一致：**代码即资产**。场景、关卡、动画全部是 TypeScript 文本，可 diff、可 review、可被单测与端到端测试覆盖。

而「外壳用 Vue、游戏用 Phaser」的双栈分工则是基于职责：大厅、图鉴、复习、家长页是 UI 密集型页面，用 SFC 写得快；游戏内是 Canvas 世界，交给 Phaser。关键约束是 **Phaser 绝不进外壳主包**：

- 完整版 Phaser 4.2.1 的 chunk 是 347.3 KB gzip / 1341.9 KB 原始；
- 裁剪版（去掉 physics / tilemaps / sound / animations 等 53 个游戏都用不到的系统）是 **220.6 KB gzip / 856.3 KB 原始**，省 36%；
- 外壳首屏（JS + CSS，含内联脚本）实测 **54.1 KB gzip / 146.1 KB 原始**，完全不含 Phaser；
- 每个游戏的业务代码只有几 KB，Phaser 是共享 chunk，只在第一次进游戏时加载一次。

裁剪不是靠 tree-shaking 猜出来的：`pnpm phaser:trim`（`scripts/build-phaser-trim.mjs`）生成 `packages/phaser-kit/vendor/phaser-trim.esm.js`，`apps/site/vite.config.ts` 用 alias 把裸 `phaser` 导入指到它，同时保证 TypeScript 仍解析官方类型。想临时回退完整包排查问题，跑 `PHASER_FULL=1 pnpm dev` 即可。

### Vue × Phaser 集成的五条踩坑清单

这段是血泪经验，直接写进代码规范（第 16 章有完整版）：

1. **Phaser 实例必须用 `shallowRef` 或 `markRaw` 持有**。用 `ref` 会让 Vue 的响应式系统深度遍历整个 Phaser 对象图（场景、纹理、WebGL 上下文），轻则卡顿，重则直接抛错。`PlayView.vue` 里的 `const mod = shallowRef<GameModule | null>(null)` 就是这条规则的落点。
2. **游戏容器不要放进 `<KeepAlive>` 或 `<Transition>`**，离开路由前必须 `await unmount()`。
3. **给游戏模块加 HMR 边界**：编辑 Phaser 场景时应整页刷新，否则热替换会叠出多个 canvas。
4. **不要在 `computed` / `watch` 里持有 Phaser 的 GameObject**，它们不是响应式数据。
5. 宿主组件最小实现就是 `defineProps` + `shallowRef` + `onMounted` / `onBeforeUnmount`。

```
┌──────────────────────────────────────────────────────────────┐
│  外壳 apps/site/src（Vue 3.5 SFC）                             │
│  游戏馆 · 游戏宿主 · 图鉴 · 到期复习 · 家长页                   │
│  状态：Pinia（progress/settings/playtime/locale）              │
│  路由：hash composable ── 样式：Tailwind                       │
└────────────────┬─────────────────────────────────────────────┘
                 │ 动态 import（代码分割，Phaser 只在这里出现）
                 ▼
┌──────────────────────────────────────────────────────────────┐
│  游戏包 games/<id>    ← 一个条目 = 一个包（可独立开发/测试）    │
│  index.ts 场景编排     logic.ts（纯 TS：取关卡脚本 + 判定）     │
└────────────────┬─────────────────────────────────────────────┘
                 │ 只依赖下面这些，绝不反向依赖外壳
                 ▼
┌────────────┬────────────┬────────────┬───────────────────────┐
│ game-kit   │ templates  │ content    │ phaser-kit            │
│ 契约/事件  │ 玩法模板库 │ 内容数据   │ 引擎启动/主题/绘制     │
└────────────┴────────────┴─────┬──────┴───────────────────────┘
                                │
                 ┌──────────────┴───────────────┐
                 │ progress（存档/复习）          │
                 │ platform（存储/音频/生命周期） │
                 │ i18n（界面文案）               │
                 └──────────────────────────────┘
```

包之间的实际依赖方向（`package.json` 里的 `workspace:*` 依赖）如下：

```
content    → zod
game-kit   → content
i18n       → content
progress   → game-kit
platform   → game-kit + progress
phaser-kit → game-kit + i18n（+ phaser）
templates  → content + game-kit + phaser-kit + i18n（+ phaser + zod）
games/*    → content + game-kit + phaser-kit + templates（+ phaser）
apps/site  → 上面所有包 + pinia + vue + 全部 53 个 games/*
```

三条重要事实：

- **`game-kit` 与 `content` 不含 Phaser 依赖**，所以外壳可以安全地 import 它们（大厅读摘要、进度记星星都走这两个包）。
- **依赖方向永远向下**：游戏包不认识外壳，模板不认识游戏包。新增一个条目不需要修改任何公共包。
- **运行时入口纪律**（2026-10-18 新增）：游戏包只许 import `@chags/templates/core` 与自己的场景子路径；一旦有人 import 模板主 barrel，24 个场景就会全部回到共享 chunk 里。这条纪律没有 lint 规则守着，靠「体积报告里多出一个 55 KB 的 chunk」来发现。

## 2.5 pnpm workspace 的组织方式

`pnpm-workspace.yaml` 只有三行目录声明（外加构建白名单）：

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
  - 'games/*'
```

每个包都是 private 包，通过 `exports` **直连源码**，不设构建步骤、不配路径别名：

```json
{
  "name": "@chags/game-pangu",
  "private": true,
  "type": "module",
  "exports": { ".": "./src/index.ts" },
  "dependencies": {
    "@chags/content": "workspace:*",
    "@chags/game-kit": "workspace:*",
    "@chags/phaser-kit": "workspace:*",
    "@chags/templates": "workspace:*",
    "phaser": "^4.2.1"
  }
}
```

这种「just-in-time package」的好处是改一处全仓即时生效：改 `packages/templates` 里的一个判定函数，Vite 开发服务器立刻热更新到游戏里，不需要 `pnpm build` 任何中间产物。

`packages/templates` 导出了大量子路径，让游戏包可以只引用需要的那一层：

```json
"exports": {
  ".": "./src/index.ts",
  "./core": "./src/core.ts",
  "./layout": "./src/layout.ts",
  "./schemas": "./src/schemas.ts",
  "./session": "./src/session.ts",
  "./substitution": "./src/substitution.ts",
  "./tap": "./src/tap.ts",
  "…": "…（24 个场景子路径）",
  "./substitution.logic": "./src/substitution.logic.ts",
  "./siege.logic": "./src/siege.logic.ts",
  "…": "…（纯逻辑子路径，供单测用）",
  "./gains": "./src/gains.ts"
}
```

这套子路径不只是「好看」：2026-10-18 之前全仓有 **161 处跨包深路径 import**（`@chags/templates/src/siege.logic` 这种），既绕过 exports 又让游戏包顺手把整个模板库拖进 chunk。现在是 0 处，可以用一句 `rg "packages/(templates|content)/src" games e2e` 复核。

`packages/content` 则把两半内容拆成两个入口：

```json
"exports": {
  ".": "./src/index.ts",
  "./full": "./src/entries/detail.ts"
}
```

`./full` 只给 Node 侧（内容体检、单测）用 —— 生产构建里谁也不许 import 它，否则首屏会把 53 条详情一起下下来。

## 2.7 chunk 是怎么切出来的

「每个游戏独立 chunk」不是 Vite 的默认行为，而是一组约定叠出来的结果，值得单独讲：

1. **注册表只放函数**：`apps/site/src/registry.ts` 里 53 行全是 `() => import('@chags/game-<id>')`，外壳只认识这个函数，不认识任何玩法；
2. **内容两半**：摘要进首屏，详情与关卡脚本由 `loadEntry()` 用 `import.meta.glob` 按条目加载（`entries/loaders.ts`），54 个 `content-<id>-*.js` 各自成 chunk；
3. **英文补丁懒加载**：53 份英文摘要补丁收在 `i18n/en.ts`，只在切到英文时 `ensurePatches()`；详情补丁命名成 `content-<id>-en-*.js`；
4. **Phaser 单独成组**：`vite.config.ts` 的 `codeSplitting.groups` 把 `node_modules/phaser` 与裁剪版产物归到 `vendor-phaser`；
5. **可读的文件名**：`chunkFileNames` 按 「游戏 / 内容 / 英文内容」三种模式改名，排查时一眼能看出「这个 1.6 MB 的文件是什么」。

```ts
chunkFileNames(chunk) {
  const id = chunk.facadeModuleId ?? '';
  const game = /[\\/]games[\\/]([^\\/]+)[\\/]src[\\/]index\.ts$/.exec(id);
  if (game) return 'assets/game-' + game[1] + '-[hash].js';
  const content = /[\\/]entries[\\/]([^\\/]+)\.game\.json$/.exec(id);
  if (content) return 'assets/content-' + content[1] + '-[hash].js';
  const en = /[\\/]i18n[\\/]en[\\/]([^\\/]+)\.game\.json$/.exec(id);
  if (en) return 'assets/content-' + en[1] + '-en-[hash].js';
  return 'assets/[name]-[hash].js';
}
```

还有一个容易被忽略的配置：`base: './'`。桌面（Tauri）与安卓（Capacitor）都是**本地文件加载**，绝对路径 `/assets/…` 在 `tauri://localhost` 或 `capacitor://localhost` 下会 404。

| `pnpm phaser:trim` | `node scripts/build-phaser-trim.mjs` | 重新生成裁剪版 Phaser |
| `pnpm keystore` | `node scripts/make-keystore.mjs` | 生成安卓签名密钥（可选） |
| `pnpm dist:win` | 站点构建 + Tauri | Windows 便携 exe |
| `pnpm dist:apk` | 站点构建 + Capacitor | 安卓 apk |
| `pnpm icons` | `python scripts/make-icons.py` | 用 Pillow 生成两套壳的图标 |

注意 `verify` 里 `size` 在最后且**串行**：体积守卫读的是刚构建出来的 `apps/site/dist`，所以顺序不能换 —— 前五步（typecheck / lint / test / content:check / build）互不依赖，并行跑，这正是它从 65.8 秒降到 5.9 秒（热）的原因。

## 2.9 一份 tsconfig 管全仓

仓库只有一个根 `tsconfig.json`，把 packages、games、apps/site、e2e、根配置全部纳入 `include`，关键开关：

```jsonc
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noImplicitOverride": true,
    "noEmit": true,
    "incremental": true,
    "tsBuildInfoFile": "./node_modules/.cache/tsconfig.tsbuildinfo",
    "types": ["vite/client", "node"],
    "paths": {
      "@chags/templates/layout": ["./packages/templates/src/layout.ts"],
      "@chags/content/full": ["./packages/content/src/entries/detail.ts"]
    }
  },
  "include": [
    "packages/*/src/**/*.ts",
    "games/*/src/**/*.ts",
    "apps/site/src/**/*.ts",
    "apps/site/src/**/*.vue",
    "apps/mobile/*.ts",
    "e2e/**/*.ts",
    "*.config.ts",
    "apps/*/*.config.ts"
  ],
  "exclude": ["**/node_modules", "**/dist", "apps/mobile/android", "apps/desktop/src-tauri"]
}
```

几处取舍说明：

- `verbatimModuleSyntax` 强制 `import type` 显式标注类型导入，配合 `isolatedModules` 让每个文件都能被独立转译（Vite 的底层要求）；
- `noEmit: true` —— 类型检查与产物构建彻底分离：`vue-tsc` 只查类型，出产物是 Vite 的事；
- `incremental` + tsbuildinfo 让本地重复 typecheck 只算变过的文件（CI 冷跑不受影响）；
- `paths` 只补两条：e2e 的「最近的 tsconfig」就是根这一份，而根 package 不是 workspace 依赖方，按包名解析不到 `@chags/*` 子路径；运行时仍走各包 `exports`，所以「深路径 import = 0」依然成立；
- 原生壳的 `android/` 与 `src-tauri/` 被排除，它们不是 TypeScript 工程的管辖范围。

同样地，Vitest 与 Playwright 都只有一份根配置，测试发现的规则见第 13 章。

## 2.10 小结

- 技术栈的核心是「Phaser 4（裁剪版）管游戏 + Vue 3.5 管外壳」，Phaser 被严格隔离在游戏与引擎包里，外壳首屏 54.1 KB，不为它付体积；
- 工程用 pnpm workspace 划出 `apps / packages / games` 三层，包与包之间 `exports` 直连源码，改一处全仓即时生效；子路径导出同时承担了「只引用需要的那一层」这个体积职责；
- 两个版本锁定（TS 5.9.3、JDK 21/17–24）都来自实测，不是保守，而是当前唯一全绿的组合；
- chunk 的切法是「注册表 + 内容两半 + 英文补丁懒加载 + Phaser 单独成组 + 可读文件名」五件事叠出来的，每一件都有对应的门禁；
- 根脚本 `pnpm verify` 是「完成」的定义，其中体积守卫放在构建之后。
