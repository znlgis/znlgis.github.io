# 第17章 - 隐藏小游戏与竹林小路

前十六章讲的是「一件小事 → 一个模板 → 一局判定 → 一份奖励」这条主线。这一章讲主线之外的岔路：孩子完成当天四件小事后，小屋墙上出现一扇小竹门，门后是三款按 4–8 岁重做的街机小游戏（消灭星星、弹一弹、俄罗斯方块），普通模式三款合计每天最多 21 局、每款另有独立的难度等级 Lv.1–12（跨天成长），另有一条更隐蔽的路——在小屋里连续点竹竹 **7 次（5 秒内）**，当天小门直接打开、三款游戏**无限畅玩、不限局数**。后者在代码里叫「竹林小路」，存档里只占一个布尔值。

这一章回答三个问题：为什么它是彩蛋而不是第十一个日常任务，解锁与「每天 21 局 + 难度等级」怎样落到纯函数与存档上，三款实时玩法怎样在「逻辑与渲染分离」下写出 99 条能跑在 Node 里的单测。

## 17.1 为什么是彩蛋，而不是第十一个任务

最省事的做法是「再加一条内容 JSON、复用某个模板、发 task:complete」。这条路会在三处崩掉：

| 冲突点 | 日常玩法 | 三款街机 | 硬套的后果 |
|---|---|---|---|
| 数据来源 | 内容 JSON 驱动的关卡脚本 | 种子随机 + 实时状态机（棋盘、球、方块队列） | 关卡 schema 要长出「棋盘」这种没人看得懂的字段 |
| 判定 | 有限步的手势判定，一局 30–90 秒 | 帧循环、反弹物理、消行、AI | 模板层被迫引入物理与帧同步 |
| 结算 | 星星 + 竹笋 + 成长值 + `task:complete` | 只有一个分数 | 任务经济被彩蛋污染：连续天数、贴纸、家长页统计全部失真 |

所以这一轮是**新契约 + 新包 + 新宿主**，只复用视觉与平台出口：契约在 `packages/game-kit/src/arcade.ts`（60 行），实现在 `games/arcade`（三款各自 `*.logic.ts` + `*.scene.ts` + 17 行入口），宿主是 `ArcadePlayView.vue`，路由是 `#/arcade` 与 `#/arcade/<id>`。8 个玩法模板、10 条内容 JSON、任务存档、vite 配置、体积预算一行都没动。

「不碰任务存档」可以 grep 验证：`games/arcade` 里没有 `progress`、没有 `task:complete`、没有 `TaskId`。彩蛋只发 `arcade:*` 四种事件，写档由外壳在 `arcade:complete` 之后调用 `ProgressManager.playArcade()`——与「模板不允许自己发奖励」是同一条纪律的镜像。

三款游戏的选择遵循同一条产品判断：保留微信小游戏的核心乐趣，去掉所有惩罚。

| 游戏 | 保留的核心乐趣 | 低龄化改造 | 不失败的处理 |
|---|---|---|---|
| 消灭星星 | 一按爆一片、下落补星、连消音调升高 | 8×10、4 色 + 花纹双通道、无倒计时 | 没有可消组时剩下的星星飞回天上并计入收集 |
| 弹一弹 | 瞄准 → 弹射 → 到处反弹 → 方块一串碎 | 任意位置拖拽瞄准、虚线 + 反弹点预测、一击碎 | 每 6 发下沉一格；贴底时「开出小花」飞走，本轮算完成 |
| 俄罗斯方块 | 拼、消行、越堆越高 | 8×14、四个大按钮 + 2 个预览、不做 hold | 堆到顶变「彩虹」，清掉最下 4 行继续玩 |

## 17.2 孩子看到的时间线

```text
早上：小屋 / 任务页照旧，界面上没有任何彩蛋痕迹
     │
完成第 4 件【不同的】今日小事
     │
     ├─ 奖励照旧（竹笋 / 星星 / 碎片 / 贴纸）
     └─ 结算浮层多出一行：「咦，竹林后面有一扇小门…」
          │  [推开门]        [等会儿]
          ▼
小屋墙上多了一扇亮着的小竹门（当天有效）
     │ 推门
     ▼
竹林游戏厅：三张卡片（Lv.N 难度 / 最好成绩 / 今天还能玩 N 局）
     │
     ▼
全屏小游戏：一局 = 一轮，20–60 秒 → 撒花 → 回游戏厅，局数 -1
     │
第二天 00:00：小门消失、局数归零，但 Lv 与最好成绩接着长
```

四个落点各自只做一件事：`completeTask()` 的返回值 `arcadeUnlocked` 只在「这一刻从不满足变成满足」时为真；`PlayView.vue` 据此显示浮层（不自动跳转）；`HomeView.vue` 用 `v-if="progress.arcadeUnlocked"` 决定小门在不在 DOM 里；`ArcadeView.vue` 在挂载时把未解锁的访问送回小屋。

「浮层只在跨过的那一刻出现」值得单独说：`completeTask()` 先取 `arcadeWasUnlocked`，结算完再取 `isArcadeUnlocked(nextDay)`：

```ts
// packages/progress/src/manager.ts（节选）
const arcadeWasUnlocked = isArcadeUnlocked(day);
// …结算奖励、状态、连续天数…
return {
  task: progress,
  isFirstToday: firstToday,
  stars,
  shoots: reward.shoots,
  xp: reward.xp,
  fragments,
  sticker,
  arcadeUnlocked: !arcadeWasUnlocked && isArcadeUnlocked(nextDay),
};
```

不做「已有 4 件就补弹一次」：老存档里今天已经做过 4 件的孩子，第二天打开会莫名其妙被弹一个「发现一扇小门」。门应该出现，浮层不该补——**补弹是在奖励一个没有发生过的瞬间**。

## 17.3 解锁判定：按数量，不按推荐集

解锁只有一行判定，落在 `packages/progress/src/arcade.ts`：

```ts
export function arcadeUnlocked(day: DayRecord | undefined): boolean {
  if (day === undefined) return false;
  return day.completed.length >= DAILY_TASK_TARGET || arcadeUnlimited(day);
}
```

`DAILY_TASK_TARGET` 住在 `daily.ts`，与「今日推荐几件」共用同一个常量（`export const DAILY_TASK_TARGET = 4;`）。为什么不按「今日推荐的那四件」判定：推荐集是日期 + 时段做种子的（第 10 章），中午与晚上会换一批，按集合判定会出现「上午解锁、中午又锁上」，而孩子明明做了四件事。按数量判定天然稳定，`day.completed` 去重、只增不减。

判定由日记录派生，不额外存「已解锁」布尔值——少一个字段就少一类不一致。「今天还能不能玩某一款」是另一个函数，它把彩蛋也考虑进去：

```ts
/** 这一款今天还能不能开局：未解锁 → 都不能；无限畅玩 → 随便玩；普通模式 → 今天还没玩满 ARCADE_DAILY_PLAYS 局就能玩 */
export function arcadeAvailable(save: SaveData, gameId: ArcadeGameId, now: number): boolean {
  const day = save.days[dayKey(now)];
  if (!arcadeUnlocked(day) || day === undefined) return false;
  void gameId; // 2026-11-07 起配额按「三款合计」算，不再区分是哪一款
  return arcadeUnlimited(day) || arcadePlaysToday(day) < ARCADE_DAILY_PLAYS;
}
```

`arcadeStatus()` 再把它们汇总成界面用的状态对象（`unlocked` / `completed` / `target` / `playsToday` / `dailyLimit` / `remainingPlays` / `unlimited`），界面与测试读同一份实现；`ARCADE_DAILY_PLAYS = 21` 与「今天玩完几局」`arcadePlaysToday(day)` 是这一层仅有的两个新概念。边界口径：重复玩同一件只算 1 件；第 4 件 23:59 完成则当天解锁、00:00 后重攒；后台跨夜回前台按新的一天算；老存档已有 4 件时门会出现但不补浮层；清档后门消失；只做 3 件时没有任何提示（完全隐藏，没有进度条）；未解锁的 `#/arcade` 深链送回小屋，不给孩子一个「锁着的页面」。

## 17.4 竹林小路：连点竹竹 7 次

隐藏触发是一个纯前端判定，落在 `HomeView.vue` 的 `onPandaTap()`：

```ts
/** 点几下 / 多长时间内点完：孩子能连出来，大人瞎点一般不会凑巧触发 */
const SECRET_TAPS = 7;
const SECRET_WINDOW_MS = 5000;

async function onPandaTap(): Promise<void> {
  pandaWiggle.value = true;
  if (wiggleTimer !== null) clearTimeout(wiggleTimer);
  wiggleTimer = setTimeout(() => {
    pandaWiggle.value = false;
    wiggleTimer = null;
  }, 260);

  if (progress.arcadeUnlimited) return;

  const now = platform.now();
  pandaTaps = [...pandaTaps.filter((at) => now - at < SECRET_WINDOW_MS), now];
  if (pandaTaps.length < SECRET_TAPS) return;
  pandaTaps = [];

  const outcome = await progress.unlockArcadeSecret();
  if (outcome === null || !outcome.ok) return;
  secretOpen.value = true;
  platform.audio.play('unlock');
  if (!settings.muted) {
    void platform.audio.speak(t('arcade.secret.voice'), locale.current).done;
  }
}
```

三个选择各有理由：**7 次**——5 次太容易被连点误触（点亲昵按钮时手指会连击），10 次以上连大人都不愿意试；触发前每点一下竹竹轻轻弹一下（`pandaWiggle`，260ms），所以它不像隐藏指令，更像一只被戳烦了的熊猫。**5 秒滑动窗口**——每次只保留最近的点击，孩子边玩边点也能自然积攒，数组随组件卸载丢掉。**放在竹竹身上**——它是小屋的视觉中心，触发点与「完成四件小事」完全分开；「戳熊猫」本来就是小屋里唯一不做任何事的手势，加一条隐藏路径不会与既有交互冲突。

写档的是 `ProgressManager.unlockArcadeSecret()`：

```ts
async unlockArcadeSecret(now = this.clock()): Promise<ArcadeSecretOutcome> {
  const today = dayKey(now);
  const data = ensureDay(this.data, now);
  const day = data.days[today]!;
  if (day.arcadeSecret) return { ok: true, already: true };
  const next: SaveData = {
    ...data,
    updatedAt: now,
    days: { ...data.days, [today]: { ...day, arcadeSecret: true } },
  };
  await this.commit(next);
  return { ok: true, already: false };
}
```

只写一个布尔值，不写奖励、不写任务统计。「当天重复触发只当摸摸头」由 `already: true` 守住：界面因此不弹浮层，但仍然知道「状态是对的」。这个字段也解释了为什么 schema 要再升一版：`arcade`（跨天成绩）是 v2 加的，`arcadeSecret`（当天彩蛋）是 v3 加的；两次都只加字段，迁移函数是恒等函数，缺的字段由 `sanitize` 逐条兜底——老玩家的竹笋、星星、成长值一根都不会少。

## 17.5 第二套契约：没有任务、没有星星

`packages/game-kit/src/arcade.ts` 只有类型。它和 `contract.ts` 的差别不是「少几个字段」，而是中心的那个名词换了：

| 维度 | `GameModule` / `GameContext` | `ArcadeModule` / `ArcadeContext` |
|---|---|---|
| 中心对象 | 一条任务（`task: TaskDetail`） | 一个彩蛋（`manifest` 自带元信息） |
| 身份 | `id: TaskId` | `id: ArcadeGameId`（`popstar` / `bounce` / `tetris`） |
| 完成信号 | `task:complete`（stars / mistakes / correct / total） | `arcade:complete`（只有 score / durationMs） |
| 难度 | 无（关卡自己定） | `ctx.level`：外壳按该款累计完成局数传入 1–12 |
| 关卡数据 | `ctx.task.levelScript` | 没有内容 JSON，种子 + 参数即可开局 |
| 退出 | `requestExit('quit' \| 'replay')` | `requestExit('quit')`：没有「再玩一次」的路由语义 |
| 配额 | 任务各自一次 | 普通模式三款合计每天 21 局；竹林小路不限局 |
| 奖励 | 外壳据 `task:complete` 结算竹笋 / 成长值 / 贴纸 | 外壳只记最高分与局数 |

```ts
// packages/game-kit/src/arcade.ts（节选）
export interface ArcadeEventMap {
  'arcade:start': { gameId: ArcadeGameId; at: number };
  'arcade:round': { gameId: ArcadeGameId; round: number; totalRounds: number };
  /** 一局真正结束：外壳据此写存档（最高分 + 局数 + 今天已玩几局） */
  'arcade:complete': { gameId: ArcadeGameId; score: number; durationMs: number };
  'arcade:exit': { reason: 'complete' | 'quit' };
}

export interface ArcadeContext {
  container: HTMLElement;
  manifest: ArcadeManifest;
  /** 复用同一个平台出口：小游戏只用到 audio / now */
  services: PlatformServices;
  locale: Locale;
  reducedMotion: boolean;
  /** 本局难度等级（1..ARCADE_LEVEL_MAX）：外壳按该款累计局数传入，游戏逻辑据此调参 */
  level: number;
  /** ?autoplay=1 自动通关 / ?instant=1 跳过过场（与日常玩法同一套开关） */
  debug?: DebugOptions;
  emit<K extends keyof ArcadeEventMap>(type: K, payload: ArcadeEventMap[K]): void;
  requestExit(reason?: 'quit'): void;
}
```

为什么仍传整个 `PlatformServices` 而不是 `{ audio, now }`：注入方式必须与日常玩法一致——同一个单例、同一套静音状态、同一个时钟。彩蛋若单独建一个迷你平台对象，静音就会变成两处状态，第 9 章「三处同一状态」的规矩当场破掉。契约上写全，注释里写清只用到两个。

`requestExit(reason?: 'quit')` 没有 `replay` 是刻意的：日常玩法的「再玩一次」是路由级语义（原地卸载再挂载），而彩蛋的每一局都由游戏厅发起——一局结算后回到游戏厅，想再玩就再点一次卡片（普通模式受 21 局配额约束，无限畅玩不受限）。少一个可选值，就少一条没人测的分支。

## 17.6 defineArcadeGame、三款入口与注册表

工厂函数与 `defineGame` 同构（38 行）：

```ts
// games/arcade/src/defineArcadeGame.ts
export function defineArcadeGame(definition: ArcadeGameDefinition): ArcadeModule {
  let game: Phaser.Game | null = null;

  return {
    manifest: definition.manifest,

    async mount(ctx: ArcadeContext): Promise<void> {
      game = createPhaserGame(ctx, { scenes: definition.scenes(ctx) });
    },

    async unmount(): Promise<void> {
      game?.destroy(true);
      game = null;
    },

    pause(): void {
      game?.loop.sleep();
    },

    resume(): void {
      game?.loop.wake();
    },
  };
}
```

每个游戏入口只有 17 行，只声明「我是谁、我要哪个场景」：

```ts
// games/arcade/src/games/popstar.ts
export const manifest: ArcadeManifest = {
  id: 'popstar',
  title: '消灭星星',
  version: '0.1.0',

```

包的 `exports` 把三款锁成三个子路径（`./popstar`、`./bounce`、`./tetris`），Vite 因此切成三个独立 chunk。外壳侧是两张表：`arcade/registry.ts` 只放「id → 动态 import」，`arcade/catalog.ts` 只放展示元数据（emoji、卡片底色、`nameKey` / `descKey`）——registry 里没有一句文案，catalog 里没有一句中文，e2e 也从 catalog 取 testid。

**vite 配置一行都没改**：`chunkFileNames` 认的是 `games/*/src/games/*.ts`，所以小游戏入口自动得到 `game-popstar-*.js` 等文件名，Phaser 仍走共享的 `vendor-phaser`。这不是运气，而是当初把命名规则写成「路径 → 前缀」而不是「任务 id 列表」的回报。

## 17.7 ArcadeScene：三款游戏的公共底座

`arcadeScene.ts`（278 行）承担六件事：设计尺寸（750×1334，与日常玩法一致）、`addBigButton()`（可点区域 ≥96 逻辑像素、厚底 + 按压反馈、命中区走 `setContainerHitArea`）、HUD 药丸（`Lv.N` 难度、还差 n 颗）、单槽表扬条（新条顶掉旧条，不遮目标）、难度透传（`protected get level()` 把 `ctx.level` 夹到 1–12 再给 `drawLevelPill()`）、以及全仓唯一发 `arcade:complete` 的收尾。最后一项值得完整看：

```ts
/** 一局的唯一收尾：发 arcade:complete（外壳写存档）、撒花、显示成绩与唯一出口。 */
protected finish(score: number): void {
  if (this.finished) return;
  this.finished = true;
  const safeScore = Math.max(0, Math.floor(score));
  this.ctx.emit('arcade:complete', {
    gameId: this.ctx.manifest.id,
    score: safeScore,
    durationMs: this.now() - this.startedAt,
  });
  this.sfx('complete');
  this.say('arcade.doneVoice');
  this.time.delayedCall(this.instant ? 0 : 420, () => this.showCelebration(safeScore));
}

/** 离开这一局（完成卡片上的按钮 / autoplay 自动走） */
protected leave(): void {
  if (this.exited) return;
  this.exited = true;
  this.ctx.emit('arcade:exit', { reason: 'complete' });
  this.ctx.requestExit();
}
```

两个 `if` 守卫挡的是同一类 bug：重复结算与重复退出。三款游戏都在多处调 `finish()`（达成目标、autoplay 结束、救援后仍达成），没有守卫就会出现「一局写两次存档、局数 +2」。单槽表扬条则来自一个具体现象：旧版一局三轮、轮次切换时会连续发两条提示（「第 2 / 3 轮」与「这一轮完成啦」），叠在一起正好盖住 HUD 的目标药丸；改成「一局 = 一轮」后这条纪律仍然保留，因为等级提升的提示与结算提示同样会撞在一起。

autoplay 的节奏也在这里统一：**走与真实操作完全相同的处理函数**，只是由场景自己喂输入——消灭星星每 120ms 用 `largestGroup` 选最大组再 `tryPop`；弹一弹按墙钟差 ×10 倍速、每 24ms 一片推进，每片先瞄准再 `fireBall`；俄罗斯方块每 80ms 用 `planPlacement` 选落点，再走 `handleRotate` / `handleMove` / `handleHardDrop`。三款都在撒花后延迟 900ms 自动 `leave()`，所以 e2e 只等 `arcade:complete:<id>` 与游戏厅重新出现。

## 17.8 消灭星星：连通组、无解兜底与确定性补星

全部规则在 `popstar.logic.ts`（349 行），场景只画棋盘、把点按换算成格子。

| 常量 | 值 | 含义 |
|---|---|---|
| `POPSTAR_COLS` × `POPSTAR_ROWS` | 8 × 10 | 棋盘；格子 80 逻辑像素 |
| `POPSTAR_FAMILY_COUNT` | 4 | 四种星星家族，颜色之外各有花纹（圆点 / 圆环 / 爱心 / 小花） |
| `POPSTAR_MIN_GROUP` | 2 | 至少 2 颗连在一起才能消；单颗点了什么都不发生（不是失败） |
| `POPSTAR_BASE_GOAL` / `POPSTAR_GOAL_PER_LEVEL` / `POPSTAR_MAX_GOAL` | 24 / 2 / 80 | 一局一轮：`goalForLevel(level) = min(80, 24 + (level-1)×2)` |
| `POPSTAR_AUTO_STEP_MS` / `POPSTAR_HINT_AFTER_MS` | 120 / 8000 | autoplay 节拍；8 秒不动轻闪最大组（不强制、不扣分） |

棋盘是行优先的一维数组（下标 = `row * COLS + col`，空洞为 `null`），一维让连通性逻辑更容易测，也让回放只需要一个数字数组：

```ts
/** 当前最大的组（不到 2 颗就不算「可消」，返回空数组）；同大小时取靠前的那组 */
export function largestGroup(board: PopstarBoard): readonly number[] {
  const visited = new Set<number>();
  let best: readonly number[] = [];
  for (let index = 0; index < board.length; index += 1) {
    if (visited.has(index) || board[index] === null) continue;
    const group = findGroup(board, index);
    for (const member of group) visited.add(member);
    if (group.length > best.length) best = group;
  }
  return best.length >= POPSTAR_MIN_GROUP ? best : [];
}
```

`neighborIndices()` 里两条不起眼但关键的处理：不能跨行绕回（`col = 0` 的左边不是上一行最后一格），不包含斜角。写错的话「连通组」用例当场红——这正是把棋盘放进纯逻辑的价值。

消除只有一个入口 `tryPop(state, group)`，真实点击与 autoplay 都走它；它先 `canonicalGroup()` 重新校验（同家族、4 邻接、≥2 颗、不重复、必须是完整的一组），校验失败**不扣任何东西**，只交给无解兜底：

```ts
/** 空棋盘没有任何组时：剩下的星星飞回天上计入收集，然后补一副新棋盘（绝不失败） */
function settleNoMove(state: PopstarState): { state: PopstarState; autoCollected: number } {
  if (state.status !== 'playing' || largestGroup(state.board).length >= POPSTAR_MIN_GROUP) {
    return { state, autoCollected: 0 };
  }
  const remaining = filledCount(state.board);
  if (remaining === 0) {
    const board = dealBoard(state.seed, `round:${state.round}:empty:${state.pops}`);
    return { state: { ...state, board }, autoCollected: 0 };
  }
  const collected = state.collected + remaining;
  // …（节选：其余字段与状态推进略）
}
```

这就是「没有可消组时不失败」的全部实现：剩下的星星换算成收集数、棋盘按种子重发一副，孩子只看到星星飞走、新的落下来。它还顺手救了另一个边界：`dealBoard()` 里有一段兜底，把死棋的左上角两颗改成同家族，保证每个种子都能玩。补星同样确定性——`collapseAndRefill()` 用 `seededRandom(hashString(...))`，同一批种子永远得到同一副棋盘，所以「第三次消除后补下来的四颗是什么」可以写成断言。

计分口径就是「一局收集的星星总数」（最多 96）：不是消除组数、不是连击倍率，幼儿园孩子也理解「收集了多少颗」。组越大音调越高（`popTone(size)`）复用 `AudioBus.tone()`，不新增音效通道。

## 17.9 弹一弹：定步长、预测线与非惩罚性压力

反弹要可测，答案是把物理钉在固定步长上：`bounce.logic.ts`（792 行）全部按 8ms 一步推进，真实帧的余数留在 `accumMs`，慢手机与 CI 结果一致。

| 常量 | 值 | 含义 |
|---|---|---|
| `BOUNCE_STEP_MS` | 8 | 物理固定步长；一帧可走多步，余数保留 |
| `shotSpeed` / `maxBounces` / `maxBalls` | 1500 px/s / 8 次 / 3 颗 | 一颗球反弹 8 次回发射器；同时最多 3 颗 |
| `reloadMs` / `BOUNCE_AIM_LIMIT_DEG` | 900ms / 75° | 装弹节奏；瞄准离竖直向上最多 75°，球永远往上打 |
| `BOUNCE_DROP_EVERY_SHOTS` | 6 | 每 6 发方块整体下沉一格（保留原作的越拖越紧） |
| `BOUNCE_STARS_PER_BLOCK` / `BOUNCE_COMBO_BONUS` | 3 / 5 | 每块 3 颗星；同一发击碎第 2、3… 块时每多一块 +5 分 |

一局一轮，方块数 `bounceBlocksForLevel(level) = min(18, 6 + (level-1))`（`level=1` 就是旧版第 1 轮的 6 块），里面混 2 个弹弹方块（`bouncyBoost = 1.18`，命中后球更快一点，是变化不是压力）；弹弹方块的数量刻意不随等级涨，`level=1` 才能与旧版逐帧一致。

```ts

  if (next.shotsThisRound % BOUNCE_DROP_EVERY_SHOTS === 0) next = sinkBlocks(next, events);
  return { state: next, fired: true, events };
}

/** 按固定步长推进一帧。dtMs 可以不是 8 的倍数，余数留在 accumMs 里。 */

```

三个细节：`MAX_STEPS_PER_ADVANCE = 128` 防「卡顿死亡螺旋」（切后台回来积累 5 秒时，不设上限会在单帧里跑 600 多步）；函数返回 `events`（碎块 / 开花 / 换轮 / 结束）而不是直接播动画，逻辑层因此不认识 Phaser 也不认识音频；方块中心越过 `flowerLine = 950` 时整轮方块「开出小花」飞走并计入收集，本轮直接完成。

瞄准预测 `predictAim()` 也是纯函数：从发射点出发最多找两个反弹点，撞到方块就停。场景把 `points` 画虚线、`bouncePoints` 画圆点——**预测与现实走同一份公式**，所以「虚线指哪儿、球就打哪儿」不需要额外保证。autoplay 同样不是作弊，而是每 24ms 模拟一小片（×10 倍速），每片先 `autoplayTarget()` 瞄准再 `fireBall()`，与孩子拖拽发射共用 `aimToward`。

## 17.10 俄罗斯方块：7-bag、彩虹救援与 80ms 的 AI

`tetris.logic.ts` 512 行，是三者中规则最多的一份。

| 常量 | 值 | 含义 |
|---|---|---|
| `TETRIS_COLS` × `TETRIS_ROWS` | 8 × 14 | 棋盘；格子 60 逻辑像素（原作 10×20） |
| `PIECE_KINDS` | I / O / T / S / Z / J / L | 7 种方块，7-bag 种子随机，右侧 2 个预览、无 hold |
| `TETRIS_GOAL_LINES` / `TETRIS_RESCUE_ROWS` | 1 行 / 4 行 | 消 1 行即完成一局（一局一轮）；堆到顶时最下 4 行变彩虹并计 1 行 |
| `TETRIS_START_FALL_MS` / `TETRIS_MIN_FALL_MS` | 1100 / 550 | 起始 1.1 秒/格，最快 0.55 秒/格 |
| `TETRIS_SCORE_PER_LINE` / `TETRIS_SCORE_PER_PIECE` | 10 / 1 | 分数 = 行数 × 10 + 落子块数 |

7-bag 只有五行，却决定「同一个种子永远发同一串方块」：

```ts
/** 一袋 7 种各一次；同一 seed + 同一袋号永远得到同一个顺序 */
export function createTetrisBag(seed: number, index: number): PieceKind[] {
  const random = seededRandom(hashString(seed + ':' + index));
  return shuffled(PIECE_KINDS, random);
}
```

堆到顶的处理最特别，写在 `lockPiece()` 里：

```ts
// 堆到顶不失败：最下面 4 行变彩虹，等价于消掉 1 行，然后继续
while (collides(nextBoard, nextActive.kind, nextActive.rotation, nextActive.x, nextActive.y)) {
  nextBoard = rescueBottomRows(nextBoard);
  lines += 1;
  rescues += 1;
  rescuedNow += 1;
  if (lines >= TETRIS_GOAL_LINES) {
    finished = true;
    break;
  }
}
```

用 `while` 而不是 `if`：极端情况下新方块出生就被占两次，救援一次不够。这条路径同时是「一局必定能结束」的保证——每次救援都 +1 行，而一局的目标只有 1 行，所以再糟糕的堆法也会立刻收尾。重力节奏是纯函数 `fallIntervalForLines(lines, level)`：起步间隔 `1100 - (level-1)×60`、下限 `550 - (level-1)×20`，再按消行数每行减 180ms——`level=1` 时与旧公式逐值相同（1100 起、550 保底），等级只改这两个端点，不改「3 行内不会眨眼就没」的推导。

autoplay 的 AI 只有两个函数：`planPlacement()` 枚举 4 种旋转 × 每一列，用 `landingY()` 找落点，再用 `evaluatePlacement()` 打分：

```ts
const score =
  cleared * 1000 -
  aggregateHeight * 1.6 -
  holes * 27 -
  bumpiness * 1.2 -
  maxHeight * 3;
```

四项惩罚对应四种坏形状：总高度（堆太高）、空洞（填不满）、起伏（坑坑洼洼）、最高列（局部尖塔）。权重是手调的，但评分函数是纯的、可测的——单测里「AI 一局内稳过（含 12 级）」直接调 `planPlacement()` 跑完整局，而不是在浏览器里看它玩。场景侧两个坑也写进了注释：预览方块要画在比预览框更高的层级（否则被底色盖住）；棋盘手势用无参 `.setInteractive()` 的默认命中区，所以它一直是好的——反过来印证第 8 章的结论。

## 17.11 每日 21 局、难度等级与「一局 = 一轮」

以上三节讲的是三款游戏「怎么玩」，这一节讲 2026-11-07 那天的三次调整——它们不动玩法内核，只动**一局多长、一天玩几局、难度从哪来**。原文见 `docs/隐藏小游戏方案.md` 的第 12、13 节。

| 项 | 旧（v3） | 新（v4） |
|---|---|---|
| 普通模式配额 | 每款每天 1 次，各自独立 | 三款合计每天 **21 局**（`ARCADE_DAILY_PLAYS`） |
| 次日 | 每款重置 | 局数归零（写在日记录 `arcadePlays`），难度与最高分从跨天记录延续 |
| 无限畅玩 | 当天三款无限玩 | 不变，且**不限局数** |
| 难度 | 固定参数 | 每款独立 `Lv.1–12`，`arcadeLevelFor(plays) = clamp(1 + floor(plays/2), 1, 12)` |
| 一局 | 3 轮 | 改为**单轮**：打完一轮即算一局、结算回游戏厅 |

**难度等级不单独存。** 它由该款累计完成局数派生：

```ts
// packages/game-kit/src/arcade.ts
export const ARCADE_LEVEL_EVERY_PLAYS = 2;
export const ARCADE_LEVEL_MAX = 12;

export function arcadeLevelFor(plays: number): number {
  const safePlays = Number.isNaN(plays) ? 0 : Math.max(0, Math.floor(plays));
  return Math.min(ARCADE_LEVEL_MAX, 1 + Math.floor(safePlays / ARCADE_LEVEL_EVERY_PLAYS));
}
```

这是整次调整里最重要的一个决定：**「第几级」只有一个来源，就是跨天保存的 `plays`**。存档不写 `level` 字段，界面不缓存 `level`，游戏也不自己算——外壳读档时调一次 `arcadeLevelFor()`，经 `ctx.level` 传进场景。少一个可写的副本，就少一类「界面显示 Lv.5、实际按 Lv.3 生成棋盘」的不一致；顺带还省掉一次存档迁移（`plays` 本来就在）。

**配额只有一处判定。** `playArcade()` 里顺序固定：非法 id → 未解锁 → 普通模式满 21 局（`reason: 'limit'`）→ 写档。满 21 局后卡片**仍然亮着**，点进去只给一句温和提示（`arcade.limitReached`）并留在游戏厅，不出现「失败」「明天再来吧」之类的关门话术——这是产品要求，也是对 4–8 岁用户的边界：不让孩子觉得「我把游戏玩坏了」。

**一局一轮是三款一起改的。** 消灭星星的单轮目标 `24 + (level-1)×2`（封顶 80）；弹一弹的单轮方块 `6 + (level-1)`（封顶 18）；俄罗斯方块消 1 行即完成（彩虹救援也计 1 行）。三者都有一个硬约束：`level = 1` 时走原常量分支，与调整前的第 1 轮逐帧/逐值一致——这样难度等级才是「在旧玩法上加成长」，而不是「换了个新玩法」。

**成瘾边界同步收紧。** 普通模式每天最多 21 局、单轮一局约 20–60 秒，合计约 7–20 分钟，20 分钟休息提醒照旧；无限畅玩是连点竹竹 7 次才触发的隐藏彩蛋，非常规入口，且仍然不发奖励、不做社交比较。

## 17.12 存档：v4、每日配额与「中途退出不算」

彩蛋对存档的改动只有四处，全部是加字段：`SAVE_SCHEMA_VERSION = 4`；`SaveData.arcade: Record<ArcadeGameId, ArcadeProgress>`（跨天保留的 `best` / `plays` / `lastPlayedDay`，难度等级由 `plays` 派生、不单独存）；`DayRecord.arcade: ArcadeGameId[]`（今天玩过哪些，日记与家长页用）；`DayRecord.arcadePlays: number`（今天已完成几局，三款合计，跨天自然归零）与 `DayRecord.arcadeSecret: boolean`（今天触发过竹林小路）。四次升级都只加字段、迁移函数是恒等函数，缺的字段由 `sanitize` 逐条兜底——老玩家的竹笋、星星、成长值一根都不会少。

**跨天与当天分开存**是关键：`SaveData.arcade` 里的最好成绩不能被午夜清零；`DayRecord.arcade` 是消耗品，跨天自动重置。若偷懒把「今天玩过」也写进跨天记录（加一个 `lastPlayedDay` 比较），午夜重置就变成「每次读取时比较日期」——一处漏判，孩子第二天就玩不了。

写档的纯函数是 `withArcadePlay()`：

```ts
/** 记录一局：最高分只增不减、总次数 +1、今天玩过、今天局数 +1。纯函数，落盘由 Manager 负责。 */
export function withArcadePlay(save: SaveData, gameId: ArcadeGameId, score: number, now: number): SaveData {
  const today = dayKey(now);
  const data = ensureDay(save, now);
  const day = data.days[today]!;
  const safeScore = Math.max(0, Math.floor(score));
  const previous: ArcadeProgress = data.arcade[gameId] ?? { best: 0, plays: 0, lastPlayedDay: null };
  return {
    ...data,
    updatedAt: now,
    arcade: {
      ...data.arcade,
      [gameId]: { best: Math.max(previous.best, safeScore), plays: previous.plays + 1, lastPlayedDay: today },
    },
    days: {
      ...data.days,
      [today]: {
        ...day,
        arcade: day.arcade.includes(gameId) ? day.arcade : [...day.arcade, gameId],
        // 难度等级由上一行的 plays 派生，这里只记「今天第几局」
        arcadePlays: arcadePlaysToday(day) + 1,
      },
    },
  };
}
```

`ProgressManager.playArcade()` 是唯一入口，四道判定顺序固定：非法 id（`unknown`）→ 未解锁（`notUnlocked`）→ 普通模式今天已满 21 局（`limit`）→ 写档。第三道写成 `!isArcadeUnlimited(day) && day.arcadePlays >= ARCADE_DAILY_PLAYS`——**彩蛋模式下不设上限**，这就是「无限畅玩」在存档层的全部实现。返回值也从 `{ok, best, plays}` 扩成 `{ok, gameId, best, plays, level, playsToday}`：外壳拿到 `level` 直接塞进 `ArcadeContext`，拿到 `playsToday` 直接刷游戏厅头部的「今天还能玩 N 局」，不需要自己再算一遍。

「中途退出不消耗机会」由宿主保证：`ArcadePlayView` 的 `handleEvent()` 只认 `arcade:complete`（且有 `recorded` 守卫），点「回去」走 `leaveNow()`——只记 `arcade:exit:quit` 并导航，一个字节都不写档。孩子误触退出，今天这 21 局里的一局还在。

| 界面状态 | 判定 | 数据来源 |
|---|---|---|
| 今天还能玩 N 局 | 已解锁且（彩蛋或今天还没满 21 局） | `arcadeStatus().remainingPlays` |
| Lv.N | 该款累计完成局数折算的难度等级 | `arcadeLevelFor(save.arcade[id].plays)` |
| 最好成绩 | 最高分只增不减 | `save.arcade[id].best` |
| 今天的 21 局玩完啦 | 已解锁、普通模式、`arcadePlays >= 21` | `day.arcadePlays` |
| ∞ 无限畅玩 | 今天触发了竹林小路 | `day.arcadeSecret` |

两个小落点各一行：家长页「今天和竹竹玩了 {n} 局小游戏」、日记「今天还和竹竹玩了：消灭星星、弹一弹」。游玩时长照旧走 `addSeconds(30)`（宿主每 30 秒一次），所以 20 分钟休息提醒对彩蛋同样有效——彩蛋不是法外之地；普通模式 21 局的配额也是按**实际玩完**计数，挂着页面不玩不会消耗。

## 17.13 外壳接线：两条路由、两个宿主、一层守卫

路由只加一个分支：

// apps/site/src/router.ts（节选）

`asArcadeGameId()` 与 `asTaskId()` 是同一套白名单收窄（`ARCADE_GAME_IDS.includes` 之后才断言），所以 `#/arcade/tetris2` 掉回游戏厅。`App.vue` 里 `ArcadeView` 与 `ArcadePlayView` 都是 `defineAsyncComponent`，`isFullScreen` 收进 `arcadePlay`——彩蛋是全屏画布，顶栏与底栏会直接压在游戏上；游戏厅则不是全屏页，孩子要能按底栏回小屋。

它们全部能在 Node 里跑，没有 jsdom、没有 canvas 桩——`*.logic.ts` 与 `progress/arcade.ts` 都不 import Phaser。这是「逻辑与渲染分离」在实时玩法上唯一一次真正的压力测试：帧循环、反弹、消行、AI 都被关在纯函数里。

e2e 新增 `e2e/arcade.spec.ts` 11 条（9 个 `test`，其中三款 autoplay 用 `for` 循环展开）：隐藏（没有门、深链回小屋）、解锁（第 4 件 → 浮层 → 三张卡）、**每日 21 局边界**（seed `arcadePlays = 21` → 卡片仍可见但点卡片与深链都被拦在游戏厅；seed `20` → 再玩一局变 21、下一局被拦）、竹林小路（连点 7 次 → 无限）、**无限畅玩第 22 局**（`arcadeSecret = true` 且已满 21 局仍能进入并完成）、**难度展示**（跨天累计 4 局显示 Lv.3，再玩两局升到 Lv.4）、三款 autoplay 写档、英文游戏厅。存档不是「先玩四关」凑的，而是直接往 IndexedDB 播种一份最小存档（`seedSave`），schemaVersion 写最新（4）——种子的形状本身也成了一条迁移用例。

观测仍靠调试桥，事件名是扁平的：`arcade:start:popstar` / `arcade:complete:popstar` / `arcade:exit:complete`。`createArcadeContext.ts` 的 `detailOf()` 负责把 payload 折成一行，与 `createGameContext` 同构，所以断言只需 `waitEvent(page, 'arcade:complete:popstar')`，不用猜 DOM。契约里的 `arcade:round` 类型仍然保留（`detailOf()` 也有对应分支），但「一局 = 一轮」之后三款游戏都不再发它——一个字段没人发，比删掉它更能说明版本演进。第 8 章那次命中区修复也在这里留了一条回归用例——`ArcadeScene.addBigButton` 与 `BaseScene.addButton` 是同一套实现，**坑也会被两个人共用**。

## 17.15 体积与边界

| 项 | 实测（2026-11-07 构建） | 说明 |
|---|---|---|
| `game-popstar` / `game-bounce` / `game-tetris` | 10,919 / 13,386 / 11,649 B（gzip 4.18 / 5.31 / 4.41 KB） | 只在点开那一款时下载 |
| 共享底座 `rng-*.js` | 4,521 B | ArcadeScene + 确定性随机，三款共用 |
| 首屏 JS + CSS | gzip 60,511 B（约 59.1 KB，预算 60 KB） | 彩蛋入口与 Lv 展示让首屏多约 0.9 KB，仍压在预算内 |
| dist 原始大小 | 1,312,440 B（约 1281.7 KB，53 个文件） | 预算 2400 KB |

三款 chunk 合计 35,954 B（gzip 约 13.9 KB），只在点进某一款时下载——「一个不玩彩蛋的孩子永远不为彩蛋付流量」与「不玩任何任务的孩子永远不为引擎付流量」是同一条纪律。等级只改每轮参数（目标数、方块数、下落节奏），不引入任何新的图片、音频或依赖，所以 Lv.1–12 的代码量几乎为零。

产品边界同样明确：普通模式每天最多 **21 局**、单轮一局约 20–60 秒，合计约 7–20 分钟，20 分钟休息提醒照旧；无限畅玩是隐藏彩蛋，不限局但同样不发奖励；没有排行榜、推送、连续签到、内购，最好成绩只在本机；不发竹笋 / 成长值 / 贴纸，不写 `task:complete`，连续天数、贴纸册、家长页统计都不受影响；一局结算后只有「回游戏厅」一个出口，避免「点一下又开一局」的无限循环，也让每局之间有一次「要不要继续」的自然停顿。

## 17.16 小结

隐藏小游戏是一次「往成熟结构里加东西」的演练：

- **新的东西用新契约**：`arcade.ts` 只有 60 行，却把「彩蛋」与「任务」彻底分开——没有 TaskId、没有星星、不发 `task:complete`；
- **共用的东西走既有出口**：视觉、音频、平台服务、按钮命中区、调试桥、体积门禁全部复用，构建配置一行没改；
- **规则放纯函数**：连通组、定步长反弹、7-bag、彩虹救援、AI 评分、解锁判定、难度派生、配额判定、写档合并全部可单测，99 条用例在 Node 里毫秒级跑完；
- **不失败是设计出来的**：无解自动收集、贴底开花、堆顶彩虹——三款游戏都没有「输」这个状态；
- **隐藏也是产品需求**：未解锁时 DOM 里没有入口、深链被送回、没有进度条、没有「锁着的页面」；彩蛋是孩子的动作（连点 7 次），不是大人的快捷键，当天有效、跨天消失、不发奖励；配额用完之后也不关门，只给一句「明天接着玩」。
- **难度用派生而不是用字段**：`level = arcadeLevelFor(plays)` 一行公式，存档、界面、游戏三处读同一份，省掉一个需要迁移的副本，也省掉「显示与实际不一致」这类 bug；
- **改规则先问「能不能只改参数」**：21 局、Lv.1–12、一局一轮三次调整都没有碰判定内核，`level = 1` 始终等于旧行为——所以旧单测只需补新用例，不需要推翻重写。

这一章是正篇的最后一章。第 14 章拆过的门禁、第 15 章讲过的两条打包链、第 16 章记下的坑，同样罩着这三款彩蛋——它们不是「顺便做的小玩具」，而是同一套契约、同一套测试、同一套体积预算下的第三类玩法包。要加第四款，路径是现成的：写一份 `*.logic.ts`、一份 `*.scene.ts`、一个 17 行的入口，在 `ARCADE_GAME_IDS` 与 `ARCADE_CATALOG` 各登记一行，其余不用动。
